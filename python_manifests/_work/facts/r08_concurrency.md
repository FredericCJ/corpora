## Facts

### The four models, and the cost of each

1. CPython offers exactly four concurrency substrates in the stdlib as of 3.14: cooperative single-threaded scheduling (`asyncio`), OS threads (`threading`, `concurrent.futures.ThreadPoolExecutor`), multiple interpreters in one process (`concurrent.interpreters`, `concurrent.futures.InterpreterPoolExecutor`), and separate OS processes (`multiprocessing`, `concurrent.futures.ProcessPoolExecutor`) - VERSION-DEPENDENT (3.14).
2. `asyncio` is correct for I/O-bound work with many concurrent waits; it gives no CPU parallelism because all tasks run on one thread of one interpreter. Its characteristic failure mode is a synchronous blocking call inside a coroutine, which stalls every other task on that loop; asyncio debug mode surfaces this by logging callbacks that exceed `loop.slow_callback_duration` (default 0.1 s) - ESTABLISHED.
3. asyncio's testability cost is that "Almost all asyncio objects are not thread safe", so any harness that drives asyncio objects from a second thread must go through `loop.call_soon_threadsafe()` or `asyncio.run_coroutine_threadsafe()`; in debug mode, non-threadsafe APIs such as `loop.call_soon()` and `loop.call_at()` "raise an exception if they are called from a wrong thread" - ESTABLISHED.
4. Threads are correct for blocking I/O and for C-extension code that releases the GIL. On a default (GIL-enabled) build they give no CPU parallelism for pure-Python bytecode; on a free-threaded build they do. Their characteristic failure modes are data races on shared mutable state and lock-ordering deadlock, neither of which raises an exception - ESTABLISHED.
5. Threads' testability cost is nondeterministic interleaving: the same test can pass thousands of times and fail once. The stdlib provides no scheduler control; the documented mitigations are barriers/events to force interleavings plus repetition (facts 111-114) - ESTABLISHED.
6. Subinterpreters are correct when you want process-like isolation with thread-like startup cost and in-process communication. "As a significant bonus, interpreters are sufficiently isolated that they do not share the GIL, which means combining threads with multiple interpreters enables full multi-core parallelism. (This has been the case since Python 3.12.)" - VERSION-DEPENDENT (3.12 for the isolation, 3.14 for the stdlib API).
7. The 3.14 What's New itself lists the current subinterpreter limitations: "Interpreter startup not yet optimized", "Each interpreter uses more memory than necessary", "Limited options for sharing objects between interpreters", "Many third-party extension modules not yet compatible", "Unfamiliar programming model for most users" - VERSION-DEPENDENT (3.14).
8. Subinterpreter isolation is not a security boundary: the docs state interpreters "in the same process can technically never be strictly isolated from one another since there are few restrictions on memory access within the same process" - ESTABLISHED.
9. Processes are correct for CPU-bound pure-Python work on GIL-enabled builds and for fault isolation. Their failure modes are pickling errors at the boundary, orphaned children, and a worker dying mid-task, which surfaces as `concurrent.futures.BrokenProcessPool` (added 3.3, derived from `BrokenExecutor`, formerly `RuntimeError`) - VERSION-DEPENDENT (3.3).
10. Processes' testability cost is that coverage, monkeypatching, fixtures and in-process fakes do not cross the boundary; the child re-imports the module under `spawn`/`forkserver`, so module-level side effects execute again in every worker - ESTABLISHED.

### Free-threaded CPython

11. PEP 779 ("Criteria for supported status for free-threaded Python") is Final with Python-Version 3.14; it is the PEP that moved free-threading to Phase II, "making the free-threaded Python build officially supported" while still optional - ESTABLISHED.
12. PEP 703 ("Making the Global Interpreter Lock Optional in CPython") is Final with Python-Version 3.13 and Resolution 2023-10-24; it is the implementation PEP, not the "officially supported" PEP. Attributing supported status to PEP 703 is wrong - ESTABLISHED.
13. Python 3.13 shipped the free-threaded build as experimental; Python 3.14's What's New headline is literally "PEP 779: Free-threaded Python is officially supported" - VERSION-DEPENDENT (3.14).
14. Phase III (free-threaded as the *default* build) is explicitly out of scope of PEP 779: "The decision to make free-threaded Python the default (phase III) is very different... That's left for a future PEP." No such PEP exists as of 2026-08-08 - ESTABLISHED.
15. Runtime detection, three documented mechanisms: `python -VV` and `sys.version` contain the string `"free-threading build"`; `sys._is_gil_enabled()` reports whether the GIL is actually disabled in the running process; `sysconfig.get_config_var("Py_GIL_DISABLED")` returns `1` if the *build* supports free threading and is "recommended" for build-configuration decisions - VERSION-DEPENDENT (3.13+).
16. `sysconfig.get_config_var("Py_GIL_DISABLED")` answers a build question, not a runtime one. A free-threaded build running under `-X gil=1` has `Py_GIL_DISABLED == 1` and `sys._is_gil_enabled() == True` simultaneously - VERSION-DEPENDENT (3.13+).
17. `-X gil=0,1` "forces the GIL to be disabled or enabled, respectively. Setting to `0` is only available in builds configured with `--disable-gil`". Added in 3.13 - VERSION-DEPENDENT (3.13).
18. `PYTHON_GIL=1` forces the GIL on; `PYTHON_GIL=0` forces it off and "needs Python configured with the `--disable-gil` build option". The `-X gil` command-line option "takes precedence over this variable". Added in 3.13 - VERSION-DEPENDENT (3.13).
19. On a free-threaded build, "The GIL may also automatically be enabled when importing a C-API extension module that is not explicitly marked as supporting free threading. A warning will be printed in this case." A process can therefore silently lose parallelism at import time - VERSION-DEPENDENT (3.13+).
20. Current project statement of single-threaded overhead: "On the pyperformance benchmark suite, the average overhead ranges from about 1% on macOS aarch64 to 8% on x86-64 Linux systems." This exact sentence appears in both the 3.14 and 3.15 free-threading HOWTOs - VERSION-DEPENDENT (3.14, 3.15).
21. The 3.14 What's New states a different figure for the same property: the "performance penalty on single-threaded code" is "roughly 5-10% (depending on platform and C compiler)". PEP 703 (2023) reported 6% (Intel Skylake) / 5% (AMD Zen 3) single-threaded and 8% / 7% multi-threaded; PEP 779 proposed "15% as a hard performance target" for Phase II. Quote whichever source you cite and do not merge the four - VERSION-DEPENDENT (3.14).
22. 3.14 enabled the specializing adaptive interpreter (PEP 659) in free-threaded mode, which is the main reason the overhead figures dropped - VERSION-DEPENDENT (3.14).
23. Locking rule on free-threaded builds: `dict`, `list` and `set` use internal locks, but the docs say "Python has not historically guaranteed specific behavior for concurrent modifications to these built-in types, so this should be treated as a description of the current implementation, not a guarantee of current or future behavior." Use `threading.Lock` - VERSION-DEPENDENT (3.13+).
24. Two documented thread-unsafe operations on free-threaded builds: accessing `frame.f_locals` for a frame executing in another thread (may crash the interpreter), and consuming the *same* iterator object from multiple threads concurrently ("threads may see duplicate or missing elements") - VERSION-DEPENDENT (3.13+).
25. 3.15 adds three stdlib remedies for the shared-iterator hazard: `threading.serialize_iterator(iterable)` (serializes `__next__`, and `send`/`throw`/`close` if present, under a lock; no value duplicated or skipped), `threading.synchronized_iterator(func)` (decorator for generator functions, wrapping each produced iterator), and `threading.concurrent_tee(iterable, n=2)` (n independent iterators, buffered until every branch has consumed a value; `n == 0` returns an empty tuple, negative `n` raises `ValueError`) - VERSION-DEPENDENT (3.15).
26. C-extension declaration of free-threading support: multi-phase-init modules add the `Py_mod_gil` slot with value `Py_MOD_GIL_NOT_USED` (guarded `#if PY_VERSION_HEX >= 0x030D0000`); single-phase-init modules call `PyUnstable_Module_SetGIL(m, Py_MOD_GIL_NOT_USED)` under `#ifdef Py_GIL_DISABLED`. "Extension modules need to explicitly indicate that they support running with the GIL disabled; otherwise importing the extension will raise a warning and enable the GIL at runtime." - VERSION-DEPENDENT (3.13+).
27. Borrowed-reference C APIs are unsafe under free threading if the container mutates concurrently; the documented strong-reference replacements are `PyList_GetItemRef()`, `PyDict_GetItemRef()`, `PyDict_GetItemStringRef()`, `PyWeakref_GetRef()`, `PyImport_AddModuleRef()` - VERSION-DEPENDENT (3.13+).
28. The critical-section API is `Py_BEGIN_CRITICAL_SECTION` / `Py_END_CRITICAL_SECTION` (one object) and `Py_BEGIN_CRITICAL_SECTION2` / `Py_END_CRITICAL_SECTION2` (two objects), built on `PyMutex`. They "must be used in matching pairs and must appear in the same C scope" and "are no-ops in non-free-threaded builds". Critically: "Critical sections may temporarily release their locks, allowing other threads to modify the protected data." They are not mutual-exclusion blocks in the classic sense - VERSION-DEPENDENT (3.13+).
29. PEP 803 ("abi3t": Stable ABI for Free-Threaded Builds) is Final for 3.15: extensions opt in with `Py_TARGET_ABI3T=<version>` (auto-defined when `Py_LIMITED_API=v` and `Py_GIL_DISABLED` are both set), `PyObject` becomes an opaque/incomplete type, wheels are tagged with the compressed set `abi3.abi3t`, and filename-tagged extensions use `.abi3t.so`. It requires PEP 697 APIs (negative `basicsize`, `PyObject_GetTypeData()`), the PEP 793 `PyModExport_*` export hook and the PEP 820 `PySlot` structure - VERSION-DEPENDENT (3.15).
30. Documentation conflict, live as of 2026-08-08: the 3.15 free-threading-extensions HOWTO still says "The free-threaded build does not currently support the Limited C API or the stable ABI" and still recommends `py_limited_api=not sysconfig.get_config_var("Py_GIL_DISABLED")`, while What's New in 3.15 announces `abi3t`. Treat the HOWTO paragraph as stale text pending update - OPEN.
31. PEP 788 is Final for 3.15: it adds `PyInterpreterGuard` (prevents finalization while held), `PyInterpreterView` (thread-safe interpreter reference without an attached thread state), `PyThreadState_Ensure()`, `PyThreadState_EnsureFromView()` and `PyThreadState_Release()`, and *soft-deprecates* the `PyGILState` family including `PyGILState_Ensure()` / `PyGILState_Release()`: "Soft deprecations only mean that these APIs will not be developed further; there is no plan to remove `PyGILState` from Python's C API." - VERSION-DEPENDENT (3.15).
32. 3.14 added two runtime knobs whose defaults differ by build: `-X thread_inherit_context=0,1` / `PYTHON_THREAD_INHERIT_CONTEXT` (a new `threading.Thread` copies the context of the caller of `Thread.start()`) and `-X context_aware_warnings=0,1` / `PYTHON_CONTEXT_AWARE_WARNINGS` (`warnings.catch_warnings` stores filter state in a `ContextVar`). Both "default to `1` on free-threaded builds and to `0` otherwise" - VERSION-DEPENDENT (3.14).
33. Consequence of fact 32: identical code observes different `contextvars` propagation into threads on `python3.14` versus `python3.14t`. Set the flag explicitly if behaviour must match across builds - VERSION-DEPENDENT (3.14).
34. 3.15 fixes a long-standing import deadlock: "The import system now acquires per-module locks in hierarchical order (parent packages before their submodules)", which previously let one thread importing `pkg.sub` and another importing `pkg.sub.mod` block each other - VERSION-DEPENDENT (3.15).

### Subinterpreters

35. PEP 734 is Final with Python-Version 3.14. The stdlib module is `concurrent.interpreters` - renamed from the PEP's original `interpreters` - and is "Added in version 3.14" - VERSION-DEPENDENT (3.14).
36. `concurrent.interpreters` public surface per `__all__`: `get_current()`, `get_main()`, `create()`, `list_all()`, `is_shareable()`, `Interpreter`, `create_queue`, `Queue`, and exceptions `InterpreterError`, `InterpreterNotFoundError`, `ExecutionFailed`, `NotShareableError`, `QueueEmpty`, `QueueFull` - VERSION-DEPENDENT (3.14).
37. The library docs name the queue exceptions `QueueEmptyError` and `QueueFullError`, while `__all__` in the shipped source exports `QueueEmpty` and `QueueFull`. Prefer the documented `QueueEmptyError`/`QueueFullError` in written specs and verify against the interpreter you target - OPEN.
38. `Interpreter` methods: `is_running()`, `close()`, `prepare_main(ns=None, **kwargs)`, `exec(code, /, dedent=True)`, `call(callable, /, *args, **kwargs)`, `call_in_thread(callable, /, *args, **kwargs)`. `exec()` and `call()` raise `ExecutionFailed` (carrying `excinfo`) when the code inside raises - VERSION-DEPENDENT (3.14).
39. What may cross an interpreter boundary, per the docs: `None`, `bool`, `bytes`, `str`, `int`, `float` and `tuple` of similarly supported objects are "directly shared or copied efficiently"; `memoryview` and `Queue` actually share mutable data; and "By default, most objects are copied with `pickle` when they are passed to another interpreter." Anything that cannot be sent raises `NotShareableError` - VERSION-DEPENDENT (3.14).
40. The docs render the constructor as `concurrent.interpreters.create_queue()` with no parameters, but the shipped source in both the 3.14 and 3.15 branches is `def create(maxsize=0, *, unbounditems=UNBOUND)`, exported as `create_queue`; PEP 734 also specifies `create_queue(maxsize=0)`. Cross-interpreter queues are therefore boundable today despite the docs - VERSION-DEPENDENT (3.14, 3.15).
41. Cross-interpreter `Queue.put(obj, block=True, timeout=None, *, unbounditems=None)` and `Queue.get(block=True, timeout=None)`; the `Queue` implements the `queue.Queue` interface. There is no `syncobj` parameter - VERSION-DEPENDENT (3.14, 3.15).
42. `concurrent.futures.InterpreterPoolExecutor(max_workers=None, thread_name_prefix='', initializer=None, initargs=())` was added in 3.14 and is declared as `class InterpreterPoolExecutor(_thread.ThreadPoolExecutor)` - one OS thread per worker, each thread owning its own interpreter. Because it *is* a `ThreadPoolExecutor` subclass, it is accepted by `loop.run_in_executor()` - VERSION-DEPENDENT (3.14).
43. `InterpreterPoolExecutor` pickles at every hop: it "serializes the `initializer` and `initargs` using `pickle`", the worker "serializes the callable and arguments using `pickle`", and "The worker likewise serializes the return value when sending it back." A closure, a lambda, a local class or an open socket cannot be submitted - VERSION-DEPENDENT (3.14).
44. `InterpreterPoolExecutor` can lose an exception: the implementation puts the exception on the results queue and, on `interpreters.NotShareableError`, substitutes `None` after reporting that the "exception is not shareable". A non-picklable exception type raised in a worker therefore does not arrive intact - VERSION-DEPENDENT (3.14, 3.15).
45. `chunksize` on `Executor.map()` "has no effect" with `ThreadPoolExecutor` and `InterpreterPoolExecutor`; it only chunks for `ProcessPoolExecutor` - ESTABLISHED.

### asyncio structured concurrency

46. `asyncio.TaskGroup` was added in 3.11. "The first time any of the tasks belonging to the group fails with an exception other than `asyncio.CancelledError`, the remaining tasks in the group are cancelled." After that, "No further tasks can then be added to the group." - VERSION-DEPENDENT (3.11).
47. On child failure, if the `async with` body is still active, "the task directly containing the `async with` statement is also cancelled. The resulting `asyncio.CancelledError` will interrupt an `await`, but it will not bubble out of the containing `async with` statement." - VERSION-DEPENDENT (3.11).
48. TaskGroup aggregates: "if any tasks have failed with an exception other than `asyncio.CancelledError`, those exceptions are combined in an `ExceptionGroup` or `BaseExceptionGroup` (as appropriate)... which is then raised." A plain `except ValueError:` around a task group does not catch a `ValueError` raised in a child; `except* ValueError:` does - VERSION-DEPENDENT (3.11).
49. Exception to fact 48: "If any task fails with `KeyboardInterrupt` or `SystemExit`, the task group still cancels the remaining tasks and waits for them, but then the initial `KeyboardInterrupt` or `SystemExit` is re-raised instead of `ExceptionGroup` or `BaseExceptionGroup`." - VERSION-DEPENDENT (3.11).
50. 3.15 adds `TaskGroup.cancel()`: "a non-exceptional, early exit of the task group's lifetime". It cancels every not-yet-done task in the group *and the group's own body*, and "The task group context manager will exit *without* `asyncio.CancelledError` being raised." It is idempotent, may be called after the group has exited, and if called before entry "the group will be cancelled upon entry" - VERSION-DEPENDENT (3.15).
51. 3.15 also adds a `GeneratorExit` special case to `TaskGroup`, documented as "Changed in version 3.15: Addition of the special case for `GeneratorExit`" - VERSION-DEPENDENT (3.15).
52. Before 3.15, early non-exceptional exit from a task group required "unintuitive boilerplate such as an extra task raising a custom exception which is then suppressed as it exits the task group" - VERSION-DEPENDENT (3.15).
53. `asyncio.timeout(delay)` and `asyncio.timeout_at(when)` were added in 3.11. Inside the block the mechanism is `asyncio.CancelledError`; "The `asyncio.timeout()` context manager is what transforms the `asyncio.CancelledError` into a `TimeoutError`, which means the `TimeoutError` can only be caught *outside* of the context manager." - VERSION-DEPENDENT (3.11).
54. `asyncio.timeout(None)` creates a deadline-less scope whose deadline can be installed later via `cm.reschedule(new_deadline)`, using `get_running_loop().time()` as the clock - VERSION-DEPENDENT (3.11).
55. `asyncio.eager_task_factory` and `asyncio.create_eager_task_factory(custom_task_constructor)` were added in 3.12. Installed with `loop.set_task_factory(asyncio.eager_task_factory)`, "coroutines begin execution synchronously during `Task` construction. Tasks are only scheduled on the event loop if they block." - VERSION-DEPENDENT (3.12).
56. The eager factory is a documented semantic change, not an optimisation: "If the coroutine returns or raises, the task is never scheduled to the event loop." Code that relies on `create_task()` returning before the coroutine body runs breaks under it - VERSION-DEPENDENT (3.12).
57. `Task.cancel(msg=None)` "arranges for a `CancelledError` exception to be thrown into the wrapped coroutine on the next cycle of the event loop" and "does not guarantee that the Task will be cancelled". It returns `False` if the task is already done or cancelled - ESTABLISHED.
58. "Should the coroutine nevertheless decide to suppress the cancellation, it needs to call `Task.uncancel()` in addition to catching the exception." `uncancel()` and `cancelling()` were added in 3.11; `uncancel()` decrements the request count and returns the remainder; 3.13 "Changed to rescind pending cancellation requests upon reaching zero" - VERSION-DEPENDENT (3.11, 3.13).
59. `uncancel()` is what makes structured blocks composable: it "allows for elements of structured concurrency like Task groups and `asyncio.timeout()` to continue running, isolating cancellation to the respective structured block." The docs also say it "isn't expected to be used by end-user code" - VERSION-DEPENDENT (3.11).
60. `cancelling() > 0` does not mean the task is cancelled: "if this number is greater than zero but the Task is still executing, `cancelled()` will still return `False`" - VERSION-DEPENDENT (3.11).
61. `asyncio.shield(aw)` protects the inner awaitable, not the caller: "if the coroutine containing it is cancelled, the Task running in `something()` is not cancelled. From the point of view of `something()`, the cancellation did not happen. Although its caller is still cancelled, so the `await` expression still raises a `CancelledError`." If the inner task is cancelled from within itself, "that would also cancel `shield()`" - ESTABLISHED.
62. `asyncio.CancelledError` "directly subclasses `BaseException`", so `except Exception:` does not catch it. The docs prescribe `try/finally` for cleanup and say that when `CancelledError` is explicitly caught "it should generally be propagated when clean-up is complete" - ESTABLISHED.
63. "Save a reference to tasks passed to this function, to avoid a task disappearing mid-execution. The event loop only keeps weak references to tasks." A fire-and-forget `asyncio.create_task(...)` whose result is discarded can be garbage-collected before completing - ESTABLISHED.
64. The "exception never retrieved" surface: a task whose exception is never read logs `Task exception was never retrieved` with the future repr and the exception, at destruction time - ESTABLISHED.
65. asyncio debug mode is enabled by any of: `PYTHONASYNCIODEBUG=1`, `-X dev` (Python Development Mode), `asyncio.run(..., debug=True)`, `loop.set_debug()`. It logs callbacks slower than `loop.slow_callback_duration` (default 100 ms / 0.1 s), logs slow I/O-selector executions, raises on non-threadsafe API calls from the wrong thread, and emits a `RuntimeWarning` with the creation traceback for never-awaited coroutines - ESTABLISHED.
66. `asyncio.run(coro, *, debug=None, loop_factory=None)`: `debug` became `None`-by-default in 3.10 "to respect the global debug mode settings", `loop_factory` was added in 3.12, and in 3.14 `coro` "can be any awaitable object". Every call creates and closes a *new* event loop - VERSION-DEPENDENT (3.10, 3.12, 3.14).
67. `asyncio.Runner(*, debug=None, loop_factory=None)` (added 3.11) is the documented seam for running several coroutines on one loop, with `Runner.run(coro, *, context=None)` accepting a custom `contextvars.Context`. It initialises lazily - the loop is created on `with`-entry or the first `run()`/`get_loop()` call - VERSION-DEPENDENT (3.11).
68. The asyncio *policy* system is deprecated and "will be removed in Python 3.16"; this covers `get_event_loop_policy()`, `set_event_loop_policy()`, `DefaultEventLoopPolicy` and `AbstractEventLoopPolicy`. Test harnesses that install a custom policy must migrate to `loop_factory` / `asyncio.Runner` - VERSION-DEPENDENT (removal in 3.16).
69. `asyncio.get_event_loop()` "Changed in version 3.14: Raises a `RuntimeError` if there is no current event loop." The old implicit loop-creation behaviour is gone - VERSION-DEPENDENT (3.14).
70. `loop.run_in_executor(executor, func, *args)`: since 3.11 "`executor` must be an instance of `ThreadPoolExecutor`". With `executor=None` a `ThreadPoolExecutor` is lazily created unless one was installed with `loop.set_default_executor()`. A `ProcessPoolExecutor` is not accepted - VERSION-DEPENDENT (3.11).
71. `asyncio.Queue` is "not thread safe"; `maxsize <= 0` means infinite. `Queue.shutdown(immediate=False)` and `asyncio.QueueShutDown` were added in 3.13; with `immediate=True` the queue is drained, the unfinished-task count is reduced by the number drained, and blocked `get()` callers raise `QueueShutDown` - VERSION-DEPENDENT (3.13).
72. `asyncio.EventLoop` "is an alias to `SelectorEventLoop` on Unix and `ProactorEventLoop` on Windows", so loop-specific behaviour (subprocess support, signal handling) differs by platform with identical code - ESTABLISHED.

### asyncio introspection and diagnosis

73. Stdlib async call-graph introspection is "Added in version 3.14": `asyncio.print_call_graph(future=None, /, *, file=None, depth=1, limit=None)`, `asyncio.format_call_graph(future=None, /, *, depth=1, limit=None)`, `asyncio.capture_call_graph(future=None, /, *, depth=1, limit=None)`, returning a `FutureCallGraph(future, call_stack, awaited_by)` whose `call_stack` is a tuple of `FrameCallGraphEntry(frame)` and whose `awaited_by` is a tuple of nested `FutureCallGraph` objects. With no current task and no `future`, `format_call_graph()` returns an empty string and `capture_call_graph()` returns `None` - VERSION-DEPENDENT (3.14).
74. 3.14 also ships out-of-process task inspection: `python -m asyncio ps PID` prints a flat task table (tid, task id, task name, coroutine stack, awaiter chain, awaiter name, awaiter id) and `python -m asyncio pstree PID` renders the await tree; if cycles are detected in the await graph the tool raises an error listing the cycle paths - VERSION-DEPENDENT (3.14).
75. The out-of-process machinery is PEP 768 ("Safe external debugger interface for CPython", Final, 3.14), which adds `sys.remote_exec(pid: int, script: str|bytes|PathLike) -> None`, executing at the next eval-breaker safe point and raising an audit event first. It can be disabled with the `PYTHON_DISABLE_REMOTE_DEBUG` environment variable (any value, including empty), `-X disable-remote-debug`, or a build configured `--without-remote-debug` - VERSION-DEPENDENT (3.14).
76. Consequence of fact 75: `python -m asyncio ps` silently has no target in hardened environments or containers that set `PYTHON_DISABLE_REMOTE_DEBUG`, and on builds compiled `--without-remote-debug` - VERSION-DEPENDENT (3.14).

### concurrent.futures semantics

77. `Executor.submit()` captures the callable's exception in the `Future`; it is re-raised on `Future.result()`. `Executor.map()` defers differently: "If a `fn` call raises an exception, then that exception will be raised when its value is retrieved from the iterator." A `map()` whose result iterator is never consumed swallows every worker exception - ESTABLISHED.
78. `Executor.shutdown(wait=True, cancel_futures=False)`: `cancel_futures` was added in 3.9 and "will cancel all pending futures that the executor has not started running. Any futures that are completed or running won't be cancelled, regardless of the value of `cancel_futures`." With both `True`, running futures complete first and only the remainder are cancelled - VERSION-DEPENDENT (3.9).
79. Default `max_workers`: `ThreadPoolExecutor` was `cpu_count * 5` in 3.5, `min(32, os.cpu_count() + 4)` from 3.8, and `min(32, (os.process_cpu_count() or 1) + 4)` from 3.13. `ProcessPoolExecutor` defaults to `os.process_cpu_count()` from 3.13, and on Windows `max_workers` "must be less than or equal to 61" with the `None` default capped at 61 - VERSION-DEPENDENT (3.8, 3.13).
80. The executor work queue is effectively unbounded, and `Executor.map()` collects its inputs eagerly: "The `iterables` are collected immediately rather than lazily, unless a `buffersize` is specified to limit the number of submitted tasks whose results have not yet been yielded. If the buffer is full, iteration over the `iterables` pauses until a result is yielded from the buffer." `buffersize` was added in 3.14 and is the only in-stdlib backpressure knob for executors - VERSION-DEPENDENT (3.14).
81. Documented executor deadlock: "Deadlocks can occur when the callable associated with a `Future` waits on the results of another `Future`." Nesting `submit()` inside a task running on the same pool with insufficient workers hangs with no error - ESTABLISHED.
82. `BrokenThreadPool` (3.7) is raised when a `ThreadPoolExecutor` worker "has failed initializing"; `BrokenProcessPool` (3.3) when a `ProcessPoolExecutor` worker "has terminated in a non-clean fashion". 3.15 improves the latter's report: "The resulting traceback will now tell you the PID and exit code of the terminated process." - VERSION-DEPENDENT (3.3, 3.7, 3.15).
83. `Future.set_result()`, `Future.set_exception()` and `Future.set_running_or_notify_cancel()` are documented as APIs that "should only be used by `Executor` implementations and unit tests" - the docs explicitly bless them for building deterministic in-test executors. Since 3.8 `set_result`/`set_exception` raise `concurrent.futures.InvalidStateError` if the future is already done - VERSION-DEPENDENT (3.8).
84. `concurrent.futures.wait(fs, timeout=None, return_when=ALL_COMPLETED)` returns a named 2-tuple of sets `(done, not_done)` where `done` includes cancelled futures; `FIRST_EXCEPTION` "will return when any future finishes by raising an exception. If no future raises an exception then it is equivalent to `ALL_COMPLETED`." `as_completed(fs, timeout=None)` measures its timeout "from the original call to `as_completed()`", not per item - ESTABLISHED.
85. `queue.Queue(maxsize=0)` is the thread-side backpressure primitive: `put()` blocks once `maxsize` is reached. `Queue.shutdown(immediate=False)` and `queue.ShutDown` were added in 3.13. `queue.SimpleQueue` is unbounded and its C implementation is reentrant - "`put()` or `get()` calls can be interrupted by another `put()` call in the same thread without deadlocking", which makes it the safe choice inside destructors and weakref callbacks - VERSION-DEPENDENT (3.13).

### Processes and start methods

86. 3.14 changed the POSIX default start method: "On POSIX platforms the default start method was changed from `fork` to `forkserver`", for `multiprocessing` and `concurrent.futures.ProcessPoolExecutor`. `spawn` remains the default on Windows and macOS. "Code that requires `fork` must explicitly specify that via `get_context()` or `set_start_method()`." - VERSION-DEPENDENT (3.14).
87. Since 3.12, "If Python is able to detect that your process has multiple threads, the `os.fork()` function that this start method calls internally will raise a `DeprecationWarning`." Mixing threads and `fork` is on a deprecation path, not merely discouraged - VERSION-DEPENDENT (3.12).
88. In 3.14 "`forkserver` now authenticates its control socket to avoid relying solely on filesystem permissions" - VERSION-DEPENDENT (3.14).
89. `set_start_method(method, force=False)` raises `RuntimeError` if the start method has already been set and `force` is not `True`; `get_context(method=None)` with the global method unset "will set it to the system default". Tests that switch start methods must therefore control ordering or use per-context objects - ESTABLISHED.

### anyio and trio

90. trio 0.33.0 (2026-02-14, Requires-Python >=3.10) is the current release; trio describes itself as "based on a new way of thinking that we call 'structured concurrency'" - VERSION-DEPENDENT (trio 0.33.0).
91. anyio 4.14.2 (2026-07-12, Requires-Python >=3.10) implements "Trio-like structured concurrency on top of asyncio" and lets applications "run unmodified on either asyncio or Trio"; anyio task groups are trio's "nurseries" - VERSION-DEPENDENT (anyio 4.14.2).
92. trio nursery guarantee: `async with trio.open_nursery() as nursery:` does not block on entry, `nursery.start_soon(async_fn, *args)` returns before the child runs, and "the block does not exit until *all* tasks have completed"; an unhandled child exception cancels the remaining children and re-raises grouped in an `ExceptionGroup` - ESTABLISHED.
93. trio cancellation is level-triggered: once a scope is cancelled, "all cancellable operations in that block will keep raising `Cancelled`". `CancelScope` exposes `deadline`, `shield`, `cancel_called` and `cancelled_caught`; `move_on_after`/`fail_after` take relative seconds and `move_on_at`/`fail_at` absolute deadlines - ESTABLISHED.
94. anyio states the contrast explicitly: anyio cancel scopes and task groups "use *level cancellation*... it will get hit with a cancellation exception any time it hits a *yield point*", whereas on plain asyncio "a `CancelledError` is raised in the task and the task then gets to handle it however it likes, even opting to ignore it entirely" (edge cancellation) - ESTABLISHED.
95. anyio shielding rule: "The shielded block will be exempt from cancellation except when the shielded block itself is being cancelled." Awaiting anything during cleanup inside a cancelled scope requires wrapping in a shielded cancel scope "or the operation will be cancelled immediately" - ESTABLISHED.
96. anyio's hard rule: "Always reraise the cancellation exception if you catch it. Failing to do so may cause undefined behavior in your application." - ESTABLISHED.
97. trio's checkpoint rule is the property asyncio lacks: "if you call an async function provided by Trio (`await <something in trio>`), and it doesn't raise an exception, then it *always* acts as a checkpoint", where a checkpoint is "a point where Trio checks for cancellation" and where the scheduler may switch tasks. Synchronous functions contain no checkpoints, so a pure-CPU loop is uncancellable - ESTABLISHED.
98. `trio.Cancelled` "inherits from BaseException, like KeyboardInterrupt and SystemExit do, so that it won't be caught by catch-all `except Exception:` blocks", and after cleanup "you should do some cleanup and then re-raise it or otherwise let it continue propagating" - ESTABLISHED.
99. anyio 4.14.0 added `TaskGroup.cancel()` (the same affordance CPython adds in 3.15), an async `itertools` module, `TaskHandle` return values, custom capacity limiters in I/O operations, and Python 3.15 support - VERSION-DEPENDENT (anyio 4.14.0).

### Determinism for tests

100. Fowler's two operative rules, verbatim: "Never use bare sleeps to wait for asynchonous responses: use a callback or polling." and "Always wrap the system clock, so it can be easily substituted for testing." His polling guidance is a small `pollingInterval` with a high `waitLimit` - ESTABLISHED.
101. The named tactic for *confining* rather than eliminating nondeterminism is Quarantine: "Place any non-deterministic test in a quarantined area. (But fix quarantined tests quickly.)" Fowler's six categories are Quarantine, Lack of Isolation, Asynchronous Behavior, Remote Services, Time, and Resource Leaks - ESTABLISHED.
102. The academic family of tactics for bounding schedule exploration (preemption bounding, delay bounding, "schedule bounding") surfaced only in search results this session; the PPoPP/TOPC papers were not loaded, so no claim about their content or findings is made here - OPEN.
103. trio ships the only mature deterministic-clock story in this ecosystem: `trio.testing.MockClock(rate=0.0, autojump_threshold=inf)`. With the default `rate=0.0` "the clock only advances through manual calls to `jump()` or when the `autojump_threshold` is triggered"; with `autojump_threshold` set, the clock "watches the execution of the run loop, and any time things have settled down and everyone's waiting for a timeout, it jumps the clock forward to that timeout". `jump(seconds)` raises `ValueError` for negative values - ESTABLISHED.
104. `trio.testing.wait_all_tasks_blocked(cushion=0.0)` "blocks until there are no runnable tasks" - the sleep-free replacement for `await asyncio.sleep(0.1)` as a synchronisation device. `trio.testing.Sequencer` forces "code in different tasks to run in an explicit linear order" - ESTABLISHED.
105. `trio.testing.RaisesGroup` matches `ExceptionGroup` shapes: by default it requires all specified exceptions present with no others, order-independent, with `allow_unwrapped=True` and `flatten_subgroups=True` modifiers. It is the assertion primitive for structured-concurrency failure modes - ESTABLISHED.
106. There is no stdlib asyncio mock clock and no stdlib deterministic asyncio scheduler. The documented substitution seam is `loop_factory` on `asyncio.run()` (3.12+) or `asyncio.Runner` (3.11+), i.e. supply a loop subclass overriding `time()` - VERSION-DEPENDENT (3.11, 3.12).
107. Making concurrent code single-threaded under test: the seam is dependency-injecting the `Executor`, then supplying a synchronous fake whose `submit()` runs inline and returns a `Future` completed via `set_result()`/`set_exception()` - the exact use the docs sanction (fact 83). `ThreadPoolExecutor(max_workers=1)` is *not* equivalent: work still runs on another thread, just serialised - ESTABLISHED.
108. Seed determinism: `PYTHONHASHSEED` accepts a decimal integer in [0, 4294967295] as a fixed hash seed, and "Specifying the value 0 will disable hash randomization"; unset or `random` means a random seed. Its stated purpose is "to allow repeatable hashing, such as for selftests for the interpreter itself". Hash randomization is on by default, so `-R` "only has an effect if the `PYTHONHASHSEED` environment variable is set to anything other than `random`" - ESTABLISHED.
109. Hypothesis `derandomize` "seed[s] Hypothesis' random number generator using a hash of the test function, so that every run will test the same set of test cases until you update Hypothesis, Python, or the test function"; default `False`, `True` in CI. It is explicitly "designed to enable deterministic CI tests rather than reproducing observed failures", and an explicit `@seed(...)` overrides it. Hypothesis' own caveat: a fixed seed reproduces cases only "assuming that there are no other sources of nondeterminisim, such as timing, hash randomization, or external state" - ESTABLISHED.
110. pytest-asyncio 1.4.0 (2026-05-26, Requires-Python >=3.10): `asyncio_mode` is `"strict"` when unset; `asyncio_default_test_loop_scope` defaults to `function`; `asyncio_default_fixture_loop_scope` currently "defaults to the fixture scope" and the docs warn that "in future versions of pytest-asyncio, the value will default to function when unset". Pin it explicitly or a future upgrade silently changes loop lifetime - VERSION-DEPENDENT (pytest-asyncio 1.4).

### Data-race and deadlock diagnosis

111. FLAGGED-SECONDARY (py-free-threading.github.io, maintained by "Quansight Labs & open source contributors"): the only race detector CPython supports directly is ThreadSanitizer, via the `--with-thread-sanitizer` configure option; the guide's build line is `./configure --disable-gil --with-thread-sanitizer --prefix $PWD/cpython-tsan`, and CPython carries a suppressions file at `Tools/tsan/suppressions_free_threading.txt`. Useful `TSAN_OPTIONS` include `halt_on_error`, `suppressions`, `allocator_may_return_null`, `exitcode`, `log_path` - ESTABLISHED.
112. FLAGGED-SECONDARY (py-free-threading.github.io): TSan instruments compiled code. It does not detect Python-level races (two threads doing `counter += 1`, or a lost update through a `dict`). No pure-Python race detector is recommended by the free-threading guide - ESTABLISHED.
113. FLAGGED-SECONDARY (py-free-threading.github.io; Quansight-Labs/pytest-run-parallel README via search summary): the practical Python-level tactic is stress plus repetition: `pytest-run-parallel` and `pytest-freethreaded` run the same test in a thread pool (explicitly "not an alternative to pytest-xdist" and "not useful to speed up the execution of a test suite"), `pytest-run-parallel --forever` loops until a crash, and `pytest-repeat --count=100` (e.g. `PYTHON_GIL=0 pytest -x -v --count=100 test_concurrent.py`) is recommended because "given the non-deterministic nature of parallel execution, tests may still pass most of the time". Thread barriers to align threads raise clash probability - ESTABLISHED.
114. FLAGGED-SECONDARY (py-free-threading.github.io): `pytest-run-parallel` automatically marks tests that use `warnings` as thread-unsafe on Python 3.13 and older, and on 3.14 when the interpreter is not configured for thread-safe warnings (see `-X context_aware_warnings`, fact 32) - VERSION-DEPENDENT (3.13, 3.14).
115. Deadlock diagnosis in-process: `faulthandler.dump_traceback(file=sys.stderr, all_threads=True)` dumps every thread's Python traceback, and `faulthandler.dump_traceback_later(timeout, repeat=False, file=sys.stderr, exit=False)` is the watchdog form - the standard "the test suite hung, show me where" instrument. `faulthandler.register(signum, ...)` is "Not available on Windows" - ESTABLISHED.
116. Critical free-threading caveat: the faulthandler docs carry "Changed in version 3.14: Only the current thread is dumped if the GIL is disabled to prevent the risk of data races." On `python3.14t` the all-threads dump you rely on for deadlock diagnosis degrades to a single-thread dump - VERSION-DEPENDENT (3.14).
117. `faulthandler.enable(file=sys.stderr, all_threads=True, c_stack=True)` installs handlers for SIGSEGV, SIGFPE, SIGABRT, SIGBUS and SIGILL; `c_stack=True` (3.14+) also prints the C stack after the Python traceback - useful when a free-threaded crash is inside an extension. Enable at startup with `-X faulthandler` or `PYTHONFAULTHANDLER` - VERSION-DEPENDENT (3.14).
118. FLAGGED-SECONDARY (py-free-threading.github.io): `gdb`/`lldb` with the CPython `py-` command set (`py-bt`) work with `PYTHON_GIL=0`, but the guide footnotes that the lldb Python integration "is not correctly working on lldb after CPython 3.12" - OPEN.
119. `threading.settrace_all_threads(func)` and `threading.setprofile_all_threads(func)` (3.12) install a trace/profile function on "all threads started from the `threading` module and all Python threads that are currently executing" - the hook for building an in-test scheduler observer without touching each thread - VERSION-DEPENDENT (3.12).
120. Free-threaded ecosystem readiness could not be quantified this session: `labs.quansight.org/blog/free-threaded-one-year-recap` returned HTTP 403, and the only counts available were search snippets. No wheel-coverage number is asserted here - OPEN.

## New content the manifest set should carry

**1. The four-model decision table** - NEW: python_concurrency_determinism_manifest.md
One table, four rows, six columns: model / correct when / parallelism obtained / boundary cost / characteristic silent failure / testability cost. asyncio: I/O concurrency, no CPU parallelism, no boundary, a blocking call stalls the whole loop, "almost all asyncio objects are not thread safe". Threads: blocking I/O and GIL-releasing C code, CPU parallelism only on free-threaded builds, shared memory, data race and lock-order deadlock, nondeterministic interleaving with no scheduler control. Subinterpreters: isolation with in-process comms, real multi-core since 3.12, pickle plus `NotShareableError` at the boundary, silent GIL re-enable from an unmarked extension, no shared fakes or fixtures. Processes: CPU-bound pure Python and fault isolation, real multi-core, pickle plus re-import, `BrokenProcessPool`, no coverage or monkeypatching across the boundary. Make the table the artefact an agent must consult before choosing a model.

**2. Free-threading: detection, gating and the honest performance statement** - NEW: python_concurrency_determinism_manifest.md
State PEP 779 (Final, 3.14) as the supported-status PEP and PEP 703 (Final, 3.13) as the implementation PEP. Give the three detection mechanisms and rule that `sysconfig.get_config_var("Py_GIL_DISABLED")` gates *builds* while `sys._is_gil_enabled()` gates *runtime*. Give `-X gil=0,1` and `PYTHON_GIL` with the precedence rule and the `--disable-gil` precondition. Quote the HOWTO overhead sentence (1% macOS aarch64 to 8% x86-64 Linux) and record that What's New 3.14 says 5-10% and PEP 703 said 5-6%; forbid merging the figures. Record that an unmarked C extension can silently re-enable the GIL with only a printed warning, and that `-X thread_inherit_context` and `-X context_aware_warnings` default differently per build.

**3. asyncio structured-concurrency contract** - NEW: python_concurrency_determinism_manifest.md
The obligations an asyncio component must satisfy: every concurrent fan-out uses `TaskGroup` (3.11+) rather than bare `create_task`; every task reference is retained, because the loop keeps only weak references; every timeout uses `asyncio.timeout` with the `TimeoutError`-caught-outside rule; `CancelledError` is `BaseException` and is re-raised after cleanup; aggregate failures are caught with `except*`; `shield` protects the inner awaitable and not the caller. Add the 3.15 affordance `TaskGroup.cancel()` for non-exceptional early exit and the pre-3.15 boilerplate it replaces. Treat the eager task factory as an opt-in semantic change that must be declared, never assumed.

**4. Diagnosability contract for async and threaded code** - error_tracing_contract_manifest.md (extend) or NEW: python_concurrency_determinism_manifest.md
Require asyncio debug mode in CI (`-X dev` or `PYTHONASYNCIODEBUG=1`) with a project-tuned `loop.slow_callback_duration`; require that "Task exception was never retrieved" is a test failure, not log noise; require `asyncio.print_call_graph()` in the failure path of long-running tasks (3.14+); document `python -m asyncio ps|pstree PID` as the production stuck-task procedure and record that it rests on PEP 768 `sys.remote_exec`, which `PYTHON_DISABLE_REMOTE_DEBUG`, `-X disable-remote-debug` or `--without-remote-debug` can turn off. Require `faulthandler` enabled with a `dump_traceback_later` watchdog in the test runner, and record the 3.14 free-threaded degradation to a single-thread dump.

**5. Backpressure and shutdown obligations for executors and queues** - NEW: python_concurrency_determinism_manifest.md
Executor work queues are unbounded and `Executor.map()` collects inputs eagerly; the only stdlib knob is `Executor.map(buffersize=...)` (3.14+). Everything else needs an explicit `queue.Queue(maxsize=N)` or `asyncio.Queue(maxsize=N)` in front of the pool. Shutdown obligations: `shutdown(wait=True, cancel_futures=True)` cancels only *pending* work and running work always finishes; `Queue.shutdown()` with `ShutDown`/`QueueShutDown` (3.13) is the graceful-drain primitive; a future that waits on another future in the same pool deadlocks silently, so nesting `submit()` is forbidden.

**6. Determinism tactics for concurrent tests** - python_testing_tooling_manifest.md (extend) or NEW: python_concurrency_determinism_manifest.md
Four injectable seams - clock, seed, executor, event loop - with the named tactic per seam. Clock: never call `time.time()` in the core; trio's `MockClock(autojump_threshold=...)` is the reference implementation and asyncio has no stdlib equivalent, so substitute via `loop_factory`. Seed: fixed `PYTHONHASHSEED`, Hypothesis `derandomize` in CI, carrying Hypothesis' own caveat about timing and external state. Executor: inject the `Executor` and use an inline fake driven by `Future.set_result()`, which the docs sanction for unit tests; `max_workers=1` is not single-threaded. Synchronisation: never sleep to wait ("Never use bare sleeps to wait for asynchonous responses: use a callback or polling"); use `wait_all_tasks_blocked()`, `Event`, `Barrier`, or `Sequencer` for explicit ordering. Close with Quarantine as the named containment tactic for the residual nondeterminism you cannot remove.

**7. Subinterpreter boundary contract** - NEW: python_concurrency_determinism_manifest.md
`concurrent.interpreters` (3.14). What crosses cheaply (`None`, `bool`, `bytes`, `str`, `int`, `float`, `tuple` thereof), what shares mutable data (`memoryview`, `Queue`), and that everything else is pickled or raises `NotShareableError`. `InterpreterPoolExecutor` is a `ThreadPoolExecutor` subclass so it is loop-compatible, pickles callable, args and return value, and can degrade a non-shareable worker exception to `None`. Record `create_queue(maxsize=0, *, unbounditems=UNBOUND)` from source against the docs' parameterless rendering. State plainly that isolation is not a security boundary.

**8. Architecture rule: concurrency at the edge, determinism in the core** - architecture_manifest_default.md (extend)
Tie the concurrency-model choice to the functional-core/imperative-shell split the manifest set already carries: the core is synchronous, single-threaded and pure, so none of this applies to it; the shell owns the loop, the pool, the queue and the clock, and owns them behind injected seams. The rule to write down: a module that both computes and schedules is untestable by construction.

## Traps for coding agents

1. **Attributing free-threaded "officially supported" status to PEP 703.** PEP 703 is Final for **3.13** and is the implementation PEP; **PEP 779** is the Final PEP for **3.14** that makes the free-threaded build "officially supported but still optional". Getting this backwards is the single most likely factual error on this topic.
2. **Claiming free-threading is the default.** It is not, on any version. Phase III has no PEP and no date. What did change: 3.15's official macOS binaries install free-threading support by default - availability, not default execution mode.
3. **Using `sysconfig.get_config_var("Py_GIL_DISABLED")` as a runtime check.** It reports build capability. Under `-X gil=1` the GIL is on while that variable is still `1`. The runtime answer is `sys._is_gil_enabled()`, whose leading underscore makes agents shy away in favour of something wrong.
4. **Assuming `-X gil=0` works anywhere.** `0` "is only available in builds configured with `--disable-gil`". On a standard build it fails. Also: `-X gil` beats `PYTHON_GIL`, so a Dockerfile env var can be silently overridden by an entrypoint flag.
5. **Assuming a free-threaded interpreter means parallelism.** Importing one C extension that does not declare `Py_mod_gil = Py_MOD_GIL_NOT_USED` can re-enable the GIL at runtime with nothing but a printed warning. The program stays correct and gets no faster.
6. **Relying on `dict`/`list`/`set` internal locks.** The docs call that "a description of the current implementation, not a guarantee". `counter += 1`, `d[k] = d[k] + 1` and read-modify-write on a list are races regardless. Use `threading.Lock`.
7. **Sharing one iterator or generator across threads.** Documented as unsafe: "threads may see duplicate or missing elements". Before 3.15 there was no stdlib fix; from 3.15 use `threading.serialize_iterator` / `synchronized_iterator` / `concurrent_tee`. Do not offer these names on 3.14.
8. **`except Exception` around a coroutine or task body.** `asyncio.CancelledError` and `trio.Cancelled` subclass `BaseException` precisely so this does not catch them. The inverse trap is worse: `except BaseException: pass` in a task body silently defeats cancellation and hangs the enclosing `TaskGroup` or timeout forever.
9. **`except ValueError:` around an `async with asyncio.TaskGroup()` block.** Child exceptions arrive as `ExceptionGroup`/`BaseExceptionGroup`. The correct form is `except* ValueError:` (3.11+). Wrapping with a plain `except` and expecting the original type is a common and silent miss.
10. **Expecting `asyncio.timeout` to raise `TimeoutError` inside its own block.** The context manager is what converts `CancelledError` into `TimeoutError`, so `TimeoutError` "can only be caught *outside* of the context manager". A `try/except TimeoutError` placed inside the `async with` never fires.
11. **Catching `CancelledError` for cleanup and not re-raising.** asyncio requires `Task.uncancel()` in addition to swallowing the exception if a task genuinely means to deny cancellation; anyio states outright that failing to re-raise "may cause undefined behavior". Cleanup that must `await` has to sit in a shielded scope or it is cancelled immediately.
12. **Reading `Task.cancelling() > 0` as "cancelled".** "if this number is greater than zero but the Task is still executing, `cancelled()` will still return `False`".
13. **Fire-and-forget `asyncio.create_task(...)`.** "The event loop only keeps weak references to tasks" - discard the return value and the task can be garbage-collected mid-flight. Either retain it or use a `TaskGroup`.
14. **Installing an eager task factory as a free speedup.** It is a semantic change: the coroutine runs synchronously during `Task` construction, and "If the coroutine returns or raises, the task is never scheduled to the event loop." Ordering and exception-timing assumptions break.
15. **Assuming asyncio cancellation is level-triggered like trio's.** anyio documents asyncio as edge-triggered: a task "gets to handle it however it likes, even opting to ignore it entirely". Code ported from trio/anyio to raw asyncio loses the guarantee that a cancelled scope keeps raising at every yield point.
16. **Assuming any `await` is a cancellation point.** Only trio guarantees the checkpoint rule for its own async functions. A pure-CPU loop with no `await` is uncancellable on every backend, and a third-party async function may contain no checkpoint at all.
17. **`Executor.map()` with an unconsumed result iterator.** Worker exceptions are raised only "when its value is retrieved from the iterator". `list(executor.map(...))` propagates; a bare `executor.map(...)` discards every failure.
18. **`shutdown(cancel_futures=True)` as a stop button.** It cancels only work not yet started: "Any futures that are completed or running won't be cancelled, regardless of the value of `cancel_futures`."
19. **Treating an executor as bounded.** It is not. `Executor.map()` even "collect[s] immediately rather than lazily" unless `buffersize` (3.14+) is passed. Feeding a generator of a million items to `map()` on 3.13 materialises a million submissions.
20. **Nesting `submit()` on the same pool.** "Deadlocks can occur when the callable associated with a `Future` waits on the results of another `Future`." No exception, no timeout, just a hang.
21. **Assuming `fork` is the multiprocessing default on Linux.** Changed in **3.14**: `forkserver` is the POSIX default, `spawn` on Windows and macOS, and "Code that requires `fork` must explicitly specify that". Code with mutable module-level state that silently worked under `fork` now sees a fresh import per worker. Separately, `fork` from a multi-threaded process has raised `DeprecationWarning` since **3.12**.
22. **Passing a `ProcessPoolExecutor` to `loop.run_in_executor`.** Since 3.11 "`executor` must be an instance of `ThreadPoolExecutor`". `InterpreterPoolExecutor` is accepted only because it subclasses `ThreadPoolExecutor`.
23. **Installing a custom asyncio event loop policy in tests.** The policy system "is deprecated and will be removed in Python 3.16". Use `asyncio.Runner(loop_factory=...)` or `asyncio.run(..., loop_factory=...)`. Relatedly, `asyncio.get_event_loop()` now "Raises a `RuntimeError` if there is no current event loop" (3.14) instead of quietly creating one.
24. **Submitting a lambda, closure or local class to `InterpreterPoolExecutor`.** Everything is pickled - initializer, initargs, callable, arguments and return value. A worker exception that is not shareable is replaced with `None`, so a failing job can look like a job that returned nothing.
25. **Believing `concurrent.interpreters.create_queue()` takes no arguments** because the docs render it that way. The shipped signature in 3.14 and 3.15 is `create(maxsize=0, *, unbounditems=UNBOUND)`, exported as `create_queue`; PEP 734 documents `maxsize` too. Conversely, do not promise a `syncobj` parameter - there is none.
26. **Naming the module `interpreters`.** PEP 734's original name was renamed before landing; the stdlib module is `concurrent.interpreters` (3.14), built on the private `_interpreters`.
27. **Treating subinterpreters as a sandbox.** Interpreters in one process "can technically never be strictly isolated from one another since there are few restrictions on memory access within the same process".
28. **Guessing the asyncio task-graph API.** It is `asyncio.print_call_graph()` / `format_call_graph()` / `capture_call_graph()` returning `FutureCallGraph(future, call_stack, awaited_by)` with `FrameCallGraphEntry(frame)` - all "Added in version 3.14", none available on 3.13. The CLI is `python -m asyncio ps PID` and `python -m asyncio pstree PID`, and it can be disabled process-wide by `PYTHON_DISABLE_REMOTE_DEBUG` or `-X disable-remote-debug`, or compiled out with `--without-remote-debug`.
29. **Relying on an all-threads `faulthandler` dump to diagnose a free-threaded deadlock.** "Changed in version 3.14: Only the current thread is dumped if the GIL is disabled to prevent the risk of data races." The instrument you reach for degrades exactly where you need it most.
30. **Expecting TSan to find Python-level races.** `--with-thread-sanitizer` instruments C. A lost update in pure Python is invisible to it. There is no recommended pure-Python race detector; the documented substitute is stress and repetition (`pytest-run-parallel`, `pytest-freethreaded`, `pytest-repeat --count=100`, `--forever`) plus barriers to widen the window.
31. **Calling `pytest-run-parallel` a speedup.** It is "not an alternative to pytest-xdist" and "not useful to speed up the execution of a test suite"; it re-runs each test in a thread pool to expose thread-unsafety.
32. **`ThreadPoolExecutor(max_workers=1)` as "single-threaded under test".** It serialises but still crosses a thread boundary, so it preserves the timing nondeterminism, exception marshalling and debugger opacity you were trying to remove. Inject a synchronous fake executor and complete futures with `set_result()` - the docs sanction those setters for "Executor implementations and unit tests".
33. **`await asyncio.sleep(0.05)` as test synchronisation.** "Never use bare sleeps to wait for asynchonous responses: use a callback or polling." Under trio the precise instrument is `trio.testing.wait_all_tasks_blocked()`; under asyncio, an `Event` - never a magic delay.
34. **Assuming a fixed seed makes a concurrent test deterministic.** Hypothesis' own wording: a fixed seed reproduces cases only "assuming that there are no other sources of nondeterminisim, such as timing, hash randomization, or external state". Pin `PYTHONHASHSEED` as well (`0` disables randomization entirely), and remember `-R` only has an effect when `PYTHONHASHSEED` is set to something other than `random`.
35. **Leaving `asyncio_default_fixture_loop_scope` unset in pytest-asyncio.** It currently "defaults to the fixture scope" and the docs warn the default will become `function`; an unpinned upgrade silently changes event-loop lifetime across the suite. `asyncio_mode` defaults to `"strict"`, so bare `async def` tests are not auto-collected as asyncio tests.
36. **Assuming C critical sections give mutual exclusion.** "Critical sections may temporarily release their locks, allowing other threads to modify the protected data." They are also "no-ops in non-free-threaded builds", so an extension can pass every GIL-build test and race only on `python3.14t`.
37. **Building a free-threaded wheel against the limited API.** The 3.14 and 3.15 HOWTOs still say the free-threaded build "does not currently support the Limited C API or the stable ABI", while 3.15's What's New announces `abi3t` via PEP 803 (`Py_TARGET_ABI3T`, wheel tag `abi3.abi3t`, `.abi3t.so`, opaque `PyObject`, requiring PEP 793 `PyModExport_*` and PEP 820 `PySlot`). Treat the HOWTO text as not yet updated, and either target `abi3t` deliberately or ship `cp315t` separately.
38. **Adding new `PyGILState_*` calls in fresh C code.** PEP 788 soft-deprecates the family for 3.15: no removal is planned, but "there will be no new `PyGILState` APIs in future versions of Python". New code should use `PyThreadState_Ensure()` / `PyThreadState_Release()` with interpreter guards and views.
39. **Version-stamping the wrong patch release.** As of 2026-08-08 the current patches are 3.14.7 and 3.13.15 (both 2026-08-05), and 3.15 is at rc1 (2026-08-04) with final scheduled 2026-10-01. 3.10 reaches end of life in 2026-10.
40. **Quoting one free-threading overhead number as *the* number.** Four different figures live in four primary sources (HOWTO 1-8%, What's New 3.14 5-10%, PEP 703 5-6% single-threaded, PEP 779's 15% Phase II target). Cite the source alongside the figure, or omit the figure.
