## Facts

### Linting and formatting

1. Ruff 0.16.2 (2026-08-07) is one binary carrying two independent gates: `ruff check` is the linter and `ruff format` is the formatter. The `ruff-pre-commit` repo exposes them as hook ids `ruff-check` (`entry: ruff check --force-exclude`) and `ruff-format` (`entry: ruff format --force-exclude`), plus a bare `ruff` hook the repo itself labels a "legacy alias" that runs `ruff check`; all three declare `types_or: [python, pyi, jupyter]` - VERSION-DEPENDENT (ruff 0.16.x).
2. Ruff 0.16.0 (2026-07-23) raised the default-enabled rule count from 59 to 413. Astral list it first among breaking changes and note the default set "was last modified in v0.1.0" - VERSION-DEPENDENT (ruff 0.16.0).
3. The default selection is a list of INDIVIDUAL rule codes, not of prefixes. From isort only `I001` is enabled; from pydocstyle only `D419`; from flake8-bandit only `S102`, `S110`, `S112`; from pycodestyle only `E722`, `E902`, `W605`. Reading the Default Rules page's per-linter headings as "isort, pydocstyle and bandit are now on by default" is wrong - VERSION-DEPENDENT (ruff 0.16.x).
4. Ruff 0.16.0 also REMOVED 18 rules from the defaults as too opinionated: `E401`, `E402`, `E701`, `E702`, `E703`, `E711`, `E712`, `E713`, `E714`, `E721`, `E731`, `E741`, `E742`, `E743`, `F403`, `F405`, `F406`, `F722` - VERSION-DEPENDENT (ruff 0.16.0).
5. Selection resolves as: the highest-priority `lint.select` becomes the basis, then `lint.extend-select` and `lint.ignore` are applied to it; "CLI options are given higher priority than `pyproject.toml` options, and the current `pyproject.toml` file is given higher priority than any inherited `pyproject.toml` files." Writing your own `select` REPLACES the 413-code default; it does not add to it - ESTABLISHED.
6. `select = ["ALL"]` enables every rule and automatically disables the pairs that contradict each other (the docs name `D203` versus `D211`) - ESTABLISHED.
7. Ruff rule codes are "one-to-three letter prefix, followed by three digits (e.g., `F401`)", and the rules index states "Ruff supports over 900 lint rules" - VERSION-DEPENDENT (ruff 0.16.x).
8. What Ruff has consolidated, from its own prefix-to-origin table: `F` Pyflakes, `E`/`W` pycodestyle, `I` isort, `N` pep8-naming, `D` pydocstyle, `DOC` pydoclint, `UP` pyupgrade, `C90` mccabe, `PL` Pylint, `PERF` Perflint, `FURB` refurb, `TRY` tryceratops, `ERA` eradicate, `FLY` flynt, `PGH` pygrep-hooks, `S` flake8-bandit, `RUF` Ruff-specific, plus roughly 45 `flake8-*` plugins (`ANN`, `ASYNC`, `B`, `A`, `BLE`, `FBT`, `COM`, `C4`, `CPY`, `DTZ`, `T10`, `DJ`, `EM`, `EXE`, `FIX`, `FA`, `INT`, `ISC`, `ICN`, `LOG`, `G`, `INP`, `PIE`, `T20`, `PYI`, `PT`, `Q`, `RSE`, `RET`, `SLF`, `SIM`, `SLOT`, `TID`, `TD`, `TC`, `ARG`, `PTH`, `YTT`) and the domain sets `AIR` (Airflow), `FAST` (FastAPI), `NPY` (NumPy-specific), `PD` (pandas-vet) - ESTABLISHED.
9. Fix safety is a first-class axis: `lint.fixable`, `lint.unfixable`, `lint.extend-safe-fixes` (promote unsafe to safe), `lint.extend-unsafe-fixes` (demote safe to unsafe). `--fix` applies only safe fixes; unsafe fixes require `--unsafe-fixes` - ESTABLISHED.
10. Ruff exit codes: `0` = no violations found OR all violations were auto-fixed; `1` = violations remain; `2` = abnormal termination (invalid configuration, CLI error, internal error). `--exit-zero` forces `0`; `--exit-non-zero-on-fix` returns `1` even when every violation was fixed - ESTABLISHED.
11. Suppression surface: `# noqa: CODE` per line; a bare `# noqa` suppresses ALL violations on the line; `# ruff: noqa` and `# ruff: noqa: CODE` exempt an entire file from anywhere in it; `# ruff: disable[code]` / `# ruff: enable[code]` bracket a range; `RUF100` reports unnecessary suppressions and `--fix` deletes them; `--add-noqa` inserts them wholesale - ESTABLISHED.
12. Ruff 0.16.0 added a native suppression syntax beside `noqa`: `# ruff: ignore[F401]` at end of line OR on the line preceding the diagnostic, optionally carrying a free-text reason (`# ruff: ignore[F401] Allow unused imports`), and able to suppress a diagnostic spanning a whole logical line; plus `# ruff: file-ignore[F401]` for files. In preview mode rule NAMES may be used instead of codes - VERSION-DEPENDENT (ruff 0.16.0).
13. `ruff format` targets Black's stable style; Astral measured ">99.9% of lines are formatted identically" across large Black-formatted codebases (Django, Zulip), with deliberate deviations including f-string expression formatting and, in preview, fluent method-chain layout - ESTABLISHED.
14. Default `line-length = 88`, matching Black. Sections: `[tool.ruff]` (general - `line-length`, `target-version`, `exclude`), `[tool.ruff.lint]` (`select`, `ignore`, `fixable`), `[tool.ruff.format]` (`quote-style`, `indent-style`). File precedence: `.ruff.toml` > `ruff.toml` > `pyproject.toml`; `extend` inherits a parent config; with `target-version` unset, "Ruff will attempt to fall back to the minimum version compatible with the `requires-python` field in a nearby `pyproject.toml`" - ESTABLISHED.
15. Lint rules that fight the formatter and belong in `lint.ignore` whenever `ruff format` owns layout: `W191`, `E111`, `E114`, `E117`, `Q000`-`Q004`, `COM812`, `COM819`. Ruff emits a warning when incompatible rules are enabled - ESTABLISHED.
16. Ruff 0.16.0 formats Python code blocks inside Markdown files BY DEFAULT (info strings `python`, `py`, `python3`, `py3`, `pyi`, `pycon`), suppressible with `<!-- fmt: off -->` / `<!-- fmt: on -->` - VERSION-DEPENDENT (ruff 0.16.0).
17. Ruff's versioning policy: a MINOR bump may remove a deprecated option or feature, change configuration incompatibly, promote a rule to stable, change "the behavior of a stable rule", add stable rules to the default set, or promote a safe fix to stable. A PATCH bump may include "Bugs are fixed, including behavior changes that fix bugs", a new backwards-compatible configuration option, a rule added in preview, or a behaviour change to a preview rule. "Ruff does not yet have a stable API; once Ruff's API is stable, the major version number and semantic versioning will be used." New rules "should always be added in preview mode" and remain there "for at least one minor release before being promoted to stable" - ESTABLISHED.
18. Ruff settings that function as thresholds: `lint.mccabe.max-complexity` default `10`; `lint.pylint.max-args` default `5`; `lint.preview` and `format.preview` default `false`; `format.docstring-code-format` default `false`, with `docstring-code-line-length` default `dynamic`; `lint.dummy-variable-rgx` default `"^(_+|(_+[a-zA-Z0-9_]*[a-zA-Z0-9]+?))$"`; `lint.per-file-ignores` default `{}`, where "An initial '!' negates the file pattern" - VERSION-DEPENDENT (ruff 0.16.x).
19. `respect-gitignore` is enabled by default (Ruff skips files omitted via `.ignore`, `.gitignore` and friends), and `force-exclude` is required to "Enforce exclusions, even for paths passed to Ruff directly on the command-line" - ESTABLISHED. This is exactly why the official pre-commit hooks pass `--force-exclude`: pre-commit hands hooks explicit filenames, which otherwise bypass `exclude`.
20. pylint 4.0.6 (2026-06-14), `requires_python >=3.10.0`, summary "python code static checker". pylint 4.0.0 shipped 2025-10-12, requires astroid 4.0.0, supports Python 3.14, and changed module-scope naming: "Module-level constants that are reassigned are treated as variables and checked against `--variable-rgx` rather than `--const-rgx`" - VERSION-DEPENDENT (pylint 4.x).
21. flake8's current release is 7.3.0, dated 2025-06-20 - 14 months old as of 2026-08-08 - with `requires_python >=3.9` and summary "the modular source code checker: pep8 pyflakes and co" - VERSION-DEPENDENT.
22. flake8 "supports storing its configuration in your project in one of `setup.cfg`, `tox.ini`, or `.flake8`", always in an INI `[flake8]` section. Its configuration page does not mention `pyproject.toml`; there is no `[tool.flake8]` support - ESTABLISHED.
23. flake8 precedence: "Values set at the command line have highest priority, then those in the project configuration file, and finally there are the defaults" - ESTABLISHED.

### Gate composition: pre-commit, uv, nox, tox

24. pre-commit 4.6.1 (2026-07-21), `requires_python >=3.10`, "A framework for managing and maintaining multi-language pre-commit hooks." - VERSION-DEPENDENT.
25. Hook AUTHOR contract (`.pre-commit-hooks.yaml`). Required: `id`, `name`, `entry` ("the entry point - the executable to run. `entry` can also contain arguments that will not be overridden"), `language`. Optional, with defaults: `files` (`''`), `exclude` (`^$`), `types` (`[file]`), `types_or` (`[]`), `exclude_types` (`[]`), `always_run` (`false`), `fail_fast` (`false`), `verbose` (`false`), `pass_filenames` (`true`), `require_serial` (`false`), `description` (`''`), `language_version` (`default`), `minimum_pre_commit_version` (`'0'`), `args` (`[]`), `stages` (all stages) - ESTABLISHED.
26. The failure contract has two prongs: "The hook must exit nonzero on failure or modify files." A formatter that rewrites a file and exits `0` still fails the pre-commit run - ESTABLISHED.
27. Consumer contract (`.pre-commit-config.yaml`). Top level: `repos` (required), `default_install_hook_types` (default `[pre-commit]`), `default_language_version` (`{}`), `default_stages`, `files` (`''`), `exclude` (`^$`), `fail_fast` (`false`), `minimum_pre_commit_version` (`'0'`), `ci`. Per hook: `id`, `alias`, `name`, `language_version`, `files`, `exclude`, `types`, `types_or`, `exclude_types`, `args`, `stages`, `additional_dependencies`, `always_run`, `verbose`, `log_file`, `pass_filenames` - ESTABLISHED.
28. Valid stages are exactly: `pre-commit`, `pre-push`, `pre-merge-commit`, `prepare-commit-msg`, `commit-msg`, `post-checkout`, `post-commit`, `post-merge`, `post-rewrite`, `pre-rebase`, `manual`. From pre-commit 3.2.0 the legacy names `commit`, `push` and `merge-commit` were renamed to their `pre-`-prefixed forms; `pre-commit migrate-config` rewrites legacy configuration - VERSION-DEPENDENT (pre-commit >= 3.2.0).
29. `pre-commit install` writes only the `pre-commit` git hook unless you pass `--hook-type` (repeatable) or set `default_install_hook_types`; `--install-hooks` also builds the environments; `pre-commit install-hooks` builds environments without writing git hook scripts - ESTABLISHED.
30. Keeping local and CI identical: `pre-commit run --all-files` is the CI invocation (a bare `run` sees only staged files); `--from-ref FROM_REF --to-ref TO_REF` runs against files changed between two refs; `--show-diff-on-failure` prints the diff the hooks produced; `--hook-stage STAGE` reaches hooks scoped to `manual`; `pre-commit autoupdate` bumps `rev` pins, with `--freeze` recording the resolved commit hash instead of the tag, `--bleeding-edge` following the default branch, `--repo` narrowing and `-j/--jobs` parallelising; `pre-commit gc` prunes unused cached repos; `pre-commit try-repo` tests a hook repo before it enters the config - ESTABLISHED.
31. uv 0.12.3 (2026-08-07). `uv run` locks and syncs before invoking the command so "the project environment is always up-to-date". `--locked`: "If the lockfile is not up-to-date, uv will raise an error instead of updating the lockfile" - the CI form. `--frozen`: use "the lockfile without checking if it is up-to-date". `uv lock --check` checks the lockfile against project metadata. `uv sync --inexact` retains extraneous packages; `uv run --exact` removes packages absent from the lockfile. `--upgrade` and `--upgrade-package` bound refresh scope - VERSION-DEPENDENT (uv 0.12.x).
32. nox 2026.7.11 (2026-07-12), "Flexible test automation.", `requires_python >=3.10`. `@nox.session` accepts `python`, `py`, `reuse_venv`, `name`, `venv_backend`, `venv_params`, `tags`, `default`, `requires`. `venv_backend` accepts `"uv"`, `"virtualenv"`, `"venv"`, `"conda"`, `"mamba"`, `"micromamba"`, `"none"`, chainable with `|` to express fallbacks. `nox.options` carries `sessions`, `default_venv_backend`, `reuse_existing_virtualenvs`, `error_on_external_run`, `error_on_missing_interpreters`. `session.install`, `session.run(..., external=True)`, `session.notify` and `@nox.parametrize` complete the surface. Configuration is executable Python in `noxfile.py` - VERSION-DEPENDENT (nox 2026.7.11).

Four config layouts exist: `tox.toml`, `pyproject.toml` `[tool.tox]` as native TOML, `pyproject.toml` `[tool.tox]` holding a `legacy_tox_ini` string, and legacy `tox.ini`. Native TOML arrived in tox 4.21.0 (2024-09-30) - FLAGGED-SECONDARY: tox.wiki's configuration page returned empty content on two fetches, so the 4.21.0 / 2024-09-30 attribution reached me through search results citing tox's own changelog anchor `v4-21-0-2024-09-30`, not a rendered primary page. ### Type checking as an incrementally adoptable gate

35. mypy 2.3.0 (2026-07-13), `requires_python >=3.10` - VERSION-DEPENDENT.
36. mypy 2.0 flipped defaults that older configs relied on: "`--local-partial-types` by default"; "`--strict-bytes` by default", i.e. "mypy no longer treats `bytearray` and `memoryview` values as assignable to the `bytes` type"; "`--allow-redefinition` now behaves like `--allow-redefinition-new`"; "Drop support for targeting Python 3.9"; and parallel type checking via `--num-workers` - VERSION-DEPENDENT (mypy 2.0+).
37. mypy 2.2 added closed TypedDicts per PEP 728 ("A closed TypedDict cannot have extra keys beyond those explicitly defined"), completed PEP 696 type-variable defaults, made `TypeForm` non-experimental, and now respects explicitly annotated return types on `__new__()`. mypy 2.3 makes instance attributes declared `Final` read-only at runtime and stops shipping mypyc-accelerated macOS x86_64 wheels - VERSION-DEPENDENT (mypy 2.2 / 2.3).
38. Per-module strictness is `[mypy-PATTERN1,PATTERN2,...]` in `mypy.ini` and `[[tool.mypy.overrides]]` with a `module` key (string or array) in `pyproject.toml`; such sections "specify additional flags that only apply to modules whose name matches at least one of the patterns" - ESTABLISHED.
39. mypy's documented precedence, highest first: (1) inline configuration in the source file, (2) sections with concrete module names (`foo.bar`), (3) unstructured wildcard patterns (`foo.*.baz`), with later sections overriding earlier ones, (4) well-structured wildcard patterns (`foo.bar.*`), with more specific overriding more general, (5) command-line options, (6) top-level configuration-file options. The command line ranks BELOW per-module sections - ESTABLISHED.
40. `strict` is documented as "Enable all optional error checking flags" and the configuration reference shows no per-module support for it. A per-module ratchet must therefore be written as the individual flags: `disallow_untyped_defs`, `disallow_incomplete_defs`, `disallow_untyped_calls`, `disallow_any_generics`, `disallow_subclassing_any`, `disallow_untyped_decorators`, `check_untyped_defs`, `warn_return_any`, `no_implicit_reexport`, `strict_equality`, `warn_unused_ignores` - VERSION-DEPENDENT (mypy 2.3).
41. Global-only options - legal in `[mypy]` but NOT per-module - include `mypy_path`, `files`, `modules`, `packages`, `exclude`, `exclude_gitignore`, `namespace_packages`, `explicit_package_bases`, `python_version`, `platform`, `always_true`, `always_false`, `python_executable`, `no_site_packages`, `warn_redundant_casts`, `warn_unused_configs`, `incremental`, `cache_dir`, `num_workers`, `plugins`, every reporting/output flag, and `junit_xml` - ESTABLISHED.
42. `follow_imports` has exactly four values - `normal` (default), `silent`, `skip`, `error` - and governs an imported `.py` module that was not named on the command line. `skip` makes that module effectively `Any`, erasing errors at the boundary instead of reporting them - ESTABLISHED.
43. Ignore hygiene primitives: `warn_unused_ignores` (default `False`) "Warns about unneeded `# type: ignore` comments"; the optional error code `ignore-without-code` rejects a bare `# type: ignore` and forces `# type: ignore[error-code]`; `unused-ignore` is the code form of the same diagnostic. `ignore_errors` (default `False`, config-file only) "Ignores all non-fatal errors" for matched modules - the reviewable marker for a not-yet-migrated module, unlike ignores scattered through source - ESTABLISHED.
44. `disable_error_code` and `enable_error_code` take comma-separated code lists globally, and enable wins: "This option will override disabled error codes from the `disable_error_code` option" - ESTABLISHED.
45. mypy's OPTIONAL error codes (the `error_code_list2` page - codes mypy "generates only if you enable certain options") are: `type-arg`, `no-untyped-def`, `redundant-cast`, `redundant-self`, `comparison-overlap`, `no-untyped-call`, `no-any-return`, `no-any-unimported`, `unreachable`, `deprecated`, `redundant-expr`, `possibly-undefined`, `truthy-bool`, `truthy-iterable`, `ignore-without-code`, `unused-awaitable`, `unused-ignore`, `explicit-override`, `mutable-override`, `unimported-reveal`, `explicit-any`, `exhaustive-match`, `untyped-decorator` - VERSION-DEPENDENT (mypy 2.3).
46. Several of those codes are switched on indirectly by their governing strictness flag rather than by `--enable-error-code`: `--disallow-untyped-defs` yields `no-untyped-def`, `--warn-return-any` yields `no-any-return`, `--strict-equality` yields `comparison-overlap`, `--warn-redundant-casts` yields `redundant-cast`, `--warn-unused-ignores` yields `unused-ignore`. That is why `--strict` produces some of them. The high-value codes `--strict` does NOT give you, and which must therefore be requested explicitly, are `unreachable`, `possibly-undefined`, `redundant-expr`, `ignore-without-code`, `explicit-override`, `mutable-override`, `truthy-bool`, `explicit-any` and `exhaustive-match` - VERSION-DEPENDENT (mypy 2.3).
47. A ratchet that cannot regress: `mypy_baseline` 0.7.4 (2026-04-13), "Integrate mypy with existing codebase." It works "exclusively with the stdout of mypy", records existing errors in a committed baseline "carefully crafted to avoid merge conflicts" and "human-readable", reports only newly introduced errors, and `mypy-baseline sync` regenerates the file. The non-regression property comes from committing the baseline and refusing any change that grows it - VERSION-DEPENDENT (mypy_baseline 0.7.x).
48. ty 0.0.69 (2026-08-06), "An extremely fast Python type checker, written in Rust.", is still on a `0.0.x` line; defensible as an advisory gate, not as a required one, until it leaves `0.0.x` - VERSION-DEPENDENT (ty 0.0.69).

### Test gates

### Maintainability metrics that are actually defensible

83. radon 6.0.1's most recent release is 2023-03-26 - over three years old at 2026-08-08 - with an empty `requires_python`. It computes cyclomatic complexity, Halstead measures (program vocabulary, program length, calculated program length, volume, difficulty, effort, time required to program, number of delivered bugs), the Maintainability Index, and raw metrics: "LOC: The total number of lines of code. 85. radon's Maintainability Index rank table: 100-20 = A "Very high"; 19-10 = B "Medium"; 9-0 = C "Extremely low". 88. Cognitive Complexity (SonarSource, author G. Ann Campbell) is built on three rules: ignore structures that merely shorthand multiple statements into one; increment for each break in the linear flow (loops, conditionals, gotos, catch clauses, sequences of logical operators, recursion); and add a further increment per level of nesting. It is explicitly a measure of understandability, not testability, and was designed against Cyclomatic Complexity's nesting blindness - FLAGGED-SECONDARY: the SonarSource white-paper PDF (`sonarsource.com/docs/CognitiveComplexity.pdf`) is served in a form this session's fetch could not render, so the three rules reached me through SonarSource's own resource page as summarised in search results rather than a rendered primary page - OPEN.
89. The strongest empirical result available for cognitive complexity: Munoz Baron, Wyrich & Wagner, "An Empirical Validation of Cognitive Complexity as a Measure of Source Code Understandability" (2020, arXiv:2007.12520) - "Cognitive Complexity positively correlates with comprehension time and subjective ratings of understandability", with mixed results for correctness of comprehension tasks and for physiological measures - ESTABLISHED (abstract read at arxiv.org/abs/2007.12520).
90. The empirical standing of cyclomatic complexity is weak, not merely contested. Shepperd's "A critique of cyclomatic complexity as a software metric" concludes that v(G) is so strongly correlated with lines of code that it "appears to add little if any significant information to that already contained in the count of executable lines", likening the pair to temperature measured in Fahrenheit and Centigrade - FLAGGED-SECONDARY: the hosted PDF was unreadable to this session's fetch and the quotation reached me through search results, not a rendered primary page - OPEN.

They are defensible as review triggers and as ratchet ceilings that prevent a function from getting worse; they are not defensible as quality scores, as release criteria, or as evidence that a refactor improved anything. Cognitive complexity has better (though still single-study-family) evidence for correlating with human comprehension time than cyclomatic complexity has for correlating with defects - ESTABLISHED as a characterisation of the cited evidence; the strength of the underlying literature is itself weak, which is the point.

### Incremental delivery mechanics

95. Trunk-based development, per trunkbaseddevelopment.com (attribution on the site: "2017-2020: Paul Hammant, with contributions from friends"), is "A source-control branching model, where developers collaborate on code in a single branch called 'trunk' and resist any pressure to create other long-lived development branches by employing documented techniques." "Trunk-Based Development is a key enabler of Continuous Integration and by extension Continuous Delivery." Release branches, where used, "are cut from the trunk on a just-in-time basis, are 'hardened' before a release ... and those branches are deleted some time after release" - ESTABLISHED.

### Documentation gates

106. PEP 257 is Active, created 29-May-2001. "A docstring is a string literal that occurs as the first statement in a module, function, class, or method definition." One-liners: "Triple quotes are used even though the string fits on one line", "The closing quotes are on the same line as the opening quotes", "There's no blank line either before or after the docstring", and "The docstring is a phrase ending in a period. Multi-line docstrings "consist of a summary line just like a one-line docstring, followed by a blank line, followed by a more elaborate description", and "Unless the entire docstring fits on a line, place the closing quotes on a line by themselves." String literals immediately after a simple assignment at module, class or `__init__` scope are "attribute docstrings" - ESTABLISHED.

Destination: NEW: `python_quality_gates_manifest.md`.

## Traps for coding agents

1. **`select` is not additive.** Writing `[tool.ruff.lint] select = ["E", "F"]` on ruff 0.16.x silently DISCARDS 400-odd default rules. Ruff's own resolution rule is that the highest-priority `select` becomes the basis; `extend-select` is the additive form. An agent "tightening" the config with `select` usually loosens it.
2. **The ruff default set is codes, not prefixes.** `I001`, `D419`, `S102`, `S110`, `S112`, `E722`, `E902`, `W605` are individually on. Concluding "isort/pydocstyle/bandit rules are on by default" and therefore not configuring them is wrong.
3. **Ruff patch releases can change behaviour.** The versioning policy admits "Bugs are fixed, including behavior changes that fix bugs" and "A rule is added in preview" into PATCH bumps. `ruff>=0.16,<0.17` is not a reproducible gate; only an exact pin is.
4. **`ruff check --fix` exits 0 after rewriting your files.** Exit code `0` covers "all violations were auto-fixed". A CI job that runs `--fix` and trusts the exit code passes while leaving the tree dirty. Use `ruff check` (no `--fix`) in CI, or add `--exit-non-zero-on-fix`.
5. **pre-commit fails a hook that modifies files even when it exits 0.** "The hook must exit nonzero on failure or modify files." Agents that write a hook which reformats in place and returns 0 will be surprised by a red run - which is the intended design, not a bug.
6. **pre-commit stage names were renamed.** `commit`, `push` and `merge-commit` became `pre-commit`, `pre-push` and `pre-merge-commit` in 3.2.0. Writing the old names in a config for pre-commit 4.6.1 is a config error, and `pre-commit migrate-config` is the fix.
7. **`pre-commit install` installs only the pre-commit hook.** A hook declared `stages: [pre-push]` never runs unless `--hook-type pre-push` was installed or `default_install_hook_types` includes it. The gate looks configured and is inert.
8. **pre-commit passes explicit filenames, defeating `exclude`.** Ruff needs `--force-exclude` to honour its own exclusions in that mode, which is why the official hooks hard-code it in `entry`. A hand-rolled ruff hook without it will lint generated and vendored code.
9. **`--frozen` is the loose flag; `--locked` is the strict one.** In uv, `--locked` errors when the lockfile is out of date and `--frozen` skips the check entirely. The name reads the other way round to most people, and CI wired with `--frozen` will happily install from a stale lockfile.
10. **mypy's command line loses to a per-module section.** The documented precedence puts concrete-module and wildcard sections ABOVE command-line options. `mypy --strict` does not override `[[tool.mypy.overrides]] disallow_untyped_defs = false`; the override wins.
11. **`strict` cannot be set per-module.** A "strict for new code, loose for legacy" ratchet must enumerate the individual flags in each override block. Writing `strict = true` inside `[[tool.mypy.overrides]]` does not do what it looks like.
12. **`follow_imports = "skip"` erases errors rather than reporting them.** It makes the target module `Any`. Reached for as a quick fix for a noisy dependency, it silently deletes type checking across that boundary. `ignore_missing_imports` and `silent` are the narrower tools.
13. **Most of the interesting mypy error codes are not in `--strict`.** `unreachable`, `possibly-undefined`, `redundant-expr`, `ignore-without-code`, `explicit-override`, `mutable-override`, `truthy-bool`, `explicit-any` and `exhaustive-match` all require explicit enabling. "We run `--strict`" is not the same as "we check for unreachable code".
14. **mypy 2.0 changed defaults.** `--local-partial-types` and `--strict-bytes` are now on by default and targeting Python 3.9 is gone. A config written against mypy 1.x that relied on `bytearray` being assignable to `bytes` starts failing on upgrade without any config change.
15. **coverage.py fails with exit status 2, not 1.** A CI script testing `if [ $? -eq 1 ]` after `coverage report --fail-under=90` treats a threshold failure as success.
16. **`precision` silently rounds coverage up into passing.** With the default `precision = 0`, 89.6% is reported and compared as 90% and PASSES `fail_under = 90`. Only `fail_under = 100` is documented to be immune: "A setting of 100 will fail any value under 100, regardless of the number of decimal places of precision."
17. **`exclude_lines` deletes the built-in exclusions.** Adding one custom pattern to `exclude_lines` silently drops `pragma: no cover` and its siblings. `exclude_also` is the additive form; `partial_also` likewise for `partial_branches`.
18. **Branch coverage is off by default.** `[run] branch = false` is the default, so a "90% coverage" gate is 90% of statements, and a fully-covered `if` whose false branch is never taken counts as covered.
19. **`fail_under` has no per-file form.** coverage.py's configuration reference documents no per-file or per-module threshold. A project-wide 90% can hide a 0%-covered new module; the only fix is an external changed-lines or per-file tool.
20. **Coverage cannot see assertion-free tests.** Executing a line and verifying its behaviour are different things, and `fail_under` measures only the first. A suite of tests that call functions and assert nothing satisfies any coverage gate.
21. **`semgrep scan` does not fail on findings.** It needs `--error`; only `semgrep ci` returns failing exit codes on findings by default. A pipeline running `semgrep scan --config auto` and checking the exit code is a decorative gate.
22. **semgrep's exit code 3 only happens under `--strict`.** "Invalid syntax of the scanned language. This error occurs only while using the `--strict` flag" - so a syntax problem is invisible in the default mode.
23. **zizmor signals findings with 11 to 14, not 1.** `1` means the audit itself errored. CI logic that treats `1` as "findings" and anything else as "clean" inverts the meaning of every zizmor run.
24. **vulture signals dead code with exit 3.** `1` means invalid input and `2` means bad arguments. And at the default confidence, dynamically referenced names (plugin registries, framework hooks, `getattr` access) are reported as dead; only `--min-confidence 100` is safe as a required gate without a whitelist.
25. **`pip-audit --strict` is not about vulnerabilities.** It means "fail the entire audit if dependency collection fails on any dependency". Without it, a dependency pip-audit could not resolve is skipped and the audit can still report clean.
26. **bandit does not find `pyproject.toml` by itself.** `[tool.bandit]` is supported, but only when passed explicitly with `-c pyproject.toml`; bare `bandit -r .` ignores it. And `exclude_dirs` exists in "YAML and TOML only", not in the INI `.bandit` file.
27. **flake8 cannot be configured from `pyproject.toml`.** It reads only `setup.cfg`, `tox.ini` or `.flake8`. An agent that writes a `[tool.flake8]` table produces a file flake8 never reads and a gate that runs with defaults.
28. **radon has no failing exit code.** It reports; it never fails. Adding `radon cc` to CI gates nothing. xenon is the wrapper that turns radon's numbers into a non-zero exit.
29. **PEP 770 adds no metadata field.** SBOMs live as opaque files in `.dist-info/sboms/`; there is deliberately no new core-metadata key. Inventing one (an `Sbom-File` field, say) will not validate anywhere.
30. **`pypa/gh-action-pypi-publish` already generates attestations.** They are on by default in the Trusted Publishing flow, so adding explicit signing steps duplicates work; and setting `password:` silently turns Trusted Publishing OFF, which also removes the default attestations.
31. **Attestations are not an install-time gate.** Their presence is evidence a consumer can record and audit. Whether pip or uv can be configured to REQUIRE them at install time was not confirmed here; do not write a manifest sentence claiming they block installation.
32. **doctest compares output byte for byte.** "If even a single character doesn't match, the test fails." Any example printing a set, a dict, a float repr or an object address is a latent flake unless `+ELLIPSIS` or `+NORMALIZE_WHITESPACE` is applied, and blank lines must be written `<BLANKLINE>`.
33. **`lint.pydocstyle.convention` subtracts, it does not add.** Choosing `"google"` disables D203, D213, D214, D215, D404 and D405-D411. An agent that sets a convention and then re-adds one of those codes through `extend-select` reintroduces exactly the rule the convention was chosen to silence.
34. **numpydoc `checks = ["all"]` demands prose that does not exist.** ES01, SA01 and EX01 require an extended summary, a See Also section and an Examples section on every documented object. As a required gate this fails almost every real codebase on day one.
35. **`--dist load` gives no ordering guarantee, and session fixtures run per worker.** pytest-xdist's default mode "Sends pending tests to any worker that is available, without any guaranteed order". Order-dependent tests become nondeterministic, and a session-scoped fixture is constructed once per worker process, not once per run - so anything that assumes a single global setup breaks under `-n auto`.
36. **`xfail_strict` defaults to `False`.** A test marked `xfail` that starts passing is silently reported as `xpass` and the suite stays green, so a fixed bug never removes its own marker.
37. **A 3.10 leg in the CI matrix expires in 2026-10.** 3.10 leaves security support then, and 3.15's first release is 2026-10-01. A matrix generated from a pre-June-2026 template is already stale in both directions.
38. **`ruff format` now rewrites Markdown by default.** Since 0.16.0 Python code blocks inside `.md` files are formatted unless suppressed with `<!-- fmt: off -->`. A repository whose documentation contains deliberately-broken example code will find it silently corrected.
