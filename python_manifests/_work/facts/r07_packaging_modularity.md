## Facts

### Packaging standards, status confirmed against the canonical python/peps sources

1. PEP 517 "A build-system independent format for source trees" is **Final** (created 30-Sep-2015). It fixes the `[build-system]` contract: `requires` (build-time dependencies), `build-backend` (a `module:object` string), and `backend-path` (a list of in-tree directories, interpreted relative to the project root, which MUST refer to a location inside the source tree) - ESTABLISHED
2. PEP 517 mandates exactly two backend hooks - `build_wheel(wheel_directory, config_settings=None, metadata_directory=None)` and `build_sdist(sdist_directory, config_settings=None)` - each returning the basename of the produced file as a unicode string. `get_requires_for_build_wheel`, `prepare_metadata_for_build_wheel` and `get_requires_for_build_sdist` are optional - ESTABLISHED
3. PEP 517 states a build frontend "SHOULD, by default, create an isolated environment for each build, containing only the standard library and any explicitly requested build-dependencies". This is why `pip install --no-build-isolation` requires the PEP 518 build dependencies to be preinstalled - ESTABLISHED
4. PEP 518 "Specifying Minimum Build System Requirements for Python Projects" is **Final** (created 10-May-2016). It fixes the existence of `pyproject.toml` itself and the `[build-system] requires` key - ESTABLISHED
5. PEP 621 "Storing project metadata in pyproject.toml" is **Final** (created 22-Jun-2020, resolution on discuss.python.org t/5472/109). It fixes the `[project]` table - ESTABLISHED
6. PEP 621 as written says "Build back-ends MUST raise an error if the metadata specifies a field statically as well as being listed in `dynamic`". PEP 808 has since relaxed exactly this rule for a named set of list and table fields - ESTABLISHED
7. PEP 639 "Improving License Clarity with Better Package Metadata" is **Final** (created 15-Aug-2019). It requires Core Metadata 2.4 and adds `License-Expression` plus the multi-use `License-File` field. In `pyproject.toml` it makes `license` a single SPDX expression **string** and adds `license-files` as an array of glob patterns - ESTABLISHED
8. Under PEP 639 the `license` table subkeys `text` and `file`, the legacy unstructured `License` core-metadata field, and `License ::` trove classifiers are all deprecated. `License` and `License-Expression` are mutually exclusive: "Tools which generate Core Metadata MUST NOT create both these fields", and PyPI must reject an upload declaring both - ESTABLISHED
9. PEP 639 rule that bites during migration: if `license-files` is present, build tools must error if `license` has any value other than a single top-level string - ESTABLISHED
10. `license-files` globs allow `*`, `?`, `**` and `[]` character ranges, use forward slashes only, and MUST NOT contain `..` parent-directory references - ESTABLISHED
11. PEP 660 "Editable installs for pyproject.toml based builds" is **Final** (created 30-Mar-2021). It adds three **optional** hooks: `build_editable(wheel_directory, config_settings=None, metadata_directory=None)`, `get_requires_for_build_editable(config_settings=None)` and `prepare_metadata_for_build_editable(metadata_directory, config_settings=None)` - ESTABLISHED
12. PEP 660's editable wheel "must not be exposed to end users, nor cached, nor distributed". If `prepare_metadata_for_build_editable` is absent the frontend should call `build_editable` and read the metadata from the result; if `get_requires_for_build_editable` is absent the default "is equivalent to `return []`" - ESTABLISHED
13. PEP 735 "Dependency Groups in pyproject.toml" is **Final** (created 20-Nov-2023, resolution 10-Oct-2024). It fixes the top-level `[dependency-groups]` table - ESTABLISHED
14. A dependency group's value list may contain PEP 508 dependency-specifier **strings** and **tables**. The only legal table form is a Dependency Group Include: "a table with exactly one key, `include-group`, whose value is a string, the name of another Dependency Group" - ESTABLISHED
15. PEP 735: "Build backends MUST NOT include Dependency Group data in built distributions as package metadata." Dependency groups are therefore invisible to anyone who installs the wheel - ESTABLISHED
16. PEP 735 group names must be normalized before comparison; duplicates after normalization are an error; includes "MUST NOT include cycles, and tools SHOULD report an error if they detect a cycle" - ESTABLISHED
17. PEP 735 distinguishes groups from extras on two axes: groups work for non-package projects, and "installation of a Dependency Group does not imply installation of a package's dependencies (or the package itself)" - ESTABLISHED
18. The dependency-groups specification states there is "no syntax or specification-defined interface for installing or referring to dependency groups. Tools are expected to provide dedicated interfaces for this purpose". `pip --group` and `uv --group` are tool conventions, not specification surface - ESTABLISHED
19. PEP 751 "A file format to record Python dependencies for installation reproducibility" is **Final**, resolution 31-Mar-2025. The lock-file standard IS accepted - ESTABLISHED
20. The PEP 751 file MUST be named `pylock.toml`, or match `r"^pylock\.([^.]+)\.toml$"` when a name is wanted or multiple lock files exist (e.g. `pylock.dev.toml`) - ESTABLISHED
21. `pylock.toml` mandatory top-level fields are `lock-version` (string, currently `"1.0"`), `created-by` (the generating tool's name) and the `[[packages]]` array of tables. `requires-python`, `environments`, `extras`, `dependency-groups` and `default-groups` are optional - ESTABLISHED
22. PEP 751 is explicitly machine-generated and install-oriented: "Installers consuming the file should be able to calculate what to install without the need for dependency resolution at install-time." Human auditing is encouraged; hand-editing is not the intended use - ESTABLISHED
23. PEP 771 "Default Extras for Python Software Packages" is **Draft** (created 13-Jan-2025, no resolution). It proposes the `default-optional-dependency-keys` array in `[project]` and the multi-use `Default-Extra` core-metadata field (metadata 2.5). It must not be written into a real project today - ESTABLISHED
24. PEP 777 "How to Re-invent the Wheel" is **Draft** (created 09-Oct-2024). It proposes a `Wheel-Version` core-metadata field for resolver-side filtering and a `.whlx` extension once the wheel major version reaches 2, and explicitly "does not specify a new wheel revision" - ESTABLISHED
25. PEP 740 "Index support for digital attestations" is **Final** (resolution 17-Jul-2024). It defines a versioned attestation JSON object (an in-toto v1 Statement bound to the file's SHA-256 digest) and a `provenance` object served by the index, exposed via the `data-provenance` attribute in the Simple Index and a `provenance` key in JSON API 1.3+, with Trusted Publishing / Sigstore as the identity source - ESTABLISHED
26. PEP 508 "Dependency specification for Python Software Packages" is **Final** (created 11-Nov-2015). PEP 440 "Version Identification and Dependency Specification" is **Final** (created 18-Mar-2013). PEP 427 "The Wheel Binary Package Format 1.0" is **Final**. PEP 491 (Wheel 1.9) is **Deferred** and has never shipped - ESTABLISHED
27. PEP 561 "Distributing and Packaging Type Information" is **Final** (created 09-Sep-2017). A distribution opts into being type-checked by shipping a `py.typed` marker file inside the package; a stub-only distribution MUST be named `foopkg-stubs` for the package `foopkg`; a partial stub distribution "MUST include `partial\n` in a `py.typed` file" - ESTABLISHED
28. PEP 420 "Implicit Namespace Packages" is **Final** (Python-Version 3.3). A namespace package is created by the **absence** of `__init__.py`, and "Namespace packages cannot contain an `__init__.py`" - ESTABLISHED
29. PEP 794 "Import Name Metadata" is **Accepted** (created 05-Jun-2025, resolution 05-Sep-2025). It adds the repeatable `Import-Name` and `Import-Namespace` core-metadata fields (Metadata 2.5) and the `[project]` keys `import-names` and `import-namespaces`, because "In Python packaging there is no requirement that a project name match the name(s) that you can import for that project" - ESTABLISHED
30. PEP 808 "Including static values in dynamic metadata" is **Accepted** (created 19-Sep-2025, resolution 19-May-2026) and drove Core Metadata **2.6**. It makes a named set of list/table `[project]` keys *appendable*: they may be declared statically AND listed in `dynamic`, and the backend may then only insert or extend - it "must not remove, reorder, or modify existing entries" - ESTABLISHED
31. The PEP 808 appendable keys are exactly `authors`, `maintainers`, `classifiers`, `dependencies`, `entry-points`, `scripts`, `gui-scripts`, `keywords`, `license-files`, `optional-dependencies`, `urls`, `import-names`, `import-namespaces`. `name`, `version`, `requires-python`, `description`, `readme` and `license` remain strictly static-or-dynamic - ESTABLISHED
32. PEP 770 "Improving measurability of Python packages with Software Bill-of-Materials" is **Final** (resolution 11-Apr-2025). It reserves the `.dist-info/sboms/` subdirectory, deliberately adds **no** core-metadata field, and requires **no** metadata-version bump so tools could adopt it immediately - ESTABLISHED
33. PEP 752 "Implicit namespaces for package repositories" is **Accepted** with resolution **29-Jun-2026**. It is about repositories reserving *package name prefixes* ("grants") and has nothing to do with PEP 420 import namespace packages. PEP 755 "Implicit namespace policy for PyPI", which codifies an implementation of 752 for PyPI, is still **Draft** - ESTABLISHED
34. PEP 723 "Inline script metadata" is **Final** (resolution 08-Jan-2024). The block is a comment fence `# /// script` ... `# ///`, with keys `dependencies` (list of PEP 508 strings) and `requires-python`, plus an optional `[tool]` table. The canonical detection regex is `(?m)^# /// (?P<type>[a-zA-Z0-9-]+)$\s(?P<content>(^#(| .*)$\s)+)^# ///$` - ESTABLISHED
35. Still **Draft** and therefore unsafe to depend on: PEP 725 (external dependencies), PEP 780 (ABI features as environment markers), PEP 804 (external dependency registry), PEP 817 and PEP 825 (Wheel Variants; 825 created 17-Feb-2026), PEP 819 (JSON Package Metadata, adding `METADATA.json`/`WHEEL.json`, created 18-Dec-2025), PEP 694 (Upload 2.0 API), PEP 710 (provenance of installed packages), PEP 807 (index support for Trusted Publishing). PEP 778 (symlinks in wheels) is Deferred - ESTABLISHED
36. Core Metadata version history: 2.1 added `Description-Content-Type` and `Provides-Extra` (PEP 566); 2.2 added `Dynamic` (PEP 643); 2.3 restricted extra names to normalized form (PEP 685); 2.4 added `License-Expression` and `License-File` (PEP 639); 2.5 added `Import-Name` and `Import-Namespace` (PEP 794); 2.6 changed handling of `Dynamic` in wheels built from source distributions (PEP 808) - ESTABLISHED
37. The wheel filename grammar is `{distribution}-{version}(-{build tag})?-{python tag}-{abi tag}-{platform tag}.whl`. Inside the wheel, directory names normalize the distribution name: "Any run of `-_.` characters should be replaced with `_`, and uppercase characters should be replaced with corresponding lowercase ones" - ESTABLISHED
38. A wheel's `.dist-info/` must contain `METADATA`, `WHEEL` and `RECORD`; `WHEEL` carries `Wheel-Version`, `Generator`, `Root-Is-Purelib`, `Tag` and optional `Build`. Installers "must fail if `Wheel-Version` has a greater major version than the version it supports" - ESTABLISHED
39. For an *installed* project, `.dist-info/` may hold `METADATA` (mandatory - "All other files may be omitted at the installing tool's discretion"), `RECORD`, `INSTALLER`, `entry_points.txt` and `direct_url.json`. `RECORD` "must list all installed files of the project, except `.pyc` files corresponding to `.py` files listed in `RECORD`, which are optional", and entries for `.pyc` files and for `RECORD` itself "commonly have empty hash and size" - ESTABLISHED

### Toolchain, and what each tool is the right default for

40. uv 0.12.3 describes itself as "An extremely fast Python package and project manager, written in Rust" and as "a single tool to replace `pip`, `pip-tools`, `pipx`, `poetry`, `pyenv`, `twine`, `virtualenv`, and more" - ESTABLISHED
41. uv's top-level command set is `run, init, add, remove, version, sync, lock, export, tree, tool, python, pip, venv, build, publish, cache, self` - ESTABLISHED
42. uv keeps its own cross-platform `uv.lock` as the primary lockfile and emits the standard format on demand via `uv export --format pylock.toml`; the only other accepted `--format` value is `requirements.txt` - ESTABLISHED
43. uv ships its own build backend named **`uv_build`**, declared as `requires = ["uv_build>=0.12.3,<0.13"]` with `build-backend = "uv_build"`. It "currently only supports pure Python code" - a project with C or Rust extensions needs setuptools, hatchling with a plugin, maturin, scikit-build-core or meson-python instead - ESTABLISHED
44. `uv_build` defaults to discovering `src/<package_name>/__init__.py`; `module-root` defaults to `src`; the package name is normalized to lowercase with `.` and `-` replaced by `_` (so `Foo-Bar` becomes `foo_bar`). `[tool.uv.build-backend]` accepts `module-name`, `module-root`, `source-include`, `source-exclude`, `wheel-exclude` and `namespace` (which disables the safety checks) - VERSION-DEPENDENT (uv 0.12.x)
45. pip 26.2.1 (2026-08-04) is the reference installer. `pip install --group <[path:]group>` installs a PEP 735 group; per the docs, "If a path is given, the name of the file must be `pyproject.toml`", defaulting to `pyproject.toml` in the current directory - VERSION-DEPENDENT (pip 25.1+)
46. `pip install -r` accepts a file "in pip's requirements.txt format, or pylock.toml format", and the pip documentation states "pylock.toml support is experimental" - VERSION-DEPENDENT (pip 26.1+)
47. `pip lock` was added in pip 25.1 (2025-04-26) as "a new, _experimental_, `pip lock` command, implementing PEP 751" and writes `pylock.toml` - VERSION-DEPENDENT (pip 25.1+)
48. `pip install --no-build-isolation` "Disable isolation when building a modern source distribution. Build dependencies specified by PEP 518 must be already installed if this option is used." `--config-settings KEY=VALUE` (repeatable) passes settings to the backend; `--dry-run` with `--report <file>` produces a JSON resolution report without installing - ESTABLISHED
49. The packaging.python.org tutorial uses a **src layout** and offers four backends with these exact declarations: `hatchling >= 1.26` / `hatchling.build`; `setuptools >= 77.0.3` / `setuptools.build_meta`; `flit_core >= 3.12.0, <4` / `flit_core.buildapi`; `pdm-backend >= 2.4.0` / `pdm.backend`. It states "This tutorial uses Hatchling by default, but it will work identically with Setuptools, Flit, PDM, and others that support the `[project]` table for metadata" - ESTABLISHED
50. hatchling's file-selection configuration lives under `[tool.hatch.build]`, `[tool.hatch.build.targets.wheel]` and `[tool.hatch.build.targets.sdist]`, with keys `packages`, `include`, `exclude`, `only-include`, `sources`, `artifacts`. "The `packages` option is semantically equivalent to `only-include` (which takes precedence) except that the shipped path will be collapsed to only include the final component" - ESTABLISHED
51. setuptools automatic package discovery "will **only** be enabled if you **don't** provide any configuration for `packages` and `py_modules`". Override it with `[tool.setuptools.packages.find]` keys `where`, `include`, `exclude`, `namespaces` (namespace scanning is enabled by default) - ESTABLISHED
52. setuptools flat-layout auto-discovery silently excludes a long reserved list of directory names including `ci, bin, debian, doc, docs, documentation, manpages, news, changelog, test, tests, unit_test(s), example(s), scripts, tools, util(s), python, build, dist, venv, env, requirements, tasks, fabfile, site_scons, benchmark(s), exercise(s), htmlcov` plus anything starting with `.` or `_`; reserved top-level *module* names include `setup, conftest, test(s), example(s), build, toxfile, noxfile, pavement, dodo, tasks, fabfile, conanfile, manage, benchmark(s), exercise(s)` - ESTABLISHED
53. With flat layout plus auto-discovery, "setuptools will refuse to create distribution archives with multiple top-level packages or modules" - ESTABLISHED
54. setuptools 83.0.0 requires Python >= 3.10. **`pkg_resources` was removed from setuptools in v82.0.0** (2026-02-08): "Most common uses of `pkg_resources` have been superseded by the `importlib.resources` and `importlib.metadata` projects. Projects and environments relying on `pkg_resources` for namespace packages or other behavior should depend on older versions of `setuptools`" - VERSION-DEPENDENT (setuptools >= 82)
55. setuptools removed `easy_install` in v80.0.0 (2025-04-27), removed "legacy-editable" installs in v79.0.0 (2025-04-20), stopped accepting uppercase or dash characters in `setup.cfg` option names in v78.0.0 (2025-03-23), and removed `--dry-run` support for `setup.py` in v81.0.0 (2026-02-06) - VERSION-DEPENDENT (setuptools >= 78)
56. pip 25.3 (2025-10-24) removed "support for the legacy `setup.py develop` editable method in setuptools", "support for the deprecated `setup.py bdist_wheel` mechanism", and the deprecated `--global-option` / `--build-option`. There is no supported non-PEP-517 install path left - VERSION-DEPENDENT (pip >= 25.3)
57. flit and flit_core 4.0.x (first published release 4.0.1, 2026-08-04) are a breaking major: "`[tool.flit.metadata]` table is no longer used for project metadata. Use the newer `[project]` table instead"; `flit build` and `flit publish` "no longer include files in the sdist based on what is committed in git or Mercurial"; and "The `--setup-py` option to generate sdists containing a `setup.py` file is no longer available". flit 3.11 added PEP 639 SPDX expressions and metadata 2.4; flit 4.0 adds `Import-Name`/`Import-Namespace` (metadata 2.5) and `-stubs` typing distributions - VERSION-DEPENDENT (flit >= 4.0)
58. poetry 2.x reads the standard PEP 621 `[project]` table, with `[tool.poetry]` retained for poetry-specific extensions; `[project]` support arrived in Poetry 2.0 (released 2025-01-05). Poetry before 2.0 used only `[tool.poetry]` - VERSION-DEPENDENT (poetry >= 2.0) FLAGGED-SECONDARY (behaviour and release date taken from python-poetry.org blog summaries surfaced in search, not from a fetched primary page)
59. `build` 1.5.0 is the neutral PEP 517 frontend. `python -m build` produces a source distribution and then a wheel *from that source distribution*, which is the only routine that catches "the sdist is missing a file the wheel build needs" - ESTABLISHED
60. twine 7.0.0 (2026-07-27) "Fix uploading packages with metadata version 2.5. The fix no longer allows metadata version 2.0." twine 6.2.0 (2025-09-04) removed MD5 digest support and restricted `--skip-existing` to PyPI and TestPyPI; twine 6.1.0 (2025-01-17) added preliminary Trusted Publishing support and removed `egg`, `wininst` and `.tar.bz2` handling - VERSION-DEPENDENT (twine >= 7.0)
61. The `wheel` project (0.47.0) is not part of a modern build path - it is the legacy `bdist_wheel` implementation. `setuptools.build_meta` declares what it needs through PEP 517's `get_requires_for_build_wheel`, so `wheel` must not appear in `[build-system] requires` - ESTABLISHED

### src layout versus flat layout, and exactly which failures src layout prevents

62. packaging.python.org: "The 'src layout' deviates from the flat layout by moving the code that is intended to be importable (i.e. `import awesome_package`, also known as import packages) into a subdirectory. This subdirectory is typically named `src/`, hence 'src layout'" - ESTABLISHED
63. "The src layout requires installation of the project to be able to run its code, and the flat layout does not." That requirement is the entire mechanism - ESTABLISHED
64. The named failure mode: "The src layout helps prevent accidental usage of the in-development copy of the code. This is relevant since the Python interpreter includes the current working directory as the first item on the import path. This means that if an import package exists in the current working directory with the same name as an installed import package, the variant from the current working directory will be used." Under flat layout, a test run from the repository root imports the working-tree copy, never the installed distribution - ESTABLISHED
65. Documented consequence of that shadowing: "This can lead to subtle misconfiguration of the project's packaging tooling, which could result in files not being included in a distribution" - the tests pass locally and the published wheel is broken - ESTABLISHED
66. Second documented failure mode: "The flat layout would add the other project files (eg: `README.md`, `tox.ini`) and packaging/tooling configuration files (eg: `setup.py`, `noxfile.py`) on the import path. This would make certain imports work in editable installations but not regular installations" - ESTABLISHED
67. "The src layout helps enforce that an editable installation is only able to import files that were meant to be importable" - ESTABLISHED
68. The `sys.path` prepend rules that cause all of the above: `python script.py` - "the directory containing that file is added to the start of `sys.path`"; `python -c` - "the current directory will be added to the start of `sys.path`"; `python -m module` - same as `-c`; interactive REPL - "the current directory will be added to the start of `sys.path`" - ESTABLISHED
69. `-P` (added in 3.11) and `PYTHONSAFEPATH` suppress exactly that prepend: "`python -m module` command line: Don't prepend the current working directory. `python script.py` command line: Don't prepend the script's directory. If it's a symbolic link, resolve symbolic links. `python -c code` and `python` (REPL) command lines: Don't prepend an empty string, which means the current working directory" - VERSION-DEPENDENT (3.11+)
70. `-I` (isolated mode) "implies `-E`, `-P` and `-s`. In isolated mode `sys.path` contains neither the script's directory nor the user's site-packages directory. All `PYTHON*` environment variables are ignored, too." It is the strongest available "is this package genuinely installed?" check - ESTABLISHED

### pyproject.toml [project] metadata that changes behaviour

71. `name` is required, must be normalized by tools immediately on read, and can never be dynamic: "A build back-end MUST raise an error if the metadata specifies `name` in `dynamic`" - ESTABLISHED
72. `version` is required but may be dynamic; `dynamic = ["version"]` supports "use cases such as filling the version from a `__version__` attribute or a Git tag" - ESTABLISHED
73. `requires-python` is "The Python version requirements of the project". packaging.python.org warns "Think twice before applying an upper bound like `requires-python = \"<= 3.10\"`" - an upper bound propagates into every downstream resolution - ESTABLISHED
74. `dependencies` entries: "Each string represents a dependency and MUST be formatted as a valid dependency specifier". `optional-dependencies` is "a table where each key specifies an extra and whose value is an array of strings"; "The keys MUST be valid values for the `Provides-Extra` core metadata. Each value in the array thus becomes a corresponding `Requires-Dist` entry for the matching `Provides-Extra` metadata" - ESTABLISHED

Test, lint and type-check dependencies belong in `[dependency-groups]`, not in an `optional-dependencies` `dev` extra - ESTABLISHED

### The import system as an architectural boundary

82. A module is inserted into `sys.modules` **before** its body runs: "The module will exist in `sys.modules` before the loader executes the module code. This is crucial because the module code may (directly or indirectly) import itself; adding it to `sys.modules` beforehand prevents unbounded recursion in the worst case and multiple loading in the best." This is the entire mechanism behind partially initialised modules - ESTABLISHED
83. "If loading fails, the failing module - and only the failing module - gets removed from `sys.modules`. Any module already in the `sys.modules` cache, and any module that was successfully loaded as a side-effect, must remain in the cache." A failed import can therefore leave half-initialised *collaborators* cached in the process - ESTABLISHED
84. The exact circular-import failure text is produced by CPython in `Python/ceval.c` as `cannot import name %R from partially initialized module %R (most likely due to a circular import)`, with a variant that appends the module's origin in parentheses - ESTABLISHED
85. Mechanically: `import a.b` binds the *module object* and tolerates a cycle as long as no attribute is touched at import time; `from a.b import thing` performs attribute lookup on a possibly-partial module and is the form that raises. Converting the import to `import a.b` plus deferred attribute access, or moving it into the function body, is the standard fix - ESTABLISHED
86. If `sys.modules[name]` exists but its value is `None`, `ModuleNotFoundError` is raised - a distinct failure from a missing entry - ESTABLISHED
87. Loading a submodule by any mechanism places a binding in the parent package's namespace: "if you have `sys.modules['spam']` and `sys.modules['spam.foo']` ... the latter must appear as the `foo` attribute of the former". So `import spam.foo` executed anywhere in the process makes `spam.foo` resolvable everywhere afterwards - an invisible ordering dependency - ESTABLISHED
88. "Relative imports use leading dots. A single leading dot indicates a relative import, starting with the current package. Two or more leading dots indicate a relative import to the parent(s) of the current package, one level per dot after the first." Relative imports may only use the `from X import Y` form, because "`import XXX.YYY.ZZZ` should expose `XXX.YYY.ZZZ` as a usable expression, but `.moduleY` is not a valid expression" - ESTABLISHED
89. "Note that relative imports are based on the name of the current module's package. Since the main module does not have a package, modules intended for use as the main module of a Python application must always use absolute imports." This is why `python src/pkg/cli.py` breaks where `python -m pkg.cli` works - ESTABLISHED
90. `__all__` in a package `__init__.py` "is taken to be the list of module names that should be imported when `from package import *` is encountered" - ESTABLISHED
91. If `__all__` is absent, `from pkg.sub import *` "does _not_ import all submodules from the package"; it imports "whatever names are defined in the package ... This includes any names defined (and submodules explicitly loaded) by `__init__.py`. It also includes any submodules of the package that were explicitly loaded by previous `import` statements." Star-import contents therefore depend on unrelated earlier imports - ESTABLISHED
92. Documented shadowing trap: adding a `reverse` function to `sound/effects/__init__.py` means `from sound.effects import *` "would only import the two submodules `echo` and `surround`, but _not_ the `reverse` submodule, because it is shadowed by the locally defined `reverse` function" - ESTABLISHED
93. `__all__` governs star-import only. It does not make anything private, does not affect `import pkg.mod`, does not affect attribute access, and is not enforced at runtime. The single-leading-underscore convention is the only "private" signal, and it is likewise unenforced - ESTABLISHED
94. PEP 562 is **Final** (Python-Version 3.7). A module may define `__getattr__(name: str) -> Any` and `__dir__() -> List[str]`. Module `__getattr__` is consulted only after normal lookup "on a module object through the normal lookup (i.e. `object.__getattribute__`)" fails, and it must raise `AttributeError` for names it cannot supply. `__dir__` "overrides the standard `dir()` search on a module" - ESTABLISHED
95. PEP 562 caveat that breaks naive lazy-export shims: "Looking up a name as a module global will bypass module `__getattr__`. This is intentional, otherwise calling `__getattr__` for builtins will significantly harm performance." Code *inside* the module never goes through that module's own `__getattr__` - ESTABLISHED
96. Corollary: any name written into the module's `__dict__` - including one resolved once and cached there - will never reach `__getattr__` again. The correct lazy-attribute pattern is to compute, assign into `globals()`, then return - ESTABLISHED
97. `__path__` on a package "is initialized to be a sequence of strings containing the name of the directory holding the package's `__init__.py` before the code in that file is executed. This variable can be modified; doing so affects future searches for modules and subpackages contained in the package" - ESTABLISHED
98. `-X importtime` "shows module name, cumulative time (including nested imports) and self time (excluding nested imports)". `-X importtime=2` "enables additional output that indicates when an imported module has already been loaded. In such cases, the string `cached` will be printed in both time columns"; values other than 1 and 2 are reserved - VERSION-DEPENDENT (3.7 for the flag, 3.14 added `=2`)
99. `-O` / `PYTHONOPTIMIZE` "Remove assert statements and any code conditional on the value of `__debug__`" - import-time invariant checks and boundary assertions written with `assert` are removed from the bytecode - ESTABLISHED
100. PEP 810 "Explicit lazy imports" is **Final**, Python-Version **3.15**, resolution 03-Nov-2025. The soft keyword `lazy` prefixes module-scope imports: `lazy import json`, `lazy import foo.bar.baz`, `lazy from json import dumps`, `lazy from . import name`, `lazy from .. import name` - VERSION-DEPENDENT (3.15)
101. PEP 810 restrictions: "Lazy imports are only permitted at module scope; using `lazy` inside a function, class body, or `try`/`except`/`finally` block raises a `SyntaxError`. Neither star imports nor future imports can be lazy (`lazy from module import *` and `lazy from __future__ import ...` both raise `SyntaxError`)" - VERSION-DEPENDENT (3.15)
102. PEP 810 global controls: `-X lazy_imports=<mode>` and `PYTHON_LAZY_IMPORTS=<mode>`, plus `sys.set_lazy_imports()` / `sys.get_lazy_imports()` at runtime and `sys.set_lazy_imports_filter(func)` where `func(importing, imported, fromlist)` returns `True` to allow laziness and `False` to force eager loading. The What's New document documents `all` and `normal` for the flag; the PEP also documents `none` (nothing is lazy even when marked) and the precedence order `sys.set_lazy_imports()` > `-X` > environment variable > default - VERSION-DEPENDENT (3.15)
103. PEP 810 back-compatibility hatch for libraries that must also run on 3.14 and earlier: a module-level `__lazy_modules__` container of fully qualified module-name strings makes ordinary `import` statements for those modules lazy on 3.15+, "with the same semantics as the `lazy` keyword", and is simply ignored by older interpreters - VERSION-DEPENDENT (3.15)
104. With PEP 810, an ImportError from a deferred import surfaces at *first use* of the name, and CPython chains the exception so the traceback shows both the `lazy import` statement site and the access site - VERSION-DEPENDENT (3.15)
105. Python 3.15 changes `importlib.metadata`: where `metadata()` and `Distribution.metadata` previously "would return an empty `PackageMetadata` object as if the file was present but empty", now "a `MetadataNotFound` exception is raised" - VERSION-DEPENDENT (3.15)
106. Python 3.15 fixes a long-standing import deadlock: "The import system now acquires per-module locks in hierarchical order (parent packages before their submodules). This fixes a long-standing deadlock where one thread importing `pkg.sub` and another importing `pkg.sub.mod` could each block the other when `pkg/sub/__init__.py` imports `pkg.sub.mod`" - VERSION-DEPENDENT (3.15)

### Plugin and extension seams

107. Entry points live in `entry_points.txt` "in the `*.dist-info` directory of the distribution", and "The file contents are in INI format, as read by Python's configparser module" - ESTABLISHED
108. An entry-point object reference is `importable.module` or `importable.module:object.attr`, resolved exactly as `modname, sep, qualname = object_ref.partition(':')`, then `obj = importlib.import_module(modname)`, then `getattr` down the dotted `qualname`. "If extras are used, they are a comma-separated list inside square brackets" - ESTABLISHED
109. Group-name convention from the specification: "To avoid clashes, consumers defining a new group should use names starting with a PyPI name owned by the consumer project, followed by `.`" - so `myapp.plugins`, never bare `plugins` - ESTABLISHED
110. Runtime discovery is `importlib.metadata.entry_points(group='myapp.plugins')`, returning an `EntryPoints` collection with `.groups`, `.names` and `.select(...)`. Each `EntryPoint` exposes `name`, `value`, `group`, `module`, `attr`, `extras`, `dist` and `.load()` - ESTABLISHED
111. `entry_points()` API history: pre-3.10 it accepted no parameters and always returned a dictionary; **Changed in version 3.12**: "`entry_points()` always returns an `EntryPoints` object (previously returned a dict keyed by group)"; **Changed in version 3.13**: "`EntryPoint` objects no longer present a tuple-like interface (`__getitem__()`)". Code doing `entry_points()['console_scripts']` is dead on 3.12+ - VERSION-DEPENDENT (3.12, 3.13)
112. `importlib.metadata.packages_distributions()` (**Added in version 3.10**) returns "a mapping from top-level module and import package names to lists of distribution package names that provide them", with the documented caveat "Not reliable with editable installs that do not supply top-level names" - VERSION-DEPENDENT (3.10+)
113. packaging.python.org lists three plugin-discovery mechanisms: "Using naming convention" (`pkgutil.iter_modules()` over a prefix), "Using namespace packages", and "Using package metadata" (entry points declared in `pyproject.toml`) - ESTABLISHED
114. Explicit warning in that guide: "It's not recommended to make your project's main top-level package a namespace package for the purpose of plugins, as one bad plugin could cause the entire namespace to break", and "Namespace packages are a complex feature and there are several different ways to create them" - ESTABLISHED
115. PEP 420 resolution algorithm, per `sys.path` entry in order: if `<dir>/foo/__init__.py` exists, import a regular package and return; else if `<dir>/foo.{py,pyc,so,pyd}` exists, import a module and return; else if `<dir>/foo` exists as a directory, **record it and continue scanning**; otherwise continue. A namespace package is created from the recorded directories only if the whole scan found no regular package or module - ESTABLISHED
116. A namespace package's `__path__` is a `_NamespacePath`, "a read-only iterable of strings", and "The import machinery will behave as if a namespace package's `__path__` is recomputed before each portion is loaded". PEP 420 notes regular packages have "a performance advantage" because a namespace package cannot be created until every path entry has been scanned - ESTABLISHED
117. Because `pkg_resources` was removed in setuptools 82.0.0, the old `pkg_resources`-style declarative namespace packages have no supported implementation on a current setuptools; PEP 420 implicit namespaces are the only live mechanism - VERSION-DEPENDENT (setuptools >= 82)
118. Composition-root dependency injection needs no framework: entry points give a name-to-callable table, and `EntryPoint.load()` is the only place the plugin module is imported, which keeps the import graph acyclic by construction - core defines the protocol, plugins import core, core never imports plugins - ESTABLISHED

### Enforcing module boundaries

119. import-linter 2.13's CLI is `lint-imports`, with the alias `import-linter lint` (the `import-linter` group command was added in 2.10, 2026-02-06). Documented options: `--config`, `--contract` (by contract id, repeatable), `--cache-dir` (default `.import_linter_cache`), `--no-cache`, `--show-timings`, `--verbose`, `--version` - ESTABLISHED
120. import-linter searches the current directory in this order: `setup.cfg` (INI), `.importlinter` (INI), `pyproject.toml` (TOML). The TOML sections are `[tool.importlinter]` and `[[tool.importlinter.contracts]]` - ESTABLISHED
121. import-linter top-level options: `root_package` (single) or `root_packages` (list, required when layering several top-level packages), `include_external_packages` ("Whether to include external packages when building the import graph"), `exclude_type_checking_imports` ("any import made under an `if TYPE_CHECKING:` statement will not be added to the graph") - ESTABLISHED
122. import-linter 2.x has **five** built-in contract types: `forbidden`, `protected`, `layers`, `independence`, `acyclic_siblings`. `protected` was added in 2.5 (2025-09-15) and `acyclic_siblings` in 2.6 (2025-11-10) - VERSION-DEPENDENT (import-linter >= 2.6)
123. `layers` semantics: `layers` is "An ordered list with the name of each layer module ... The order is from higher to lower level layers"; higher may depend on lower and not the reverse; and "This includes indirect imports (i.e. chains of imports via other modules)". The rule applies to all descendants, so `mypackage.low.one` may not import `mypackage.high.two` - ESTABLISHED
124. `layers` syntax details: a layer wrapped in parentheses - `(medium)` - "will be ignored if [it is] not present in the file system"; siblings on one line separated by `|` are independent and "not allowed to import from each other"; separated by `:` they may import each other; mixing `|` and `:` on one line is an invalid contract. `layers` explicitly "Does not support wildcards" - ESTABLISHED
125. `containers` (absolute module names, wildcard-capable) lets one contract apply the same layer stack under several parents, with `layers` names then relative to the container. Layers in *different* containers are unconstrained relative to each other: "it will allow `mypackage.foo.low` to import `mypackage.bar.high`, as they are in different containers" - ESTABLISHED
126. `exhaustive = true` plus optional `exhaustive_ignores` makes a layers contract fail when a *new* module appears in a container without being declared as a layer - the only import-linter setting that catches "someone added a package and nobody classified it". "Exhaustive contracts are only supported for layers that define containers" - ESTABLISHED
127. `forbidden` options: `source_modules`, `forbidden_modules` (may include root-level external packages such as `django` "but not `django.db.models`", and then `include_external_packages = True` is required), `ignore_imports`, `unmatched_ignore_imports_alerting`, `allow_indirect_imports`, `as_packages` (default `True`) - ESTABLISHED
128. `forbidden` defaults are package-wide and transitive - descendants are checked and "Indirect imports will also be checked". `as_packages = False` restricts checking to exactly the listed modules. With `as_packages = True`, overlapping source and forbidden modules that share descendants are *allowed*, so `source_modules = ["mypackage.one"]` with `forbidden_modules = ["mypackage.one.**"]` does nothing at all unless `as_packages = false` - ESTABLISHED
129. `independence` takes `modules` and checks "that there are no imports in any direction between the modules, even indirectly" - the contract for sibling bounded contexts that must not know about each other - ESTABLISHED
130. `protected` takes `protected_modules` and `allowed_importers`: nothing outside the allow-list may import the protected modules. With `as_packages = True`, "descendants of a protected module are also allowed to import each other" - ESTABLISHED
131. `acyclic_siblings` takes `ancestors`, optional `depth` (integer >= 0, **default 10**; depth 0 checks only direct children) and `skip_descendants`. Documented caveat: "neither the `depth` or `skip_descendants` options prevent deeper imports from being considered when analyzing children in earlier generations ... If you want to ignore an import altogether, use `ignore_imports` instead" - ESTABLISHED
132. Shared options: `ignore_imports` entries are written `mypackage.foo.importer -> mypackage.bar.imported`; `unmatched_ignore_imports_alerting` is `error` (**default**), `warn` or `none`. A stale ignore that no longer matches any import therefore fails the run by default, which is what stops the ignore list rotting - ESTABLISHED
133. import-linter wildcards: `*` "stands in for a module name, without including subpackages", `**` includes subpackages. `mypackage.*` matches `mypackage.foo` but not `mypackage.foo.bar`; `mypackage.foo*` is "not a valid expression. (The wildcard must replace a whole module name.)" Not every field supports wildcards - `layers` does not - ESTABLISHED
134. import-linter's documented pre-commit integration "must use `language: system` to allow Import Linter to analyze your packages from within a virtual environment"; a remote hook with id `import-linter` also exists - ESTABLISHED
135. Tach 0.35.0 is "a Python tool to enforce dependencies and interfaces, written in Rust", installed via `pip install tach`, configured by `tach.toml` at the project root, and checked with `tach check`, which exits non-zero on violation and is meant to run "like a linter or test runner, e.g. in pre-commit hooks, on-save hooks, and in CI pipelines" - ESTABLISHED
136. `tach.toml` top-level keys include `modules`, `interfaces`, `layers`, `exclude`, `source_roots`, `exact` (default **false**; "causes `tach check` to fail if any declared dependencies are found to be unused"), `forbid_circular_dependencies` (default **false**), `ignore_type_checking_imports` (default **true** - silences failures from imports under `TYPE_CHECKING`), `layers_explicit_depends_on` (default **false**), `respect_gitignore` (default **true**, also accepts `"if_git_repo"`), `root_module`, `rules`, plus `[cache]` and `[external]` tables - ESTABLISHED
137. Per-module Tach keys: `path` (glob patterns allowed, e.g. `"libs.**"`; `paths` is shorthand for a group), `depends_on`, `cannot_depend_on` (which "takes precedence over `depends_on`"), `layer`, `visibility`, `utility` (default false - "all other modules may import from it without declaring an explicit dependency"), `unchecked` (default false) - ESTABLISHED
138. Tach's most dangerous default: "Omitting the `depends_on` field means the module will be allowed to import from any other module. However, it will still be subject to those modules' public interfaces." An unlisted `depends_on` is not "no dependencies", it is "all dependencies"; `depends_on = []` is the strict form - ESTABLISHED
139. Tach interfaces are declared separately as `[[interfaces]]` with `expose` ("a list of regex patterns which define the public interface"), optional `from` (regex list of adopting modules; "If an interface entry does not specify `from`, all modules will adopt the interface"), `visibility`, and `exclusive` (default false, which "requires that matching modules use _only_ this interface"). "A module can match multiple interface entries - if an import matches _any_ of the entries, it will be considered valid" - ESTABLISHED
140. Tach layers: an ordered top-level `layers` list, first entry highest. "Higher layers may import from lower layers, but lower layers may NOT import from higher layers." By default cross-layer dependencies need no `depends_on` entry; `layers_explicit_depends_on = true` requires them, while utility modules "remain accessible without explicit declaration" - ESTABLISHED
141. Other Tach commands: `tach init [--force]`, `tach mod` (interactive module editor), `tach sync [--add]` (without `--add` it *removes* modules that no longer exist in the source roots), `tach check [--exact] [--dependencies] [--interfaces]`, `tach check-external`, `tach report [--dependencies] [--usages] [--external] [--raw]`, `tach show [--web] [--mermaid]`, `tach map [--direction {dependencies,dependents}] [--closure PATH]`, `tach test` (plus a pytest plugin with `--tach`, `--tach-base`, `--tach-head`, `--tach-verbose`), `tach install` - ESTABLISHED
142. deptry 0.25.1 checks *dependency declarations against actual imports* - a different axis from import-linter and Tach. ### Versioning and the change contract

148. PEP 440's canonical public version form is `[N!]N(.N)*[{a|b|rc}N][.postN][.devN]`, optionally with `+<local version label>`. Pre-release spellings normalize: `a`/`alpha` to `a`, `b`/`beta` to `b`, and `rc`/`c`/`pre`/`preview` to `rc` - ESTABLISHED
149. `~=` is the compatible-release operator: "For a given release identifier `V.N`, the compatible release clause is approximately equivalent to the pair of comparison clauses: `>= V.N, == V.*`" - so `~= 1.4.5` means `>= 1.4.5, < 1.5.0`, pinning one more component than most people intend - ESTABLISHED
150. `== 1.1.*` is prefix matching and matches `1.1`, `1.1.post1` **and `1.1a1`** - wildcard equality does not exclude pre-releases - ESTABLISHED
151. `===` is arbitrary equality: "simple string equality operations which do not take into account any of the semantic information such as zero padding or local versions" - ESTABLISHED
152. PEP 440's pre-release rule: "Pre-releases of any kind, including developmental releases, are implicitly excluded from all version specifiers, _unless_ they are already present on the system, explicitly requested by the user, or if the only available version that satisfies the version specifier is a pre-release." Separately, "The exclusive ordered comparison `>V` MUST NOT allow a pre-release of the specified version unless the specified version is itself a pre-release" - ESTABLISHED
153. PEP 387 "Backwards Compatibility Policy" is **Active** (created 18-Jun-2009) and is CPython's own policy plus the de-facto template for libraries: "Wait for the warning to appear in at least two minor Python versions of the same major version, or one minor version in an older major version", with the stated preference "to wait 5 years before removal (e.g., warn starting in Python 3.10, removal in 3.15)" - ESTABLISHED
154. PEP 387 also requires that the warning message "should include the release the incompatibility is expected to become the default and a link to an issue that users can post feedback to". `PendingDeprecationWarning` "may be used in special cases where the old and new versions of the API will coexist for many releases" - ESTABLISHED
155. `DeprecationWarning` is **invisible by default** except when raised from `__main__`. The default filter list, in precedence order, is `default::DeprecationWarning:__main__`, `ignore::DeprecationWarning`, `ignore::PendingDeprecationWarning`, `ignore::ImportWarning`, `ignore::ResourceWarning`. A library deprecation nobody sees is not a deprecation - ESTABLISHED
156. PEP 702 is **Final**, Python-Version **3.13**, resolution 07-Nov-2023. The decorator lives in `warnings`, not `typing`: `@warnings.deprecated(message, /, *, category=DeprecationWarning, stacklevel=1)` - VERSION-DEPENDENT (3.13+; use `typing_extensions.deprecated` below that)
157. `warnings.deprecated` runtime semantics: "The warning specified by _category_ will be emitted at runtime on use of deprecated objects. For functions, that happens on calls; for classes, on instantiation and on creation of subclasses. If the _category_ is `None`, no warning is emitted at runtime." `stacklevel=1` (the default) emits "at the direct caller of the deprecated object". "Static type checker behavior is not affected by the _category_ and _stacklevel_ arguments" - VERSION-DEPENDENT (3.13+)
158. The message is stored in the `__deprecated__` attribute on the decorated object. On an `@overload`, "the decorator must be after the `@typing.overload` decorator for the attribute to exist on the overload as returned by `typing.get_overloads()`" - VERSION-DEPENDENT (3.13+)
159. For a hand-rolled shim, `warnings.warn(message, DeprecationWarning, stacklevel=2)` is the correct call: "This makes the warning refer to `deprecated_api`'s caller, rather than to the source of `deprecated_api` itself (since the latter would defeat the purpose of the warning message)". `stacklevel=1` points at your own library and is useless to the caller - ESTABLISHED
160. To deprecate a module-level *symbol* so callers actually see it, remove the name from the module globals and re-expose it through a PEP 562 `__getattr__` that issues the warning - because module globals bypass `__getattr__`, leaving the old name assigned silently disables the warning - ESTABLISHED

### Monorepo, workspace and editable installs for incremental local builds

"Every workspace requires a root, which is also itself a workspace member" - ESTABLISHED

## New content the manifest set should carry

**1. The Build-System Contract: PEP 517/518/621 and the pyproject Spine** - destination: NEW: python_module_boundaries_manifest.md
`[build-system]` is the only portable contract between a source tree and any installer: `requires`, `build-backend` as `module:object`, `backend-path` for in-tree backends. Frontends isolate builds by default, which is exactly why `--no-build-isolation` demands preinstalled build dependencies. Name the four mainstream backends with the pins packaging.python.org actually publishes, plus `uv_build` (pure-Python only) and the extension backends (maturin, scikit-build-core, meson-python). State that `wheel` must never appear in `requires`; that `python -m build` builds the wheel *from the sdist* and is therefore the packaging test, not a formality; and that pip 25.3 removed the last non-PEP-517 install path, so `setup.py`-era advice is now actively wrong.

**2. Layout Is a Boundary: src/ versus Flat** - destination: NEW: python_module_boundaries_manifest.md
State the mechanism rather than the preference. The interpreter prepends the script directory or the current directory to `sys.path`, so a flat layout lets the working tree shadow the installed distribution and the test suite exercises a copy that will never ship. Quote the two documented consequences: files silently missing from the distribution, and imports that work editable but not installed. Give the diagnostic: `python -P -c "import pkg; print(pkg.__file__)"` from the repository root, `-I` for the strict version. Note setuptools' flat-layout reserved-name lists and its refusal to build with multiple top-level packages - both are silent behaviours that make a flat layout look like it works.

**3. Dependency Declaration: dependencies, extras, dependency-groups, lock files** - destination: NEW: python_module_boundaries_manifest.md
Four axes with four audiences. `dependencies` = always needed, ships in metadata. `optional-dependencies` = consumer-selectable features, ships as `Provides-Extra` plus gated `Requires-Dist`. `[dependency-groups]` (PEP 735, Final) = this checkout's workflows, **never** ships, composes with `{include-group = "..."}`, no cycles. `pylock.toml` (PEP 751, Final, resolution 2025-03-31) = the reproducible install record, machine-generated, `lock-version = "1.0"`, mandatory `created-by` and `[[packages]]`. **4. Metadata Fields That Change Behaviour** - destination: NEW: python_module_boundaries_manifest.md

**5. Import Mechanics as Architecture: Cycles, Side Effects, Lazy Imports** - destination: NEW: python_module_boundaries_manifest.md
Ground every rule in mechanism. A module enters `sys.modules` before its body runs, so a cycle yields a partially initialised module and the exact message `cannot import name X from partially initialized module Y (most likely due to a circular import)`. `import a.b` survives cycles that `from a.b import thing` cannot. A failed import removes only the failing module from the cache, leaving half-built collaborators behind. Loading any submodule binds it on its parent, creating invisible ordering dependencies. Then the deliberate seams: `__all__` (star-import only, no privacy), the underscore convention, PEP 562 module `__getattr__` with the "module globals bypass `__getattr__`" caveat, and PEP 810 `lazy` (Final, 3.15) with its module-scope-only restriction and `-X lazy_imports` / `PYTHON_LAZY_IMPORTS` / `__lazy_modules__` / `sys.set_lazy_imports_filter` controls. ## Traps for coding agents

1. **"There is no standard Python lock file" is wrong.** PEP 751 is Final with resolution 31-Mar-2025 and the file is `pylock.toml` (or `pylock.<name>.toml`). Do not write prose implying the ecosystem is still waiting.
2. **A dependency group is not an extra, and it never ships.** Putting test dependencies in `[project.optional-dependencies.dev]` publishes them as a `Provides-Extra` on PyPI forever; `[dependency-groups]` is explicitly excluded from built distributions. Conversely, putting a consumer-facing optional feature in `[dependency-groups]` makes it uninstallable by anyone downstream.
3. **`pip install proj[group]` cannot install a dependency group.** Groups need `pip install --group <name>` (pip 25.1+) or `uv sync --group <name>`. There is deliberately no specification-level syntax for referring to them, so the extras syntax silently resolves to "no such extra".
4. **`~=1.4.5` means `>=1.4.5, <1.5.0`, not `<2.0`.** Reaching for the compatible-release operator to express semver-caret behaviour is a common and silent over-constraint; `>=1.4.5,<2` is what caret actually means.
5. **`== 1.1.*` matches `1.1a1`.** Wildcard equality does not exclude pre-releases, even though bare `>=` and `<=` specifiers do exclude them by default.
6. **`license = { text = "MIT" }` and `License :: OSI Approved :: MIT License` are deprecated.** The current form is `license = "MIT"` as an SPDX expression plus `license-files = ["LICENSE"]`, and declaring both `License` and `License-Expression` makes PyPI reject the upload.
7. **PEP 621 says a field may not be both static and in `dynamic`; PEP 808 says thirteen of them may.** Only `authors, maintainers, classifiers, dependencies, entry-points, scripts, gui-scripts, keywords, license-files, optional-dependencies, urls, import-names, import-namespaces` may be both, and only in the append direction. `version`, `requires-python`, `description`, `readme` and `license` still cannot, and `name` can never be dynamic at all.
8. **Flat layout makes the test suite lie.** Running tests from the repository root imports the working tree, not the installed wheel, because the interpreter prepends the current directory to `sys.path`. Under src layout the same run imports the installed distribution - which is what actually ships. This is the single highest-value structural decision in this territory.
9. **`python -P` is the verification nobody runs.** `python -P -c "import pkg; print(pkg.__file__)"` from the repository root is the two-second proof that the package is genuinely installed rather than shadowed. `-P` and `PYTHONSAFEPATH` exist only from 3.11; `-I` is the stronger, older form.
10. **`wheel` in `[build-system] requires` is cargo cult.** `setuptools.build_meta` requests what it needs via `get_requires_for_build_wheel`, and pip 25.3 removed the `setup.py bdist_wheel` mechanism outright.
11. **`pkg_resources` no longer exists on a current setuptools.** Removed in setuptools 82.0.0 (2026-02-08). Code using `pkg_resources.iter_entry_points`, `resource_filename`, or `pkg_resources`-style declarative namespace packages must move to `importlib.metadata` / `importlib.resources` / PEP 420, or pin an ancient setuptools.
12. **`entry_points()['console_scripts']` has been broken since Python 3.12** - `entry_points()` "always returns an `EntryPoints` object" - and `EntryPoint` lost its tuple interface in 3.13. The portable form is `entry_points(group=...)`, with `importlib_metadata` as the backport below 3.10.
13. **A missing `__init__.py` does not mean "not a package"; it means "namespace package".** PEP 420 will import a directory with no `__init__.py`, and setuptools' `[tool.setuptools.packages.find]` has `namespaces` enabled by default, so a stray `tests/` or `scripts/` directory can be silently packaged and shipped as a namespace portion.
14. **PEP 752 "namespaces" are not import namespaces.** PEP 752 (Accepted 29-Jun-2026) is repository name-prefix reservation. PEP 420 is import-time namespace packages. Accepting 752 changes nothing about how `import` behaves.
15. **`from pkg import *` without `__all__` is not "everything".** It imports only names already bound in `__init__.py` plus submodules that some earlier, unrelated import happened to load - so its result changes with import order elsewhere in the program. And defining a function with the same name as a submodule shadows that submodule.
16. **`__all__` is not access control and `_private` is not enforced.** Neither stops `from pkg.mod import _thing`. Only import-linter or Tach contracts (`protected`, `visibility`, interfaces) actually stop it, and only at lint time.
17. **A module's own code bypasses its own `__getattr__`.** PEP 562: "Looking up a name as a module global will bypass module `__getattr__`." A lazy-export or deprecation shim in `__init__.py` never fires for code inside that same module, and stops firing forever once the name is written into the module `__dict__`.
18. **Switching `from a.b import x` to `import a.b` is a real cycle fix; wrapping the import in `try/except ImportError` is not.** The `from` form does attribute lookup on a possibly-partial module; the plain form only binds the module object. Suppressing the ImportError hides the cycle and converts it into an `AttributeError` or `None` later.
19. **`lazy` imports do not exist before Python 3.15**, and even on 3.15 they are a `SyntaxError` inside functions, class bodies and `try`/`except`/`finally` blocks, and for `import *` and `__future__` imports. For libraries supporting 3.14 and earlier, `__lazy_modules__` is the forward-compatible declaration and PEP 562 `__getattr__` is the fully portable one.
20. **`-X lazy_imports=all` is not free.** It changes *when* ImportErrors and import side effects occur. Any module whose top-level code registers something - signal handlers, plugin registration, warnings filters, `multiprocessing` start methods - has that side effect deferred to first attribute access, which may be never.
21. **`assert` disappears under `-O`.** Import-time invariant checks, "this plugin must be registered" guards and boundary assertions written with `assert` are removed from the bytecode by `-O` / `PYTHONOPTIMIZE`.
22. **`DeprecationWarning` is invisible unless the caller is `__main__`.** Deprecating a symbol and expecting downstream users to notice is a no-op unless they run `-W error::DeprecationWarning`; a library's own CI must enable it or nothing detects self-inflicted use of deprecated internals.
23. **`@deprecated` lives in `warnings`, not `typing`.** `from warnings import deprecated` on 3.13+, `from typing_extensions import deprecated` below that. Passing `category=None` disables the runtime warning entirely while still marking the object for type checkers - occasionally right, usually not what was meant.
24. **`stacklevel=1` points at your own library.** Hand-rolled deprecation wrappers need `stacklevel=2`, or more when further wrapped, for the warning to name the caller's line.
25. **`@deprecated` goes after `@overload`, not before.** The `__deprecated__` attribute only lands on the overload retrievable via `typing.get_overloads()` when `@deprecated` is the inner decorator.
26. **Tach's omitted `depends_on` means "may import anything".** An agent that leaves `depends_on` off "because there are no dependencies yet" has written a permissive configuration, not a strict one. Write `depends_on = []`.
27. **An import-linter `forbidden` contract with overlapping source and forbidden modules can silently do nothing.** With the default `as_packages = True` a source module may import forbidden modules with which it shares descendants, so `source_modules = ["pkg.one"]` with `forbidden_modules = ["pkg.one.**"]` has no effect at all unless `as_packages = false`.
28. **import-linter `layers` is ordered highest-first and supports no wildcards.** Reversing the list inverts the architecture without any error. `|` means independent siblings, `:` means siblings may import each other, mixing them on one line is invalid, and `(name)` marks a layer optional.
29. **A layers contract does not notice new modules unless `exhaustive = true`** - and `exhaustive` only works when `containers` is set. Without it, adding an unclassified package beside the layers passes CI indefinitely.
30. **A stale `ignore_imports` entry fails the run by default.** `unmatched_ignore_imports_alerting` defaults to `error`, so pasting speculative ignore lines breaks CI once the underlying import disappears. That default is the feature - do not set it to `none`.
31. **Naming a third-party package in a forbidden contract requires `include_external_packages = True`,** and only root-level names are permitted: `django`, never `django.db.models`.
32. **deptry and import-linter check different things.** deptry compares imports against *declared dependencies* (DEP001-DEP005); import-linter and Tach constrain *internal* structure. Neither substitutes for the other, and deptry's inline `# deptry: ignore` only applies to the import-level rules DEP001, DEP003 and DEP004 - never to declaration-level findings such as DEP002.
33. **pydeps needs Graphviz `dot` on PATH** and is a visualiser: it has no pass/fail contract and cannot gate CI, however good the picture looks.
34. **`uv init` now packages by default** (uv 0.12.0, 2026-07-28) and writes a `uv_build` `[build-system]`. Agents expecting the pre-0.12 unpackaged scaffold must pass `--no-package`. And `uv_build` "currently only supports pure Python code" - the moment a C or Rust extension appears, the backend must change.
35. **uv's pre-release resolution default changed in 0.12.0** from `if-necessary-or-explicit` to `if-necessary`. A lock refresh across that boundary can legitimately drop a pre-release that resolved before, which looks like a regression and is not.
36. **`uv sync --frozen` is not `--locked`.** `--frozen` uses the lockfile *without* checking it against `pyproject.toml`, so a hand-edited dependency is silently ignored. CI wants `--locked`, which fails when the lockfile is stale.
37. **`flit_core >= 3.12.0, <4` is what packaging.python.org still publishes**, but flit 4.0.x shipped 2026-08-04 and removed `[tool.flit.metadata]`, VCS-based sdist file selection and `--setup-py`. Copying the tutorial pin gets flit 3, and copying flit-3-era `[tool.flit.metadata]` examples into a flit-4 project fails outright.
38. **twine 7.0.0 refuses metadata version 2.0.** A pipeline that has been building with a very old backend starts failing at the *upload* step, not the build step, which makes the diagnosis look unrelated to the build configuration.
39. **Editable installs make `packages_distributions()` unreliable** - the standard library documentation says so explicitly - so import-name-to-distribution mapping must never be a load-bearing runtime mechanism in a development environment.
40. **PEP 771 default extras and the PEP 777/817/825 wheel evolution work are all Draft.** Do not emit `default-optional-dependency-keys`, `Default-Extra`, `Wheel-Version`, `.whlx` or variant-wheel filenames into a real project.
41. **Relative imports fail in `__main__`.** "modules intended for use as the main module of a Python application must always use absolute imports." `python src/pkg/cli.py` and `python -m pkg.cli` are not interchangeable, and console-script entry points always take the module-import path.
42. **Python 3.10 reaches end-of-life in October 2026** per `devguide.python.org/versions/`, and setuptools 83 and pip 26.2 already require >= 3.10. A `requires-python = ">=3.9"` written today claims support the toolchain no longer provides.
43. **`python -m build` is not `pip wheel`.** `build` produces the sdist first and then builds the wheel from it, which is the only routine that catches a `MANIFEST.in`/`sdist`-selection bug. Building only a wheel from the working tree can pass while the published sdist is unbuildable.
44. **Core Metadata is at 2.6, not 2.1 or 2.2.** Emitting a hardcoded `Metadata-Version: 2.1` (a habit inherited from old `setup.py` templates) discards `License-Expression`, `Import-Name` and the PEP 808 `Dynamic` semantics, and can strand the artefact on the wrong side of an uploader's validation.
