## Facts

1. Stdlib `@dataclass` performs no type validation whatsoever. The CPython docs state: "With two exceptions described below, nothing in `@dataclass` examines the type specified in the variable annotation." The two exceptions are detecting `typing.ClassVar` and `dataclasses.InitVar` - both structural, neither a value check - ESTABLISHED.
2. `@dataclass` signature and defaults, verbatim from docs.python.org: `init=True, repr=True, eq=True, order=False, unsafe_hash=False, frozen=False, match_args=True, kw_only=False, slots=False, weakref_slot=False`. `slots` is FALSE by default in stdlib dataclasses - the opposite of `attrs.define` - ESTABLISHED.
3. `attrs.define` signature defaults, verbatim from attrs' API docs: `slots=True, frozen=False, weakref_slot=True, auto_exc=True, order=False, auto_detect=True, on_setattr=None, match_args=True, cache_hash=False, force_kw_only=False`. `attrs.frozen` "Behaves the same as `attrs.define` but sets *frozen=True* and *on_setattr=None*" - ESTABLISHED.
4. Under `attrs.define`/`attrs.frozen`, validators and converters run on ATTRIBUTE ASSIGNMENT as well as in `__init__`: "When using `attrs.define()` or `attrs.frozen`, however, attrs will run the validators even when setting the attribute." Legacy `@attr.s` classes run validators only during initialisation. This is attrs' most important divergence from both stdlib dataclasses and pydantic-by-default - ESTABLISHED.
5. attrs' documented per-attribute initialisation order is: default/default factory, then converter, then validators, then `__attrs_post_init__`. "Converters are run before validators, so you can use validators to check the final form of the value." `__attrs_post_init__` "is automatically detected and run after attrs is done initializing your instance" - ESTABLISHED.
6. attrs validators can be switched off process-wide: `attrs.validators.set_disabled(True)` or the `with attrs.validators.disabled():` context manager. An attrs validator is therefore NOT a guaranteed enforcement mechanism for a boundary invariant; any imported code can disable it globally - ESTABLISHED.
7. attrs disclaims the validation role outright: "attrs emphatically does **not** try to be a validation library, but a toolkit to write well-behaved classes like you would write yourself," and characterises pydantic as "first and foremost a *data validation & type coercion library*" - ESTABLISHED.
8. `msgspec.Struct` annotations are not enforced at construction. msgspec's own docs: "Unlike some other libraries (e.g. pydantic), the type annotations on a `msgspec.Struct` class are not checked at runtime during normal use. Types are only checked when decoding a serialized message when using a typed decoder." Calling `MyStruct(field="wrong type")` succeeds silently - ESTABLISHED.
9. msgspec Struct class options and defaults, per msgspec.dev/structs: `frozen=False`, `eq=True`, `order=False`, `kw_only=False`, `omit_defaults=False`, `forbid_unknown_fields=False`, `tag=None`, `tag_field` defaults to `"type"` when tagged, `rename=None`, `array_like=False`, `gc=True`. `forbid_unknown_fields=False` means unknown input keys are silently discarded on decode - ESTABLISHED.
10. A frozen msgspec Struct raises `AttributeError` (message form `AttributeError: immutable type: 'Point'`), NOT `dataclasses.FrozenInstanceError`. `frozen=True` "disables modifying attributes after initialization, and adds a `__hash__` method to the class definition" - ESTABLISHED.
11. msgspec's `__post_init__` hook runs on decode and convert, not only on `__init__`: it "is also called when: Decoding into a struct type (e.g. `msgspec.json.decode(..., type=MyStruct)`) ... Converting into a struct type (e.g. `msgspec.convert(..., type=MyStruct)`)". This makes `__post_init__` the correct place for msgspec cross-field invariants, because the decode path bypasses nothing - ESTABLISHED.
12. msgspec is STRICT by default; pydantic is LAX by default. msgspec: "Unlike some other libraries (e.g. pydantic), `msgspec` won't perform any unsafe implicit conversion by default ("strict" mode)"; `strict=False` may be passed to any decode function or `Decoder` class for lax rules. pydantic: `ConfigDict.strict` "Defaults to `False`", and in lax mode pydantic "will attempt to coerce values to the desired type when possible" (`'123'` -> `int`) - ESTABLISHED.
13. msgspec's exception hierarchy: `MsgspecError(Exception)`; `EncodeError(MsgspecError)`; `DecodeError(MsgspecError, ValueError)`; `ValidationError(DecodeError)`. Because `DecodeError` also inherits `ValueError`, a boundary handler written as `except ValueError` catches every msgspec validation failure - ESTABLISHED.
14. msgspec validation errors carry a JSONPath-style location inside the message string. The documented form is: `msgspec.ValidationError: Expected 'str', got 'int' - at '$.groups[1]'` (msgspec renders the type names and path in backticks). The location is embedded in prose, not exposed as a structured field, so machine consumers must parse the string - ESTABLISHED (msgspec.dev/usage shows this exact form); the formal grammar of the path was not confirmed - OPEN.
15. msgspec constraints are expressed as `Annotated[T, msgspec.Meta(...)]`; `Meta` fields are `gt, ge, lt, le, multiple_of, pattern, min_length, max_length, tz, title, description, examples, extra_json_schema, extra` - ESTABLISHED.
16. `msgspec.convert(obj, type, *, strict=True, from_attributes=False, dec_hook=None, builtin_types=None, str_keys=False)` is msgspec's in-memory parse entry point (the analogue of `TypeAdapter.validate_python`). `msgspec.json.decode(buf, *, type='Any', strict=True, dec_hook=None)` parses and validates in one pass - ESTABLISHED.
17. pydantic's guarantee is one-directional and it says so: "Pydantic guarantees the types and constraints of the output, not the input data." Nothing about the input object survives validation as a claim - only the constructed model instance is guaranteed - ESTABLISHED.
18. `ValidationError.errors()` returns a list of dicts with exactly these documented keys and meanings: `type` - "A computer-readable identifier of the error type"; `loc` - "The error's location as a list"; `msg` - "A human-readable explanation of the error"; `input` - "The input provided for validation"; `ctx` - "An optional object which contains values required to render the error message"; `url` - "The documentation URL giving information about the error". `error_count()` "Returns the number of errors"; `json()` "Returns a JSON representation of the list errors" - ESTABLISHED.
19. `errors()` accepts `include_url: bool = True`, `include_context: bool = True`, `include_input: bool = True`. For a boundary emitting compact machine-readable payloads, call `exc.errors(include_url=False, include_context=False)`. FLAGGED-SECONDARY on provenance: the version-matched `api/pydantic_core/` reference page returned HTTP 404 on the new docs host this session, so these names and defaults are corroborated from pydantic's error-handling page plus pydantic GitHub discussions rather than from the API reference itself - ESTABLISHED.
20. pydantic tells you not to raise its error type yourself: "Validation code should not raise the `ValidationError` itself, but rather raise a `ValueError` or a `AssertionError` (or subclass thereof) which will be caught and used to populate the final `ValidationError`." Any other exception type raised inside a validator escapes uncaught and does not become a `ValidationError` - ESTABLISHED.
21. pydantic's own validators documentation warns that `assert` inside a validator is not enforcement: `AssertionError` works via `assert` statements, but "these statements are skipped when Python is run with the -O optimization flag." A `@field_validator` whose only check is an `assert` therefore passes everything under `-O`; this is the highest-consequence interaction between `-O` and any validation library - ESTABLISHED.
22. `PydanticCustomError(error_type, message_template, context)` is the documented way to emit a stable machine-readable error identity from user validation code; pydantic describes it as "a bit more verbose, but provides extra flexibility" over raising `ValueError` - ESTABLISHED.
23. pydantic's four validator modes have distinct contracts. *before*: runs before pydantic's internal parsing and coercion, receives raw input of any type. *after*: "run after Pydantic's internal validation. They are generally more type safe and thus easier to implement." *plain*: "act similarly to *before* validators but they **terminate validation immediately** after returning, so no further validators are called and Pydantic does not do any of its internal validation against the field type." *wrap*: can run code before and after and can terminate - ESTABLISHED.
24. Validator ordering in an `Annotated` stack is asymmetric: "*before* and *wrap* validators are run from right to left, and *after* validators are then run from left to right"; writing `Annotated[int, BeforeValidator(a), BeforeValidator(b)]` and expecting `a` then `b` is wrong - ESTABLISHED.
25. `@model_validator` supports `mode='before' | 'after' | 'wrap'`; there is no `mode='plain'` for model validators. `@field_validator` supports all four - ESTABLISHED.
26. pydantic `ConfigDict` defaults that silently weaken enforcement, each quoted from the config API reference: `strict` default `False`; `extra` "Defaults to `'ignore'`"; `frozen` "Defaults to `False`"; `validate_assignment` "Whether to validate the data when the model is changed. Defaults to `False`"; `validate_default` "Whether to validate default values during validation. Defaults to `False`"; `revalidate_instances` "The default is `'never'` (no revalidation)"; `arbitrary_types_allowed` "Defaults to `False`"; `coerce_numbers_to_str` "Defaults to `False`"; `defer_build` "Defaults to False" - ESTABLISHED.
27. Consequences of #26 an agent must plan around: unknown input keys are dropped, not rejected; a validated model can be driven into an invalid state by plain attribute assignment; a field default that violates its own constraints is never checked; and an already-constructed model (including a subclass instance) passed as a nested field is accepted without revalidation - ESTABLISHED.
28. `model_construct()` "Creates models without running validation," and pydantic's own guidance is: "You should only ever use the `model_construct()` method with data which has already been validated, or that you definitely trust." It is a deliberate hole in the parse boundary - ESTABLISHED.
29. `TypeAdapter` is the parse entry point for non-`BaseModel` types (dataclasses, primitives, `list[SomeModel]`, `TypedDict`), exposing `validate_python()`, `validate_json()`, `dump_python()`, `dump_json()`, `json_schema()` and `rebuild()` (added in v2.10). `dump_json()` returns bytes, unlike `BaseModel.model_dump_json()` which returns `str` - ESTABLISHED.
30. `TypeAdapter` construction is expensive and must be hoisted: "When creating an instance of `TypeAdapter`, the provided type must be analyzed and converted into a pydantic-core schema. This comes with some non-trivial overhead, so it is recommended to create a `TypeAdapter` for a given type just once and reuse it in loops or other performance-critical code." Constructing one per request is the most common pydantic performance defect - ESTABLISHED.
31. pydantic's own performance page prescribes: use `model_validate_json()` rather than `model_validate(json.loads(...))` so parsing and validation happen in one pass; prefer concrete `list`/`tuple`/`dict` annotations over `Sequence`/`Mapping` (abstract types force extra isinstance checks and multiple validation attempts); "Use tagged union, not union" (a `Literal` discriminator); avoid wrap validators because they "are generally slower than other validators"; and apply the `FailFast` annotation to sequences to stop at the first bad item. pydantic also states `TypedDict` is "~2.5x faster than nested models" (vendor-sourced) - ESTABLISHED.
32. `pydantic.dataclasses.dataclass` validates, unlike the stdlib decorator, but is explicitly "**not** a replacement for Pydantic models": `validate_python()`, `dump_python()` and JSON-schema generation are not methods on the dataclass; "you can wrap the dataclass with a `TypeAdapter` and make use of its methods" - ESTABLISHED.
33. In a pydantic dataclass, `__post_init__()` "will be called between the calls to *before* and *after* model validators" - ordering is before-model-validators, then `__post_init__`, then after-model-validators. An agent that assumes `__post_init__` runs last (as it does in stdlib dataclasses) will place cross-field checks where later validators can still mutate the data - ESTABLISHED.
34. Pydantic generic dataclasses do not parameterise validation: "Pydantic currently treats `Foo[int]` the same as `Foo[Any]`, without performing validation." Generic `BaseModel`s do not share this limitation - ESTABLISHED.
35. `TypeAdapter(SomeStdlibDataclass).validate_python({...})` is the documented way to add validation to a stdlib dataclass without changing its decorator; this is the cheapest retrofit for a codebase already built on `dataclasses` - ESTABLISHED.
36. cattrs enables PEP 654 exception groups for validation BY DEFAULT: "*cattrs* has a detailed validation mode since version 22.1.0, and this mode is enabled by default," and "In detailed validation mode, any structuring errors will be grouped and raised together as a `cattrs.BaseValidationError`, which is a PEP 654 ExceptionGroup." Concrete subclasses are `cattrs.ClassValidationError` (classes) and `cattrs.IterableValidationError` (sequences and mappings) - ESTABLISHED.
37. cattrs detailed validation can be turned off per converter with `detailed_validation=False`, in which case "any errors during un/structuring will bubble up directly as soon as they happen." cattrs notes the trade: "the structuring hooks are slightly slower but produce richer and more precise error messages" - ESTABLISHED.
38. cattrs positions itself exactly on the parse-don't-validate seam: it is "a Swiss Army knife for (un)structuring and validating data in Python," works "best with attrs classes, and dataclasses," deliberately avoids "polluting your data model with serialization details," and states the principle "validation belongs to the edges" - ESTABLISHED.
39. `@typing.runtime_checkable` buys only member-presence checking, and the stdlib says so twice. "`@runtime_checkable` will check only the presence of the required methods or attributes, not their type signatures or types," and "An `isinstance()` check against a runtime-checkable protocol can be surprisingly slow compared to an `isinstance()` check against a non-protocol class. Consider using alternative idioms such as `hasattr()` calls for structural checks in performance-sensitive code" - ESTABLISHED.
40. `isinstance()` works against both data and non-data protocols; `issubclass()` works only against non-data protocols. The typing spec: "`isinstance()` can be used with both data and non-data protocols, while `issubclass()` can be used only with non-data protocols. This restriction exists because some data attributes can be set on an instance in constructor and this information is not always available on the class object." Applying `@runtime_checkable` to a non-protocol class raises `TypeError` - ESTABLISHED.
41. Two 3.12 changes to runtime-checkable protocols that change results silently: `isinstance()` now uses `inspect.getattr_static()` rather than `hasattr()` to look up attributes, so "some objects which used to be considered instances of a runtime-checkable protocol may no longer be considered instances of that protocol on Python 3.12+, and vice versa"; and protocol members are "frozen" at class creation, so "Monkey-patching attributes onto a runtime-checkable protocol will still work, but will have no impact on `isinstance()` checks" - VERSION-DEPENDENT (3.12).
42. `typing.cast` is a pure no-op: "Cast a value to a type. This returns the value unchanged. This helps convince a type checker that the return value has the desired type." No check, no coercion, no logging - ESTABLISHED.
43. `typing.NewType` is a no-op wrapper: "At runtime, however, calling a `NewType` returns its argument unchanged," and "the expression `some_value is Derived(some_value)` is always true at runtime." It gives identity discipline to the checker and zero runtime guarantee. `NewType` became a class in 3.10 with "some additional runtime cost"; "The performance of calling `NewType` has been restored to its level in Python 3.9" in 3.11 - VERSION-DEPENDENT (3.10, 3.11).
44. `typing.Final` and `@typing.final` are pure no-ops: "There is no runtime checking of these properties." Assigning over a `Final` name succeeds at runtime; subclassing a `@final` class succeeds at runtime. The no-op status is ESTABLISHED; the nesting of `Final` inside `ClassVar` and vice versa arrived in 3.13 - VERSION-DEPENDENT (3.13).
45. `typing.TYPE_CHECKING` is "A special constant that is assumed to be `True` by 3.5.2+ type checkers. It is `False` at runtime." Every name imported only inside an `if TYPE_CHECKING:` block does not exist at runtime; using such a name in a `pydantic.BaseModel` annotation, a `TypeAdapter` target, or any `annotationlib`/`get_type_hints` call that resolves to `VALUE` raises `NameError` unless the model is rebuilt with an explicit namespace - ESTABLISHED.
46. `TypedDict` instances are plain `dict`s at runtime with no key or value enforcement; `Literal[...]` constrains values for the checker only; both need a validator (pydantic `TypeAdapter`, msgspec typed decode) to mean anything at the boundary. `Annotated[T, x]` attaches metadata only - tools without special logic for `x` "should ignore it and simply treat the type as T" - ESTABLISHED.
47. `annotated-types` 0.8.0 supplies `Gt, Ge, Lt, Le, MultipleOf, Len, MinLen, MaxLen, Timezone, Predicate` as pure metadata and performs no checking itself: "While `annotated-types` avoids runtime checks for performance, users should not construct invalid combinations such as `MultipleOf("non-numeric")` or `Annotated[int, Len(3)]`," and "It is up to the implementer to determine how this metadata is used." An `Annotated[int, Gt(0)]` annotation on a stdlib dataclass field enforces nothing - ESTABLISHED.
48. Pydantic's documentation host has moved. `https://docs.pydantic.dev/latest/concepts/type_adapter/` and `https://docs.pydantic.dev/latest/errors/validation_errors/` both return HTTP 301 to `https://pydantic.dev/docs/validation/latest/...` (observed this session). Version-pinned paths such as `docs.pydantic.dev/2.6/migration/` still resolve. Every `docs.pydantic.dev/latest/...` citation in the manifest set is now a redirect. The date of the move could not be established - OPEN.
49. `assert expr, msg` compiles to `if __debug__: if not expr: raise AssertionError(msg)`. The reference manual: "the built-in variable `__debug__` is `True` under normal circumstances, `False` when optimization is requested (command line option `-O`). The current code generator emits no code for an `assert` statement when optimization is requested at compile time." Also: "Assignments to `__debug__` are illegal. The value for the built-in variable is determined when the interpreter starts" - ESTABLISHED.
50. `-O` is broader than "removes asserts". The CLI docs: "Remove assert statements **and any code conditional on the value of `__debug__`**. Augment the filename for compiled (bytecode) files by adding `.opt-1` before the `.pyc` extension." So `if __debug__: check_invariants(x)` also disappears - ESTABLISHED.
51. `-OO` does everything `-O` does "and also discard docstrings," with `.opt-2` bytecode naming. Any contract carried in a docstring - doctests, icontract/deal rendered documentation, a `Raises:` section a tool parses - is gone under `-OO`. `PYTHONOPTIMIZE`: "If this is set to a non-empty string it is equivalent to specifying the `-O` option. If set to an integer, it is equivalent to specifying `-O` multiple times" - ESTABLISHED.
52. The assert docs also state the design rule for messages: "it is unnecessary to include the source code for the expression that failed in the error message; it will be displayed as part of the stack trace." A message should add what the traceback lacks - values, intent, remediation - ESTABLISHED.
53. Design-by-contract libraries inherit the `-O` vanishing problem; they are not an escape from it. icontract: contracts respect `__debug__`, and running Python with `-O` or `-OO` disables all contracts. deal: "If you run Python with `-O` option, all contracts will be disabled. Under the hood, it's controlled by the `__debug__`". Neither icontract nor deal may therefore be the enforcement mechanism for a boundary or security check - ESTABLISHED.
54. `deal.ContractError` inherits from `AssertionError`. Subclasses: `PreContractError`, `PostContractError`, `InvContractError`, `ExampleContractError`, `RaisesContractError`, `ReasonContractError`, `MarkerError` (with `SilentContractError`, `OfflineContractError`), and `NoMatchError`. A blanket `except AssertionError` therefore swallows every deal violation - ESTABLISHED.
55. deal's runtime switches are `deal.disable()`, `deal.enable()`, `deal.reset()` (restores the default derived from `__debug__`), and `deal.activate()` for module-level checks. The permanent form is documented with a misspelled keyword: `deal.disable(permament=True)` - after which re-enabling "raises `RuntimeError`", and it must be called before importing decorated functions. Guessing `permanent=True` fails; the spelling is as documented at deal.readthedocs.io/basic/runtime.html - ESTABLISHED.
56. deal warns you if the on/off state looks wrong for the environment: "deal will emit a `RuntimeWarning` if you accidentally enable contracts in production or disable them in tests"; pass `warn=False` to suppress. Even when disabled non-permanently, "functions are still get wrapped in case you want to enable contracts again," so a residual per-call cost remains - ESTABLISHED.
57. deal's public decorators are `pre`, `post`, `ensure`, `inv`, `example`, `raises`, `reason`, `has`, `safe`, `chain`, `dispatch`, `pure`. `safe` is "Alias for `@deal.raises()`" and wraps "a function that never raises an exception". `pure` is documented as "Alias for `@deal.chain(deal.has(), deal.safe)`" - i.e. purity in deal means "no side effects declared and no exceptions raised", enforced at runtime only while contracts are enabled - ESTABLISHED.
58. icontract's decorators are `@icontract.require`, `@icontract.ensure`, `@icontract.invariant`, each taking `condition`, `description`, `enabled` and `error`. Postconditions receive a reserved `result` parameter. Violations raise `icontract.ViolationError` whose message includes "the human-readable representation of the condition", the description, and a "representation of all the values" - the most diagnosable violation message of any Python DbC library - ESTABLISHED.
59. icontract implements the Liskov rules: adding preconditions in a child class WEAKENS them ("The caller needs to provide either arguments that satisfy the preconditions associated with the function of the parent class *or* arguments that satisfy the preconditions of the function of the child class"), while postconditions and invariants are strengthened. Exception: "preconditions and postconditions of base classes are *not* inherited for the `__init__` method" - ESTABLISHED.
60. icontract has a second, orthogonal off-switch: `icontract.SLOW` "reflects the environment variable `ICONTRACT_SLOW`" and gates contracts meant to run only in development. A contract written `@require(lambda x: expensive(x), enabled=icontract.SLOW)` does not run in any environment where `ICONTRACT_SLOW` is unset - ESTABLISHED.
61. icontract 2.7.3 declares no Python floor (`requires_python` is `null`) and its classifiers stop at `Programming Language :: Python :: 3.13` - it does not advertise Python 3.14 support. deal 4.24.6 declares `>=3.8` and carries no per-version `Programming Language :: Python :: 3.x` classifiers at all. Neither project's metadata asserts 3.14/PEP 649 readiness. Whether either actually works on 3.14 was not determined - OPEN.
62. beartype's checking is O(1) by design and therefore does NOT validate whole containers. Its FAQ: wrapper functions are "guaranteed to unconditionally run in **O(1)** non-amortized worst-case time with negligible constant factors" because beartype performs "a one-way random walk over the expected data structure", doing a shallow isinstance check at each nesting level plus "a **deep type-check** that an item randomly selected from that container itself satisfies the first check". Over many calls it claims to cover all reachable children "in **O(n log n) calls**" (vendor-sourced claim, quoted verbatim) - ESTABLISHED.
63. typeguard's default is equally partial but for a different reason: `CollectionCheckStrategy` has members `FIRST_ITEM` ("check only the first item") and `ALL_ITEMS` ("check all items"), and the default of `TypeCheckConfiguration.collection_check_strategy` is `FIRST_ITEM`. `check_type(value, expected_type, *, forward_ref_policy=ForwardRefPolicy.WARN, typecheck_fail_callback=None, collection_check_strategy=CollectionCheckStrategy.FIRST_ITEM)`. A `list[int]` containing one int and nine strings passes typeguard's default check - ESTABLISHED.
64. beartype's own FAQ quantifies the contrast on a triply-nested list of 1000^3 integers: typeguard "~6,420 seconds (107 minutes)" checking every integer versus beartype "~13.8 microseconds" checking one random integer per call. This is a vendor-sourced claim by beartype about a competitor; treat as directional, not as measured in your workload - ESTABLISHED.
65. typeguard raises `TypeCheckError`, "Raised by typeguard's type checkers when a type mismatch is detected" - not `TypeError`. Its `ForwardRefPolicy` members are `ERROR` ("propagate the NameError when the forward reference lookup fails"), `WARN` ("emit a TypeHintWarning if the forward reference lookup fails") and `IGNORE` ("silently skip checks for unresolveable forward references"); the default is `WARN`, so an unresolvable annotation degrades to a warning and NO check - ESTABLISHED.
66. typeguard instruments by rewriting source: `@typechecked` "instruments functions by fetching the source code, parsing it to an abstract syntax tree using `ast.parse()`, modifying it to add type checking, and finally compiling the modified AST into byte code"; `install_import_hook()` does the same at import time. Two documented limitations: it "is not reliable when used in nested functions", and "You should always place this decorator closest to the original function, as it will not work when there is another decorator wrapping the function" - ESTABLISHED.
67. Annotations are no longer evaluated eagerly from 3.14. What's New: "The annotations on functions, classes, and modules are no longer evaluated eagerly. Instead, annotations are stored in special-purpose annotate functions and evaluated only when necessary (except if `from __future__ import annotations` is used)." PEP 649 is Status Final, Python-Version 3.14; PEP 749 ("Implementing PEP 649") is Status Final, Python-Version 3.14 - VERSION-DEPENDENT (3.14).
68. `annotationlib` (added 3.14) defines `Format` as an `IntEnum` with FOUR members: `VALUE = 1`, `VALUE_WITH_FAKE_GLOBALS = 2` ("only used internally and should not be passed to the functions in this module"), `FORWARDREF = 3`, `STRING = 4`. PEP 649's original third format `SOURCE` was renamed `STRING` by PEP 749; an agent citing `Format.SOURCE` or a three-member enum is wrong - VERSION-DEPENDENT (3.14).
69. `annotationlib.get_annotations(obj, *, globals=None, locals=None, eval_str=False, format=Format.VALUE)` "supersedes `inspect.get_annotations()`". The stdlib annotations HOWTO is explicit: "You should avoid accessing `__annotations__` directly on any object. Instead, use `annotationlib.get_annotations()` (Python 3.14+) or `inspect.get_annotations()` (Python 3.10+)" - VERSION-DEPENDENT (3.14).
70. `Format.FORWARDREF` returns "real annotation values ... for defined values, and `ForwardRef` proxies for undefined values. Real objects may contain references to `ForwardRef` proxy objects." A `ForwardRef` carries `__forward_arg__` (the source text) and `evaluate(*, owner=None, globals=None, locals=None, type_params=None, format=Format.VALUE)` - VERSION-DEPENDENT (3.14).
71. CPython 3.14's `dataclasses` module now reads annotations through `annotationlib`, in FORWARDREF format. The 3.14 source contains `import annotationlib` and `cls_annotations = annotationlib.get_annotations(cls, format=annotationlib.Format.FORWARDREF)`. Consequence: a dataclass field whose annotation names an undefined type is accepted at class-creation time and its annotation is a `ForwardRef`, not a type object - VERSION-DEPENDENT (3.14).
72. Because dataclasses see FORWARDREF-format annotations, `ClassVar`/`InitVar` detection remains partly textual and has a documented blind spot. The 3.14 source comments note that with string annotations `CV = ClassVar` at module level is detected, "But in this example cv1 will not be detected as a ClassVar" when the alias is bound inside the class body; solving it "would involve a eval() penalty for every single field of every dataclass that's defined. It was judged not worth it" - the module's own words call it a "fairly obscure corner case" - VERSION-DEPENDENT (3.14).
73. `dataclasses` raises `ValueError` for a mutable default, with the exact message `mutable default {type} for field {name} is not allowed: use default_factory`. The detection rule changed in 3.11: "Instead of looking for and disallowing objects of type `list`, `dict`, or `set`, unhashable objects are now not allowed as default values. Unhashability is used to approximate mutability." A custom mutable-but-hashable class therefore slips through as a shared default - VERSION-DEPENDENT (3.11).
74. Frozen stdlib dataclasses are emulation, not immutability. The docs open with "It is not possible to create truly immutable Python objects." `frozen=True` adds `__setattr__`/`__delattr__` that raise `FrozenInstanceError`, "a subclass of `AttributeError`". `object.__setattr__(inst, name, value)` bypasses the freeze entirely - and is exactly the mechanism the generated `__init__` itself uses: "`__init__()` cannot use simple assignment to initialize fields, and must use `object.__setattr__()`" - ESTABLISHED.
75. Setting derived attributes inside `__post_init__` on a `frozen=True` dataclass requires `object.__setattr__(self, name, value)`; plain assignment raises `FrozenInstanceError`. `__post_init__` is called by the generated `__init__`, so "If no `__init__()` method is generated, then `__post_init__()` will not automatically be called" - a dataclass declared `init=False` silently skips all `__post_init__` validation - ESTABLISHED.
76. Frozen-ness is not mixable across a dataclass hierarchy. CPython 3.14's `dataclasses.py` raises `TypeError` with exactly these messages: "cannot inherit non-frozen dataclass from a frozen one" and "cannot inherit frozen dataclass from a non-frozen one". Confirmed in the 3.14 source; the prose docs do not state this rule - ESTABLISHED.
77. The hash/eq/frozen truth table, verbatim: "If *eq* and *frozen* are both true, by default `@dataclass` will generate a `__hash__()` method for you. If *eq* is true and *frozen* is false, `__hash__()` will be set to `None`, marking it unhashable... If *eq* is false, `__hash__()` will be left untouched meaning the `__hash__()` method of the superclass will be used" - the last branch silently reintroduces id-based hashing on a value object - ESTABLISHED.
78. Defining `__setattr__` or `__delattr__` on a class you also decorate `@dataclass(frozen=True)` raises `TypeError`: "If `__setattr__()` or `__delattr__()` is defined in the class and *frozen* is true, then `TypeError` is raised" - ESTABLISHED.
79. pydantic `frozen=True` is "faux-immutable": it controls "whether `__setattr__` is allowed, and also generates a `__hash__()` method for the model. This makes instances of the model potentially hashable if all the attributes are hashable." Like dataclass frozen it is shallow - a frozen model holding a `list` field permits mutation of that list - ESTABLISHED.
80. Immutability depth summary across the four systems: none of stdlib frozen dataclass, `attrs.frozen`, pydantic `frozen=True`, or msgspec `frozen=True` is deep. All four block rebinding the attribute; none freezes the referenced object. Only `tuple`, `frozenset`, `str`, `bytes` and numbers are genuinely immutable containers/values, and even a `tuple` may hold mutable elements. Annotating a parameter `Mapping[str, int]` is a static promise only; the object may be a `dict` - ESTABLISHED.
81. "Parse, don't validate" (Alexis King, published 2019-11-05) states the mechanic precisely in terms of return type: `validateNonEmpty` "always returns `()`, the type that contains no information," whereas `parseNonEmpty` "returns `NonEmpty a`, a refinement of the input type that preserves the knowledge gained in the type system." A Python parse function must therefore return a NEW type that only the parser can construct - returning `None`, `bool`, or the same `dict` it received is validation, not parsing - ESTABLISHED.
82. The antipattern the essay names is "shotgun parsing": "a programming antipattern whereby parsing and input-validating code is mixed with and spread across processing code - throwing a cloud of checks at the input, and hoping, without any systematic justification, that one or another would catch all the 'bad' cases." Its maxims: make illegal states unrepresentable; push the burden of proof upward (get data into precise representations at the boundary before any processing); let your datatypes inform your code; and be suspicious of functions that return unit - ESTABLISHED.
83. Why annotations carry nothing at runtime, stated as a mechanism rather than a slogan: from 3.14 an annotation is a lazily-evaluated entry in an `__annotate__` function; nothing in the interpreter consults it on assignment, call, or return. Every runtime guarantee in Python comes from code that executes - a validator, a converter, a `__setattr__`, a decorator-generated wrapper - never from the annotation itself - ESTABLISHED.
84. Division of labour, in one line each. `dataclasses`: free boilerplate, zero runtime guarantee, zero dependency. `attrs`: boilerplate plus per-attribute converters/validators that also fire on assignment under `@define`, slots by default, globally disableable, no coercion of annotations. `pydantic BaseModel`/`TypeAdapter`/`pydantic.dataclasses`: full annotation-driven parse and coercion at the boundary with a structured `ValidationError`, lax by default, per-schema build cost. `msgspec.Struct`: fastest construction and typed decode with strict-by-default validation at decode/convert only, no validation at `__init__`. `cattrs`: converter-based structuring for attrs/dataclasses with PEP 654 grouped errors, keeping serialisation concerns out of the model - ESTABLISHED.
85. pydantic's headline speed claim is a 2023 comparison against its own v1: "Pydantic V2 is 5-50x faster than Pydantic V1," published 2023-04-03 in the v2 pre-release announcement. It is vendor-sourced, three years old as of today, and says nothing about pydantic's speed relative to msgspec, cattrs, or hand-written parsing. VENDOR-SOURCED; established only as a quotation - ESTABLISHED.
86. msgspec's published benchmark claims, all vendor-sourced and self-flagged: JSON serialise-plus-validate "~12x faster than pydantic V2 (2.5.2)", "~10x faster than cattrs (23.2.3)", "~6x faster than mashumaro (3.11)", "~85x faster than pydantic V1 (1.10.13)"; Struct creation "~4x faster than standard classes, attrs, dataclasses" and "~17x faster than pydantic"; equality "~4-30x"; ordering "~5-60x"; install size 0.46 MiB versus pydantic 6.71 MiB. Environment: "~2020 x86 Linux laptop, CPython 3.11". VENDOR-SOURCED throughout - ESTABLISHED.
87. msgspec states the bias caveat itself: "Benchmarks are *hard*" and "it's hard to write a nonbiased benchmark. I wrote msgspec, naturally whatever benchmark I publish it's going to perform well in." Note also that the pydantic version compared (2.5.2) predates 2.13.4 by roughly two and a half years, so the 12x figure cannot be quoted as current. VENDOR-SOURCED, and stale on its own terms - ESTABLISHED.
88. msgspec claims typed decoding is free relative to untyped decoding: "Specifying the expected types allows `msgspec` to perform validation during decoding, with *no* added runtime cost". VENDOR-SOURCED, unreproduced here - ESTABLISHED.
89. Python release status as of today, from devguide.python.org/versions: 3.14 - bugfix, first released 2025-10-07, EOL 2030-10; 3.13 - bugfix, first released 2024-10-07, EOL 2029-10; 3.12, 3.11, 3.10 - security-only; 3.9 - end-of-life (2025-10-31); 3.15 - prerelease, scheduled 2026-10-01, EOL 2031-10 - ESTABLISHED.

Free-threaded CPython is officially supported from 3.14 (PEP 779), with a single-threaded penalty "now roughly 5-10%, depending on the platform and C compiler used." msgspec's 0.20.0 notes record "Support Python 3.14, including freethreaded mode" (the msgspec half is VENDOR-SOURCED) - VERSION-DEPENDENT (3.14).

There will be more work required and there's going to be a lot more churn once everyone starts testing 3.14 earnestly." attrs 26.1.0 carries one backwards-incompatible change: "Field aliases are now resolved *before* calling `field_transformer`, so transformers receive fully populated `Attribute` objects with usable `alias` values instead of `None`" - ESTABLISHED.

Its own issue #610, "[Bug] CPython 3.14.2 + PEP 649 `annotationlib.ForwardRef` + PEP 484 self-reference = `TypeError: unhashable type: 'cell'`", was opened 2026-01-13 against beartype 0.22.9 and is now closed - but 0.22.9, uploaded 2025-12-13, is still the latest release on PyPI as of today, so no released beartype contains the fix. Both halves were independently confirmed; the maintainer's release timeline for the fix is OPEN - ESTABLISHED.

95. `from __future__ import annotations` is not removed in 3.14 but is on a deprecation path: per PEP 749 it continues to work in 3.14; it becomes a `DeprecationWarning` after 3.13 reaches EOL; and it raises `SyntaxError` two releases after that. Mixing it with runtime validation libraries also produces the double-quoting footgun documented in the annotations HOWTO: with the future import, `def foo(a: "str")` yields `{'a': "'str'"}` - the annotation "is quoted *twice*" - VERSION-DEPENDENT (3.14+).
96. typeguard 4.6.0 (2026-07-26) "Dropped support for Python 3.9" and "Fixed compatibility with Python 3.15", and added "support for type checking against the PEP 661 `sentinel` type" plus a `typeguard-packages-ignore` pytest-plugin option. 4.5.0 (2026-02-15) "Restored the `check_argument_types()` and `check_return_type()` functions that were dropped in v3.0.0", added `extra_items` TypedDict support, and "Fixed `NameError` when evaluating forward references on Python 3.14" - VERSION-DEPENDENT (typeguard 4.5/4.6).
97. Converting library validation errors into a project taxonomy has exactly three shapes to handle, and they are not alike: pydantic gives ONE `ValidationError` carrying a LIST of machine-readable dicts (`type`/`loc`/`msg`/`input`/`ctx`/`url`); cattrs gives a PEP 654 `ExceptionGroup` (`ClassValidationError`/`IterableValidationError`) requiring `except*` or `.exceptions` traversal; msgspec gives ONE `ValidationError` (also a `ValueError`) with the path rendered into the message string and no structured fields. A single boundary adapter must therefore special-case all three, not catch a common base - ESTABLISHED.
98. To keep validation messages machine-readable, the stable identity must be the `type`/error-code field, never the prose. pydantic's `type` is "A computer-readable identifier of the error type" and `PydanticCustomError(error_type, message_template, context)` lets you mint your own; `msg` and its localised rendering are explicitly the human channel. pydantic's own recommended customisation route is post-processing `ValidationError.errors()` and rewriting the `'msg'` field, leaving `type` untouched - ESTABLISHED.
99. `loc` is a list and its element types are heterogeneous - `str` for model/dict keys, `int` for sequence indices, and for tagged unions the tag value appears as a segment. Joining `loc` with `"."` unconditionally produces wrong paths for list indices; render it as a structured array in machine output. The list structure is per pydantic's docs ("The error's location as a list"); the exhaustive set of segment kinds was not confirmed - OPEN.
100. A parse boundary that is honest about all of the above has four obligations: (a) return a distinct type the caller could not have forged; (b) raise from the project's own taxonomy, not the library's, so swapping pydantic for msgspec is not a breaking API change; (c) preserve the library error as `__cause__` via `raise ProjectError(...) from exc` so the machine-readable detail survives; (d) contain zero `assert` statements, because `-O` deletes them and pydantic will additionally swallow the resulting `AssertionError` into a passing validation. Each component is confirmed above - ESTABLISHED.

**"The four-way boundary-library decision table"** — destination: `python_typing_contract_manifest.md` (new subsection under §5).
A single table with rows for stdlib `dataclasses`, `attrs`, `pydantic` (BaseModel/TypeAdapter/pydantic.dataclasses), `msgspec.Struct` and `cattrs`, and columns for: validates at construction? validates on assignment? coerces by default? rejects unknown keys by default? error shape; dependency weight; where it belongs. The load-bearing cells are the counter-intuitive ones: attrs is the only one that validates on assignment by default (`@define`); msgspec is the only one strict by default; pydantic is the only one that validates at construction; pydantic's `extra` default is `'ignore'` and msgspec's `forbid_unknown_fields` default is `False`, so both silently drop unknown keys unless configured. Close with the rule: pick ONE boundary library per project and wrap it behind a project-owned parse function.

**"The `-O` / `-OO` enforcement audit"** — destination: `error_tracing_contract_manifest.md` (expand §14).
Enumerate everything the optimisation flags delete and who else opts into `__debug__`: bare `assert`; `if __debug__:` blocks; docstrings and therefore doctests under `-OO`; all icontract contracts; all deal contracts. Then the sting: pydantic converts `AssertionError` from a validator into `ValidationError`, so `assert` inside a validator becomes a silent pass rather than a loud failure. Give the audit as a greppable checklist and a one-line policy: production images are built and run WITHOUT `-O`, and no check that must survive is expressed as `assert`, `if __debug__:`, or a DbC decorator.

**"Converting library validation errors into the project taxonomy"** — destination: `error_tracing_contract_manifest.md` (new section between §15 and §16).
The adapter pattern for each of the three live error shapes. pydantic: catch `ValidationError`, call `.errors(include_url=False)`, map each `type` to a project error code, keep `loc` as a structured array (never `".".join(loc)` — indices are ints), re-raise as the project error with `from exc`. cattrs: the default is a PEP 654 group, so use `except*` or walk `.exceptions`, flattening to the same code/path/message triple. msgspec: catch `msgspec.ValidationError` (note it is also a `ValueError`) and accept that the path arrives inside the message string. State the invariant: the project's error taxonomy is public API and must not leak the boundary library's exception types.

**"Parse functions: signature, return type, and the forgery test"** — destination: `error_tracing_contract_manifest.md` (expand §15).
Ground the slogan in King's actual mechanic: validation returns unit, parsing returns "a refinement of the input type that preserves the knowledge gained in the type system." A Python parse function therefore returns a distinct type — a frozen dataclass, an `attrs.frozen` class, a msgspec Struct, a pydantic model — never `bool`, `None`, or the input `dict`. Apply the forgery test: if arbitrary code elsewhere can construct the return type without going through the parser, the type carries no proof. Name the leaks that fail the test: `model_construct()`, `object.__setattr__`, `NewType` (a no-op callable), `cast` (returns its argument unchanged), and plain attribute assignment on a pydantic model with `validate_assignment=False`.

**"Runtime type-checkers are samplers, not validators"** — destination: NEW: `python_runtime_typecheck_manifest.md`.
beartype and typeguard look like they enforce annotations but check only a sample. beartype is explicitly O(1) via "a one-way random walk", checking one randomly selected item per container per call. typeguard's default `collection_check_strategy` is `CollectionCheckStrategy.FIRST_ITEM` — literally the first element. Both are development-time defect detectors and API-contract smoke tests, not boundary validators; neither replaces a parse step. Cover the operational hazards: typeguard's `ForwardRefPolicy` default is `WARN`, so an unresolvable annotation degrades to no check; `@typechecked` rewrites source via `ast.parse` and breaks under an outer decorator and in nested functions; and beartype 0.22.9 (2025-12-13) still fails at decoration time on 3.14 self-referential annotations despite the fix having landed in trunk.

**"3.14 annotation evaluation and the libraries that read annotations"** — destination: `python_typing_contract_manifest.md` (new subsection under §8), or NEW: `python_annotations_runtime_manifest.md` if it outgrows a subsection.
PEP 649 + PEP 749: annotations become lazy `__annotate__` functions; the four `annotationlib.Format` members with `SOURCE` renamed to `STRING`; `annotationlib.get_annotations()` supersedes `inspect.get_annotations()`; never touch `__annotations__` directly. Then the downstream consequences a coding agent must anticipate: CPython's own `dataclasses` now reads FORWARDREF-format annotations, so undefined field types no longer error at class creation; `ClassVar` detection retains a documented textual blind spot for class-body aliases; pydantic still resolves eagerly and falls back to `model_rebuild()`; `if TYPE_CHECKING:` imports still produce `NameError` on any VALUE-format resolution; and `from __future__ import annotations` is on a three-stage path to `SyntaxError`.

**"Immutability depth, and the four bypasses"** — destination: `python_typing_contract_manifest.md` (expand §6).
All four frozen mechanisms are shallow and each raises a different exception: stdlib `FrozenInstanceError` (a subclass of `AttributeError`), attrs `FrozenInstanceError`, pydantic's `ValidationError` family on assignment, msgspec plain `AttributeError: immutable type: 'Point'`. Document the bypasses: `object.__setattr__` (which the generated frozen `__init__` uses itself), mutable field contents, `__post_init__` on a frozen class needing `object.__setattr__`, and `init=False` skipping `__post_init__` entirely. Add the inheritance rule with CPython's exact messages ("cannot inherit non-frozen dataclass from a frozen one" / "cannot inherit frozen dataclass from a non-frozen one") and the eq/frozen/`__hash__` truth table, including the `eq=False` branch that silently restores id-based hashing on a value object.

## Traps for coding agents

1. **`assert` inside a pydantic validator fails OPEN, not closed.** pydantic builds its `ValidationError` from `ValueError` or `AssertionError` raised in validators. Under `-O` the `assert` is removed from the bytecode, so no `AssertionError` is raised, so validation PASSES. The agent gets a validator that looks correct, tests green, and admits invalid data in any optimised deployment. pydantic's own docs carry the warning. Always `raise ValueError(...)` or `PydanticCustomError(...)`.
2. **icontract and deal are disabled by default in production.** An agent asked to "enforce a precondition" will reach for `@deal.pre` or `@icontract.require` and believe it has built enforcement. Both are gated on `__debug__` and vanish under `-O`; deal's own docs say so. They are executable documentation and test-time oracles, not enforcement.
3. **`deal.disable(permament=True)` — the keyword is misspelled in deal's own API.** `permanent=True` is a `TypeError`. Confirmed at deal.readthedocs.io/basic/runtime.html.
4. **`deal.ContractError` subclasses `AssertionError`.** A boundary handler written `except AssertionError:` to "catch programmer errors" also catches every deal contract violation, and vice versa — a `pytest.raises(AssertionError)` test passes for the wrong reason.
5. **msgspec is strict by default; pydantic is lax by default.** They are mirror images. `msgspec.json.decode(b'{"n":"3"}', type=M)` raises where `M.model_validate({"n":"3"})` succeeds and coerces. An agent that ports code between them without setting `strict=` / `ConfigDict(strict=True)` silently changes the acceptance set of the API.
6. **A `msgspec.Struct` constructor validates nothing.** `Point(x="not a number")` succeeds. Types "are only checked when decoding a serialized message when using a typed decoder." An agent that uses Structs as internal value objects and assumes annotation enforcement is wrong; only the decode/convert path checks. (`__post_init__` does run on decode and convert, which is where Struct invariants belong.)
7. **pydantic `validate_assignment` defaults to `False`.** A validated model can be walked into an invalid state one attribute at a time, immediately after a successful parse. The parse boundary guarantees the object at construction only.
8. **pydantic `validate_default` defaults to `False`.** A field default that violates its own `Field(gt=0)` constraint is never checked. The bug appears only for callers who omit the field.
9. **pydantic `revalidate_instances` defaults to `'never'`.** Passing an already-constructed model instance (including a subclass carrying extra state) as a nested field skips validation entirely. An agent building a trust boundary around "everything goes through the model" has a hole here.
10. **pydantic `extra` defaults to `'ignore'` and msgspec's `forbid_unknown_fields` defaults to `False`.** Neither rejects unknown input keys out of the box. A typo'd config key is silently dropped rather than reported — the single most common cause of "my setting had no effect".
11. **`model_construct()` skips ALL validation by design.** It is easy to reach for as a performance fix and it deletes the boundary. pydantic's guidance: use it "only ... with data which has already been validated, or that you definitely trust."
12. **`Annotated` validator order is right-to-left for *before*/*wrap* and left-to-right for *after*.** An agent stacking `BeforeValidator`s and expecting reading order gets them reversed.
13. **`@model_validator` has no `mode='plain'`.** Only `before`, `after`, `wrap`. `@field_validator` has all four.
14. **In a pydantic dataclass, `__post_init__` runs in the MIDDLE** — "between the calls to *before* and *after* model validators" — not last as in stdlib dataclasses. Cross-field invariants placed there can still be invalidated by an after-validator.
15. **`typing.Final`, `@final`, `cast`, `NewType`, `TYPE_CHECKING`, `TypedDict`, `Literal` and `Annotated` are all runtime no-ops** for enforcement purposes. `Final`: "There is no runtime checking of these properties." `cast`: "This returns the value unchanged." `NewType`: "`some_value is Derived(some_value)` is always true at runtime." `TypedDict` is a plain `dict`. `Annotated[T, x]` metadata is ignored by tools without special logic for `x`. An agent that "adds type safety" with these has added documentation.
16. **`@runtime_checkable` checks member PRESENCE only** — "not their type signatures or types" — and `isinstance()` against a protocol "can be surprisingly slow". `issubclass()` additionally fails for protocols with non-method members ("`issubclass()` can be used only with non-data protocols"). Using a runtime-checkable Protocol as a validation gate accepts any object with the right attribute names.
17. **`if TYPE_CHECKING:` imports do not exist at runtime.** Names imported there and used in a pydantic annotation, a `TypeAdapter` target, or any VALUE-format annotation resolution raise `NameError`. Pydantic's escape hatch is `model_rebuild(_types_namespace=...)`.
18. **beartype and typeguard do not validate containers.** beartype checks one randomly selected item per container per call (O(1) by design); typeguard's default `collection_check_strategy` is `FIRST_ITEM`. A `list[int]` of one int and nine strings passes both defaults. Neither is a boundary validator.
19. **typeguard's `ForwardRefPolicy` default is `WARN`** — "emit a TypeHintWarning if the forward reference lookup fails". An unresolvable annotation silently becomes NO check rather than an error.
20. **`@typechecked` must be innermost.** "it will not work when there is another decorator wrapping the function", and it "is not reliable when used in nested functions" because it recovers the function object via the garbage collector.
21. **beartype 0.22.9 breaks at IMPORT time on Python 3.14 self-referential annotations.** Issue #610 (`TypeError: unhashable type: 'cell'`) is closed in trunk, but 0.22.9 (2025-12-13) is still the newest release, so no released version carries the fix. Pinning beartype on a 3.14 target is a live risk.
22. **`-O` removes more than asserts:** "any code conditional on the value of `__debug__`" goes too. **`-OO` discards docstrings**, which deletes every doctest and every docstring-carried contract. Neither is recoverable at runtime.
23. **`__debug__` cannot be set.** "Assignments to `__debug__` are illegal. The value for the built-in variable is determined when the interpreter starts." There is no runtime toggle for assert behaviour.
24. **A frozen dataclass's own `__init__` uses `object.__setattr__`.** The bypass is not exotic — it is the documented implementation. Never describe `frozen=True` as immutability; it is "emulate[d]", and "It is not possible to create truly immutable Python objects."
25. **`__post_init__` does not run when `init=False`.** "If no `__init__()` method is generated, then `__post_init__()` will not automatically be called." A dataclass built entirely by a classmethod factory with `init=False` skips every validation an agent put in `__post_init__`.
26. **Mutable-default detection is hashability-based since 3.11**, not type-based: "unhashable objects are now not allowed as default values. Unhashability is used to approximate mutability." A custom class that is mutable but defines `__hash__` sails through and is shared across all instances. Exact error when caught: `mutable default {type} for field {name} is not allowed: use default_factory`.
27. **Frozen-ness cannot be mixed in a dataclass hierarchy.** CPython raises `TypeError` with "cannot inherit non-frozen dataclass from a frozen one" and "cannot inherit frozen dataclass from a non-frozen one" — a common failure when wrapping a third-party frozen dataclass.
28. **`eq=False` leaves `__hash__` untouched**, falling back to the superclass's — id-based hashing on what the agent intended as a value object. Only `eq=True, frozen=True` generates a value-based `__hash__`; `eq=True, frozen=False` sets `__hash__ = None`.
29. **attrs validators run on assignment under `@define`/`@frozen` but not under legacy `@attr.s`.** Porting between the two decorator families silently changes when checks fire.
30. **attrs validators can be turned off globally** by `attrs.validators.set_disabled(True)` anywhere in the process. Never treat an attrs validator as a security or boundary guarantee.
31. **attrs converters run BEFORE validators.** "Converters are run before validators, so you can use validators to check the final form of the value." An agent writing a validator to reject the raw input form will find the converter has already transformed it.
32. **`slots` defaults differ:** `attrs.define` is `slots=True`, stdlib `@dataclass` is `slots=False`. Code that monkey-patches an attribute onto an attrs instance fails where it worked on a dataclass.
33. **cattrs raises an ExceptionGroup by default.** Detailed validation "is enabled by default" and errors arrive as `cattrs.ClassValidationError` / `cattrs.IterableValidationError`, both PEP 654 groups. A handler written `except cattrs.ClassValidationError as e: log(e)` loses every nested cause; use `except*` or walk `.exceptions`.
34. **msgspec's error path is a string, not a field.** The location arrives rendered into the message (`... - at $.groups[1]`). There is no `loc` list to consume — unlike pydantic. Machine-readable output requires parsing prose or wrapping at the field level.
35. **`msgspec.DecodeError` is also a `ValueError`.** Convenient for a broad boundary catch, dangerous for a narrow one: `except ValueError` around a decode call also swallows unrelated `ValueError`s from your own code.
36. **`TypeAdapter` construction is the hidden cost.** Building one inside a request handler pays full schema analysis per request. Hoist to module scope. `dump_json()` returns bytes while `BaseModel.model_dump_json()` returns str — an easy `TypeError` when the two are used interchangeably.
37. **Pydantic generic dataclasses do not validate their parameters:** "Pydantic currently treats `Foo[int]` the same as `Foo[Any]`, without performing validation." Generic `BaseModel`s do. An agent that reaches for a generic pydantic dataclass loses the check silently.
38. **`annotationlib.Format` has four members and the third is named `STRING`, not `SOURCE`.** PEP 649 proposed `SOURCE`; PEP 749 renamed it. `VALUE_WITH_FAKE_GLOBALS` is internal and "should not be passed to the functions in this module".
39. **On 3.14, a dataclass field annotated with an undefined name no longer errors at class creation**, because `dataclasses` fetches annotations with `Format.FORWARDREF`. The failure moves to whoever later resolves the annotation — a runtime validator, a schema generator — often far from the definition.
40. **`ClassVar` detection in dataclasses is partly textual and has a documented blind spot**: an alias bound inside the class body (`CV = ClassVar` in class scope) is not recognised, and CPython judged fixing it "not worth it" because it "would involve a eval() penalty for every single field of every dataclass". Such a field becomes a real, per-instance dataclass field.
41. **`from __future__ import annotations` double-quotes explicit string annotations**: `def foo(a: "str")` yields `{'a': "'str'"}`. It also remains on a deprecation path to `SyntaxError` two releases after 3.13's EOL. Do not add it to new 3.14+ code.
42. **`docs.pydantic.dev/latest/...` now 301-redirects to `pydantic.dev/docs/validation/latest/...`.** Any tool or agent that treats a non-200 as a dead link will report pydantic's documentation as missing.
43. **Vendor benchmarks compare against stale competitors.** msgspec's "~12x faster than pydantic V2" is measured against pydantic 2.5.2 on CPython 3.11; today's pydantic is 2.13.4. msgspec itself says "it's hard to write a nonbiased benchmark. I wrote msgspec, naturally whatever benchmark I publish it's going to perform well in." Never quote either vendor's multiplier as a current fact.
44. **`annotated-types` enforces nothing.** `Annotated[int, Gt(0)]` on a stdlib dataclass or an attrs field is inert metadata: the library "avoids runtime checks for performance" and "It is up to the implementer to determine how this metadata is used." Only pydantic/msgspec-style consumers act on it.
45. **icontract declares no Python floor and no 3.14 classifier**; deal declares no per-version classifiers at all. Dependency resolvers will happily install both on 3.14 without any compatibility signal.
