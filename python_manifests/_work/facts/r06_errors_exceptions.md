## Facts

### Version matrix of the exception machinery

1. PEP 654 (`ExceptionGroup`, `BaseExceptionGroup`, `except*`) is Final with header `Python-Version: 3.11`, created 2021-02-22, accepted by Thomas Wouters 2021-09-24 - VERSION-DEPENDENT (3.11).
2. PEP 678 (`BaseException.add_note`, `__notes__`) is Final with header `Python-Version: 3.11`, created 2021-12-20 - VERSION-DEPENDENT (3.11).
3. PEP 657 (fine-grained error locations - the tilde/caret markers that underline the offending sub-expression) is Final with header `Python-Version: 3.11`, created 2021-05-08 - VERSION-DEPENDENT (3.11).
4. PEP 657 exposes locations as `code.co_positions()`, yielding four-tuples `(start_line, end_line, start_column, end_column)` per instruction (or `None`), and C-level `PyCode_Addr2Location()` - VERSION-DEPENDENT (3.11).
5. The PEP 657 location tables cost roughly 22% additional `.pyc` size (CPython stdlib measured 28.4 MB to 34.7 MB) and are suppressed by `-X no_debug_ranges` or the `PYTHONNODEBUGRANGES` environment variable, both added in 3.11; suppressing them also removes the visual column markers from every traceback - VERSION-DEPENDENT (3.11).
6. Tracebacks are colourised by default in the terminal from 3.13; the `traceback` module docs carry "Added in version 3.13: Output is colorized by default" - VERSION-DEPENDENT (3.13).
7. Colour control precedence is exactly `PYTHON_COLORS` > `NO_COLOR` > `FORCE_COLOR` > `TERM`; `PYTHON_COLORS=1` forces colour on and `0` off (added 3.13), `TERM=dumb` disables colour, and `NO_COLOR` disables all colour and "takes precedence over FORCE_COLOR" - VERSION-DEPENDENT (3.13).
8. 3.14 extends colour beyond tracebacks: the default interactive shell highlights Python syntax (disabled by `PYTHON_BASIC_REPL` or any colour-disabling variable), and `argparse` help, `calendar`, and `json` CLI output are coloured by default - VERSION-DEPENDENT (3.14).
9. 3.15 (rc1) colourises **unraisable exceptions** by default (gh-134170), plus `ast`, `pickletools`, `tokenize`, `sqlite3`, `timeit` and `http.server` CLI/log output, and `python --help` - VERSION-DEPENDENT (3.15).
10. PEP 758 shipped in 3.14: `except TimeoutError, ConnectionRefusedError:` (no parentheses) is legal for both `except` and `except*`. `except A, B as e:` remains a SyntaxError - "When using the `as` clause to capture the exception instance parentheses must be used as before." - VERSION-DEPENDENT (3.14).
11. PEP 765 shipped in 3.14: the compiler emits a `SyntaxWarning` when a `return`, `break` or `continue` appears in a `finally` block. The reference docs carry "Changed in version 3.14: The compiler emits a SyntaxWarning when a return, break or continue appears in a finally block (see PEP 765)." The PEP explicitly leaves "whether, and when, this will become a SyntaxError" open - VERSION-DEPENDENT (3.14).
12. PEP 768 shipped in 3.14: `sys.remote_exec(pid, script)` schedules a Python file for execution in another live process at an interpreter safe point, and `python -m pdb -p 1234` attaches to a running process. Opt out with `-X disable_remote_debug`, `PYTHON_DISABLE_REMOTE_DEBUG` (non-empty string), or build with `--without-remote-debug` - VERSION-DEPENDENT (3.14).
13. `sys.remote_exec` requires the remote interpreter to match the local one in major.minor, and "If either the local or remote interpreter is pre-release (alpha, beta, or release candidate) then the local and remote interpreters must be the same exact version." It raises audit events `sys.remote_exec` locally and `cpython.remote_debugger_script` in the target - VERSION-DEPENDENT (3.14).
14. 3.14 added asyncio task-graph introspection usable against a live process: `python -m asyncio ps PID`, `python -m asyncio pstree PID`, plus `asyncio.capture_call_graph()` and `asyncio.print_call_graph()` - VERSION-DEPENDENT (3.14).
15. 3.15 (rc1) adds `asyncio.TaskGroup.cancel()` "to allow early termination of a task group, eliminating the need for unintuitive boilerplate involving custom exceptions" (gh-127214). It does not exist in 3.14 - VERSION-DEPENDENT (3.15).
16. 3.15 (rc1) lets `sys.monitoring` enable and disable `PY_THROW`, `PY_UNWIND`, `RAISE`, `EXCEPTION_HANDLED` and `RERAISE` per code object, and returning `DISABLE` from a callback now disables the event for that code object instead of raising `ValueError` (gh-146182) - VERSION-DEPENDENT (3.15).
17. 3.15 (rc1) improves `AttributeError` suggestions: it proposes reachable nested attributes ("Did you mean '.inner.area' instead of '.area'?"), suggests Python equivalents for JavaScript/Java/Ruby/C# method names on builtins (`[1,2,3].push(4)` gives "Did you mean '.append'?"), and suggests names for `delattr` / `del obj.x` (gh-136588). `ImportError.__repr__` and `ModuleNotFoundError.__repr__` now render `name=<name>` and `path=<path>` (gh-74185) - VERSION-DEPENDENT (3.15).
18. PEP 810 (3.15, Final, resolved 2025-11-03) makes a failed lazy import surface at **first use of the name**, not at the import statement; the exception type is unchanged (`ImportError`, `ModuleNotFoundError`, `SyntaxError`) but "The exception is enhanced with chaining to show both where the lazy import was defined and where it was accessed". Controlled by `-X lazy_imports=normal|all|none`, `PYTHON_LAZY_IMPORTS`, `sys.set_lazy_imports()`; `lazy` is a soft keyword valid only at module level - VERSION-DEPENDENT (3.15).
19. `sys.exception()` (3.11) returns the instance handled by the innermost active handler, or `None`; `sys.exc_info()` is now derived from that instance, so mutating a handled exception is reflected in later `exc_info()` calls (changed 3.11). `sys.last_exc` (3.12) supersedes the deprecated `sys.last_type` / `sys.last_value` / `sys.last_traceback` - VERSION-DEPENDENT (3.11/3.12).

### except-star semantics agents get wrong

20. A `try` statement "can have either `except` or `except*` clauses, but not both" - mixing them is a SyntaxError, not a runtime error - ESTABLISHED.
21. `except*:` with no type is a SyntaxError: "The exception type for matching is mandatory in the case of `except*`" - ESTABLISHED.
22. Naming a group type in `except*` is a **runtime `TypeError`**, not a syntax error: "A TypeError is raised if a matching type is a subclass of BaseExceptionGroup, because that would have ambiguous semantics." This includes user subclasses of `ExceptionGroup` - ESTABLISHED.
23. Each `except*` clause runs at most once and receives a **subgroup**, produced by `split()`: "each `except*` clause splits it into the subgroups of matching and non-matching exceptions. If the matching subgroup is not empty, it becomes the handled exception ... and assigned to the target". The non-matching remainder is passed to the next `except*` clause - ESTABLISHED.
24. The `as` target of an `except*` clause is **always a group**, never a leaf: "If the exception raised from the try block is not an exception group and its type matches one of the `except*` clauses, it is caught and wrapped by an exception group with an empty message string. This ensures that the type of the target `e` is consistently BaseExceptionGroup." Leaves live in `e.exceptions` - ESTABLISHED.
25. `break`, `continue` and `return` "cannot appear in an `except*` clause" (SyntaxError), because "the exceptions in an ExceptionGroup are assumed to be independent, and the presence or absence of one of them should not impact handling of the others" - ESTABLISHED.
26. Leftovers propagate automatically: "After all `except*` clauses execute, the group of unhandled exceptions is merged with any exceptions that were raised or re-raised from within `except*` clauses. This merged exception group propagates on." There is nothing to re-raise by hand - ESTABLISHED.
27. `except Exception` catches `ExceptionGroup` but **not** `BaseExceptionGroup`: "This design is so that `except Exception` catches an ExceptionGroup but not BaseExceptionGroup." - ESTABLISHED.
28. `ExceptionGroup(msg, excs)` "raises a TypeError if any contained exception is not an Exception subclass"; `BaseExceptionGroup(msg, excs)` "returns an ExceptionGroup rather than a BaseExceptionGroup if all contained exceptions are Exception instances" - so the constructor you call is not necessarily the type you get - ESTABLISHED.
29. Members of a group must be **instances, not types**; the docs state this explicitly and give the accumulate-then-raise pattern (`excs.append(e)` in a loop, then `raise ExceptionGroup("Test Failures", excs)`) - ESTABLISHED.
30. `subgroup(condition)` and `split(condition)` accept an exception type or tuple of types; a **callable** condition is accepted only from 3.13 ("Added in version 3.13: condition can be any callable which is not a type object"). They preserve nesting, omit empty nested groups, and copy `__traceback__`, `__cause__`, `__context__` and `__notes__` onto the derived group - VERSION-DEPENDENT (3.13).
31. `derive(excs)` must be overridden for a group **subclass** to survive `split` / `subgroup`; `BaseExceptionGroup` defines `__new__`, so a subclass needing a different constructor signature must override `__new__`, not `__init__` - ESTABLISHED.
32. Exception groups "are generic over the type of their contained exceptions", so `except* ValueError as e` gives a type checker an `ExceptionGroup[ValueError]`-shaped binding - ESTABLISHED.
33. `asyncio.TaskGroup` is the canonical group producer: on the first non-`CancelledError` failure "the remaining tasks in the group are cancelled", and surviving non-`CancelledError` exceptions "are combined in an ExceptionGroup or BaseExceptionGroup (as appropriate) which is then raised" from `__aexit__`. The `CancelledError` raised by that sibling cancellation is not a member of the group - ESTABLISHED.
34. TaskGroup treats two base exceptions specially: "If any task fails with KeyboardInterrupt or SystemExit, the task group still cancels the remaining tasks and waits for them, but then the initial KeyboardInterrupt or SystemExit is re-raised instead of ExceptionGroup or BaseExceptionGroup" - ESTABLISHED.
35. `contextlib.suppress` became group-aware in 3.12: "If the code within the with block raises a BaseExceptionGroup, suppressed exceptions are removed from the group. Any exceptions of the group which are not suppressed are re-raised in a new group which is created using the original group's derive() method." Before 3.12 it did not look inside groups - VERSION-DEPENDENT (3.12).
36. A `@contextlib.contextmanager` generator sees the exception re-raised at the `yield`; if it catches it only to log, "the generator must reraise that exception. Otherwise the generator context manager will indicate to the `with` statement that the exception has been handled" - a silent swallow - ESTABLISHED.
37. `except*` is syntax and therefore cannot be backported. On < 3.11 the `exceptiongroup` package requires the callback form: "Due to the lack of the `except*` syntax introduced by PEP 654 in earlier Python versions, you need to use `exceptiongroup.catch()`", whose argument "must be a dict (or any Mapping) where each key is either an exception class or an iterable of exception classes" mapping to a one-argument callable - ESTABLISHED.
38. `exceptiongroup` 1.3.1 is a no-op on modern interpreters: "If this package is imported on Python 3.11 or later, the built-in implementations of the exception group classes are used instead, TracebackException is not monkey patched and the exception hook won't be installed." Its `requires-python` is `>=3.7` - ESTABLISHED.

### Chaining

39. `raise X from Y` requires `Y` to be an exception instance, an exception class (instantiated for you), or `None`; it sets `X.__cause__` (writable) and, as a side effect, `__suppress_context__ = True` - ESTABLISHED.
40. `__context__` is set automatically whenever a new exception is raised while another is being handled, and "An exception may be handled when an `except` or `finally` clause, or a `with` statement, is used" - not only inside `except` - ESTABLISHED.
41. Rendering: `__cause__` prints as "The above exception was the direct cause of the following exception."; `__context__` prints as "During handling of the above exception, another exception occurred." and **only** when `__cause__` is `None` and `__suppress_context__` is false - ESTABLISHED.
42. `raise New(...) from None` "effectively replaces the old exception with the new one for display purposes (e.g. converting KeyError to AttributeError), while leaving the old exception available in `__context__` for introspection when debugging" - the original is hidden, not destroyed - ESTABLISHED.
43. A bare `raise` re-raises "the exception that is currently being handled, which is also known as the active exception"; with no active exception it raises `RuntimeError` - ESTABLISHED.
44. `raise Other(...).with_traceback(tb)` converts an exception type while keeping the original traceback; the current frame is then pushed onto the new exception's traceback - ESTABLISHED.
45. `add_note(note)` appends to `__notes__`, raises `TypeError` if `note` is not a `str`, and `__notes__` "is created when `add_note()` is called" - reading `exc.__notes__` before any `add_note` raises `AttributeError`. Notes render "immediately after the exception message, in the order in which they were added, with each note starting on a new line". `del err.__notes__` clears them - ESTABLISHED.
46. `traceback.format_exception_only()` includes `__notes__` since 3.11; `TracebackException` exposes `__notes__` (3.11) and `exceptions` (3.11), and gained `show_group=` on `format_exception_only()` in 3.13 to render nested group members recursively with indentation by depth - VERSION-DEPENDENT (3.11/3.13).
47. `TracebackException.exc_type` is deprecated since 3.13 in favour of the string `exc_type_str`; the constructor gained `save_exc_type` (default `True`) - VERSION-DEPENDENT (3.13).
48. Group rendering is truncated by default: `TracebackException(..., max_group_width=15, max_group_depth=10)`, and "The formatted output is truncated when either limit is exceeded." A 200-member group does not print in full - VERSION-DEPENDENT (3.11).
49. `sys.tracebacklimit` "determines the maximum number of levels of traceback information printed... The default is 1000. When set to 0 or less, all traceback information is suppressed and only the exception type and value are printed" - ESTABLISHED.

### The two propagation channels and exhaustiveness

50. There is no stdlib `Result` / `Either`. `typing.Never` and `typing.assert_never` are the stdlib exhaustiveness primitives: `Never` added 3.11, `NoReturn` added 3.6.2, and "Never and NoReturn have the same meaning in the type system and static type checkers treat both equivalently" - VERSION-DEPENDENT (3.11).
51. `typing.assert_never` is in `typing` since 3.11 and in `typing_extensions` since 4.1.0; `typing.assert_type` since 3.11 / `typing_extensions` 4.2.0 - VERSION-DEPENDENT (3.11).
52. At runtime `assert_never` raises `AssertionError(f"Expected code to be unreachable, but got: {value}")` where `value = repr(arg)` truncated at `_ASSERT_NEVER_REPR_MAX_LENGTH = 100` characters plus an ellipsis (CPython 3.14 `Lib/typing.py`). Its docstring: "If a type checker finds that a call to assert_never() is reachable, it will emit an error. At runtime, this throws an exception when called." - ESTABLISHED.
53. Writing `assert False` or a hand-rolled `raise AssertionError` in the fallback branch loses the static guarantee: "we would not get the benefits of exhaustiveness checking" because "the type checker will not warn us" - ESTABLISHED.
54. Checker-native exhaustiveness exists but is opt-in in mypy: error code `exhaustive-match`, "If enabled with `--enable-error-code exhaustive-match`, mypy generates an error if a match statement does not match all possible cases/types", shipped in mypy 1.17 (2025-07-14). pyright has `reportMatchNotExhaustive`, enabled by default in strict mode - VERSION-DEPENDENT (mypy 1.17+).
55. `returns` (dry-python) 0.29.0, released 2026-08-02, carries `Development Status :: 4 - Beta`, requires `Python <4.0, >=3.11` (3.10 support dropped in 0.27.0), and supplies `Result`, `Maybe`, `IO` and `@safe`. Full inference requires its mypy plugin `returns.contrib.mypy.returns_plugin`; 0.29.0 declares mypy 1.19-2.4 support. 0.29.1 is marked WIP in the changelog and unreleased - ESTABLISHED.
56. `result` (rustedpy) is dead. Last release 0.17.0, 2024-06-02; PyPI classifiers still stop at Python 3.12; the README banner reads "THIS PROJECT IS NO LONGER MAINTAINED"; issue #201 "Project Status: UNMAINTAINED" (2024-12-23) states "this project is no longer receiving the attention and maintenance it needs" and "no more releases will be made, no more fixes or features"; the repository was archived read-only on 2026-06-25 - ESTABLISHED.
57. `expression` 5.6.0, released 2025-02-19, carries `Development Status :: 5 - Production/Stable` and requires `Python <4, >=3.10`; it supplies `Option`, `Result`, `Try` and effect/pipeline combinators. No release in roughly 17 months as of 2026-08-08 - ESTABLISHED.
58. Net state of the Result ecosystem on 2026-08-08: one actively released typed option (`returns`, self-labelled Beta, mypy-plugin-coupled, 3.11+), one stable-labelled but dormant option (`expression`), one archived option (`result`). A hand-rolled frozen-dataclass union plus `assert_never` carries no dependency, no checker plugin and no maintenance risk - ESTABLISHED.

### Exception hierarchies as a versioned contract

59. "programmers are encouraged to derive new exceptions from the Exception class or one of its subclasses, and not from BaseException" - ESTABLISHED.
60. "It's recommended to only subclass one exception type at a time to avoid any possible conflicts between how the bases handle the `args` attribute, as well as due to possible memory layout incompatibilities." The docs add that layout is an implementation detail that "might change between Python versions, leading to new conflicts in the future. Therefore, it's recommended to avoid subclassing multiple exception types altogether." - ESTABLISHED.
61. Exception classes "are usually kept simple, often only offering a number of attributes that allow information about the error to be extracted by handlers for the exception" - the documented basis for structured attributes over string parsing. "Most exceptions are defined with names that end in 'Error'." - ESTABLISHED.
62. `@warnings.deprecated` (PEP 702, Final, `Python-Version: 3.13`, resolved 2023-11-07; `typing_extensions` 4.5.0) is the machine-readable way to retire a member of an error contract. It emits `DeprecationWarning` at call time (wrapping `__new__` for classes), accepts `category=` (use `category=None` to keep only the static diagnostic) and `stacklevel=`, and applies to classes, functions, methods, `TypedDict`, `NamedTuple` and individual overloads; type checkers "must produce diagnostics when encountering usage of deprecated objects" including attribute access and imports - VERSION-DEPENDENT (3.13).

### Narrow catching, else/finally, EAFP

63. If a `finally` clause executes `return`, `break` or `continue` while an exception is in flight, "the saved exception is discarded" - the reference docs' own example is `try: 1/0` with `finally: return 42`, which returns 42. No flag recovers the exception; only the 3.14 SyntaxWarning flags the construct - ESTABLISHED.
64. "The exception information is not available to the program during execution of the `finally` clause." - ESTABLISHED.
65. A `return` in `finally` overrides a `return` in the `try` body: "a `return` statement executed in the `finally` clause will always be the last one executed" - ESTABLISHED.
66. `continue` in a `finally` clause was illegal before 3.8 - VERSION-DEPENDENT (3.8).
67. `else` on `try` "is better than adding additional code to the `try` clause because it avoids accidentally catching an exception that wasn't raised by the code being protected" - ESTABLISHED.
68. Bare `except:` and `except BaseException:` also catch `KeyboardInterrupt`, `SystemExit` and `GeneratorExit`; since 3.8 `asyncio.CancelledError` is also a `BaseException` subclass and is caught by them - ESTABLISHED.
69. The `as` name is cleared at the end of the clause: "When an exception has been assigned using `as target`, it is cleared at the end of the `except` clause." This applies to `except*` too - the name is not readable after the block - ESTABLISHED.
70. EAFP is the documented idiom; the LBYL TOCTOU caveat is documented verbatim in the glossary: `if key in mapping: return mapping[key]` "can fail if another thread removes `key` ... This issue can be solved with locks or by using the EAFP approach." - ESTABLISHED.
71. `assert expr, msg` compiles to `if __debug__: if not expr: raise AssertionError(msg)`; "The current code generator emits no code for an `assert` statement when optimization is requested at compile time" (`-O`), and `__debug__` is fixed at interpreter start ("Assignments to `__debug__` are illegal") - ESTABLISHED.
72. Python Development Mode does **not** rescue asserts: "The Python Development Mode does not prevent the `-O` command line option from removing `assert` statements nor from setting `__debug__` to False." - ESTABLISHED.
73. `-X dev` / `PYTHONDEVMODE` is equivalent to `PYTHONMALLOC=debug PYTHONASYNCIODEBUG=1 python -W default -X faulthandler`: it shows `DeprecationWarning`, `ImportWarning`, `PendingDeprecationWarning` and `ResourceWarning`, installs allocator debug hooks, calls `faulthandler.enable()`, enables asyncio debug mode, checks `encoding` / `errors` arguments (3.9+), logs `io.IOBase` destructor `close()` exceptions (3.8+), and sets `sys.flags.dev_mode`. It does **not** enable `tracemalloc` - VERSION-DEPENDENT (3.7+).
74. `faulthandler.enable(file=sys.stderr, all_threads=True, c_stack=True)` installs handlers for `SIGSEGV`, `SIGFPE`, `SIGABRT`, `SIGBUS` and `SIGILL`; `c_stack=True` (added 3.14) also prints the C stack. Enable at startup with `-X faulthandler` or `PYTHONFAULTHANDLER`. `faulthandler.register()` is "Not available on Windows." - VERSION-DEPENDENT (3.14 for `c_stack`).

### The four unhandled-exception hooks and their coverage gaps

75. `sys.excepthook(type, value, traceback)` is called "When an exception other than SystemExit is raised and uncaught" - `SystemExit` never reaches it - ESTABLISHED.
76. `sys.unraisablehook(unraisable)` (3.8) covers exceptions Python cannot raise: "when a destructor raises an exception or during garbage collection (`gc.collect()`)". `unraisable` carries `exc_type`, `exc_value`, `exc_traceback`, `err_msg`, `object`; the default hook formats `f'{err_msg}: {object!r}'` and uses the "Exception ignored in" message when `err_msg` is `None`. Storing `exc_value` in a custom hook can create a reference cycle; storing `object` can resurrect a finalizing object - VERSION-DEPENDENT (3.8).
77. `threading.excepthook(args)` (3.8) handles "uncaught exception raised by `Thread.run()`"; `args` carries `exc_type`, `exc_value`, `exc_traceback`, `thread`. "If `exc_type` is SystemExit, the exception is silently ignored." If the hook itself raises, `sys.excepthook` handles that. `threading.__excepthook__` was added only in 3.10 - VERSION-DEPENDENT (3.8/3.10).
78. asyncio has its own channel: `loop.set_exception_handler(handler)` with `handler(loop, context)`, where `context` keys are `'message'`, and optionally `'exception'`, `'future'`, `'task'`, `'handle'`, `'protocol'`, `'transport'`, `'socket'`, `'source_traceback'`, `'handle_traceback'`, `'asyncgen'`. `loop.call_exception_handler` "should not be overloaded in subclassed event loops"; since 3.12 the handler "may be called in the Context of the task or handle where the exception originated" - VERSION-DEPENDENT (3.12).
79. `concurrent.futures` silently drops callback failures: for `Future.add_done_callback(fn)`, "If the callable raises an `Exception` subclass, it will be logged and ignored. If the callable raises a `BaseException` subclass, the behavior is undefined." - ESTABLISHED.
80. `Executor.map` defers failure: "If a `fn` call raises an exception, then that exception will be raised when its value is retrieved from the iterator." A never-iterated map result never reports anything - ESTABLISHED.
81. So `sys.excepthook` alone covers none of: thread failures, destructor/GC/weakref failures, asyncio callback and never-retrieved failures, executor done-callback failures, or `SystemExit`. A process that wants every failure logged must install all four hooks plus a loop exception handler - ESTABLISHED.

### warnings

82. Default filters in a regular release build, in order of precedence, are exactly: `default::DeprecationWarning:__main__`, `ignore::DeprecationWarning`, `ignore::PendingDeprecationWarning`, `ignore::ImportWarning`, `ignore::ResourceWarning`. "In a debug build, the list of default warning filters is empty." - ESTABLISHED.
83. "Changed in version 3.7: DeprecationWarning is once again shown by default when triggered directly by code in `__main__`." A deprecation raised from inside a library module is therefore invisible in a default run - VERSION-DEPENDENT (3.7).
84. `-W` and `PYTHONWARNINGS` full form is `action:message:category:module:lineno`. Empty fields match everything; trailing empty fields may be omitted; action names may be abbreviated (`-Wi` equals `-Wignore`). Actions: `default`, `error`, `ignore`, `always`, `all` (alias of `always`), `module`, `once` - ESTABLISHED.
85. Filter precedence runs in opposite directions depending on the mechanism: for `-W`, "when a warning matches more than one option, the action for the last matching option is performed"; `PYTHONWARNINGS` entries have "filters later in the list taking precedence over those earlier"; but `filterwarnings` and `simplefilter` insert at the **front** (earlier entries win) unless `append=True` - ESTABLISHED.
86. In `-W` and `PYTHONWARNINGS` the `message` field "must match the whole warning message; this match is case-insensitive" and the `module` field matches the fully qualified module name case-sensitively. `filterwarnings(message=..., module=...)` treats both as **regular expressions** matched against the start of the string. `simplefilter` takes no message or module at all: "regular expressions are not needed as the filter inserted always matches any message in any module as long as the category and line number match." - ESTABLISHED.
87. 3.15 (rc1) lets `-W` and `PYTHONWARNINGS` carry regexes: "if `message` starts and ends with a forward slash (`/`), it specifies a regular expression as above; otherwise it is a literal string that the start of the warning message must match" - the same rule applies to `module` (gh-134716) - VERSION-DEPENDENT (3.15).
88. Repeat-suppression keys differ per action: `default` keys on (message, category, module, lineno); `module` on (message, category, module); `once` on (message, category) - ESTABLISHED.
89. `__warningregistry__` defeats naive tests: once a warning has been emitted under `once` or `default`, it is not shown again unless the registry is cleared, even after the filters change. `warnings.resetwarnings()` "Discards the effect of all previous calls to `filterwarnings()` and `simplefilter()`, including `-W` command-line options" - so it also discards the defaults, not merely your additions - ESTABLISHED.
90. `catch_warnings(record=True, ...)` restores the filters and `showwarning` on exit and yields records with `message`, `category`, `filename`, `lineno`, `file`, `line`, `source`. In default builds it mutates **global** module state and is not safe under threads or asyncio - ESTABLISHED.
91. 3.14 adds `sys.flags.context_aware_warnings` (`-X context_aware_warnings`, `PYTHON_CONTEXT_AWARE_WARNINGS`), default **True only for free-threaded builds**: when true, `catch_warnings` uses a `ContextVar`, is thread- and asyncio-safe, and does not replace `showwarning` under `record=True`; when false it is not safe for concurrent use. `sys.flags.thread_inherit_context` governs whether new threads inherit the context - VERSION-DEPENDENT (3.14).
92. `SyntaxWarning` is **not** in the default-ignored set, so the PEP 765 `finally` warning is visible without configuration; the 3.14 notes give the suppression recipe as `-Werror -Wignore::SyntaxWarning` or `PYTHONWARNINGS=error,ignore::SyntaxWarning` - VERSION-DEPENDENT (3.14).

### asyncio-specific failure surfaces

93. `asyncio.CancelledError` subclasses `BaseException` since 3.8 ("Changed in version 3.8: CancelledError is now a subclass of BaseException rather than Exception"), so `except Exception` does not catch it. "In almost all situations the exception must be re-raised." - VERSION-DEPENDENT (3.8).
94. `Task.cancel()` "arranges for a CancelledError exception to be thrown into the wrapped coroutine on the next cycle of the event loop" and returns `False` if the task was already done or cancelled. It "does not guarantee that the Task will be cancelled" - a coroutine can suppress it - ESTABLISHED.
95. Suppressing cancellation is incomplete without `Task.uncancel()`: "Should the coroutine nevertheless decide to suppress the cancellation, it needs to call `Task.uncancel()` in addition to catching the exception." `uncancel()` (3.11) decrements the request count and returns the remainder; "once execution of a cancelled task completed, further calls to `uncancel()` are ineffective". `Task.cancelling()` (3.11) returns cancel requests minus `uncancel()` calls - VERSION-DEPENDENT (3.11).
96. `Task.exception()` does not return cancellation or pending state as a value: it "raises a CancelledError exception" if the task was cancelled and "raises an InvalidStateError exception" if the task is not done. `Task.result()` behaves the same way but re-raises the coroutine's exception - ESTABLISHED.
97. `asyncio.timeout()` and `timeout_at()` convert the cancellation they cause into `TimeoutError`, and "the `TimeoutError` can only be caught *outside* of the context manager" - ESTABLISHED.
98. `asyncio.gather(..., return_exceptions=False)` (the default) propagates the first exception to the awaiting task but "Other awaitables in the `aws` sequence won't be cancelled and will continue to run" - the opposite of `TaskGroup`. With `return_exceptions=True`, "exceptions are treated the same as successful results, and aggregated in the result list" - ESTABLISHED.
99. "Task exception was never retrieved" fires only at garbage-collection time: "If a `Future.set_exception()` is called but the Future object is never awaited on, the exception would never be propagated to the user code. In this case, asyncio would emit a log message when the Future object is garbage collected." Debug mode adds the task-creation traceback - ESTABLISHED.
100. The loop keeps only weak references to tasks, so a fire-and-forget task can vanish before it finishes: "Save a reference to the result of this function, to avoid a task disappearing mid-execution... For reliable 'fire-and-forget' background tasks, gather them in a collection" (a `set` plus `task.add_done_callback(background_tasks.discard)`). "Note that this approach never awaits the tasks, so if a task fails, its exception is never retrieved and asyncio logs a 'Task exception was never retrieved' message when the task is garbage collected." - ESTABLISHED.
101. "asyncio uses the `logging` module and all logging is performed via the `asyncio` logger. The default log level is `logging.INFO`." Never-retrieved exceptions therefore appear only if the `asyncio` logger has a handler; the exact record level chosen by `loop.default_exception_handler` is listed under Open items - ESTABLISHED.
102. A called-but-not-awaited coroutine raises no exception at all; asyncio emits `RuntimeWarning: coroutine 'test' was never awaited`, which is visible only because `RuntimeWarning` is not in the default-ignored set - ESTABLISHED.
103. asyncio debug mode is enabled by `PYTHONASYNCIODEBUG=1`, Python Development Mode, `asyncio.run(..., debug=True)` or `loop.set_debug()`; it makes non-threadsafe API misuse raise, logs slow callbacks (`loop.slow_callback_duration`, default 100 ms) and logs the I/O selector when it is slow - ESTABLISHED.

**Fine-grained error locations (PEP 657) and the flags that erase them**
Destination: `error_tracing_contract_manifest.md`

## Traps for coding agents

1. **`except*` mixed with `except` in the same `try` is a SyntaxError.** Agents refactoring one clause at a time produce a file that will not compile. The docs are absolute: a `try` "can have either `except` or `except*` clauses, but not both."
2. **`except* ExceptionGroup` raises `TypeError` at runtime** - and so does `except* MyOwnGroupSubclass`, because the rule is "a matching type is a subclass of `BaseExceptionGroup`". It is not a syntax error, so it survives linting and fails in production.
3. **The `as` target of `except*` is never the leaf exception.** Even a single, non-group `ValueError` is "wrapped by an exception group with an empty message string", so `e` is always a `BaseExceptionGroup`. Code like `except* ValueError as e: log(e.args[0])` reads the group's args, not the ValueError's.
4. **`return` / `break` / `continue` inside an `except*` clause is a SyntaxError.** The natural "handle the first error and return early" shape is illegal.
5. **Do not re-raise the leftovers of `except*`.** They are merged and propagated automatically; a manual `raise` duplicates them.
6. **`except Exception` does not catch `BaseExceptionGroup`.** A `TaskGroup` that collects even one `BaseException` (a `KeyboardInterrupt`-family member, a custom `BaseException`) produces a group that walks past every `except Exception` in the stack.
7. **`BaseExceptionGroup(...)` may hand back an `ExceptionGroup`.** `isinstance` checks and `type(...) is` comparisons written against the constructor name are wrong whenever every member happens to be an `Exception`.
8. **`ExceptionGroup` members must be instances.** `ExceptionGroup("m", [ValueError])` - a class, not an instance - is a mistake the type name invites.
9. **A callable `condition` for `split` / `subgroup` is 3.13+.** On 3.11 and 3.12 passing a lambda fails; only types and tuples of types work.
10. **`exc.__notes__` does not exist until `add_note` has been called.** `exc.__notes__.append(...)` raises `AttributeError` on a fresh exception. `add_note` also raises `TypeError` for any non-`str`, including an object that was never formatted.
11. **No backport gives you `add_note` on < 3.11.** `exceptiongroup` backports the group classes, `catch()`, traceback formatting and `suppress`; it does not touch `BaseException`. `typing_extensions` never did.
12. **`raise X from Y` sets `__suppress_context__ = True` as a side effect.** Any implicit `__context__` captured at the same site stops being displayed - so wrapping "helpfully" can hide the second, real failure that happened inside the handler.
13. **`from None` does not delete the original.** It stays in `__context__` and is reachable by any handler or logger that inspects it - convenient for debugging, but not a redaction mechanism.
14. **`__context__` is also set inside `finally` and `with`, not just `except`.** A cleanup failure in `finally` chains onto the original error: "If the `finally` clause raises another exception, the saved exception is set as the context of the new exception."
15. **`return` in a `finally` block silently discards the in-flight exception.** `try: 1/0` with `finally: return 42` returns 42. 3.14 emits a `SyntaxWarning` (PEP 765) and nothing more; on 3.13 and earlier there is no signal at all.
16. **`SyntaxWarning` is a compile-time warning.** Whether it is re-emitted when a cached `.pyc` is reused is not documented - do not rely on seeing it on the second run (see Open items). Enforce with `-W error::SyntaxWarning` on a clean build.
17. **`except A, B:` without parentheses is 3.14+ only, and `except A, B as e:` is still a SyntaxError.** In Python 2 the same text meant `except A as B`, so an agent porting old code can produce a construct that is legal-looking, version-gated, and semantically different from its source.
18. **`assert` disappears under `-O`, and `-X dev` does not bring it back** - the devmode docs say so explicitly. Any check that must run in production must not be an `assert`.
19. **`assert_never` is not `assert False`.** Only `assert_never` gives static exhaustiveness; its runtime failure is `AssertionError("Expected code to be unreachable, but got: ...")` with the repr truncated at 100 characters, so an enormous offending value is not fully logged.
20. **mypy does not check `match` exhaustiveness by default.** `--enable-error-code exhaustive-match` is required (mypy 1.17+); pyright's `reportMatchNotExhaustive` is on only in strict mode. `assert_never` works in both without configuration.
21. **`DeprecationWarning` is invisible unless it is triggered from `__main__`.** A library that deprecates an exception type shows nothing in a normal run; only `-W`, `PYTHONWARNINGS`, `-X dev` or a pytest `filterwarnings` setting surfaces it.
22. **The `-W` message field is a literal, case-insensitive match, not a regex** - unlike `filterwarnings(message=...)`, which is a regex. 3.15 adds slash-delimited `/regex/` fields to `-W` and `PYTHONWARNINGS`; earlier versions do not have them.
23. **Filter precedence runs in opposite directions.** For `-W` and `PYTHONWARNINGS` the *last* matching entry wins; for `filterwarnings` and `simplefilter` the *first* wins, because they insert at the front unless `append=True`.
24. **`warnings.resetwarnings()` also throws away the default filters and any `-W` options** - it does not merely undo your own calls, so calling it in a fixture changes global visibility for everything that follows.
25. **`__warningregistry__` can make a warning assertion pass once and fail forever after.** Use `simplefilter("always")` inside `catch_warnings(record=True)`; `catch_warnings` alone does not clear the registry.
26. **`catch_warnings` is not thread-safe or asyncio-safe in a normal build.** `sys.flags.context_aware_warnings` (3.14) fixes it but defaults to true only for free-threaded builds; enable with `-X context_aware_warnings` or `PYTHON_CONTEXT_AWARE_WARNINGS`.
27. **`sys.excepthook` is never called for `SystemExit`, for thread failures, for destructor/GC failures, or for asyncio failures.** An "install one hook and log everything" design misses four whole channels.
28. **`threading.excepthook` silently ignores `SystemExit`** - a worker thread calling `sys.exit()` produces no output at all.
29. **`concurrent.futures` done-callback exceptions are "logged and ignored", and `Executor.map` failures surface only when the iterator is consumed.** A submitted-and-forgotten callable can fail with no visible trace.
30. **`Task.exception()` raises rather than returns for cancelled or unfinished tasks** - `CancelledError` and `InvalidStateError` respectively. Code that treats it as a nullable getter crashes on the cancellation path.
31. **`asyncio.CancelledError` is a `BaseException`.** `except Exception` misses it (correctly) and bare `except:` / `except BaseException:` swallow it (catastrophically, since cancellation then stops working). If you must swallow it, `Task.uncancel()` is also required.
32. **`TimeoutError` from `asyncio.timeout` can only be caught outside the `async with`** - a `try/except TimeoutError` inside the block never fires.
33. **`asyncio.gather(return_exceptions=False)` does not cancel the siblings** when one fails; they keep running. Only `TaskGroup` cancels.
34. **"Task exception was never retrieved" arrives at garbage-collection time, or never.** The loop holds tasks weakly, so a fire-and-forget task can be collected mid-flight; keep a strong reference set with `add_done_callback(set.discard)`.
35. **The `asyncio` logger defaults to `INFO` and needs a handler.** With no logging configured, never-retrieved exceptions can be invisible.
36. **A coroutine called but never awaited raises nothing** - it emits `RuntimeWarning: coroutine 'x' was never awaited`, which is visible only because `RuntimeWarning` is not in the default-ignored set.
37. **`contextlib.suppress` does not look inside exception groups before 3.12.** A `suppress(FileNotFoundError)` wrapping group-raising code suppresses nothing on 3.11.
38. **A `@contextmanager` that catches an exception only to log it must re-raise it**, or the `with` statement treats the failure as handled and execution continues past it.
39. **Group tracebacks are truncated by default** at `max_group_width=15` and `max_group_depth=10`; a wide validation group does not print in full, which reads like lost errors.
40. **`sys.tracebacklimit = 0` prints only the exception type and value.** Anything setting it in a config destroys source-traceability with no other symptom.
41. **`-X no_debug_ranges` / `PYTHONNODEBUGRANGES` removes the column markers process-wide.** Set for `.pyc` size in a base image, it quietly degrades every traceback the app will ever print.
42. **`TracebackException.exc_type` is deprecated since 3.13** - tooling that reads it should move to `exc_type_str`.
43. **On 3.15, an `ImportError` can surface far from its `import` statement.** PEP 810 lazy imports defer the failure to first use of the name, with chaining that shows both sites; code that wraps its imports in `try/except ImportError` at module top will not catch it.
44. **`rustedpy/result` is archived.** An agent reaching for `from result import Ok, Err` is adding an abandoned dependency whose last release predates Python 3.13. `returns` requires 3.11+ and a mypy plugin; `expression` has not shipped in 17 months.
45. **Multiple inheritance of exception types is discouraged outright** - not only for `args` handling but because C-level memory layout "might change between Python versions, leading to new conflicts in the future".
46. **`python -m pdb -p PID` needs matching interpreter versions** (exact match if either side is a pre-release) and can be disabled build-wide with `--without-remote-debug`, so it is not something to assume is available in a hardened image.
