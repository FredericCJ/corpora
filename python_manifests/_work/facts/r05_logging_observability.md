## Facts

### The severity model

1. `logging` defines exactly six level constants - `NOTSET=0`, `DEBUG=10`, `INFO=20`, `WARNING=30`, `ERROR=40`, `CRITICAL=50` - of which five are emittable severities; the values are literal module-level assignments in `Lib/logging/__init__.py`. - ESTABLISHED
2. The library reference "Logging Levels" table lists NOTSET as a row and gives it two distinct meanings: "When set on a logger, indicates that ancestor loggers are to be consulted to determine the effective level. If that still resolves to `NOTSET`, then all events are logged. When set on a handler, all events are handled." The handler half is the commonly-missed half. - ESTABLISHED
3. The library reference and the HOWTO do **not** use the same wording for the level table. Library reference DEBUG: "Detailed information, typically only of interest to a developer trying to diagnose a problem."; HOWTO DEBUG: "Detailed information, typically of interest only when diagnosing problems." Library reference WARNING: "...or that a problem might occur in the near future (e.g. 'disk space low')."; HOWTO WARNING: "...or indicative of some problem in the near future (e.g. 'disk space low')." Quote one page, not "both". - ESTABLISHED
4. Custom levels are destructive: "If you define a level with the same numeric value, it overwrites the predefined value; the predefined name is lost." - ESTABLISHED
5. `logging.WARN` and `logging.FATAL` exist as aliases (`WARN = WARNING`, `FATAL = CRITICAL`) and are both exported in `logging.__all__`, but they are absent from the documented levels table. - ESTABLISHED
6. `_levelToName` maps only CRITICAL/ERROR/WARNING/INFO/DEBUG/NOTSET, while `_nameToLevel` additionally maps `'WARN' -> WARNING` and `'FATAL' -> FATAL`. Consequence: `getLevelName(30)` always returns `'WARNING'`, never `'WARN'`, but `setLevel('WARN')` works. - ESTABLISHED
7. `Logger.warn` is implemented as `warnings.warn("The 'warn' method is deprecated, use 'warning' instead", DeprecationWarning, 2)` followed by delegation to `warning`. It is not removed, so it fails silently under default warning filters. ruff flags it as `LOG009 undocumented-warn` and `G010 logging-warn`. - ESTABLISHED
8. `getLevelNamesMapping()` was **Added in version 3.11** (not 3.12 or 3.13) and "The returned mapping is copied from an internal mapping on each call to this function" - safe to mutate, but it costs a dict copy per call. - VERSION-DEPENDENT (3.11)
9. `getLevelName(level)` is bidirectional: it accepts an int and returns a name, and also accepts "a string representation of the level such as 'INFO'" and returns the numeric value. On no match it returns the string `'Level %s' % level` rather than raising. The string-to-int direction was removed in 3.4 and "reinstated in 3.4.2". - ESTABLISHED
10. `setLevel` accepts a string level name since 3.2, but "levels are internally stored as integers, and methods such as e.g. `getEffectiveLevel()` and `isEnabledFor()` will return/expect to be passed integers". - VERSION-DEPENDENT (3.2)
11. The root logger is created with level `WARNING`; every other logger is created with `NOTSET`. Verbatim: "When a logger is created, the level is set to `NOTSET` ... Note that the root logger is created with level `WARNING`." So INFO and DEBUG are silent until an application lowers a threshold. - ESTABLISHED
12. `logging.disable(level=CRITICAL)` installs a process-wide override that "takes precedence over the logger's own level", and `Logger.isEnabledFor` checks `self.disabled`, then `self.manager.disable >= level`, before consulting the effective level. `logging.disable(logging.NOTSET)` removes the override. The `CRITICAL` default arrived in 3.7. - VERSION-DEPENDENT (3.7)
13. Because `disable` is checked first, a library that calls `logging.disable()` silences the whole application, including loggers it does not own. Nothing in the API scopes it. - ESTABLISHED

### print vs warnings.warn vs logging

14. The HOWTO dispatch table is explicit and narrow: `print()` for "Display console output for ordinary usage of a command line script or program"; a logger's `info()`/`debug()` for "Report events that occur during normal operation of a program (e.g. for status monitoring or fault investigation)". - ESTABLISHED
15. The warning split is one row with two answers: `warnings.warn()` "in library code if the issue is avoidable and the client application should be modified to eliminate the warning", versus a logger's `warning()` "if there is nothing the client application can do about the situation, but the event should still be noted". Avoidability by the *caller* is the discriminator, not severity. - ESTABLISHED
16. For errors the table says "Raise an exception" and reserves `error()`/`exception()`/`critical()` for "Report suppression of an error without raising an exception (e.g. error handler in a long-running server process)". Logging an error you also raise is not what the table sanctions. - ESTABLISHED
17. `logging.captureWarnings(True)` redirects `warnings` into logging: "a warning will be formatted using `warnings.formatwarning()` and the resulting string logged to a logger named `'py.warnings'` with a severity of `WARNING`." This is the only supported bridge between the two subsystems, and `'py.warnings'` is the logger name to configure. - ESTABLISHED

### Library-vs-application discipline

18. Two Note blocks in "Configuring Logging for a Library" carry the rules verbatim: "It is strongly advised that you *do not log to the root logger* in your library. Instead, use a logger with a unique and easily identifiable name, such as the `__name__` for your library's top-level package or module." and "It is strongly advised that you *do not add any handlers other than* `NullHandler` *to your library's loggers*. This is because the configuration of handlers is the prerogative of the application developer who uses your library ... if you add handlers 'under the hood', you might well interfere with their ability to carry out unit tests and deliver logs which suit their requirements." - ESTABLISHED
19. The docs do **not** say a library must add a `NullHandler`. They say WARNING+ reaching `sys.stderr` in the absence of configuration "is regarded as the best default behaviour", and make the NullHandler conditional: "If for some reason you *don't* want these messages printed in the absence of any logging configuration, you can attach a do-nothing handler to the top-level logger for your library." - ESTABLISHED
20. Current `NullHandler` wording is "does not do any formatting or output. It is essentially a 'no-op' handler for use by library developers"; `emit()` and `handle()` "do nothing" and `createLock()` "returns `None` for the lock, since there is no underlying I/O to which access needs to be serialized". Added in version 3.1. - ESTABLISHED
21. The "No handlers could be found for logger X.Y.Z" message is a pre-3.2 artefact. Since 3.2 `logging.lastResort` "replaces the earlier error message saying that 'no handlers could be found for logger XYZ'". Citing that message as the reason to add a NullHandler is a decade out of date. - VERSION-DEPENDENT (3.2)
22. `logging.lastResort` is "a `StreamHandler` writing to `sys.stderr` with a level of `WARNING`", "No formatting is done on the message - just the bare event description message is printed", and it "is not associated with any logger". Setting `logging.lastResort = None` restores pre-3.2 behaviour. - VERSION-DEPENDENT (3.2)
23. The canonical library one-liner from the HOWTO is `logging.getLogger('foo').addHandler(logging.NullHandler())`, applied to the top-level package logger only, with the org-scoped variant `'orgname.foo'`. - ESTABLISHED
24. `getLogger(name)` is a singleton factory: "Multiple calls to `getLogger()` with the same name will always return a reference to the same `Logger` object." Direct `Logger(...)` instantiation is flagged by ruff `LOG001 direct-logger-instantiation`. - ESTABLISHED
25. Effective-level resolution, verbatim: "If a value other than `NOTSET` has been set using `setLevel()`, it is returned. Otherwise, the hierarchy is traversed towards the root until a value other than `NOTSET` is found, and that value is returned." If the walk reaches a root still at NOTSET, "all messages will be processed". - ESTABLISHED
26. Propagation ignores ancestor gating: "Messages are passed directly to the ancestor loggers' handlers - neither the level nor filters of the ancestor loggers in question are considered." Only the originating logger's effective level plus filters, and then each handler's own level plus filters, gate a record. `propagate` is set to `True` by the constructor. - ESTABLISHED
27. Propagation stops at the first logger in the chain with `propagate` false: "If any logger in the chain `A.B.C`, `A.B`, `A` has its `propagate` attribute set to false, then that is the last logger whose handlers are offered the event to handle." - ESTABLISHED
28. Attaching a handler to both a logger and an ancestor duplicates output: "If you attach a handler to a logger *and* one or more of its ancestors, it may emit the same record multiple times." The documented remedy is "attach handlers only to the root logger, and to let propagation take care of the rest." - ESTABLISHED
29. `logging.getHandlerByName(name)` and `logging.getHandlerNames()` were **Added in version 3.12** and are the supported way for application code to reach a handler that `dictConfig` created, without module-level globals. - VERSION-DEPENDENT (3.12)
30. `logging.raiseExceptions` defaults to `True`; "If `raiseExceptions` is `False`, exceptions get silently ignored." Handler errors route through `Handler.handleError`, which writes to `sys.stderr` only when `raiseExceptions and sys.stderr`. A process that sets it False converts every handler fault into silence. - ESTABLISHED

### dictConfig and configuration

31. `version` in a `dictConfig` dict is mandatory and single-valued: "to be set to an integer value representing the schema version. The only valid value at present is 1". That is still true in the 3.14 and 3.15 docs. - ESTABLISHED
32. `disable_existing_loggers` "If absent, this parameter defaults to `True`" - so a `dictConfig` call made after imports silently disables every module logger created at import time unless the key is set to False. It "is ignored if *incremental* is `True`". - ESTABLISHED
33. `incremental` "defaults to `False`, which means that the specified configuration replaces the existing configuration". Two successive `dictConfig` calls do not merge. - ESTABLISHED
34. A config entry may name a factory via the special key `'()'` (an absolute import path) with all remaining keys passed as keyword arguments, and may set post-construction attributes via the special key `'.'` whose value maps attribute names to values. - ESTABLISHED
35. `filters` lists in `dictConfig` accept filter *instances* in addition to ids since **3.11**; `QueueHandler`/`QueueListener` became configurable through `dictConfig` in **3.12**; the `defaults` key on formatter configs was added in **3.12**. A 3.12 floor covers all three. - VERSION-DEPENDENT (3.12)
36. `logging.config.listen()` is a remote-code-execution surface: "Because portions of the configuration are passed through `eval()`, use of this function may open its users to a security risk", mitigated only by the `verify` callable, which "is called with a single argument - the bytes received across the socket - and should return the bytes to be processed, or `None`". - ESTABLISHED
37. There is still **no JSON formatter in the stdlib** `logging` module as of 3.15.0rc1; the documented formatter classes are `logging.Formatter` and `logging.BufferingFormatter` only. JSON output requires a third-party formatter or a hand-written `Formatter` subclass. - VERSION-DEPENDENT (3.15)

### extra, LoggerAdapter, filters

38. `extra` populates `LogRecord.__dict__` directly, and collisions raise. `Logger.makeRecord` contains: `if (key in ["message", "asctime"]) or (key in rv.__dict__): raise KeyError("Attempt to overwrite %r in LogRecord" % key)`. The failure is a `KeyError` at the call site, not a dropped field. - ESTABLISHED
39. Because every documented LogRecord attribute is assigned in `LogRecord.__init__`, `extra` keys named `name`, `msg`, `args`, `levelname`, `levelno`, `pathname`, `filename`, `module`, `lineno`, `funcName`, `created`, `msecs`, `relativeCreated`, `thread`, `threadName`, `process`, `processName`, `taskName`, `exc_info`, `stack_info` all raise. `message` and `asctime` are guarded explicitly because the `Formatter` adds them later. Namespacing every key is the only safe policy. - ESTABLISHED
40. A missing extra key is a different failure from a colliding one: if the format string references an attribute that is absent, "the message will not be logged because a string formatting exception will occur". A format string with custom fields makes those fields mandatory on every call routed to that handler. - ESTABLISHED
41. `LoggerAdapter` gained a `merge_extra` parameter in **3.13**. Without it, `process()` "inserts an 'extra' key in the keyword argument whose value is the dict-like object passed to the constructor" and "if you had passed an 'extra' keyword argument in the call to the adapter, it will be silently overwritten". Call-site `extra` is lost unless `merge_extra=True`. - VERSION-DEPENDENT (3.13)
42. Filters may mutate records: the cookbook's `InjectingFilter` both stamps attributes (`record.method`, `record.ip`, `record.user`, `record.appName`) and returns a boolean deciding whether the record survives. A filter that forgets to `return True` silently drops every record. - ESTABLISHED
43. ruff `G101 logging-extra-attr-clash` is the lint that catches fact 38 statically; the surrounding family is `LOG001`, `LOG002 invalid-get-logger-argument`, `LOG004 log-exception-outside-except-handler`, `LOG007 exception-without-exc-info`, `LOG009`, `LOG014 exc-info-outside-except-handler`, `LOG015 root-logger-call`, plus `G001`-`G004`, `G010`, `G201 logging-exc-info`, `G202 logging-redundant-exc-info`. All are stable, none preview. - ESTABLISHED

### Structured logging

44. structlog 26.1.0 processor contract: a processor is called with three positional arguments - `logger` (the wrapped logger), `method_name` (the name of the wrapped method), and `event_dict` (current context merged with the current event, e.g. context `{"a": 42}` plus event `"foo"` yields `{"a": 42, "event": "foo"}`). - ESTABLISHED
45. Only the **last** processor in a structlog chain knows about the output system; it must return a `str`/`bytes`/`bytearray`, an `(args, kwargs)` tuple, or a dict of keyword arguments. Ordering is load-bearing, not stylistic. - ESTABLISHED
46. `structlog.DropEvent` is the filtering mechanism: "If a processor raises `structlog.DropEvent`, the event is silently dropped." - ESTABLISHED
47. `structlog.stdlib.ProcessorFormatter` is the interop seam: it runs structlog processors over arbitrary `logging.LogRecord`s. The structlog side must end with `structlog.stdlib.ProcessorFormatter.wrap_for_formatter`; non-structlog ("foreign") records are pre-processed via the formatter's `foreign_pre_chain`; and `ProcessorFormatter.remove_processors_meta` must be first in the formatter's own chain. Substituting `render_to_log_kwargs()` for `wrap_for_formatter` breaks the wiring. - ESTABLISHED
48. `structlog.stdlib.ExtraAdder` "adds data passed in the `extra` parameter of the `logging` module's log methods to the event dictionary" - this is how stdlib `extra={...}` emitted by libraries survives into a structlog-rendered pipeline. - ESTABLISHED
49. `cache_logger_on_first_use=True` "effectively freezes configuration after creating the first bound logger" - configure once at startup and treat any later `structlog.configure()` as a bug. - ESTABLISHED
50. For JSON output with usable tracebacks, structlog's own guidance pairs `structlog.processors.dict_tracebacks` (backed by `structlog.tracebacks.ExceptionDictTransformer`) with `structlog.processors.JSONRenderer()`. - ESTABLISHED
51. structlog 26.1.0 (2026-06-06) removed Python 3.8/3.9 support, added Python 3.15 support, added `structlog.stdlib.BoundLogger.is_enabled_for()` and `get_effective_level()`, added `CallsiteParameter.QUAL_MODULE` to `CallsiteParameterAdder`, and deprecated better-exceptions support ("will be removed within a year"). - ESTABLISHED
52. python-json-logger is **actively maintained, not abandoned**: 4.1.0 (2026-03-29), maintained by Nicholas Hairs at github.com/nhairs/python-json-logger with docs at nhairs.github.io/python-json-logger, classified "Development Status :: 6 - Mature", `Requires-Python >=3.10`, not yanked. - ESTABLISHED
53. The python-json-logger import path moved: since 3.1.0 "`pythonjsonlogger.jsonlogger` is now `pythonjsonlogger.json`", so the current class path is `pythonjsonlogger.json.JsonFormatter`; `RESERVED_ATTRS` and `merge_record_extra` moved to `pythonjsonlogger.core`. 4.0.0 (2025-10-06) removed the ability to pass strings instead of objects for `json_default`/`json_encoder`/`json_serializer`. 4.1.0 added Python 3.14 support and dropped 3.8/3.9. - ESTABLISHED
54. Because python-json-logger is a `logging.Formatter` subclass it composes with the stdlib route (`extra=` plus a `dictConfig` `'()'` factory entry) and needs no application-wide rewrite; structlog's `ProcessorFormatter` is a competing formatter for the same slot. Running both on one handler is not a supported configuration. - OPEN

### Queue handoff, asyncio, performance

55. `QueueHandler.prepare()` is destructive by design: "it overwrites the record's `msg` and `message` attributes with the merged message (obtained by calling the handler's `format()` method), and sets the `args`, `exc_info` and `exc_text` attributes to `None`." The documented consequence: "a handler on the `QueueListener` side won't have the information to do custom formatting, e.g. of exceptions." A JSON formatter on the listener side receives a pre-rendered string, not fields. - ESTABLISHED
56. `QueueListener(queue, *handlers, respect_handler_level=False)` **ignores handler levels by default**: only "If `respect_handler_level` is `True`, a handler's level is respected". The argument was added in 3.5 and the default kept the legacy behaviour. Per-handler fan-out silently stops working behind a queue unless you pass it. - VERSION-DEPENDENT (3.5)
57. `QueueHandler.emit` enqueues via `put_nowait()`; on failure (e.g. a bounded queue that filled) it calls `handleError()`, which "can result in the record silently being dropped (if `logging.raiseExceptions` is `False`) or a message printed to `sys.stderr`". Unbounded (`queue.Queue(-1)`) trades record loss for unbounded memory. - ESTABLISHED
58. In **3.14** `QueueListener` became a context manager - "When entering the context, the listener is started. When exiting the context, the listener is stopped. `__enter__()` returns the `QueueListener` object" - and `QueueListener.start()` now "Raises `RuntimeError` if called and the listener is already running". Code that defensively called `start()` twice breaks on 3.14. - VERSION-DEPENDENT (3.14)
59. `QueueListener.stop()` matters for correctness, not tidiness: "if you don't call this before your application exits, there may be some records still left on the queue, which won't be processed." - ESTABLISHED
60. The cookbook's asyncio guidance is explicit that the problem is not only slow handlers: "when logging from async code, network and even file handlers could lead to problems (blocking the event loop) because some logging is done from `asyncio` internals. It might be best, if any async code is used in an application, to use the above approach for logging, so that any blocking code runs only in the `QueueListener` thread." - ESTABLISHED
61. Multi-process file logging is unsupported: "logging to a single file from multiple processes is *not* supported, because there is no standard way to serialize access to a single file across multiple processes in Python." Documented alternatives are `SocketHandler` plus a receiver, `QueueHandler` with a listener process, or a custom handler using `multiprocessing.Lock`. With `multiprocessing`, use `multiprocessing.Queue`, not `queue.SimpleQueue`. - ESTABLISHED
62. Argument formatting is deferred, verbatim: "Formatting of message arguments is deferred until it cannot be avoided." The `%`-style call form `logger.debug('Message with %s, %s', a, b)` is what makes deferral possible. - ESTABLISHED
63. The stdlib docs never mention f-strings in this context. The authority for "do not f-string a log message" is ruff `G004 logging-f-string` (flake8-logging-format), whose stated rationale is that `extra`/argument passing "is more consistent, more efficient, and less error-prone than formatting the string directly". Attribute this to ruff, not to python.org. - ESTABLISHED
64. `G002 logging-percent-format` flags `logger.info("%s" % x)` - eager `%` applied to the message *before* the call - which is the opposite of the recommended `logger.info("%s", x)`. Do not conflate them; a lint exception "for %-style logging" is not needed and would suppress a genuine rule. - ESTABLISHED
65. `isEnabledFor` is already memoised in CPython: `Logger.isEnabledFor` returns `self._cache[level]` on hit and otherwise computes under `_lock`, checking `self.disabled`, then `self.manager.disable >= level`, then `level >= self.getEffectiveLevel()`. The HOWTO note advising callers to cache the result themselves predates this cache; the remaining reason to guard with `isEnabledFor` is avoiding evaluation of *expensive arguments*, not avoiding the level check. The `_cache` logic is verbatim from the source; the reading that the HOWTO note is thereby superseded is inference, not a documented statement. - ESTABLISHED
66. The four record-enrichment flags are module-level and default True: `logThreads = True`, `logMultiprocessing = True`, `logProcesses = True`, `logAsyncioTasks = True`. Setting them False is the documented way to cut per-record cost; `logMultiprocessing=False` in particular skips a `sys.modules.get('multiprocessing')` lookup and a `current_process()` call per record. - ESTABLISHED
67. `LogRecord.taskName` was added in **3.12** and is derived defensively: `self.taskName = None; if logAsyncioTasks: asyncio = sys.modules.get('asyncio'); if asyncio: try: self.taskName = asyncio.current_task().get_name() except Exception: pass`. It is `None` in any sync-only program (asyncio never imported) and `None` outside a running loop (the `RuntimeError` from `current_task()` is swallowed). A format string containing `%(taskName)s` renders `None`, it does not fail. - VERSION-DEPENDENT (3.12)
68. `stacklevel` was added in **3.8**: "If greater than 1, the corresponding number of stack frames are skipped when computing the line number and function name set in the `LogRecord`". Any logging helper or wrapper must pass `stacklevel=2` (or more) or every record names the helper's own file and line. - VERSION-DEPENDENT (3.8)
69. `exc_info` accepts an exception **instance** since **3.5**, in addition to a `sys.exc_info()` triple or a truthy flag; `stack_info` (3.2) is independent of `exc_info` and prints frames under the header "Stack (most recent call last):" from the bottom of the stack up to the logging call (`stack_info` itself is 3.2). - VERSION-DEPENDENT (3.5)
70. Python 3.14.7 (2026-08-05) fixed gh-79366: "Fixed a race condition in `logging`: if a handler was removed while a record was being emitted, the following handlers of the same logger could be skipped." Dynamic `removeHandler` during emission was unsafe on every earlier release. - VERSION-DEPENDENT (3.14.7)
71. The free-threaded build is officially supported (not experimental) from 3.14 under PEP 779 (Status Final, resolved 2025-06-16, Python-Version 3.14), shipping as a separate binary and still optional. Handler-level locking assumptions in custom handlers deserve review under a free-threaded build. - VERSION-DEPENDENT (3.14)

### Correlation

72. `contextvars` is the async-and-thread-correct carrier: "Each thread has its own effective stack of `Context` objects" and "`ContextVar` objects behave in a similar fashion to `threading.local()` when values are assigned in different threads." A worker thread therefore does **not** see bindings made on the parent thread. - ESTABLISHED
73. asyncio Tasks *do* inherit: "If no `context` is provided, the Task copies the current context and later runs its coroutine in the copied context." The explicit `context=` keyword on `asyncio.create_task`/`Task` was added in **3.11**. Because it is a copy, bindings made inside a Task do not leak back to the parent. - VERSION-DEPENDENT (3.11)
74. `ContextVar.get()` raises `LookupError` when unset and no default was supplied - a correlation filter calling `.get()` without a default raises inside `Filter.filter()` on the first record logged outside a request scope. - ESTABLISHED
75. `ContextVar.set()` returns a `Token` for `reset()`; `Token` objects became usable as context managers in **3.14**, which is the cleanest way to scope a correlation binding. - VERSION-DEPENDENT (3.14)
76. structlog's equivalent is `structlog.contextvars`: `clear_contextvars()` at scope entry, `bind_contextvars(...)` to stamp, and `merge_contextvars` placed **first** in the processor chain so context-local binds reach every event. - ESTABLISHED
77. `opentelemetry-instrumentation-logging` (`LoggingInstrumentor`) injects exactly four LogRecord attributes: `otelTraceID`, `otelSpanID`, `otelServiceName`, `otelTraceSampled`. ### Security and redaction

97. OWASP's "Data to exclude" list is concrete and is the citable authority (python.org's logging pages say nothing about secrets): application source code, session identification values, access tokens, "Sensitive personal data and some forms of personally identifiable information (PII)", authentication passwords, database connection strings, "Encryption keys and other primary secrets", bank account or payment card holder data, "Data of a higher security classification than the logging system is allowed to store", commercially-sensitive information, and "Information it is illegal to collect in the relevant jurisdictions". - ESTABLISHED
98. OWASP also requires sanitisation, usually forgotten: "Perform sanitization on all event data to prevent log injection attacks e.g. carriage return (CR), line feed (LF) and delimiter characters", plus "Synchronize time across all servers and devices". A multi-line attacker-controlled string forges log entries in any line-delimited sink. - ESTABLISHED
99. Filter-vs-Formatter is a coverage question and the Filter wins. A `Filter` attached to the **logger** sees every record before propagation reaches any handler, so it protects all sinks; a `Filter` attached to a handler protects only that handler; a `Formatter` protects only the sinks that use it. The mechanism follows from the documented two-stage gating and propagation semantics rather than from a single quoted sentence. - ESTABLISHED
100. Formatter-level redaction has a specific hole: `%(message)s` is `record.msg % record.args`, so rewriting only `record.msg` leaves secrets in `record.args`, and `record.exc_info`/`exc_text` carry argument values inside tracebacks. Redaction must cover `msg`, `args`, `exc_info`/`exc_text`, and every `extra` key. - ESTABLISHED
101. Redaction must sit **upstream of `QueueHandler`**, because `QueueHandler.prepare()` has already formatted the message before the listener thread sees it - a redacting formatter on the listener side receives a pre-rendered string and, per the documented warning, cannot recover the fields. - ESTABLISHED
102. structlog's equivalent placement rule: a redacting processor must run before the renderer, and a processor may enforce a hard deny by raising `structlog.DropEvent`. - ESTABLISHED

### Diagnosability beyond logs

103. OTel states the limit of logs directly: "Logs aren't enough for tracking code execution, as they usually lack contextual information, such as where they were called from. **1. "Queue-based handoff: the four defaults that bite"** — destination: `logging_observability_manifest.md` (new §9a, adjacent to the performance section).
Cover the whole `QueueHandler`/`QueueListener` contract as one unit, because the pieces fail together.
`prepare()` pre-renders the message and nulls `args`/`exc_info`/`exc_text`, so any structured or
redacting formatter must live on the QueueHandler side. `respect_handler_level` defaults to `False`,
so per-handler fan-out silently stops working behind a queue. `enqueue()` uses `put_nowait()` and
routes failures through `handleError()`, so a bounded queue drops records (silently when
`raiseExceptions` is False) while an unbounded one grows without limit. `stop()` is required for
drain-on-exit. On 3.14+ prefer the context-manager form and know that a second `start()` now raises
`RuntimeError`. Close with the cookbook's own reason to adopt this in async code: network and file
handlers "could lead to problems (blocking the event loop) because some logging is done from
`asyncio` internals."

**2. "asyncio and threads: what the record actually carries"** — destination: `logging_observability_manifest.md` (extend §8).
`LogRecord.taskName` (3.12) is derived from `asyncio.current_task().get_name()` only when
`logAsyncioTasks` is True and `asyncio` is already in `sys.modules`, inside a bare
`try/except Exception: pass` — so it is `None` in sync programs and outside a running loop, and
`%(taskName)s` renders the string `None` rather than failing. `contextvars` is the correct correlation
carrier because a Task copies the current context at creation (explicit `context=` since 3.11) while a
new thread starts from its own context stack and behaves "in a similar fashion to `threading.local()`"
— correlation IDs propagate into tasks but must be re-bound in worker threads and executor callbacks.
`ContextVar.get()` raises `LookupError` when unset without a default, which is the usual way a
correlation Filter blows up on the first out-of-scope record; `Token` became a context manager in 3.14.

**3. "Severity mapping to OpenTelemetry SeverityNumber"** — destination: `logging_observability_manifest.md` (extend §2), or `NEW: observability_signals_manifest.md`.
Python's five severities are not 1..5 on the wire. The OTel logs data model defines ranges 1-4 TRACE,
5-8 DEBUG, 9-12 INFO, 13-16 WARN, 17-20 ERROR, 21-24 FATAL, with the rule that a format offering one
level per range uses the range's lowest value — so DEBUG/INFO/WARNING/ERROR/CRITICAL map to
5/9/13/17/21. Record also that a record representing an erroneous event with no source severity
"is recommended to set `SeverityNumber` to ERROR (numeric 17)". Note that TraceId/SpanId/TraceFlags/
EventName are first-class LogRecord *fields*, not attributes, which is why `otelTraceID`-in-the-format-
string is a stdlib-side convenience, not the wire format.

**4. "OpenTelemetry adoption gate: spec-stable is not implementation-stable"** — destination: `NEW: observability_signals_manifest.md`.
The one-page decision aid this manifest set lacks. The spec marks Logging Bridge API / Logging SDK /
logs OTLP `stable` (spec 1.59.0), while opentelemetry.io/status marks **Python** Logs `Development`
with Traces and Metrics `Stable` and Profiles unimplemented. Record the concrete evidence of the gap:
the Python logs SDK sits at `opentelemetry.sdk._logs`; `LoggingHandler` was deprecated in 1.40.0 in
favour of the `0.65b0` beta `opentelemetry-instrumentation-logging`; the Events API/SDK was deleted
outright in 1.44.0. Record the two-track versioning (`1.44.0` stable line, `0.65b0` beta line moving
in lockstep) so pins cover both. State the house rule: adopt OTel traces/metrics freely when
distributed; treat OTel logs as pre-stable and keep stdlib `logging` as the emission surface with a
bridge in front.

**5. "Semantic conventions an emitter must get right"** — destination: `NEW: observability_signals_manifest.md`, cross-referenced from `error_tracing_contract_manifest.md`.
A short, high-churn reference for attribute names, pinned to semconv 1.44.0. Stable code attributes
are `code.function.name` (fully-qualified, no arguments), `code.file.path`, `code.line.number`,
`code.column.number`, `code.stacktrace`; the older `code.function`, `code.filepath`, `code.lineno`,
`code.column`, `code.namespace` are all formally Deprecated. Exception attributes `exception.type`/
`exception.message`/`exception.stacktrace` are Stable with type-or-message conditionally required;
`exception.escaped` is Deprecated. The whole `log.*` namespace is still Development. Flag the
in-progress migration: `OTEL_SEMCONV_EXCEPTION_SIGNAL_OPT_IN` with values `logs` and `logs/dup` moves
exception recording off span events, and exception log records should use an event name with a
`.exception` suffix.

**6. "Redaction placement: Filter at the logger, never the Formatter"** — destination: `logging_observability_manifest.md` (replace §11's mechanism paragraph).
Turn the current coin-flip into a decision with a stated reason. Coverage: logger-Filter >
handler-Filter > Formatter, because propagation offers records to ancestor handlers without
re-consulting ancestor levels or filters. Surface area: `record.msg`, `record.args` (because
`%(message)s` is `msg % args`), `record.exc_info`/`exc_text`, and every `extra` key. Ordering:
upstream of `QueueHandler.prepare()`, and before the renderer in a structlog chain. Include OWASP's
log-injection requirement (strip CR/LF/delimiters) as an obligation separate from secret redaction,
since a filter that only masks values still lets a multi-line attacker-controlled string forge entries.

**7. "The lint contract for logging"** — destination: `python_testing_tooling_manifest.md` (tooling belongs there), cross-referenced from `logging_observability_manifest.md` §9.
Enumerate ruff's `LOG` and `G` families as the mechanical enforcement of this manifest's rules, naming
which manifest rule each enforces: `LOG015` enforces "never log to root", `LOG001` enforces "always
`getLogger()`", `LOG002` catches `getLogger(__file__)`, `G004`/`G001`/`G002`/`G003` enforce lazy args,
`G101` catches the `extra` collision that raises `KeyError` at runtime, `LOG004`/`LOG014`/`G201`/`G202`
police exception logging, `LOG009`/`G010` police `.warn`. State plainly that no lint exception is
required for the recommended `%`-args idiom — the earlier assumption to the contrary was wrong.

## Traps for coding agents

1. **`extra={"taskName": ...}` and friends raise `KeyError`, not "field ignored".** Any key already present in `LogRecord.__dict__` triggers `KeyError("Attempt to overwrite %r in LogRecord")` from `Logger.makeRecord` — including `name`, `msg`, `args`, `module`, `filename`, `lineno`, `funcName`, `process`, `processName`, `thread`, `threadName` and `taskName`. Agents reach for `extra={"module": ...}` or `extra={"name": ...}` constantly. Namespace every key.
2. **`extra={"message": ...}` and `extra={"asctime": ...}` also raise** even though neither is set in `__init__` — they are guarded by an explicit literal list because the `Formatter` adds them later.
3. **`getLevelNamesMapping()` is 3.11, not 3.13.** Guessing "3.12/3.13" for a 3.11 API produces a needless version gate. Likewise `taskName` and `logAsyncioTasks` are 3.12, `merge_extra` is 3.13, `getHandlerByName`/`getHandlerNames` are 3.12, `stacklevel` is 3.8.
4. **`QueueListener` ignores handler levels by default.** `respect_handler_level=False` is the constructor default. An agent that moves an existing console-INFO/file-DEBUG fan-out behind a queue will emit every record to every handler and never see a warning.
5. **A JSON formatter on the listener side of a queue receives a pre-rendered string.** `QueueHandler.prepare()` has already merged msg+args and nulled `args`/`exc_info`/`exc_text`. The structured pipeline must be on the QueueHandler side, or `prepare()` must be overridden.
6. **`QueueListener.start()` raises `RuntimeError` on a second call as of 3.14.** Idempotent-start helpers that worked on 3.13 now throw.
7. **`dictConfig` disables your loggers by default.** `disable_existing_loggers` defaults to `True`, so configuring logging after your modules have imported (and called `getLogger(__name__)`) silences them. Set it explicitly to `False` unless replacement is intended.
8. **Two `dictConfig` calls do not merge.** `incremental` defaults to `False`; the second call replaces the first. And `disable_existing_loggers` is ignored whenever `incremental` is True.
9. **`version: 1` is not a placeholder.** It is required and "The only valid value at present is 1". Agents sometimes write `version: 2` or omit it.
10. **`logging.WARN` and `Logger.warn()` still exist and still work.** `warn()` emits a `DeprecationWarning`, which default filters hide, so the deprecation is invisible at runtime. Meanwhile `getLevelName(30)` can never return `'WARN'` because `_levelToName` has no such entry — code that round-trips names through `getLevelName` and compares to `'WARN'` silently never matches.
11. **NOTSET on a *handler* means "handle everything", not "defer".** The deferral semantics are logger-only. `handler.setLevel(logging.NOTSET)` is not a no-op that inherits from somewhere.
12. **Propagation does not re-check ancestor levels or filters.** Setting the root logger to ERROR does not stop a child logger's DEBUG record from reaching root's handlers if the child's own effective level allows it — only the child's effective level and each handler's own level gate it. Agents "raise the root level to quiet things down" and are surprised.
13. **The root logger starts at WARNING, every other logger at NOTSET.** That asymmetry is why `basicConfig(level=DEBUG)` works while `getLogger("x").setLevel(DEBUG)` alone produces nothing beyond the WARNING-level `lastResort`.
14. **`logging.disable()` is global and checked before everything else.** A library that calls it, or a test that calls it and forgets `logging.disable(logging.NOTSET)`, silences the entire process irrespective of per-logger configuration.
15. **Defining a custom level at an existing numeric value destroys the built-in name**: "If you define a level with the same numeric value, it overwrites the predefined value; the predefined name is lost."
16. **A `Filter` that forgets `return True` drops every record.** `Filter.filter` is both the injection hook and the predicate; used as a field-stamper it must still return truthy.
17. **A custom format string containing `%(request_id)s` makes that field mandatory.** "the message will not be logged because a string formatting exception will occur" if any call omits it. Use a Filter that supplies a default, not a hope.
18. **`LoggerAdapter` silently discards call-site `extra`** unless `merge_extra=True` (3.13+): "if you had passed an 'extra' keyword argument in the call to the adapter, it will be silently overwritten."
19. **f-strings in log calls are a lint violation, but `%`-args are not.** The trap is the inverse belief. `G004` flags `logger.info(f"...")`; `G002` flags `logger.info("%s" % x)`; nothing flags `logger.info("%s", x)`. Do not add a suppression for the correct idiom.
20. **`isEnabledFor` is already cached by CPython.** Hand-rolling a `_debug_enabled` boolean buys almost nothing and goes stale on reconfiguration (the internal `_cache` is invalidated by the logging machinery; yours is not). Guard only to avoid *building arguments*.
21. **`logging.config.listen()` is an `eval()`-based RCE surface**: "portions of the configuration are passed through `eval()`". Never expose it without a `verify` callable, and preferably not at all.
22. **`raiseExceptions = False` converts every handler fault into silence**, including full-queue drops from `QueueHandler`. It is a production knob with a diagnosability cost, not a tidiness setting.
23. **Logging to one file from several processes is unsupported** — not slow, not racy-but-fine: "not supported, because there is no standard way to serialize access to a single file across multiple processes in Python." Use a listener process or a socket receiver. And with `multiprocessing`, use `multiprocessing.Queue`, not `queue.SimpleQueue`.
24. **`taskName` is `None` far more often than agents assume** — any sync program, and any call outside a running event loop (the `RuntimeError` is swallowed). A format string using `%(taskName)s` renders the literal `None`.
25. **contextvars do not cross into threads.** They copy into asyncio Tasks at creation, but a `threading.Thread` or `ThreadPoolExecutor` worker starts on its own context stack, "in a similar fashion to `threading.local()`". A correlation ID bound on the request thread vanishes in the executor.
26. **`ContextVar.get()` raises `LookupError` with no default.** Inside a `Filter`, that turns the first log call outside a request scope into an exception during logging.
27. **"OpenTelemetry logs are stable" is false for Python.** The *spec* is stable; the *Python* Logs signal is `Development` per opentelemetry.io/status. The SDK path is literally `opentelemetry.sdk._logs`.
28. **`LoggingHandler` is deprecated** as of opentelemetry-sdk 1.40.0 in favour of `opentelemetry-instrumentation-logging` — which is versioned `0.65b0`, i.e. beta. Both facts must be stated together or the recommendation misleads.
29. **The OTel Events API/SDK no longer exists.** Removed in 1.44.0; "Use `LogRecord` with the `event_name` field set instead". Code or tutorials referencing the events module are dead.
30. **OTel Python has two version lines that must be pinned together**: `1.44.0` for api/sdk and `0.65b0` for semconv and every instrumentation package. Pinning only the `1.x` line lets the beta line drift.
31. **`code.function`, `code.filepath`, `code.lineno`, `code.namespace` are all deprecated semconv names.** Emit `code.function.name` (fully qualified), `code.file.path`, `code.line.number`. This is the semconv mistake an agent is most likely to make from memory.
32. **`exception.escaped` is deprecated**, and exception recording is moving off span events onto log records behind `OTEL_SEMCONV_EXCEPTION_SIGNAL_OPT_IN` (`logs` | `logs/dup`).
33. **The whole `log.*` semconv namespace is Development**, so `log.record.uid`/`log.file.name`/`log.iostream` are not stable ground for a schema.
34. **Python severities are not SeverityNumber 1-5.** DEBUG/INFO/WARNING/ERROR/CRITICAL map to 5/9/13/17/21 under the range rules. An off-by-range mapping makes every log look like TRACE.
35. **`OTEL_PYTHON_LOG_CORRELATION` defaults to `false`.** Installing `opentelemetry-instrumentation-logging` and expecting trace ids in log lines without setting it (or `set_logging_format=True`) produces nothing.
36. **There is still no JSON formatter in the stdlib** as of 3.15.0rc1 — the documented formatters are `Formatter` and `BufferingFormatter`. An agent writing `logging.JSONFormatter`, or a `dictConfig` entry with `class: logging.JsonFormatter`, is inventing an API.
37. **python-json-logger is alive and its import path moved.** Use `pythonjsonlogger.json.JsonFormatter`; `pythonjsonlogger.jsonlogger` has been deprecated since 3.1.0. And 4.0.0 removed string-valued `json_default`/`json_encoder`/`json_serializer`, so `dictConfig` entries passing dotted-path strings for those now fail.
38. **structlog's chain order is semantic.** `merge_contextvars` must be first; `ProcessorFormatter.remove_processors_meta` must be first in the formatter's chain; `wrap_for_formatter` must be last on the structlog side (`render_to_log_kwargs` is not a substitute); only the last processor may return a rendered string.
39. **`structlog.configure()` after the first bound logger is created may not take effect** when `cache_logger_on_first_use=True`, which is the recommended setting. Reconfiguration in tests needs an explicit reset, not a second `configure()`.
40. **`warnings.warn` and `logger.warning` are not interchangeable.** The docs split them on *whether the caller can fix it*: `warnings.warn` "if the issue is avoidable and the client application should be modified", `logger.warning` "if there is nothing the client application can do about the situation". The bridge between them is `captureWarnings(True)` into logger `'py.warnings'` at WARNING, not any automatic routing.
41. **The HOWTO's error row says "Raise an exception"**, reserving `error()`/`exception()`/`critical()` for "Report suppression of an error without raising an exception". Log-and-raise is not what the table sanctions.
42. **Removing a handler while a record is being emitted was racy until 3.14.7** (gh-79366, 2026-08-05): "the following handlers of the same logger could be skipped." Dynamic handler swapping in long-running processes needs that floor or its own lock.
43. **`logMultiprocessing` is True by default**, and populating `processName` consults `sys.modules.get('multiprocessing')` and calls `current_process()` on every record. In a hot single-process path, setting `logging.logMultiprocessing = False` (and `logProcesses`/`logAsyncioTasks` as appropriate) is a real, documented saving agents never consider.
44. **`docs.python.org/3/` now serves 3.14.7**, not 3.13. An agent citing "the current docs" while asserting 3.13-era behaviour is quoting a moved target; pin the version in the URL (`/3.14/`, `/3.15/`) when the claim is version-sensitive.
