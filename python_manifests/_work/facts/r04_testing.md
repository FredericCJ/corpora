## Facts

1. The current pytest release is 9.1.1, dated 2026-06-19 in the official changelog and shown as "Jun 19, 2026" on PyPI; the PyPI JSON API reports `info.version` = 9.1.1. pytest 9.1.0 (2026-06-13) is no longer current - VERSION-DEPENDENT (pytest 9.1.1).
2. pytest requires Python >=3.10 (`requires_python` on the PyPI JSON API); pytest 9.0.0 dropped Python 3.9 after its end of life - VERSION-DEPENDENT (pytest 9.x).
3. pytest 9.1.0 "Added official Python 3.15 support" (changelog issue #14524) - VERSION-DEPENDENT (pytest 9.1.0).
4. The pytest changelog dates 9.0.0 as 2025-11-05 while the PyPI release history shows the artefact upload as "Nov 8, 2025"; the changelog is the release-notes date and the two disagree by three days - ESTABLISHED (both pages fetched 2026-08-08).
5. A `pytest 9.2 [UNRELEASED DRAFT] (2026-08-06)` section exists in the development changelog at docs.pytest.org/en/latest/. Nothing in it is released; do not pin against it - OPEN (unreleased).
6. pytest supports native TOML configuration in `pyproject.toml` under the `[tool.pytest]` table, documented as "Use `[tool.pytest]` to leverage native TOML types (supported since pytest 9.0)". The older `[tool.pytest.ini_options]` table is documented as "supported since pytest 6.0" and still works. The two tables **cannot coexist** in one file - VERSION-DEPENDENT (pytest 9.0+).
7. pytest also reads dedicated `pytest.toml` / `.pytest.toml` files, whose options live under a `[pytest]` table (not `[tool.pytest]`) - VERSION-DEPENDENT (pytest 9.0+).
8. The configuration-file precedence order is: `pytest.toml` / `.pytest.toml`, then `pytest.ini` / `.pytest.ini`, then `pyproject.toml`, then `tox.ini` (needs a `[pytest]` section), then `setup.cfg` (needs a `[tool:pytest]` section). "Options from multiple `configfiles` candidates are never merged - the first match wins." `pytest.toml` "will always match and take highest precedence, even if empty" - VERSION-DEPENDENT (pytest 9.x).
9. Fixture scopes are exactly five: `function` (default), `class`, `module`, `package`, `session`. `scope` may be a callable for dynamic scope but must return one of those five strings - ESTABLISHED.
10. Fixture finalisation is LIFO. Yield fixtures "use `addfinalizer` behind the scenes"; for multiple fixtures "the first teardown code to run is from the right-most fixture, i.e. the last test parameter", and for finalizers "the first fixture to run is last call to `request.addfinalizer`" - ESTABLISHED.
11. If a yield fixture raises **before** its `yield`, pytest "won't try to run the teardown code after that yield fixture's yield statement", but every fixture that already ran successfully for that test is still torn down. `request.addfinalizer` differs: "pytest will run that finalizer once it's been added, even if that fixture raises an exception after adding the finalizer" - ESTABLISHED.
12. conftest.py discovery walks **downward from the filesystem root**: for each test path, "Before a `conftest.py` file is loaded, load `conftest.py` files in all of its parent directories." Session and test-running hooks "invoke all hooks defined in `conftest.py` files closer to the root of the filesystem" first - ESTABLISHED.
13. Fixture override precedence is directory conftest < module-level fixture < direct test parametrization; a subdirectory conftest overrides a parent conftest, and the overridden "base or super fixture can be accessed from the overriding fixture". As of pytest 9.1.0 (issue #14513) "Fixture definition override resolution now determined first by visibility in the collection tree rather than registration order" - VERSION-DEPENDENT (pytest 9.1.0).
14. `@pytest.mark.parametrize(..., indirect=True)` routes each parameter value into a fixture of the same name, which reads it as `request.param` and returns the transformed value to the test. `indirect` accepts a list/tuple of argnames for partial indirection (`indirect=["x"]`), leaving other argnames direct. The documented motivation is "more expensive setup at test run time in the fixture, rather than having to run those setup steps at collection time" - ESTABLISHED.
15. In the unreleased pytest 9.2 draft, `indirect`, `ids` and `scope` become keyword-only parameters of `@pytest.mark.parametrize` (issue #8593); passing them positionally will raise `TypeError` - OPEN (unreleased).
16. Unregistered marks "always emit a warning in order to avoid silently doing something surprising due to mistyped names". `--strict-markers` makes "any unknown marks applied with the `@pytest.mark.name_of_the_mark` decorator ... trigger an error". There is a config-file equivalent: `strict_markers = true` - ESTABLISHED.
17. pytest 9.0.0 added a "strict mode" ini option: "Added a 'strict mode' enabled by the `strict` configuration option. When set to `true`, the `strict` option currently enables `strict_config`, `strict_markers`, `strict_parametrization_ids`, `strict_xfail`." `strict_xfail` is an alias for the older `xfail_strict`, `strict_config` for `--strict-config`, `strict_markers` for `--strict-markers`; the unifying PR is pytest-dev/pytest#13839, merged 2025-10-26. Because `strict` will pick up future strictness options automatically, it is recommended only with a locked pytest version - VERSION-DEPENDENT (pytest 9.0+).
18. **pytest 9.0.0 through 9.0.3 silently ignored `--strict-markers` and `--strict-config` when they were supplied via `addopts`.** The root cause is the `OverrideIniAction` compatibility code added in pytest 9 (commit efa9eff); unknown markers and unknown config keys degraded from errors to warnings, so suites appeared to pass. Fixed in pytest 9.1.0: "Fixed regression where `--strict-markers` and `--strict-config` specified through `addopts` were silently ignored" (issue #14442) - VERSION-DEPENDENT (broken 9.0.0-9.0.3, fixed 9.1.0).
19. Applying marks to a fixture function is no longer merely ineffective: pytest 9.0 **removed** the tolerance, and "Decorating a fixture function with marks like `@pytest.mark.usefixtures` now raises an error" - VERSION-DEPENDENT (pytest 9.0+).
20. pytest 9.0 also removed: nose-style bare `setup`/`teardown` methods (use `setup_method`/`teardown_method`), the `pytest.Instance` collector (collection tree is now Class -> Function, not Class -> Instance -> Function), and `py.path.local`-flavoured path arguments from hooks such as `pytest_ignore_collect`, `pytest_collect_file`, `pytest_pycollect_makemodule`. A synchronous test depending on an asynchronous fixture is now an error rather than a warning - VERSION-DEPENDENT (pytest 9.0+).
21. Assertion rewriting is scoped: "pytest only rewrites test modules directly discovered by its test collection process, so asserts in supporting modules which are not themselves test modules will not be rewritten." Shared assertion helpers therefore lose introspection unless `pytest.register_assert_rewrite()` is called **before** the module is imported, which the docs say to do in the root `conftest.py` - ESTABLISHED.
22. Rewriting is disabled per-module by putting the string `PYTEST_DONT_REWRITE` in the module docstring, and globally by `--assert=plain`. Rewritten modules are cached to disk as `.pyc`; caching is suppressed with `sys.dont_write_bytecode = True` in `conftest.py` - ESTABLISHED.
23. pytest ships `pytest.RaisesGroup` and `pytest.RaisesExc` for asserting about `ExceptionGroup` / `BaseExceptionGroup` structure; pytest 9.1.1 fixed bugs in `RaisesGroup` logic - VERSION-DEPENDENT (pytest 9.x).
24. pytest has **native subtests** since 9.0: a `subtests` fixture whose `subtests.test(msg=..., **kwargs)` context manager reports each block independently and continues after failure. The docs say "Added in version 9.0" and "This feature is experimental. Its behavior, particularly how failures are reported, may evolve in future releases." It originated as the `pytest-subtests` plugin and "since 9.0 has been merged into the core." Subtests run at execution time and cannot be selected individually from the command line; parametrize runs at collection time and can be - VERSION-DEPENDENT (pytest 9.0+).
25. pytest 9.1.0 added `--max-warnings` plus a `max_warnings` config option to fail a run when the warning count exceeds a threshold; `assertion_text_diff_style` to render string-equality failures as separate Left/Right blocks; `pytest.register_fixture()` for imperative fixture registration; and datetime/timedelta support in `pytest.approx()` (an explicit `abs` or `rel` timedelta tolerance is required - relative tolerance is not supported for `datetime`) - VERSION-DEPENDENT (pytest 9.1.0).
26. pytest 9.1.0 deprecated (removal in pytest 10): class-scoped fixtures written as plain instance methods without `@classmethod` (issue #10819 - they set attributes on a different instance than the test methods see); `request.getfixturevalue()` during teardown for a fixture not already requested (#12882); non-Collection iterables such as generators as `argvalues` for `parametrize` (#13409, they are exhausted after first iteration); `config.inicfg` (#13946); `pytest.console_main()` (#1764); `--pastebin` (#14434, moved to the `pytest-pastebin` plugin); marker-based hook configuration (#14335) - VERSION-DEPENDENT (pytest 9.1.0).
27. Under `--doctest-modules`, pytest 9.1.0 records a breaking change: autouse fixtures with module, package or session scope defined inline in a Python test module "now possibly execute twice"; the documented workaround is to move those fixture definitions into `conftest.py` (issue #14533) - VERSION-DEPENDENT (pytest 9.1.0).
28. `pytest.yield_fixture` is deprecated for removal in pytest 10, and pytest 9.1.0 marks it deprecated to type checkers via the `deprecated` decorator (issue #14342) - VERSION-DEPENDENT (pytest 9.1.0+).
29. pytest-asyncio's `asyncio_mode` accepts `auto` and `strict`; "If no asyncio mode is specified, the mode defaults to strict", meaning every coroutine test needs `@pytest.mark.asyncio` or it is silently not awaited by this plugin - VERSION-DEPENDENT (pytest-asyncio 1.4.0).
30. `asyncio_default_fixture_loop_scope`, when unset, "defaults to the fixture scope", and pytest-asyncio warns that "In future versions of pytest-asyncio, the value will default to `function` when unset". `asyncio_default_test_loop_scope` unset "defaults to function scope". Both accept `function`, `class`, `module`, `package`, `session` - VERSION-DEPENDENT (pytest-asyncio 1.4.0).
31. AnyIO ships its own pytest plugin in the AnyIO distribution (nothing extra to install), driven by `@pytest.mark.anyio`, which "has the same effect as applying the `pytest.mark.usefixtures('anyio_backend')`". The `anyio_backend` fixture is function-scoped and by default "runs everything on all supported backends". `anyio_mode = "auto"` exists but "does not work if `pytest-asyncio` is installed and configured to use its own `auto` mode, as it will conflict with the AnyIO plugin" - ESTABLISHED (AnyIO docs).
32. The AnyIO plugin and pytest-asyncio differ in a way that changes program semantics, not just syntax: AnyIO "runs all async fixtures and tests in the same task, so context variables set in async fixtures or tests ... will affect other async fixtures and tests within the same runner", whereas pytest-asyncio "runs the setup and teardown phases of each async fixture in a new async task per operation, making context variable propagation impossible and preventing task groups and cancel scopes from functioning properly" - ESTABLISHED (AnyIO docs; this is AnyIO's own characterisation of pytest-asyncio).
33. coverage.py enables branch coverage with `coverage run --branch` (config `[run] branch`, default `False`). It records "pairs of line numbers: a source and destination for each transition from one line to another", compares measured transitions against statically-derived possible transitions, and paints partially-covered lines yellow in HTML with the un-taken destination line numbers annotated - ESTABLISHED.
34. `# pragma: no branch` marks an intentionally partial branch (e.g. `while True:`). If one arm of a conditional is excluded, coverage.py stops treating the conditional as a branch at all. Generator expressions can report a partial branch "because the generator did not iterate until `StopIteration` is raised" - ESTABLISHED.
35. coverage.py's measurement core is selected by `[run] core` with allowed values `ctrace`, `sysmon`, `pytrace`. The `sysmon` (PEP 669 `sys.monitoring`) core is "Only available in Python 3.12+, and the default in Python 3.14+. The sysmon core does not yet support plugins, dynamic contexts, or some concurrency libraries. In Python 3.12 and 3.13, it does not support branch coverage." - VERSION-DEPENDENT (coverage.py 7.15.x on CPython 3.12+).
36. sysmon became the default on Python 3.14+ in coverage.py **7.9.1 (2025-06-13)**: "On Python 3.14+, the 'sysmon' core is now the default". `sys.monitoring` branch-coverage support landed earlier, in coverage.py 7.7.0 (2025-03-16): "The experimental sys.monitoring support now works for branch coverage if you are using Python 3.14.0 alpha 6 or newer" - VERSION-DEPENDENT (coverage.py 7.9.1 / 7.7.0).
37. Dynamic contexts answer "what test ran this line?". Only one built-in value is supported: `[run] dynamic_context = test_function`, which "start[s] a new dynamic context for every test function"; any function whose name starts with `test` becomes its own context. Static contexts come from `--context=CONTEXT` / `[run] context`; when both exist "they are joined with a pipe symbol to be recorded as a single string." Reporting uses `--contexts` (comma-separated regexes) and `coverage html --show-contexts` - ESTABLISHED.
38. Dynamic contexts and the sysmon core are mutually exclusive, and until very recently the combination failed silently through the API path pytest-cov uses. coverage.py 7.15.3 (2026-08-02): "the sysmon core is incompatible with dynamic contexts. Previously, the combination would be prevented when read from the coverage.py configuration. But using the context API as pytest-cov does, contexts would be silently dropped. Now a warning is issued" - VERSION-DEPENDENT (coverage.py 7.15.3).
39. **pytest-cov 7.0.0 (2025-09-09) dropped subprocess measurement support.** Coverage of code that runs in child processes now requires opting in via coverage.py config: `[run] patch = subprocess`. pytest-cov 7.0.0 also requires coverage >= 7.10.6 - VERSION-DEPENDENT (pytest-cov 7.x).
40. coverage.py's `[run] patch` option was added in coverage.py 7.10 and accepts `execv`, `_exit`, `fork`, `subprocess`. `subprocess` "configures Python to start coverage automatically, and will apply to processes created with `subprocess`, `os.system()`, or one of the `execv` or `spawnv` family of functions"; `_exit` saves data before `os._exit()`; `execv` is "Not available on Windows" - VERSION-DEPENDENT (coverage.py 7.10+).
41. coverage.py config lives in `[tool.coverage.run]`, `[tool.coverage.report]`, `[tool.coverage.html]`, `[tool.coverage.paths]` tables in `pyproject.toml`. Defaults that matter: `branch = False`, `parallel = False`, `concurrency = "thread"`, `relative_files = False`, `sigterm = False`, `show_missing = False`, `skip_covered = False`. `fail_under`, `partial_branches`, `exclude_also`, `omit`, `source` have no default - ESTABLISHED.
42. Martin Fowler, "TestCoverage" (2012-04-17): "Test coverage is a useful tool for finding untested parts of a codebase. Test coverage is of little use as a numeric statement of how good your tests are." And: "If you make a certain level of coverage a target, people will try to attain it. The trouble is that high coverage numbers are too easy to reach with low quality testing." And: "If you are testing thoughtfully and well, I would expect a coverage percentage in the upper 80s or 90s. I would be suspicious of anything like 100% - it would smell of someone writing tests to make the coverage numbers happy, but not thinking about what they are doing." - ESTABLISHED (primary).
43. Hypothesis `settings` defaults, from the API reference: `max_examples = 100`, `deadline = 200` milliseconds (int, float or `timedelta`), `derandomize = False`, `print_blob = False`, and `database` = a `DirectoryBasedExampleDatabase` at `.hypothesis/examples`. If that location is unusable "Hypothesis will emit a warning and fall back to an `InMemoryExampleDatabase`"; `database=None` means "no storage will be used" - VERSION-DEPENDENT (Hypothesis 6.165.x).
44. **Hypothesis silently changes its own defaults in CI.** `is_in_ci()` checks the environment variables `CI`, `__TOX_ENVIRONMENT_VARIABLE_ORIGINAL_CI`, `TF_BUILD` (Azure Pipelines), `bamboo.buildKey`, `BUILDKITE`, `CIRCLECI`, `CIRRUS_CI`, `CODEBUILD_BUILD_ID`, `GITHUB_ACTIONS`, `GITLAB_CI`, `HEROKU_TEST_RUN_ID`, `TEAMCITY_VERSION`. When any is set, the `"ci"` profile is loaded: `derandomize=True, deadline=None, database=None, print_blob=True, suppress_health_check=[HealthCheck.too_slow]` - VERSION-DEPENDENT (Hypothesis 6.165.x).
45. The consequence of fact 44 is operational: in CI there is **no example database**, so a counterexample found in CI is not replayed on the next CI run; instead `derandomize=True` makes the input set a deterministic function of the test function plus the Hypothesis/Python version, so it changes when any of those change. `print_blob=True` is the intended recovery path - it prints a `@reproduce_failure(...)` blob to paste locally - VERSION-DEPENDENT (Hypothesis 6.165.x).
46. `deadline` is not a hard per-example timeout. The documented behaviour: "We treat the deadline as a soft limit in some cases, where that would avoid flakiness due to timing variability" - the deadline is raised during generation and shrinking and the failing case is then replayed against the real deadline, so "tests right on the cusp of being too slow may pass artificially". Exceeding it raises `DeadlineExceeded` - VERSION-DEPENDENT (Hypothesis 6.165.x).
47. `HealthCheck` members are exactly: `data_too_large`, `filter_too_much`, `too_slow`, `large_base_example`, `function_scoped_fixture`, `differing_executors`, `nested_given`. `FailedHealthCheck` is raised when one trips - VERSION-DEPENDENT (Hypothesis 6.165.x).
48. `HealthCheck.function_scoped_fixture` exists because a pytest function-scoped fixture requested by an `@given` test "runs once for the whole function, not once per test case" - the fixture is **not** reset between generated inputs, so mutated state leaks across examples. Suppress it only when the fixture is genuinely idempotent - VERSION-DEPENDENT (Hypothesis 6.165.x).
49. The documented way to suppress a health check globally is a settings profile registered in `conftest.py`: `settings.register_profile("my_profile", suppress_health_check=[HealthCheck.filter_too_much])` followed by `settings.load_profile("my_profile")`. The docs warn against blanket suppression because several checks "catch subtle interactions that may save you hours of debugging" - ESTABLISHED.
50. `Phase` members are exactly `Phase.explicit`, `Phase.reuse`, `Phase.generate`, `Phase.target`, `Phase.shrink`, `Phase.explain`, and all are enabled by default. `Phase.reuse` is what replays the database; `Phase.explicit` runs `@example` cases - VERSION-DEPENDENT (Hypothesis 6.165.x).
51. Core strategies in `hypothesis.strategies`: `integers()`, `floats()`, `text()`, `binary()`, `lists()`, `dictionaries()`, `sets()`, `tuples()`, `sampled_from()`, `one_of()`, `builds()`, `from_type()`, `data()`, `composite()`, `recursive()`, `deferred()`, `dates()`, `datetimes()`, `none()`, `just()`, `booleans()`. `@composite` supplies a `draw` callable so later draws can depend on earlier values. `builds(C, ...)` draws args/kwargs and calls the callable, inferring strategies from annotations (pass `...` to force inference). `from_type(T)` "Looks up the appropriate search strategy for the given type" - ESTABLISHED.
52. `.map(f)` transforms after generation; `.filter(pred)` narrows inside the strategy and can trip `HealthCheck.filter_too_much`; `.flatmap()` makes one strategy depend on another's output; `assume()` rejects at test level and is the least efficient of the four. Prefer constructing the right strategy over filtering it - ESTABLISHED.
53. Stateful API: `RuleBasedStateMachine` plus `@rule` (with `target`/`targets` naming the destination bundle), `@initialize` ("All `@initialize()` decorated methods will be called before any `@rule()` decorated methods, in an arbitrary order. Each `@initialize()` method will be called exactly once per run."), `@precondition`, `@invariant` (accepts `check_during_init=True`), `Bundle("name")`, `consumes()` to remove a bundle value after use, `multiple()` to return several values to a target, and `run_state_machine_as_test()`. `stateful_step_count` defaults to 50 - VERSION-DEPENDENT (Hypothesis 6.165.x).
54. pytest does not collect a `RuleBasedStateMachine` subclass. You must expose it: `TestMyMachine = MyMachine.TestCase`. Failing runs print a replayable Python transcript ("most of the time you should just be able to copy and paste the code into a test to reproduce it") of the form `state = DatabaseComparison(); var1 = state.add_key(k=b''); ...` - ESTABLISHED.
55. As of Hypothesis 6.160.0 (2026-07-22) `Bundle` supports efficient `.filter()` and `.map()`; as of 6.164.0 (2026-07-30) `functions()` generates async functions and generator functions - VERSION-DEPENDENT (Hypothesis 6.160.0 / 6.164.0).
56. **Hypothesis is no longer pure Python.** 6.156.0 (2026-07-01): "As of this release, Hypothesis now requires a rust toolchain to build from source (if not installing from a native wheel)." Native wheels are published for CPython 3.10-3.14 plus 3.14t and (except musllinux) PyPy 3.11, on Linux x86_64/aarch64 manylinux+musllinux, macOS x86_64/arm64, Windows x64, plus Pyodide wasm32 for 3.13. The docs do not describe a retained pure-Python fallback - VERSION-DEPENDENT (Hypothesis 6.156.0+).
57. Hypothesis 6.159.0 (2026-07-22) changed user-facing terminology from "example" to "test case" in messages and docs; the `max_examples` setting name is unchanged - VERSION-DEPENDENT (Hypothesis 6.159.0).
58. pytest-xdist distribution modes are `load` (default: "Sends pending tests to any worker that is available, without any guaranteed order"), `loadscope` (group by module for functions / class for methods), `loadfile` (group by file), `loadgroup` (group by the `xdist_group` mark), `worksteal` (even initial split, idle workers steal), and `no`. `-n auto` "uses as many processes as your computer has physical CPU cores"; `-n logical` uses logical cores and requires `psutil` - VERSION-DEPENDENT (pytest-xdist 3.8.0).
59. pytest-xdist's last release is 3.8.0 (2025-07-01) - over a year old as of 2026-08-08. 60. pytest-randomly 4.1.0 reseeds at the start of the run and again before each test's setup, call and teardown, deriving each seed from the base seed plus the test ID. 2. **Two pytest TOML tables that cannot coexist, and a precedence chain that ignores `pyproject.toml` entirely.** An empty `pytest.ini` or `pytest.toml` anywhere up the tree "will always match and take highest precedence, even if empty", and candidates are "never merged - the first match wins". Adding `[tool.pytest]` to `pyproject.toml` in such a repo changes nothing, silently.
3. **`[tool.pytest]` and `[tool.pytest.ini_options]` are different data models, not synonyms.** The former takes native TOML types (booleans, integers, arrays); the latter takes INI-flavoured values. Copying values between them without retyping produces wrong config or a parse error.
4. **`pytest.toml` uses `[pytest]`, not `[tool.pytest]`.** The `tool.` prefix belongs to `pyproject.toml` only. pytest 9.2's draft even adds an error for top-level options in `pytest.toml` without a `[pytest]` table (#14638).
5. **Hypothesis rewrites its own defaults when it sees a CI environment variable.** `database=None` in CI means the counterexample found in yesterday's CI run is not replayed today; `deadline=None` means a slow-test regression is invisible in CI but fails locally at 200 ms; `derandomize=True` means "flaky" property failures instead appear and disappear in blocks when Hypothesis or Python is upgraded. An agent debugging "it fails locally but not in CI" will chase the wrong cause.
6. **`HealthCheck.function_scoped_fixture`: a function-scoped fixture is not reset per generated example.** It runs once per test function. Any fixture holding mutable state (a list, a dict, an in-memory DB, a `Mock`) accumulates across all 100 examples. Agents routinely suppress this check to make a test pass, which converts a real leak into a silent one.
7. **Hypothesis `deadline` is a soft limit.** It is raised during generation and shrinking and only enforced on replay, so a test "right on the cusp of being too slow may pass artificially". Do not treat `deadline` as a performance assertion.
8. **`assume()` and `.filter()` are not free.** Heavy rejection trips `HealthCheck.filter_too_much` and silently reduces the effective example count long before it errors. Construct the constrained strategy (`integers(min_value=1)`) rather than filtering a wide one.
9. **pytest will not collect a `RuleBasedStateMachine`.** Without an explicit `TestMyMachine = MyMachine.TestCase` line, the whole state machine is dead code that reports zero tests and zero failures.
10. **Hypothesis is no longer a pure-Python wheel.** Since 6.156.0 it needs a Rust toolchain to build from source. Any platform, architecture or Python variant outside the published wheel matrix now fails at install time in a container that has no `cargo`.
11. **`--branch` is off by default in coverage.py.** A quoted "94% coverage" without `[run] branch = true` is statement coverage and is compatible with every `else:` in the codebase being untested.
12. **On Python 3.14 the default coverage core silently cannot do what you asked.** `sysmon` is the default and supports neither plugins nor dynamic contexts. Before coverage.py 7.15.3 the pytest-cov context API path dropped contexts with no message at all, producing an empty per-test attribution report that looked like a reporting bug.
13. **pytest-cov 7.0.0 stopped measuring subprocesses.** Coverage of anything launched via `subprocess`, `os.system()` or `execv`/`spawnv` now requires `[run] patch = subprocess` in coverage config. Symptom: a CLI's own module shows 0% while its tests pass. `patch = execv` is unavailable on Windows.
14. **Assertion rewriting stops at the collection boundary.** Assertions inside a shared `tests/helpers.py` produce bare `AssertionError` with no introspection, because "pytest only rewrites test modules directly discovered by its test collection process". `pytest.register_assert_rewrite("tests.helpers")` must run in the root `conftest.py` **before** the first import of that module - after the import it does nothing.
15. **Marks on fixtures now raise.** Pre-9.0 code with `@pytest.mark.usefixtures` or `@pytest.mark.skipif` above `@pytest.fixture` was silently ineffective; on pytest 9.0+ it is an error. An agent porting old suites will read the error as a pytest bug.
16. **pytest 9.0 removed bare `setup`/`teardown` methods.** nose-style test classes that worked on pytest 8.x now run with no setup at all if the names are not `setup_method`/`teardown_method`. Removals are quiet by nature - the methods simply are not called.
17. **A synchronous test requesting an async fixture is an error on pytest 9.0+, not a warning.** Previously it yielded a coroutine object that the test then compared or truth-tested, usually passing by accident.
18. **pytest-asyncio defaults to `strict`.** An `async def test_...` without `@pytest.mark.asyncio` is not run by the plugin. Combined with pytest 9's async handling this is a test that reports as collected and contributes nothing.
19. **pytest-asyncio's `asyncio_default_fixture_loop_scope` unset means "the fixture's own scope" today and "`function`" in a future release**, and the plugin warns about exactly this. Setting it explicitly now is the only way to keep behaviour stable across upgrades.
20. **pytest-asyncio runs each async fixture's setup and teardown in a new task.** Cancel scopes and task groups spanning setup and teardown do not work, and context variables set in a fixture do not reach the test. Code that is correct under AnyIO's plugin is broken under pytest-asyncio and vice versa; this is a semantic difference, not a marker rename.
21. **Enabling both pytest-asyncio auto mode and AnyIO auto mode conflicts.** AnyIO's docs say its `anyio_mode = "auto"` "does not work if `pytest-asyncio` is installed and configured to use its own `auto` mode"; the fix is to remove `asyncio_mode` so pytest-asyncio falls back to strict.
22. **`--dist load` guarantees no ordering.** Any test that depends on another test having run, on a shared module-level global, or on a session fixture's mutation order breaks only under `-n`, and then intermittently. `loadscope`/`loadfile`/`loadgroup` co-locate but do not make dependent tests correct - they hide the defect.
23. **`-n auto` counts physical cores, `-n logical` counts logical cores and needs `psutil`.** An agent assuming `auto` uses hyperthreads will mis-size CI runners.
24. **pytest-xdist 3.8.0 predates pytest 9.0.** It is the one load-bearing plugin in this stack with no release since 2025-07-01. Treat xdist-plus-pytest-9 as a combination to smoke-test rather than assume.
25. **Randomised order plus a random seed is only reproducible if you record the seed.** pytest-randomly prints it in the header; CI logs that are truncated or discarded destroy the only handle on the failure. `--randomly-seed=last` works locally, not across machines.
26. **`--randomly-dont-reorganize` still reseeds** and `--randomly-dont-reset-seed` still shuffles. They are independent switches; an agent that reaches for one to "turn off randomness" gets half of it.
27. **respx mocks HTTPX; responses mocks `requests`.** Installing the wrong one produces tests that issue real network calls while the fixture reports as active. The failure mode is a passing test suite with outbound traffic.
28. **Anything using testcontainers is not a unit test** under the Feathers definition - it requires a container runtime and environmental setup. Marking such tests and excluding them from the default run is what keeps the fast suite fast; leaving them unmarked makes the whole suite fail on any machine without Docker.
29. **`@pytest.mark.parametrize` with a generator as `argvalues` is deprecated in pytest 9.1.0** precisely because generators are exhausted after first iteration - previously this produced a suite that silently collected fewer cases on re-collection.
30. **pytest 9.2 (draft) makes `indirect`, `ids` and `scope` keyword-only.** Code written today as `@pytest.mark.parametrize("x", vals, True)` will raise `TypeError` on that release.
31. **Class-scoped fixtures written as plain instance methods are deprecated in pytest 9.1.0** because "such fixtures set attributes on different instances than test methods use" - a class-scoped fixture assigning `self.client` is not visible to the tests. Use `@classmethod`.
32. **Under `--doctest-modules`, module/package/session-scoped autouse fixtures defined inline in a test module may execute twice** on pytest 9.1.0 (#14533). Expensive or non-idempotent session setup silently doubles. Move it to `conftest.py`.
33. **mutmut 3 does not mutate code outside functions.** Module-level constants, dataclass field defaults and top-level configuration are untouched, so a clean mutation score says nothing about them. mutmut 2 had a different execution model that did.
34. **Mutation testing on a suite that is not already green, or not already fast, produces garbage or never finishes.** Cost scales with mutant count times suite runtime. An agent that adds `mutmut run` to a PR gate on a multi-minute suite has built a timeout.
35. **A 100% mutation score gate is worse than no gate**, for the same Goodhart reason Fowler gives for coverage. "No new surviving mutants in protected modules" is the enforceable version.
36. **Coverage percentage is a diagnostic.** Fowler: "high coverage numbers are too easy to reach with low quality testing", and he would be "suspicious of anything like 100%". A `fail_under` gate paired with assertion-free tests is a mechanism for producing exactly that.
37. **Fixture teardown is LIFO across the parameter list, right to left.** An agent writing a fixture that assumes a sibling fixture is still alive during its own teardown must know which side of the parameter list it is on. Errors raised before a `yield` skip that fixture's own teardown but not its predecessors'.
38. **conftest.py hooks fire root-first, not nearest-first.** The conftest nearest the test overrides *fixtures*, but hook implementations from conftests "closer to the root of the filesystem" are invoked first. Agents conflate the two orderings.
39. **Fixture override resolution changed in pytest 9.1.0** from registration order to "visibility in the collection tree" (#14513). Suites that relied on the old order to pick between two same-named fixtures can resolve differently after upgrading, with no error.
40. **`indirect=True` changes what the test receives.** The parametrize value goes to the fixture as `request.param`, and the test receives the fixture's return value. An agent adding `indirect=True` to make a fixture parametrizable, without a fixture of that name that reads `request.param`, gets a fixture-lookup error; adding it to a fixture that ignores `request.param` gets silently constant test data.
41. **The `subtests` fixture is pytest-native since 9.0 but explicitly experimental**, and subtests cannot be selected individually from the command line the way parametrized cases can. Reaching for subtests when the cases are known at collection time trades away selectability for nothing.
42. **Python 3.10 leaves security support in October 2026.** A support matrix written today that includes 3.10 will be claiming support for an end-of-life interpreter within three months.
43. **Only mocks require behaviour verification.** An agent that reaches for `Mock` by default is choosing implementation coupling; `autospec=True` or `spec_set=True` at least prevents the mock's surface from drifting from the real object's when the real API changes. A `Mock()` with no spec accepts every call, including misspelled ones, and returns a truthy `Mock`, so `assert result.is_valid()` passes against nothing.
44. **A fake without a shared contract suite is not a fake.** The whole justification for preferring fakes over mocks is that the fake implements the real contract; that only holds if one parametrized suite runs against both the fake and the real implementation. Otherwise the fake encodes the author's belief about the contract, and drift is undetectable.
