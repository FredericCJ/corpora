## Facts

### Release cycle and support windows

1. CPython 3.14.7, released 2026-08-05, is the newest release of the newest stable feature line; python.org's "Download the latest version" points at it, and its release page calls it "the seventh maintenance release of Python 3.14" with "around 499 bugfixes, build improvements and documentation changes" from 86 contributors - VERSION-DEPENDENT (3.14)
2. 3.15 is in the release-candidate phase, not alpha and not beta: 3.15.0rc1 shipped 2026-08-04, rc2 is scheduled 2026-09-01, and 3.15.0 final is scheduled 2026-10-01, all per PEP 790 ("PEP 790 - Python 3.15 Release Schedule", status Active) - VERSION-DEPENDENT (3.15)
3. PEP 790's beta-1 line reads "3.15.0 beta 1: Thursday, 2026-05-07 (No new features beyond this point.)", so the 3.15 feature set has been frozen since 2026-05-07 and no new 3.15 feature can appear now - VERSION-DEPENDENT (3.15)
4. The 3.15.0rc1 announcement states "Entering the release candidate phase, only reviewed code changes which are clear bug fixes are allowed between this release candidate and the final release" and "There will be no ABI changes from this point forward in the 3.15 series", and adds "Any binary wheels built against Python 3.15.0 release candidates will work with future versions of Python 3.15" - VERSION-DEPENDENT (3.15)
5. Python 3.16 does not exist as any downloadable artefact today. Per PEP 826 ("PEP 826 - Python 3.16 Release Schedule", status Active), 3.16 development began 2026-05-07, alpha 1 is scheduled 2026-10-13, beta 1 / feature freeze is 2027-05-04 ("No new features beyond this point."), and 3.16.0 final is 2027-10-05 - VERSION-DEPENDENT (3.16)
6. `main` in the CPython repo is 3.16, and devguide states it "is the only branch that accepts new features" - a feature merged today ships in 3.16, not 3.15 - VERSION-DEPENDENT (3.16)
7. PEP 745 lists 3.14.7 as the latest actual bugfix release and schedules 3.14.8 through 3.14.14, with 3.14.14 (around 2027-10) described as "the final regular bugfix release with binary installers"; security-only source releases then run "until approximately October 2030" - VERSION-DEPENDENT (3.14)
8. PEP 719 reads: "3.13 will receive bugfix updates approximately every 2 months for approximately 24 months. Around the time of the release of 3.15.0 final, the final 3.13 bugfix update will be released. After that, it is expected that security updates (source only) will be released until 5 years after the release of 3.13.0 final, so until approximately October 2029." So 3.13 leaves the bugfix phase around 2026-10 - VERSION-DEPENDENT (3.13)
9. PEP 693 reads: "3.12 received bugfix updates approximately every 2 months for approximately 18 months ... security updates (source only) will be released until 5 years after the release of 3.12.0 final, so until approximately October 2028." 18 months for 3.12 versus 24 months for 3.13 confirms the bugfix-phase extension took effect with 3.13 - VERSION-DEPENDENT (3.12, 3.13)
10. devguide's development-cycle page defines the security phase as "A branch less than 5 years old but no longer in bugfix mode is a security branch. The only changes made to a security branch are those fixing issues exploitable by attackers such as crashes, privilege escalation and, optionally, other issues such as denial of service attacks", and adds "Any release made from a security branch is source-only and done only when actual security fixes have been applied to the branch" - ESTABLISHED
11. Consequence of fact 10: 3.12, 3.11 and 3.10 get no binary installers. The 3.12.13 release page says "Python 3.12 isn't receiving regular bug fixes anymore, and binary installers are no longer provided for it" and "releases of those are made irregularly in source-only form until October 2028" - VERSION-DEPENDENT (3.10, 3.11, 3.12)
12. Security-branch releases have no cadence: the 2026-03-03 tri-release announcement states "As these Python versions are now in security-fix-only mode, these are source-only releases, and there is no pre-set release cadence." Pinning `3.11.15` is reproducible but says nothing about how soon a CVE fix will land - VERSION-DEPENDENT (3.10, 3.11, 3.12)
13. Python 3.10 reaches end of life in October 2026 (devguide, estimated) - roughly two months from now. Python 3.9 is already EOL, with 2025-10-31 shown as an actual, not estimated, date - VERSION-DEPENDENT (3.9, 3.10)
14. devguide's security policy limits CVE eligibility to branches whose status is "bugfix" or "security"; branches with status "feature" or "prerelease" are not eligible for CVE IDs, so 3.15.0rc1 and the coming 3.16 alphas sit outside the CVE process - ESTABLISHED
15. PEP 2026 ("Calendar versioning for Python", Python-Version 3.26) has status **Rejected**. Numbering continues 3.15, 3.16, 3.17; there is no Python 3.26 and no CalVer scheme - ESTABLISHED

### 3.14 - what matters for testability, diagnosability, modularity

16. PEP 768 ("Safe external debugger interface for CPython") shipped in 3.14: `sys.remote_exec(pid, script_path)` schedules a Python file for execution inside another running interpreter, and `python -m pdb -p PID` attaches pdb to a live process. It is compiled in by default (`Py_REMOTE_DEBUG` defined), disabled per process with `-X disable_remote_debug` / `PYTHON_DISABLE_REMOTE_DEBUG`, and removable at build time with `--without-remote-debug` - VERSION-DEPENDENT (3.14)
17. PEP 649 plus PEP 749 make annotations lazily evaluated in 3.14 and add `annotationlib` with three formats: `Format.VALUE` (evaluates, raises `NameError` on undefined names), `Format.FORWARDREF` (substitutes `ForwardRef` objects), `Format.STRING` (returns source text). `annotationlib.get_annotations(obj, format=...)` is the supported accessor - VERSION-DEPENDENT (3.14)
18. PEP 734 shipped `concurrent.interpreters` (subinterpreters in the stdlib) and `concurrent.futures.InterpreterPoolExecutor`; documented limitations are unoptimised startup, higher per-interpreter memory, restricted object sharing, and broad PyPI incompatibility - VERSION-DEPENDENT (3.14)
19. `concurrent.futures.ProcessPoolExecutor` gained `terminate_workers()` and `kill_workers()`, and the default start method on Unix (except macOS) changed to `forkserver` in 3.14 - a behaviour change that breaks code implicitly relying on `fork` inheriting module state - VERSION-DEPENDENT (3.14)
20. asyncio gained out-of-process introspection in 3.14: `python -m asyncio ps PID` prints a task table and `python -m asyncio pstree PID` prints the hierarchical await tree; the in-process equivalents are `asyncio.capture_call_graph()` and `asyncio.print_call_graph()` - VERSION-DEPENDENT (3.14)
21. `faulthandler.enable()` in 3.14 is `enable(file=sys.stderr, all_threads=True, c_stack=True)`; `c_stack` was added in 3.14 and appends a C stack trace after the Python traceback. `faulthandler.dump_c_stack(file=sys.stderr)` was also added in 3.14, requires system `backtrace(3)` and `dladdr1(3)`, and its speed "can be arbitrarily slow" depending on the DWARF level of binaries in the stack - VERSION-DEPENDENT (3.14)
22. Also changed in 3.14: when the GIL is disabled, `faulthandler` dumps only the current thread rather than all threads - VERSION-DEPENDENT (3.14)
23. PEP 784 added `compression.zstd` and re-exported `gzip`, `bz2`, `lzma` and `zlib` under a `compression` package namespace in 3.14, with zstd support reaching `tarfile`, `zipfile` and `shutil` - VERSION-DEPENDENT (3.14)
24. PEP 765 makes `return` / `break` / `continue` that leaves a `finally` block emit a `SyntaxWarning` in 3.14 - a genuine latent-bug detector that only fires if warnings are visible - VERSION-DEPENDENT (3.14)
25. PEP 761: "Python 3.14 and onwards no longer provides PGP signatures for release artifacts. Instead, Sigstore is recommended for verifiers." Build pipelines that gpg-verify python.org tarballs break from 3.14 onward - VERSION-DEPENDENT (3.14)
26. `-X importtime=2` (in addition to plain `-X importtime`) was added in 3.14 and also traces already-cached imports; `PYTHONPROFILEIMPORTTIME` accepts "1" and "2" with the same meanings - VERSION-DEPENDENT (3.14)

### 3.15 - what matters (confirmed against the 3.15.0rc1 docs, feature-frozen since 2026-05-07)

27. PEP 686 ("Make UTF-8 mode default") has status **Final** with Python-Version 3.15: from 3.15 Python uses UTF-8 as the default encoding for files, stdio and pipes regardless of locale. Revert with `PYTHONUTF8=0` or `-X utf8=0`; the locale encoding stays reachable through `encoding="locale"` and `locale.getencoding()` - VERSION-DEPENDENT (3.15)
28. PEP 810 ("Explicit lazy imports", status **Final**, Python-Version 3.15) adds a `lazy` soft keyword usable only on module-level `import` / `from ... import` statements. Modes are `normal` (honour the keyword; default), `all` (make imports lazy where possible) and `none` (force everything eager), selected with `-X lazy_imports=<mode>` or `PYTHON_LAZY_IMPORTS`. Runtime API: `sys.set_lazy_imports()`, `sys.get_lazy_imports()`, `sys.set_lazy_imports_filter(func)`, `sys.get_lazy_imports_filter()`, with filter signature `func(importer: str, name: str, fromlist: tuple | None) -> bool`. A module can opt in with a module-level `__lazy_modules__`, which is inert on older Pythons - VERSION-DEPENDENT (3.15)
29. PEP 810 forbids `lazy` inside functions, classes and `try` blocks, with `from ... import *`, and with `from __future__ import ...` - VERSION-DEPENDENT (3.15)
30. PEP 810's documented breakage: import exceptions surface at first *use* rather than at the import statement; module side effects run at first use; a lazily bound name is a `types.LazyImportType` object until reified; and the module does not appear in `sys.modules` until reification. Error reports chain the lazy-import site to the access site - VERSION-DEPENDENT (3.15)
31. PEP 799 ("A dedicated `profiling` package", status **Final**, Python-Version 3.15) reorganises profiling into `profiling.tracing` (the relocated `cProfile` implementation, deterministic) and `profiling.sampling` (the new statistical sampler, codename "tachyon"). `cProfile` remains "an alias for backwards compatibility". The `profile` module deprecates in three steps: 3.15 emits `DeprecationWarning` on import, 3.16 on all uses, removal in 3.17 - VERSION-DEPENDENT (3.15)
32. The 3.15 What's New documents `python -m profiling.sampling` with `run`, `attach` and `dump` forms, the `--pstats`, `--collapsed`, `--flamegraph`, `--gecko`, `--heatmap` and `--live` output modes, `--async-aware` for coroutine-aware stacks and `--opcodes` for bytecode-level attribution, and states it can attach to a running process by PID without restarting it - VERSION-DEPENDENT (3.15)
33. PEP 831 ("Frame Pointers Everywhere", status **Final**, Python-Version 3.15) adds `-fno-omit-frame-pointer` and `-mno-omit-leaf-frame-pointer` to `BASECFLAGS` by default so third-party C extensions inherit them through `sysconfig`; `--without-frame-pointers` opts out (that option exists in 3.15 and not in 3.14). Measured cost is 0.5% on Apple M2, 0.2-2.3% on AArch64 and 1.5-1.9% on x86-64 - VERSION-DEPENDENT (3.15)
34. PEP 831's rationale is operational: `perf_events` and the eBPF stack helpers `bpf_get_stackid()` / `bpf_get_stack()` walk frame-pointer chains with no DWARF fallback, so without frame pointers bpftrace/Pyroscope-class tools produce truncated or empty Python stacks - ESTABLISHED
35. PEP 728 ("TypedDict with Typed Extra Items", status **Final**, Python-Version 3.15) adds the class and functional parameters `extra_items=<type>` and `closed=True`. `extra_items=Never` is equivalent to `closed=True` (the latter preferred). Extra items are always non-required regardless of `total=`, and combining `extra_items` with `Required[]` / `NotRequired[]` is an error. Runtime introspection uses `__extra_items__` (holds `typing.NoExtraItems` when unset) and `__closed__` (holds `None` when unset); both reflect only what was passed, ignoring inheritance - VERSION-DEPENDENT (3.15)
36. PEP 661 ("Sentinel Values", status **Final**, Python-Version 3.15) adds a **built-in** `sentinel(name, /, repr=None)` callable. Two calls with the same name return **distinct** objects; `copy.copy()` and `copy.deepcopy()` return the same object; sentinels importable by module and name survive pickling while locals do not; sentinels are truthy and usable in `|` type expressions (`value: int | MISSING = MISSING`) - VERSION-DEPENDENT (3.15)
37. 3.15 also ships PEP 814 (`frozendict` built-in: immutable, hashable, order-independent equality and hash), PEP 798 (unpacking in comprehensions: `[*L for L in lists]`, `{**d for d in dicts}`, including generator and async forms), PEP 747 (`typing.TypeForm`), PEP 800 (`typing.disjoint_base`), PEP 829 (`.start` package startup files plus the `site.StartupState` API), PEP 782 (`PyBytesWriter`), PEP 788 (interpreter guards and views; soft-deprecates `PyGILState_Ensure()` / `PyGILState_Release()` with no removal planned) and `math.integer` (PEP 791) - VERSION-DEPENDENT (3.15)
38. `sys.monitoring` in 3.15 makes the unwinding and exception events (`PY_THROW`, `PY_UNWIND`, `RAISE`, `EXCEPTION_HANDLED`, `RERAISE`) controllable per code object, and returning `DISABLE` from their callbacks now disables them for the whole code object instead of raising `ValueError` - VERSION-DEPENDENT (3.15)
39. 3.15 adds `sys.abi_info`, a namespace describing the running build's ABI - VERSION-DEPENDENT (3.15)
40. `pdb` in 3.15 uses the new interactive shell by default; `os.path.realpath(strict=os.path.ALLOW_MISSING)` was added for CVE-2025-4517; `tarfile` gained path-traversal mitigations for CVE-2025-4138, CVE-2024-12718, CVE-2025-4330 and CVE-2025-4435 - VERSION-DEPENDENT (3.15)

### Free-threaded CPython

41. PEP 703 ("Making the Global Interpreter Lock Optional in CPython") is **Final** with Python-Version 3.13. The build flag is `--disable-gil`; the configure docs state it "Defines the `Py_GIL_DISABLED` macro and adds `\"t\"` to `sys.abiflags`" - ESTABLISHED
42. PEP 703 states the free-threaded build "will not be ABI compatible with the standard CPython build or with the stable ABI due to changes to the Python object header needed to support biased reference counting", and defines Phase I (3.13, experimental, two ABIs), Phase II (supported, optional) and Phase III (default) - ESTABLISHED
43. In 3.13 free-threading was explicitly experimental: the 3.13 What's New reads "CPython now has experimental support for running in a free-threaded mode ... This is an experimental feature and therefore is not enabled by default", with `sys.version` and `python -VV` containing "experimental free-threading build" - VERSION-DEPENDENT (3.13)
44. PEP 779 ("Criteria for supported status for free-threaded Python") is **Final** (accepted 2025-06-16) and targets 3.14. It defines Phase II acceptance as at most 15% single-threaded slowdown (measured around 10% at acceptance), at most 20% higher memory (pyperformance geometric mean), APIs judged stable, and improved internals documentation. Its stated meaning of official support: "the design is finalised, the APIs are usable and stable, and we're satisfied the performance and complexity cost is not prohibitive." - VERSION-DEPENDENT (3.14)
45. The 3.14 What's New release-highlight line is "PEP 779: Free-threaded Python is officially supported". Officially supported still means *optional*: the GIL-enabled build remains the normal build, and PEP 779 leaves Phase III criteria "for a future PEP" - VERSION-DEPENDENT (3.14)
46. Whether and when free-threading becomes the default build is not scheduled: no PEP defines Phase III and no version is committed - OPEN
47. PEP 779 left stable-ABI support for free-threaded builds as an open question ("chicken and egg problem"); PEP 803 answered it in 3.15 - VERSION-DEPENDENT (3.15)
48. Single-threaded overhead figures differ by source and both are current: the 3.14 What's New says "The performance penalty on single-threaded code in free-threaded mode is now roughly 5-10%, depending on the platform and C compiler used", while the free-threading HOWTO in the 3.14 docs gives about 1% on macOS aarch64 and about 8% on x86-64 Linux (pyperformance geometric mean). Always quote the platform, never a bare number - VERSION-DEPENDENT (3.14)
49. Build and runtime identification, per the free-threading HOWTO: build-time check is `sysconfig.get_config_var("Py_GIL_DISABLED") == 1`; runtime check is `sys._is_gil_enabled()`; `python -VV` contains "free-threading build"; the interpreter installs with a `t` suffix, e.g. `python3.14t` - VERSION-DEPENDENT (3.13+)
50. `-X gil=0|1` and `PYTHON_GIL=0|1` toggle the GIL at startup, and `-X gil=0` requires a `--disable-gil` build (both added in 3.13) - VERSION-DEPENDENT (3.13+)
51. Importing a C extension that does not declare free-threading support (via the `Py_mod_gil` slot or `PyUnstable_Module_SetGIL()`) causes the GIL to be re-enabled automatically, with a warning printed. The process keeps running - it simply is no longer free-threaded - VERSION-DEPENDENT (3.13+)
52. Documented free-threading hazards: accessing another thread's `frame.f_locals` is unsafe and may crash; sharing one iterator across threads is not thread-safe and can yield duplicated or skipped elements; built-in `dict`/`list`/`set` have internal locks but no guaranteed concurrent-mutation semantics, so use `threading.Lock`; code objects, string constants and interned strings are immortal and never deallocated; memory overhead comes from larger object headers, mimalloc instead of pymalloc, QSBR reclamation delay, and biased/deferred/per-thread reference counting - ESTABLISHED
53. `-X tlbc=0|1` / `PYTHON_TLBC` (added 3.14, free-threaded builds only, default 1) controls thread-local bytecode. Disabling it lowers memory at the cost of specialisation - VERSION-DEPENDENT (3.14)
54. `-X context_aware_warnings=0|1` and `-X thread_inherit_context=0|1` (both added 3.14, with `PYTHON_CONTEXT_AWARE_WARNINGS` and `PYTHON_THREAD_INHERIT_CONTEXT`) default to 1 on free-threaded builds and 0 on GIL builds. Warning-filter state therefore becomes a `ContextVar` on free-threaded builds, changing how `warnings.catch_warnings()` behaves across threads - VERSION-DEPENDENT (3.14)
55. PEP 803 ("`abi3t`: Stable ABI for Free-Threaded Builds") is **Final** with Python-Version 3.15. Extensions define `Py_TARGET_ABI3T=<version>` and declare the compressed wheel tag set `abi3.abi3t`. Migration requires PEP 697 APIs (negative `basicsize`, `PyObject_GetTypeData()`) instead of embedding `PyObject`, plus the PEP 793 `PyModExport_*` export hook with the PEP 820 `PySlot` structure; `PyObject`, `PyVarObject` and `PyModuleDef` become opaque, `PyObject_HEAD` is unusable, and `PyModuleDef` can no longer be statically allocated - VERSION-DEPENDENT (3.15)
56. The 3.15 What's New warns that "build tools like Setuptools, meson-python, scikit-build-core, and Maturin do not support `abi3t`" at the time of writing, and advises extensions to keep shipping `abi3` plus a version-specific `cp315t` wheel until tooling catches up - VERSION-DEPENDENT (3.15)

### JIT and tail-call interpreter

57. PEP 744 ("JIT Compilation") is still status **Draft** with Python-Version 3.13. It states "The JIT is currently not part of the default build configuration, and it is likely to remain that way for the foreseeable future" and that the JIT "is about as fast as the existing specializing interpreter on most platforms", with roughly 10-20% higher memory use. Do not cite PEP 744 as an accepted commitment - ESTABLISHED
58. The build switch is `--enable-experimental-jit=[no|yes|yes-off|interpreter]`, added in 3.13, default `no`; bare `--enable-experimental-jit` means `=yes`. `yes` builds it enabled (disable at runtime with `PYTHON_JIT=0`); `yes-off` builds it disabled (enable with `PYTHON_JIT=1`); `interpreter` enables the tier-2 "JIT interpreter", useful only for debugging the JIT itself. On Windows the equivalents are `PCbuild/build.bat --experimental-jit` and `--experimental-jit-interpreter` - VERSION-DEPENDENT (3.13+)
59. `PYTHON_JIT` (added 3.13) is the only runtime switch documented in `using/cmdline.html`. There is no `-X jit` option - VERSION-DEPENDENT (3.13+)
60. Official 3.14 macOS and Windows binaries "include an experimental JIT compiler" per the 3.14.7 release page; whether they were built `yes` or `yes-off` - that is, whether the JIT is live without `PYTHON_JIT=1` - is not stated on the release page - OPEN
61. 3.15 upgrades the JIT substantially; the 3.15.0rc1 announcement quantifies it as an "8-9% geometric mean performance improvement on x86-64 Linux" and a "12-13% speedup on AArch64 macOS" - VERSION-DEPENDENT (3.15)
62. The tail-call interpreter is a separate, orthogonal mechanism: `--with-tail-call-interp` (added 3.14) "requires a C compiler with proper tail call support, and the `preserve_none` calling convention. For example, Clang 19 and newer supports this feature", targets x86-64 and AArch64, and PGO (`--enable-optimizations`) is "highly recommended". CPython documents "a geometric mean of 3-5% faster on the standard `pyperformance` benchmark suite" - VERSION-DEPENDENT (3.14)
63. The widely circulated 10-15% tail-call figure from early 2025 was inflated by an LLVM 19 codegen regression in the *baseline* build rather than by the tail-call interpreter itself; the corrected geometric mean is the 3-5% now in the CPython docs - FLAGGED-SECONDARY (blog.nelhage.com, fidget-spinner.github.io, lwn.net) - VERSION-DEPENDENT (3.14)
64. In 3.15 the official Windows 64-bit binaries use the tail-calling interpreter, so the shipped Windows interpreter changes its C-level dispatch shape between 3.14 and 3.15 - VERSION-DEPENDENT (3.15)

### Diagnosis switchboard: -X options and PYTHON* variables

65. `-X dev` / `PYTHONDEVMODE=1` enables, per `library/devmode.html`: the `default` warning filter (surfacing `DeprecationWarning`, `ImportWarning`, `PendingDeprecationWarning` and `ResourceWarning`, equivalent to `-W default`); the debug memory-allocator hooks (equivalent to `PYTHONMALLOC=debug`, catching buffer under/overflow, allocator-API violations and unsafe GIL usage); `faulthandler` (equivalent to `-X faulthandler`); asyncio debug mode (equivalent to `PYTHONASYNCIODEBUG=1`); validation of the `encoding` and `errors` arguments of `open()`, `str.encode()` and `bytes.decode()`; logging of exceptions raised in the `io.IOBase` destructor; and it sets `sys.flags.dev_mode` to True - ESTABLISHED
66. Dev mode explicitly does **not** enable `tracemalloc` (the overhead is judged too large), does not stop `-O` from stripping `assert`, and does not change `__debug__`. The `ResourceWarning` it surfaces says "Enable tracemalloc to get the object allocation traceback" - you must add `-X tracemalloc=5` yourself - ESTABLISHED
67. Setting `PYTHONMALLOC=default` alongside dev mode keeps dev mode while turning the allocator debug hooks back off - the documented escape when the hooks are too slow - ESTABLISHED
68. Default warning filters in a release build are exactly, in precedence order: `default::DeprecationWarning:__main__`, `ignore::DeprecationWarning`, `ignore::PendingDeprecationWarning`, `ignore::ImportWarning`, `ignore::ResourceWarning`. "In a debug build, the list of default warning filters is empty", so a debug interpreter shows everything - ESTABLISHED
69. `PYTHONWARNINGS` takes comma-separated filters of the form `action:message:category:module:lineno`, and later filters take precedence over earlier ones; `-W error` turns warnings into exceptions - ESTABLISHED
70. `faulthandler` handles `SIGSEGV`, `SIGFPE`, `SIGABRT`, `SIGBUS` and `SIGILL`, and is installed at startup by `-X faulthandler` / `PYTHONFAULTHANDLER`. Because the handler may only call signal-safe functions, its output is deliberately impoverished: ASCII only (with `backslashreplace`), 500 characters per string, filename/function/line with no source text, at most 100 frames and 100 threads, most-recent-call-first. `faulthandler.dump_traceback_later(timeout, repeat=False, file=sys.stderr, exit=False)` is a watchdog thread useful for hang diagnosis; `faulthandler.register()` is unavailable on Windows - ESTABLISHED
71. `-X tracemalloc[=NFRAME]` / `PYTHONTRACEMALLOC=NFRAME` starts allocation tracing at interpreter start with an NFRAME-deep traceback; without it, tracemalloc-dependent warning messages carry no allocation site - ESTABLISHED
72. `-X perf` / `PYTHONPERFSUPPORT=1` enables the Linux `perf` trampoline so Python frames appear in `perf` output. Precedence is `sys` functions > `-X` option > environment variable; the in-process API is `sys.activate_stack_trampoline("perf")`, `sys.deactivate_stack_trampoline()` and `sys.is_stack_trampoline_active()`. Support is Linux-only on selected architectures - verify with `python -m sysconfig | grep HAVE_PERF_TRAMPOLINE` - VERSION-DEPENDENT (3.12+)
73. Without frame pointers the interpreter "may not be able to show Python functions in the output of `perf`". The documented remedies are building with `-fno-omit-frame-pointer -mno-omit-leaf-frame-pointer` (verify with `python -m sysconfig | grep 'no-omit-frame-pointer'`) or using `-X perf_jit` / `PYTHON_PERF_JIT_SUPPORT=1`, which emits unwind information on the fly, requires `perf record --call-graph dwarf` plus a `perf inject --jit` pass, needs perf v6.8+ (or v6.7.2+), and costs more overhead and slower post-processing. The maximum `--call-graph dwarf` stack dump is 65528 bytes (default 8192), which matters for `-O0` builds - VERSION-DEPENDENT (3.13+)
74. The integer/string conversion limit: `sys.get_int_max_str_digits()` and `sys.set_int_max_str_digits()`, `sys.flags.int_max_str_digits`, `-X int_max_str_digits=N` and `PYTHONINTMAXSTRDIGITS=N`, all added in 3.11 and backported to security branches. The default is 4300 (`sys.int_info.default_max_str_digits`); the minimum non-zero setting is 640 (`sys.int_info.str_digits_check_threshold`); `0` disables the limit. Exceeding it raises **`ValueError`**: `int('1'*5000)` produces `ValueError: Exceeds the limit (4300 digits) for integer string conversion: value has 5000 digits; use sys.set_int_max_str_digits() to increase the limit`. (Constant values read from a live interpreter's `sys.int_info`; the fields themselves are documented in `library/sys.html`.) - VERSION-DEPENDENT (3.11+)
75. Other development-relevant switches confirmed in `using/cmdline.html`: `-X showrefcount` (3.4, debug builds only); `-X pycache_prefix=PATH` / `PYTHONPYCACHEPREFIX` (3.8); `-X warn_default_encoding` / `PYTHONWARNDEFAULTENCODING` (3.10, emits `EncodingWarning`); `-X no_debug_ranges` / `PYTHON_NODEBUGRANGES` (3.11, drops the fine-grained location tables); `-X frozen_modules=on|off` / `PYTHON_FROZEN_MODULES` (3.11/3.13, default on in release builds and off in debug builds); `-X cpu_count=n` / `PYTHON_CPU_COUNT` (3.13, overrides `os.cpu_count()` and `os.process_cpu_count()`); `-X presite=pkg.mod` / `PYTHON_PRESITE` (3.13, debug builds only); `PYTHONSAFEPATH` / `-P` (3.11); `PYTHONHASHSEED` (`random` default, integer 0-4294967295, `0` disables randomisation); `PYTHON_COLORS` alongside `NO_COLOR` and `FORCE_COLOR`; `PYTHON_BASIC_REPL` (3.13); `PYTHONBREAKPOINT` (3.7, defaults to `pdb.set_trace`, empty or "0" makes `breakpoint()` a no-op) - ESTABLISHED

### Minimum-target policy

89. `Requires-Python` is core metadata (introduced in metadata version 1.2), must be a specifier per the PyPA version-specifiers spec, and "cannot be followed by an environment marker". Installation tools "may look at this when picking which version of a project to install" - it is a resolver exclusion filter, not a statement of tested versions - ESTABLISHED
90. SPEC 0 ("Minimum Supported Dependencies", endorsed, Scientific Python) recommends dropping support for a Python version 36 months after its release and for a core package 24 months after its release, noting that "core packages may or may not decide to provide bug fix releases during the full 2 year period" - ESTABLISHED
91. SPEC 0's published Python drop schedule: 3.11 (released 2022-10-24) drop Q4 2025; 3.12 (2023-10-02) drop Q4 2026; 3.13 (2024-10-07) drop Q4 2027; 3.14 (2025-10-07) drop Q4 2028. On 2026-08-08 a SPEC 0 follower supports 3.12, 3.13 and 3.14 - and drops 3.12 within months - ESTABLISHED
92. SPEC 0 supersedes NumPy's NEP 29; NEP 29's window was 42 months against SPEC 0's 36, so a project still citing NEP 29 is holding a wider window than the ecosystem it believes it tracks. SPEC 0's own numbers are primary; the supersession status is FLAGGED-SECONDARY (numpy issue #26700, scikit-hep, scientific-python discussions) - ESTABLISHED
93. CPython's own support window (5 years from the feature release) is strictly wider than SPEC 0's (3 years). A `requires-python = ">=3.11"` line today sits inside CPython's supported set but two versions below SPEC 0's floor of 3.12; the two policies answer different questions and a SPEC line must say which it follows - ESTABLISHED

**7. "requires-python is not your test matrix" - software_spec_discipline_manifest.md**
`Requires-Python` is a resolver exclusion filter in core metadata (from version 1.2), cannot carry an environment marker, and proves nothing about what CI ran. A SPEC line should state three separate things: the `requires-python` floor, the CI matrix, and the support *policy* it follows (CPython's 5-year window versus SPEC 0's 36-month window, which today put the floor at 3.11 and 3.12 respectively). Add the anti-pattern: an upper bound such as `<3.15` or `<4` silently makes the package uninstallable on the next interpreter.

## Traps for coding agents

1. **"Latest Python is 3.14"** is right about the line and wrong about the artefact: the latest release is **3.14.7 (2026-08-05)**. Pinning `3.14.0` in CI pins a build ten months and roughly 1,400 bugfixes behind.
2. **3.15 is not in beta.** It is at **rc1** (2026-08-04), features frozen since 2026-05-07 and ABI frozen from rc1. "Wait for 3.15 before testing" is no longer defensible; wheels built against rc1 work on final 3.15.
3. **3.16 does not exist yet.** Its first artefact (alpha 1) is scheduled 2026-10-13. Any claim about a released 3.16 behaviour is fabrication.
4. **PEP 2026 CalVer was rejected.** There is no Python 3.26. An agent half-remembering the CalVer proposal will emit version numbers that do not exist.
5. **`import sre_constants` / `sre_parse` / `sre_compile` fails on 3.15.** The only replacements are the private `re._constants` / `re._parser` / `re._compiler`. Libraries that reach into `sre_*` - a common trick in property-based generators and regex introspection - break on 3.15 with no supported migration path.
6. **UTF-8 becomes the default encoding in 3.15 (PEP 686).** Code whose tests passed only because the platform locale happened to be UTF-8, or that relied on locale encoding on Windows, changes behaviour. The escape hatches are `encoding="locale"`, `PYTHONUTF8=0` and `-X utf8=0`; the early-warning switch is `-X warn_default_encoding` on 3.10+.
7. **`lazy import` moves failure in time, not away.** `ModuleNotFoundError` and every import-time side effect fire at first *attribute use*, the module is absent from `sys.modules` until then, and the bound name is a `types.LazyImportType` object in the meantime. Tests that assert on import-time errors, or that patch `sys.modules`, will not see what they expect.
8. **`lazy` is illegal inside a function, class or `try` block, and with `import *`.** Sprinkling it inside a function body to "defer" an import is a syntax error, not an optimisation.
9. **`DeprecationWarning` is invisible by default outside `__main__`.** The default filters are `default::DeprecationWarning:__main__` followed by `ignore::DeprecationWarning`. A library can add a deprecation warning and its test can assert the warning is raised, and both pass while no user ever sees it. Use `-W error::DeprecationWarning`, `-X dev`, or pytest `filterwarnings`.
10. **`-X dev` does not enable `tracemalloc`.** The `ResourceWarning` it surfaces literally tells you to enable tracemalloc; you must add `-X tracemalloc=N` yourself. `-X dev` also does not stop `-O` from stripping `assert`.
11. **`getopt` is not deprecated.** The 3.14 docs carry only a "This module is considered feature complete" note - no deprecation, no removal version. "getopt is deprecated, removal in 3.15" is a fabrication that plausible-sounding 3.14 summaries invite.
12. **`abi3` wheels do not load on free-threaded builds.** The free-threaded ABI is separate (`sys.abiflags` gains `t`, wheel tags `cp314t` / `cp315t`), and `abi3t` (PEP 803, new in 3.15) is not yet supported by setuptools, meson-python, scikit-build-core or Maturin. "We ship abi3, so we support free-threading" is false.
13. **A free-threaded interpreter can silently be running with the GIL on.** Importing any extension that does not set the `Py_mod_gil` slot re-enables the GIL with only a printed warning. A "free-threaded" benchmark that shows no scaling is frequently just this. Assert with `sys._is_gil_enabled()` at runtime.
14. **`sys._is_gil_enabled()` is a private API reporting *runtime* state, not build type.** For build-time decisions use `sysconfig.get_config_var("Py_GIL_DISABLED") == 1`. Conflating the two produces wheel-selection bugs.
15. **There is no `-X jit`.** The only documented runtime switch is `PYTHON_JIT=0|1`, and it does nothing unless the interpreter was built with `--enable-experimental-jit`. Whether the official 3.14 macOS/Windows binaries used `yes` or `yes-off` is undocumented, so test both settings rather than assuming.
16. **PEP 744 is still a Draft.** Citing it as an accepted plan for a default-on JIT misrepresents the record; it says the JIT "is likely to remain" outside the default build configuration.
17. **Profiles are not comparable across build configurations.** JIT on/off, tail-call versus computed-goto dispatch, frame pointers on/off, and free-threaded versus GIL all change instruction counts and stack shape. 3.15 flips two of these by default (Windows 64-bit tail calls; PEP 831 frame pointers), so a 3.14-to-3.15 performance comparison is confounded unless build flags are recorded.
18. **`-X perf` produces empty or truncated Python frames without frame pointers.** Most pre-3.15 distro builds omit them. Either rebuild with `-fno-omit-frame-pointer -mno-omit-leaf-frame-pointer`, or use `-X perf_jit` with `--call-graph dwarf` (needs perf 6.8+ and a `perf inject --jit` pass, and costs more overhead).
19. **`int_max_str_digits` raises `ValueError`, not `OverflowError`,** at a default of **4300** digits, for `int(str)`, `str(int)` and `repr(int)`. `hex()`, `oct()` and `bin()` are unaffected. The minimum non-zero setting is **640**; only `0` disables the limit. Serialising large integers to JSON is the usual way this surfaces in production.
20. **`-X no_debug_ranges` silently degrades tracebacks.** It shrinks `.pyc` files by dropping the fine-grained location table - exactly the data that draws the `^^^^` carets. Never set it in an environment you intend to debug.
21. **`ProcessPoolExecutor` changed its default start method to `forkserver` on Unix (except macOS) in 3.14.** Code that implicitly relied on `fork` inheriting module-level state, open handles or monkeypatches now fails, often only under load.
22. **The 3.16 asyncio removals are close.** `asyncio.iscoroutinefunction()` and the whole event-loop-policy API (`get_event_loop_policy()`, `set_event_loop_policy()`, `DefaultEventLoopPolicy`, both Windows policies, `AbstractEventLoopPolicy`) are removed in 3.16. Move to `inspect.iscoroutinefunction()` and `asyncio.Runner` / `asyncio.run()` now.
23. **`module.__cached__` and `module.__package__` are gone in 3.15,** along with `ctypes.SetPointerType()`, `pathlib.PurePath.is_reserved()`, `platform.java_ver()`, `types.CodeType.co_lnotab`, `http.server.CGIHTTPRequestHandler`, `python -m http.server --cgi` and `zipimport.zipimporter.load_module()`. Import-machinery introspection code is the usual casualty.
24. **`sentinel("MISSING")` called twice gives two different objects.** Identity checks against a freshly created sentinel silently fail. Create once at module scope and share the reference - the same discipline as `MISSING = object()`.
25. **`frozendict` (3.15) is not a `dict` for `isinstance` purposes.** The docs steer you to `isinstance(arg, (dict, frozendict))` or `collections.abc.Mapping`. Validation code gated on `isinstance(x, dict)` starts rejecting valid 3.15 mappings.
26. **`--with-tail-call-interp` needs Clang 19+ and the `preserve_none` calling convention.** A GCC toolchain cannot produce that build, so "enable the tail-call interpreter" is not portable advice, and PGO (`--enable-optimizations`) is strongly recommended alongside it.
27. **Security-phase Pythons have no installers.** 3.12, 3.11 and 3.10 are source-only, released on no cadence. CI that downloads a python.org installer for 3.11, or expects a python.org-built binary, fails - and "3.11 is supported" does not imply a fix arrives promptly.
28. **3.10 reaches EOL in October 2026** - about two months out - and SPEC 0 followers already dropped 3.11 (Q4 2025) and drop 3.12 in Q4 2026. A `requires-python = ">=3.10"` line is simultaneously inside CPython's support window and two versions below the scientific ecosystem's floor. State which policy you follow.
29. **`requires-python` is an exclusion filter, not a tested matrix.** pip and PyPI use it to refuse installation; it proves nothing about CI. And an upper bound (`<4`, `<3.15`) makes the package uninstallable on the next interpreter, with no warning at publish time.
30. **PGP signatures for python.org artefacts ended with 3.14 (PEP 761).** Verification pipelines must move to Sigstore; a `gpg --verify` step against a 3.14+ tarball simply finds nothing to verify.
31. **`-X importtime=2` is 3.14+.** On 3.13 and earlier only plain `-X importtime` exists, and it does not trace cached imports.
32. **`cProfile` becomes an alias in 3.15 and `profile` starts warning.** `profile` emits `DeprecationWarning` on import in 3.15, on all uses in 3.16, and is removed in 3.17. New code should import `profiling.tracing`; anything asserting on the `cProfile` module's identity or `__file__` may break.
33. **Free-threaded builds change warning-filter scoping.** `-X context_aware_warnings` defaults to *true* on free-threaded builds, making warning state a `ContextVar`. `warnings.catch_warnings()` therefore behaves differently across threads on a free-threaded interpreter than on a GIL one - a real source of flaky warning assertions.
34. **`faulthandler` output is intentionally minimal** - ASCII only, 500 characters per string, no source lines, at most 100 frames and 100 threads, most-recent-call-first - because the handler may only use signal-safe functions. Treating it as a substitute for a real traceback loses information; and on 3.14+ with the GIL disabled it dumps only the current thread.
