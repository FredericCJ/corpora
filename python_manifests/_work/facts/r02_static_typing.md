## Facts

### Checker identity, maturity, and standing

1. mypy 2.3.0 (2026-07-13) requires Python >= 3.10 to run and refuses `--python-version 3.9` outright: "Mypy no longer supports type checking code with `--python-version 3.9`. Use `--python-version 3.10` or newer." - VERSION-DEPENDENT (mypy 2.0+)
2. pyrefly is Meta's checker and is no longer pre-release: PyPI classifies it `Development Status :: 5 - Production/Stable`, and its own v1.0 announcement states "Pyrefly ... has reached stable version 1 status, meaning we are confident that Pyrefly is ready for production use." 1.0.0 landed 2026-05-12; current is 1.2.0 (2026-08-01). - ESTABLISHED
3. pyrefly's production claim is backed by named deployments in its own post: "Pyrefly was already the default type checker for developers working on Instagram at Meta," plus adoption by "PyTorch, NumPy, Pandas (stubs) and JAX." - ESTABLISHED
4. pyrefly versions its own breaking changes loosely: its PyPI page recommends the `pyrefly suppress` command when upgrading, because breaking diagnostic changes may land across minor versions. A pyrefly minor bump is therefore a re-baselining event, not a patch. - VERSION-DEPENDENT (pyrefly 1.x)
5. ty is Astral's checker and is explicitly NOT production-ready by its own statement. Its README says "ty is currently in beta" and, under "Version policy": "ty uses `0.0.x` versioning. ty does not yet have a stable API; breaking changes, including changes to diagnostics, may occur between any two versions." PyPI classifies it `Development Status :: 4 - Beta`. - ESTABLISHED
6. Because ty's own policy admits diagnostic changes "between any two versions," ty cannot be used as a stable CI gate without pinning an exact patch version; an unpinned `uvx ty check` can change its verdict between two runs on unchanged code. - VERSION-DEPENDENT (ty 0.0.x)
7. ty officially supports type checking code targeting Python 3.10 and later; 3.7-3.9 "can still be selected, but may result in false negatives or false positives due to a lack of bundled standard library stubs." - VERSION-DEPENDENT (ty 0.0.69)
8. The `pyright` PyPI distribution is not the checker: it is "a command line wrapper for pyright," which downloads/invokes the Node-based implementation. Pinning the PyPI version pins the wrapper's target version, not a pure-Python analyzer. - ESTABLISHED
9. basedpyright (1.39.9, 2026-06-27) is a separate fork of pyright with additional rules; its rule names (for example `reportAny`) do NOT exist in upstream pyright - a grep of microsoft/pyright `docs/configuration.md` finds no `reportAny`, `reportExplicitAny`, or `reportIgnoreCommentWithoutRule`. - ESTABLISHED
10. Two further checkers now appear in the official conformance results and are not folklore: `pycroscope` 0.4.0 and `zuban` 0.9.1. zuban's PyPI classifier is `Development Status :: 1 - Planning` despite a 0.9.x version number - the classifier and the version number disagree, so treat maturity as OPEN. - OPEN

### The typing spec, its authority, and the conformance suite

11. The typing spec (https://typing.python.org/en/latest/spec/) is normative for the *type system* only, and PEP 729 (Status: Active, Process) explicitly denies it force over implementations: "The Typing Council has no direct authority over type checkers; it cannot force them to implement particular features or make behavior changes." - ESTABLISHED
12. PEP 729 further states that checkers "are free to deviate from the spec if they do not have the resources to fully implement it or if they believe a different behavior better serves their users," requiring only that deviations be documented. Cross-checker agreement is therefore not merely unachieved in practice - it is not required in principle. - ESTABLISHED
13. The spec declines to make the gradual guarantee binding: "In Python's type system, we don't take the gradual guarantee as a strict requirement, but it's a useful guideline." - ESTABLISHED
14. The spec fixes assignability in terms of consistent subtyping: "An expression can be assigned to a variable ... if its type is a consistent subtype of the variable's type annotation." It also warns that "The consistency relation is not transitive," unlike subtyping - so `A` consistent with `B` and `B` consistent with `C` does not license `A` to `C`. - ESTABLISHED
15. The spec's normative rule for `Any` is permissive, not strict: "A static type checker should not emit static type errors on an expression or statement if `Any` might represent a static type which would avoid the error." A checker that errors on an `Any`-mediated expression is being *more* strict than the spec requires. - ESTABLISHED
16. The conformance suite lives at python/typing `conformance/`, is organized by spec chapter (concepts, annotations, typeforms, specialtypes, generics, qualifiers, classes, aliases, literals, protocols, callables, constructors, overloads, dataclasses, typeddicts, tuples, namedtuples, narrowing, directives, distribution, historical), and encodes optionality directly: `# E` means "an error must be raised on this line," `# E?` means "an error may be raised" because "the spec allows multiple behaviors." - ESTABLISHED
17. Conformance scoring is fractional (partial conformance counts as a half), which is why scores like `136.5 / 142` appear. Tests total 142 in the current results file. - VERSION-DEPENDENT (results commit 2026-08-07)
18. Current official conformance results (python/typing main, results.html last committed 2026-08-07), against the versions the suite actually ran: pyrefly 1.3.0-dev.1 = 141/142 (99.3%); zuban 0.8.2 = 141/142 (99.3%); pyright 1.1.410 = 136.5/142 (96.1%); pycroscope 0.4.0 = 131/142 (92.3%); ty 0.0.67 = 126/142 (88.7%); mypy 2.1.0 = 109/142 (76.8%). - VERSION-DEPENDENT (see per-checker versions)
19. mypy is the LOWEST-scoring checker in the official conformance table, at 76.8%. Its dominance is historical and ecosystem-driven, not spec-driven; an agent must not treat "mypy accepts it" as "the spec permits it," nor "mypy rejects it" as "the spec forbids it." - VERSION-DEPENDENT (mypy 2.1.0 as tested)
20. Conformance percentage is not a proxy for practical strictness or usefulness. The suite "focuses on static type checking not general Python semantics," and its own README states that "many important aspects of type checking are not standardized at all, and therefore not covered by conformance tests." A 99.3% checker and a 76.8% checker can still disagree on any unspecified behavior, of which there are many. - ESTABLISHED
21. Vendor conformance claims circulating in secondary write-ups (for example a "Basilisk 100% (141/141)" claim) do NOT appear in the official python/typing results table, which lists only mypy, pycroscope, pyrefly, pyright, ty, and zuban. Treat any conformance figure not present in that file as unverified. - FLAGGED-SECONDARY / OPEN

### mypy strict mode - exact, and changed

22. As of mypy 2.3.0, `--strict` enables exactly 13 flags, confirmed both from the docs ("For this version of mypy, the list of flags enabled by strict is:") and from `mypy/main.py` at tag `v2.3.0` (13 options carry `strict_flag=True`): `--disallow-any-generics`, `--disallow-subclassing-any`, `--disallow-untyped-calls`, `--disallow-untyped-defs`, `--disallow-incomplete-defs`, `--check-untyped-defs`, `--disallow-untyped-decorators`, `--warn-redundant-casts`, `--warn-unused-ignores`, `--warn-return-any`, `--no-implicit-reexport`, `--strict-equality`, `--extra-checks`. - VERSION-DEPENDENT (mypy 2.3)
23. The mypy 2.x `--strict` set is SMALLER than mypy 1.19's. At tag `v1.19.0`, 15 options carried `strict_flag=True`; the two dropped are `--warn-unused-configs` and `--strict-bytes`. `--strict-bytes` was dropped because it became the default in mypy 2.0; `--warn-unused-configs` is simply no longer implied by `--strict` and must now be requested explicitly. - VERSION-DEPENDENT (mypy 1.19 -> 2.0)
24. Consequence of fact 23: upgrading 1.19 -> 2.x silently STOPS reporting unused/misspelled per-module config sections unless `--warn-unused-configs` is added back by hand. Stale `[mypy-*]` overrides then rot invisibly. - VERSION-DEPENDENT (mypy 2.0+)
25. mypy's docs carry two explicit escape clauses an agent must not paper over: "Note: the exact list of flags enabled by running `--strict` may change over time," and "Note: the `--warn-unreachable` flag is not automatically enabled by the strict flag." - ESTABLISHED
26. `--strict` has no precedence: "The strict flag does not take precedence over other strict-related flags. Directly specifying a flag of alternate behavior will override the behavior of strict, regardless of the order in which they are passed." So `--strict --no-warn-return-any` silently downgrades strict, order-independently. - ESTABLISHED
27. `--strict` does NOT enable `--disallow-any-explicit` (error code `explicit-any`), `--warn-unreachable` (`unreachable`), or the opt-in codes `deprecated`, `redundant-expr`, `possibly-undefined`, `truthy-bool`, `truthy-iterable`, `ignore-without-code`, `unused-awaitable`, `explicit-override`, `mutable-override`, `unimported-reveal`, `redundant-self`, `exhaustive-match`. "strict" does not mean "no `Any`". - VERSION-DEPENDENT (mypy 2.3)
28. mypy 2.0 flipped `--local-partial-types` to default on, and the changelog warns the legacy behaviour is on borrowed time: "explicitly disabling this continues to be supported, but this support will be removed in the future as the legacy behaviour is hard to support with other current and future features in mypy, like the daemon or the new implementation of flexible redefinitions." - VERSION-DEPENDENT (mypy 2.0+)
29. mypy 2.0 made `--strict-bytes` the default: "Per PEP 688, mypy no longer treats `bytearray` and `memoryview` values as assignable to the `bytes` type." Code that passed `bytearray` where `bytes` was annotated compiled clean under 1.x and errors under 2.x. Restore the old behaviour only with `--no-strict-bytes`. - VERSION-DEPENDENT (mypy 2.0+)
30. mypy 2.0 redefined `--allow-redefinition`: it "now behaves like `--allow-redefinition-new` in mypy 1.20 and earlier." The new behaviour "requires `--local-partial-types`, which is now enabled by default," and unlike the old flag it does NOT allow two type annotations for the same variable - previously-accepted code can now error. The old semantics survive as `--allow-redefinition-old`. - VERSION-DEPENDENT (mypy 2.0+)
31. mypy 2.0 added experimental parallel checking: `--num-workers N` (short `-nN`), with "performance gains of up to 5x when using 8 worker processes." Critically, "Parallel type checking implicitly enables the new native parser. There are still some minor semantic differences between parallel and non-parallel modes" - so `-n8` can produce a different diagnostic set than a serial run. - VERSION-DEPENDENT (mypy 2.0+)
32. mypy's Rust `--native-parser` is not yet default but is imminent: "We are planning to enable the new native parser (`--native-parser`) by default soon." Any project already passing `--num-workers` is on the native parser today, whether or not it asked. - VERSION-DEPENDENT (mypy 2.3)
33. mypy 2.2 made the fixed-format cache the default (JSON still reachable via `--no-fixed-format-cache`) and enabled the SQLite cache by default. Cache-format changes invalidate incremental state across the upgrade. - VERSION-DEPENDENT (mypy 2.2)
34. mypy 2.0 removed the legacy bundled-stub special case: "Mypy now consistently respects `--ignore-missing-imports` for all packages." Packages that previously reported missing types despite `--ignore-missing-imports` now go quiet - a strictness *loss* on upgrade. - VERSION-DEPENDENT (mypy 2.0+)
35. mypy per-module config uses `[mypy-PATTERN1,PATTERN2,...]` in INI form and `[[tool.mypy.overrides]]` with a `module` key in `pyproject.toml`. Precedence is: inline source config > concrete module names > unstructured wildcards (later wins) > structured wildcards (more specific wins) > command line > global `[mypy]`. - ESTABLISHED
36. `warn_redundant_casts` is GLOBAL-ONLY in mypy and cannot be set per module, along with `python_version`, `platform`, `mypy_path`, `files`, `exclude`, `namespace_packages`, `explicit_package_bases`, `cache_dir`, `incremental`, `sqlite_cache`, `num_workers`, and `plugins`. Attempting per-module ratcheting of these is silently ineffective. - ESTABLISHED
37. `warn_unused_ignores`, `enable_error_code`, and `disable_error_code` ARE per-module settable, which is the mechanism for genuine per-module strictness ratcheting. - ESTABLISHED
38. mypy's own incremental-adoption guidance is: start on 5,000-50,000 lines; suppress whole packages with per-module `ignore_errors = True`; fix imports with per-module `ignore_missing_imports = True` (preferred over the global `--disable-error-code=import-untyped`, which "can hide errors later on"); require annotations on new/modified code; then turn on `disallow_untyped_defs` per completed module; then aim at `--strict`. - ESTABLISHED
39. mypy ships NO native baseline mechanism - its `existing_code` guidance never mentions one. Baselining is third-party: `mypy-baseline` 0.7.4 (2026-04-13). - ESTABLISHED

### pyright strict mode - exact, and its blind spots

40. pyright's `typeCheckingMode` has four values, `"off" | "basic" | "standard" | "strict"`, and the CLI/config default is `"standard"`. `"off"` still reports "Python syntax and semantic errors." - VERSION-DEPENDENT (pyright main-branch docs, read 2026-08-08)
41. microsoft/pyright `docs/configuration.md` documents 91 rows in the per-mode default-severity table. Exactly 36 rules escalate to `error` in `strict` from a non-error level in `standard`. - VERSION-DEPENDENT (pyright main-branch docs, read 2026-08-08)
42. The 36 strict-only escalations are: `reportMissingTypeStubs`, `reportAssertAlwaysTrue`, `reportInvalidStringEscapeSequence`, `reportInvalidTypeVarUse`, `reportSelfClsParameterName`, `reportUnsupportedDunderAll`, `reportUnusedExpression`, `reportWildcardImportFromLibrary` (these eight from `"warning"`), plus from `"none"`: `reportConstantRedefinition`, `reportDeprecated`, `reportDuplicateImport`, `reportIncompleteStub`, `reportInconsistentConstructor`, `reportInvalidStubStatement`, `reportMatchNotExhaustive`, `reportMissingParameterType`, `reportMissingTypeArgument`, `reportPrivateUsage`, `reportTypeCommentUsage`, `reportUnknownArgumentType`, `reportUnknownLambdaType`, `reportUnknownMemberType`, `reportUnknownParameterType`, `reportUnknownVariableType`, `reportUnnecessaryCast`, `reportUnnecessaryComparison`, `reportUnnecessaryContains`, `reportUnnecessaryIsInstance`, `reportUnusedClass`, `reportUnusedImport`, `reportUnusedFunction`, `reportUnusedVariable`, `reportUntypedBaseClass`, `reportUntypedClassDecorator`, `reportUntypedFunctionDecorator`, `reportUntypedNamedTuple`. - VERSION-DEPENDENT (pyright main-branch docs, read 2026-08-08)
43. TEN pyright rules remain `"none"` EVEN IN STRICT and must be opted into by name: `reportCallInDefaultInitializer`, `reportImplicitOverride`, `reportImplicitStringConcatenation`, `reportImportCycles`, `reportMissingSuperCall`, `reportPropertyTypeMismatch`, `reportUninitializedInstanceVariable`, `reportUnnecessaryTypeIgnoreComment`, `reportUnreachable`, `reportUnusedCallResult`. - VERSION-DEPENDENT (pyright main-branch docs, read 2026-08-08)
44. Fact 43 mirrors mypy fact 25 exactly: NEITHER checker reports unreachable code in strict mode (`--warn-unreachable` off in mypy strict; `reportUnreachable` `"none"` in pyright strict), and pyright strict does NOT report useless suppressions (`reportUnnecessaryTypeIgnoreComment` = `"none"`) whereas mypy strict DOES (`--warn-unused-ignores`). - VERSION-DEPENDENT (mypy 2.3, pyright 1.1.411-era docs)
45. Three inference-widening booleans are `false` in off/basic/standard and `true` only in strict: `strictListInference`, `strictDictionaryInference`, `strictSetInference`. These change inferred types, not just diagnostics, so `strict` alters what the checker *believes*, not merely what it *says*. - VERSION-DEPENDENT (pyright main-branch docs)
46. Two booleans are `false` even in strict: `deprecateTypingAliases` (PEP 585 aliases such as `typing.List` are NOT flagged unless enabled) and `enableExperimentalFeatures`. - VERSION-DEPENDENT (pyright main-branch docs)
47. `reportMissingModuleSource` is `"warning"` in ALL FOUR modes including strict - the only rule that never reaches `error`. A stub-only dependency with no source therefore never fails a strict pyright run on severity alone. - VERSION-DEPENDENT (pyright main-branch docs)
48. Five rules escalate `basic` -> `standard`: `reportFunctionMemberAccess`, `reportIncompatibleMethodOverride`, `reportIncompatibleVariableOverride`, `reportOverlappingOverload`, `reportPossiblyUnboundVariable`. Override-compatibility checking is therefore absent in `basic`. - VERSION-DEPENDENT (pyright main-branch docs)
49. pyright's `pythonVersion` has NO fixed default: "If no version is specified, pyright will use the version of the current python interpreter, if one is present." The same source tree checked on two machines with different interpreters gets two different verdicts. `pythonPlatform` behaves the same way. Both MUST be pinned in `pyrightconfig.json` for reproducible CI. - ESTABLISHED
50. pyright per-directory strictness uses `executionEnvironments`, an ordered array: "Each source file within a project is associated with at most one execution environment -- the first one whose root directory contains that file." Order is semantic; a broad `root` placed first shadows every later entry. - ESTABLISHED
51. pyright honours `# type: ignore` only while `enableTypeIgnoreComments` is `true` (the default), and that switch "does not affect `# pyright: ignore` comments" - disabling it leaves pyright-specific suppressions live while silently reactivating every PEP 484 suppression in the tree. - ESTABLISHED
52. pyright's `useLibraryCodeForTypes` defaults to `true`: it infers types from unstubbed library source. This is the origin of most `Unknown` leakage that strict mode's `reportUnknown*` family then reports. - ESTABLISHED
53. `disableBytesTypePromotions` defaults to `true` in pyright across all four modes, matching PEP 688 and mypy 2.0's `--strict-bytes` default. On this one point the two checkers have converged. - VERSION-DEPENDENT (pyright main-branch docs, mypy 2.0+)

### ty and pyrefly configuration surfaces

54. ty has NO strict mode. Its docs state plainly: "ty does not have flags such as `--check-untyped-defs` or `strictListInference`, because these are ty's default behaviour and are not currently configurable," and "ty's default mode is currently stricter by default than either mypy or pyright in many ways." - VERSION-DEPENDENT (ty 0.0.69)
55. ty checks unannotated function bodies unconditionally: "Unlike mypy, ty checks the bodies of unannotated functions unconditionally, so there is no ty rule corresponding to mypy's `check_untyped_defs` setting." - VERSION-DEPENDENT (ty 0.0.69)
56. ty documents 122 lint rules with three levels (`ignore` / `warn` / `error`). By default 91 are `error`, 23 are `warn`, and 8 are `ignore`. - VERSION-DEPENDENT (ty 0.0.69)
57. The 8 ty rules OFF by default are: `blanket-ignore-comment`, `division-by-zero`, `missing-override-decorator`, `missing-type-argument`, `possibly-missing-attribute`, `possibly-missing-import`, `possibly-unresolved-reference`, `unsupported-dynamic-base`. Notably `missing-type-argument` is off - ty does NOT flag bare `list`/`dict` by default, unlike `mypy --disallow-any-generics`. - VERSION-DEPENDENT (ty 0.0.69)
58. `unused-ignore-comment` and `unused-type-ignore-comment` are `warn`, not `error`, in ty by default - so stale suppressions do not fail a ty run on severity alone. - VERSION-DEPENDENT (ty 0.0.69)
59. `ty`'s `terminal.error-on-warning` DEFAULTS TO `true`: ty exits with code 1 on warnings. This is the opposite of the usual convention and means enabling a `warn`-level rule breaks CI. - VERSION-DEPENDENT (ty 0.0.69)
60. ty's `python-version` defaults to 3.14 (selectable 3.7-3.15) - a fixed default, unlike pyright's ambient-interpreter default. - VERSION-DEPENDENT (ty 0.0.69)
61. ty exposes two named soundness knobs rather than a strict mode: `strict-equality-semantics` (refuses to narrow `x: str` to `Literal["a"]` after `if x == "a"`, because a `str` subclass could compare equal) and `strict-generic-narrowing` (narrows `isinstance(value, list)` to the top materialization `Top[list[Unknown]]`). - VERSION-DEPENDENT (ty 0.0.69)
62. ty has first-class INTERSECTION types, which neither mypy nor pyright expresses: `A & B` means "both A and B", and ty prints them in diagnostics as e.g. `Serializable & Versioned` and `Unknown & Iterable`. It also prints materialization types such as `Top[list[Unknown]]`. Any log-scraping or error-matching tooling written against mypy/pyright output will not parse these. - VERSION-DEPENDENT (ty 0.0.69)
63. ty distinguishes `Unknown` (implicit, inferred-from-untyped) from `Any` (explicit), the same axis pyright draws, and unlike mypy which tracks a single `Any`. - VERSION-DEPENDENT (ty 0.0.69)
64. ty permits redeclaration: rebinding one name with a different declared type in the same scope (`paths: str` then `paths: list[str]`) is allowed by design, "designed for adoption." mypy rejects this even under `--allow-redefinition`, which "doesn't allow giving two type annotations for the same variable." - VERSION-DEPENDENT (ty 0.0.69, mypy 2.0+)
65. ty suppression syntax is `# ty: ignore[<rule>]`, and it also honours `# type: ignore` (all rules) and `# type: ignore[ty:<rule>]`. `analysis.respect-type-ignore-comments` (default `true`) governs the PEP 484 form. An `unused-ignore-comment` diagnostic "can only be suppressed using `# ty: ignore[unused-ignore-comment]`" - a bare ignore will not silence it. - VERSION-DEPENDENT (ty 0.0.69)
66. ty's escape hatches for untyped dependencies are `analysis.allowed-unresolved-imports` (glob-based suppression) and `analysis.replace-imports-with-any` (substitutes `Any` for named modules). The latter is a deliberate, auditable `Any` injection point - the equivalent of mypy's per-module `ignore_missing_imports` but with the `Any` made explicit in config. - VERSION-DEPENDENT (ty 0.0.69)
67. ty per-path strictness uses `[[overrides]]`; later overrides take precedence. There is no per-module INI-style section. - VERSION-DEPENDENT (ty 0.0.69)
68. ty ships library-specific rules, e.g. `pydantic-discarded-extra-argument` (default `warn`). Checker rule sets are no longer library-agnostic, so a rule name may have no analogue in any other checker. - VERSION-DEPENDENT (ty 0.0.69)
69. pyrefly has SIX named presets, not a strict boolean: `off` ("Silences every error kind"), `basic`, `legacy` (looser, for mypy migration), `default`, `strict`, and `all` ("Enables every error kind at error severity"). The `preset` key selects one. - VERSION-DEPENDENT (pyrefly 1.2)
70. pyrefly's default for a project with NO existing type-checker config is the `basic` preset, which "shows only high-confidence errors that are very likely to indicate real bugs or crashes, like syntax errors and missing imports." A green `pyrefly` run on a fresh project therefore means almost nothing. - VERSION-DEPENDENT (pyrefly 1.x)
71. pyrefly auto-migrates foreign config: if a mypy or pyright config is present, "Pyrefly reads your existing configuration and does its best to match your configuration," synthesizing an in-memory config. This means pyrefly's effective strictness is a function of files it was never pointed at - deleting `mypy.ini` silently changes pyrefly's behaviour. - VERSION-DEPENDENT (pyrefly 1.x)
72. pyrefly's `strict` preset is not a single switch either; `strict-callable-subtyping` (strict parameter compatibility for callable subtyping) is `true` under the `strict` preset and `false` otherwise. - VERSION-DEPENDENT (pyrefly 1.2)
73. pyrefly key config: `check-unannotated-defs` defaults to `true` (like ty, unlike mypy), `infer-return-types` defaults to `"checked"`, `min-severity` defaults to `"error"`, `permissive-ignores` defaults to `false`, and `enabled-ignores` defaults to `["type", "pyrefly"]`. Per-path overrides use `[[sub-config]]` with a `matches` glob; only `errors`, `replace-imports-with-any`, `check-unannotated-defs`, `infer-return-types`, and `ignore-errors-in-generated-code` may be overridden there. - VERSION-DEPENDENT (pyrefly 1.2)
74. pyrefly is the only mainstream checker with a first-class bulk-suppression command: `pyrefly suppress` (equivalent to `pyrefly check --suppress-errors`), with `--comment-location=same-line`, and `--remove-unused` / `--remove-unused=type` / `--remove-unused=all` to reap stale suppressions. This is native baseline-by-annotation rather than baseline-by-file. - VERSION-DEPENDENT (pyrefly 1.2)
75. pyrefly file-level suppression is `# pyrefly: ignore-errors` (or `ignore-errors[code]`) and MUST appear before any code; misplacement yields a `misplaced-ignore` warning rather than silent failure. - VERSION-DEPENDENT (pyrefly 1.2)

### Named, concrete divergences an agent must not paper over

76. mypy skips unannotated function bodies by default; pyright, ty, and pyrefly all check them by default. Per pyright's own comparison doc, mypy "skips all functions or methods that do not have type annotations" unless `--check-untyped-defs`. - ESTABLISHED
77. Return-type inference: pyright "infers the return type from `return` and `yield` statements within the function's body"; mypy "never infers return types and assumes that functions without a return type annotation have a return type of `Any`." This single difference changes the type of every unannotated call site. - ESTABLISHED
78. Union vs join: pyright "always uses a union operation" when merging types; mypy "typically (but not always) uses a 'join' operation, which merges types by finding a common supertype." For heterogeneous containers, mypy's join "often produces a type that is not what was intended." - ESTABLISHED
79. Literal retention in tuples: pyright "retains these literal types" in tuple expressions; mypy "widens the types to their non-literal type." Code depending on literal-typed tuple elements type-checks differently in each. - ESTABLISHED
80. Narrowing `Any`: pyright "never narrows `Any` when performing type narrowing for assignments"; mypy is "inconsistent about when it applies type narrowing to `Any` type arguments." Do not rely on either behaviour. - ESTABLISHED
81. Annotated-variable narrowing: pyright narrows on assignment "regardless of whether the assignment statement includes a variable type annotation"; mypy "skips assignment-based type narrowing when the target variable includes a type annotation." Adding a redundant annotation can *lose* narrowing in mypy. - ESTABLISHED
82. Type-guard expression coverage differs: pyright supports `x == L`, `x in y`, and `bool(x)` as narrowing forms, and supports aliasing a conditional expression used as a type guard; mypy currently supports none of these. - ESTABLISHED
83. Constructor evaluation differs: pyright "attempts to follow the runtime behavior as closely as possible," evaluating `__new__` and conditionally `__init__`; mypy "first evaluates the `__init__` method if present, and it ignores the annotated return type of the `__new__` method." mypy 2.2 partially closed this - it now respects explicitly annotated `__new__()` return types - with two back-compat exceptions: an `Any` return still yields the current class, as does a supertype return inherited from a superclass. - VERSION-DEPENDENT (mypy 2.2)
84. Function bodies that are just `...`: pyright "does not enforce the return type annotation"; mypy "treats `...` function bodies as though they are executable and enforces the return type annotation." Protocol and stub-style declarations therefore need different handling per checker. - ESTABLISHED
85. `None` returns: mypy "flags as an error" consuming the result of a `-> None` function; pyright "does not special-case `None` in this manner." - ESTABLISHED
86. Value-constrained TypeVars: mypy "analyzes the class or function multiple times, once for each constraint," emitting one error per constraint; pyright uses "conditional types" instead. Error *counts* are not comparable between checkers even where both are correct. - ESTABLISHED
87. Overload resolution under `Any`: when an argument is `Any` and overloads are ambiguous, pyright evaluates "the resulting return type as the supertype"; mypy "evaluates the return type as `Any`." The mypy result silently disables downstream checking. - ESTABLISHED
88. Class decorators: pyright "honors class decorators"; mypy "largely ignores them." Decorator-based class transforms behave differently unless expressed via PEP 681 `@dataclass_transform`. - ESTABLISHED
89. Import side effects: pyright "intentionally does not model implicit side effects of the Python import loading mechanism," treating reliance on them as an error; mypy "models side effects of the import loader." Code that accesses `pkg.submodule` after only `import pkg` is legal to mypy, an error to pyright. - ESTABLISHED
90. Circular references: mypy's "multi-pass analyzer" resolves some cycles (metaclass dependencies, TypeVar bounds, class decorators) that pyright cannot. This is one of the few axes where mypy is strictly more capable. - ESTABLISHED
91. Type comments: mypy has "full support"; pyright "supports type comments only in locations where there is a way to provide an annotation using modern syntax." Legacy `# type:` comments are not portable. - ESTABLISHED
92. Plugins: mypy has a plug-in mechanism; pyright has none, "due to concerns about discoverability, maintainability, and performance." ty and pyrefly likewise ship no plugin API. Any correctness that a project currently derives from a mypy plugin evaporates under every other checker. - ESTABLISHED
93. `Any` accounting: pyright "differentiates between explicit and implicit forms of `Any`" (surfacing the implicit form as `Unknown` under the strict `reportUnknown*` family); mypy tracks `Any` uniformly and gates it behind `--warn-return-any` / `--disallow-any-*`. There is no rule-name mapping between the two families. - ESTABLISHED

### Deferred annotations: PEP 649 / PEP 749 / annotationlib

94. PEP 649 ("Deferred Evaluation Of Annotations Using Descriptors") is Final, Python-Version 3.14; PEP 749 ("Implementing PEP 649") is Final, Python-Version 3.14. - ESTABLISHED
95. Deferred evaluation is the DEFAULT in 3.14: "The annotations on functions, classes, and modules are no longer evaluated eagerly. Instead, annotations are stored in special-purpose annotate functions and evaluated only when necessary (except if `from __future__ import annotations` is used)." - VERSION-DEPENDENT (3.14+)
96. Consequently, on 3.14+ "It is no longer necessary to enclose annotations in strings if they contain forward references" - quoted forward references and the `__future__` import both become removable once 3.13 support is dropped. - VERSION-DEPENDENT (3.14+)
97. `from __future__ import annotations` is now DEPRECATED but its behaviour is UNCHANGED: "this statement is now deprecated and it is expected to be removed in a future version of Python. This removal will not happen until after Python 3.13 reaches its end of life in 2029 ... In Python 3.14, the behavior of code using `from __future__ import annotations` is unchanged." - VERSION-DEPENDENT (3.14+)
98. The `__future__` import and PEP 649 are MUTUALLY EXCLUSIVE, not additive: with the import present, annotations are stored as strings and `get_annotations()` retrieves the stringified form; PEP 649's lazy-object model does not apply. Leaving the import in place on 3.14 forfeits the entire feature. - VERSION-DEPENDENT (3.14+)
99. PEP 563 ("Postponed Evaluation of Annotations") has status **Superseded** on peps.python.org - it is not merely deprecated in docs, it is formally superseded. - ESTABLISHED
100. `annotationlib` was added in 3.14 and is the supported introspection entry point. `annotationlib.get_annotations(obj, *, globals=None, locals=None, eval_str=False, format=Format.VALUE)` returns a NEW dict each call. - VERSION-DEPENDENT (3.14+)
101. `annotationlib.Format` has three usable members with non-contiguous values: `Format.VALUE = 1` (evaluate; may raise `NameError`), `Format.FORWARDREF = 3` (real values where defined, `ForwardRef` proxies elsewhere; "never throws an exception"), `Format.STRING = 4` (source-like strings; cannot recover comments, whitespace, or certain expression forms). Do not assume `Format` is a contiguous 1/2/3 enum. - VERSION-DEPENDENT (3.14+)
102. `annotationlib.call_annotate_function(annotate, format, *, owner=None)` exists specifically because "compiler-generated annotate functions only support `VALUE` format when called directly" - calling `__annotate__` yourself with `FORWARDREF`/`STRING` does not work. - VERSION-DEPENDENT (3.14+)
103. `annotationlib.ForwardRef` carries `__forward_arg__` (the code string, which "may not be exactly equivalent to the original source") and `evaluate(*, owner=None, globals=None, locals=None, type_params=None, format=Format.VALUE)`. - VERSION-DEPENDENT (3.14+)
104. Three annotation execution models now coexist and must be named explicitly in any spec: stock eager evaluation (3.0-3.13 default), stringified (`from __future__ import annotations`, 3.7+), and deferred/lazy (3.14+ default). Third-party libraries that read `__annotations__` "may need changes to support unquoted annotations before they work as expected." - VERSION-DEPENDENT (3.14+)
105. `inspect.signature()` gained an `annotation_format` argument and `inspect.Signature.format()` gained `unquote_annotations`, both in 3.14, for controlling which `annotationlib.Format` is used. - VERSION-DEPENDENT (3.14+)

### What the type system still cannot express

133. Value ranges remain inexpressible: Python's type system has no dependent or refinement types, so "a positive int" or `0 <= x <= 100` cannot be stated as a type. `Literal`/`Enum` close a finite domain but express no ordering or interval. - ESTABLISHED
134. Cross-field invariants (`start_date <= end_date`; "if `kind == 'A'` then `payload` is required") are inexpressible. Tagged unions of `TypedDict`/dataclasses approximate the discriminated case only, and PEP 728 `closed=True` is what makes `in`-check narrowing across such a union sound at all. - VERSION-DEPENDENT (3.15 for closed)
135. Ordering and temporal constraints ("`open()` before `read()`") are inexpressible: there is no typestate, and an object's type does not change when its internal state mutates. - ESTABLISHED
136. Units of measure are inexpressible. `NewType` per unit prevents accidental substitution at call boundaries but arithmetic between `NewType`s is not dimensionally checked - `Meters(3) + Feet(2)` type-checks as `int` addition. - ESTABLISHED
137. Stateful protocols are inexpressible: `Protocol` captures shape at one instant, not a legal call sequence. - ESTABLISHED
138. Deep immutability and purity are inexpressible: there is no `pure`/`const` qualifier. `frozen=True` is shallow and bypassable via `object.__setattr__`; `Final` prevents rebinding a name, never mutation of the referenced object; `Mapping[str, int]` is a static promise the callee will not mutate, not a runtime guarantee. - ESTABLISHED
139. Python 3.15 adds a builtin `frozendict` type (PEP 814, listed in the 3.15 release highlights). This is a runtime immutable mapping, which narrows the gap for container-level immutability but still does not express *deep* immutability. - VERSION-DEPENDENT (3.15)
140. Checker-only / zero-runtime-effect constructs, exhaustively: `typing.cast(typ, val)` returns `val` unchanged with no check or coercion; `assert_type(val, typ)` returns its first argument unchanged and checks type EQUIVALENCE (not assignability) at check time; `reveal_type(obj)` emits a checker diagnostic; `Final` and `@final` have "no runtime checking of these properties"; `@override` is inert at runtime; `TypeForm(obj)` returns `obj`; `@disjoint_base` returns the object unchanged; `NewType` is a thin callable returning its argument. - ESTABLISHED
141. Metadata-only constructs: `Annotated[T, x]` must be treated as `T` "by any tool or library without special logic for x" (PEP 593). The `annotated-types` vocabulary (`Gt`, `Ge`, `Lt`, `Le`, `Interval`, `MultipleOf`, `MinLen`, `MaxLen`, `Len`) is inert unless a runtime consumer such as pydantic reads it; annotated-types is at 0.8.0 (2026-07-23) and is classified `Development Status :: 4 - Beta`. - VERSION-DEPENDENT (annotated-types 0.8.0)
142. `assert` is stripped from bytecode under `-O` / `-OO` / `PYTHONOPTIMIZE` (which set `__debug__ = False`), so it must never carry validation, sanitization, or authorization. This is unchanged and remains the single most consequential runtime-vs-static confusion. - ESTABLISHED

### Strictness ratcheting, concretely

143. There is no portable "strictness" axis across the four checkers. mypy ratchets by FLAG and per-module config section; pyright ratchets by a 91-row RULE table plus ordered `executionEnvironments`; ty ratchets by 122 RULE LEVELS plus `[[overrides]]`; pyrefly ratchets by six PRESETS plus `[[sub-config]]`. A spec that says "strict mode" specifies nothing. - VERSION-DEPENDENT (mypy 2.3, pyright 1.1.411, ty 0.0.69, pyrefly 1.2)
144. Baseline strategies differ in kind, and this determines migration cost: mypy has no native baseline (third-party `mypy-baseline` 0.7.4, file-based); pyrefly has native bulk annotation via `pyrefly suppress` with `--remove-unused` reaping; ty and pyright have suppression comments but no bulk-insert command documented. Choosing pyrefly makes "annotate the debt" cheap; choosing mypy makes "record the debt in a file" the only cheap option. - VERSION-DEPENDENT (mypy 2.3, pyrefly 1.2, ty 0.0.69, pyright 1.1.411)
145. The unused-suppression controls are the ratchet's ratchet, and they are inconsistently defaulted: mypy `--warn-unused-ignores` IS in `--strict` (error code `unused-ignore`); pyright `reportUnnecessaryTypeIgnoreComment` is `"none"` even in strict; ty `unused-ignore-comment` / `unused-type-ignore-comment` default to `warn`; pyrefly reaps them via `pyrefly suppress --remove-unused`. Without explicitly enabling these, suppressions accumulate permanently. - VERSION-DEPENDENT (mypy 2.3, pyright 1.1.411, ty 0.0.69, pyrefly 1.2)
146. `# type: ignore` without a code is itself detectable but not by default: mypy's `ignore-without-code` error code is opt-in, and ty's `blanket-ignore-comment` rule defaults to `ignore`. Requiring coded suppressions (`# type: ignore[arg-type]`) needs an explicit opt-in in both. - VERSION-DEPENDENT (mypy 2.3, ty 0.0.69)
147. The order of ratcheting that mypy's own docs endorse - suppress whole packages, then fix imports, then require annotations on new code, then `disallow_untyped_defs` per finished module, then global `--strict` - is per-module strictness applied bottom-up, not a global flag flipped at the end. - ESTABLISHED

## New content the manifest set should carry

**"The four-checker landscape and how to choose"** -> `python_typing_contract_manifest.md` (replace/expand §1).
Four checkers are now in production use and they are not interchangeable. mypy 2.3.0 is the ecosystem default and the only one with a plugin API, but scores lowest on official conformance (109/142, 76.8%). pyright 1.1.411 is the reference for narrowing and inference breadth (136.5/142). pyrefly 1.2.0 is Meta's, production-stable since 1.0.0 on 2026-05-12, top of the conformance table (141/142), and the only one with a native bulk-suppression command. ty 0.0.69 is Astral's, fastest by its own claim, and explicitly beta with no stable API — usable as a fast local pre-check, not as a release gate. Record each choice with its exact pinned version, and record that dropping a mypy plugin is a correctness regression no other checker can absorb.

**"Why cross-checker agreement is not a goal you can adopt"** -> `python_typing_contract_manifest.md` (new subsection under §1), or NEW: `typing_checker_divergence.md`.
Ground the claim in PEP 729's disclaimer of authority and the spec's refusal to bind the gradual guarantee, then enumerate the divergences that actually bite: unannotated bodies (mypy alone skips them), return-type inference (mypy infers none, assumes `Any`), union vs join widening, literal retention in tuples, narrowing of `Any`, annotation-suppressed narrowing in mypy, type-guard expression coverage, `...`-body enforcement, `None`-return consumption, class-decorator honouring, import side effects, and plugin availability. Close with the operational rule: pick ONE checker as the release gate; every other checker is advisory, and its findings are triaged, not merged.

**"Deferred annotations: the three execution models"** -> `python_typing_contract_manifest.md` (new §), or NEW: `python_annotation_runtime_manifest.md`.
Name the three models explicitly — eager (<=3.13), stringified (`__future__`), deferred (3.14+ default) — and state that they are mutually exclusive rather than layered. Cover `annotationlib.get_annotations`, the non-contiguous `Format` values, why `call_annotate_function` exists (compiler-generated annotate functions only accept `VALUE` directly), `ForwardRef.evaluate`, and the `inspect.signature(annotation_format=...)` hook. State the deprecation timeline for `from __future__ import annotations` (removal no earlier than 3.13 EOL in 2029) and the migration trigger: drop the import once 3.13 support is dropped, but only after auditing every library that reads `__annotations__`.

**"Strictness ratcheting: four incompatible mechanisms"** -> `python_typing_contract_manifest.md` (new §), or NEW: `typing_adoption_ratchet.md`.
mypy ratchets by flag plus `[mypy-*]` / `[[tool.mypy.overrides]]`, with a documented precedence chain and a set of global-only options (`warn_redundant_casts`, `python_version`, `platform`, `plugins`, ...) that cannot be ratcheted per module. pyright ratchets by a 91-row rule table plus ordered `executionEnvironments` (first matching root wins). ty ratchets by 122 rule levels plus `[[overrides]]` (last match wins). pyrefly ratchets by six presets plus `[[sub-config]]` with a closed list of overridable keys. Give the adoption order mypy itself endorses, and name the baseline options: `mypy-baseline` 0.7.4 for mypy, `pyrefly suppress --remove-unused` for pyrefly, comments only for ty and pyright.

**"Suppression hygiene and the unused-ignore asymmetry"** -> `error_tracing_contract_manifest.md`, or `python_typing_contract_manifest.md` §"Confine escape hatches".
The four checkers default differently on stale suppressions: mypy strict reports them, pyright strict does not, ty warns, pyrefly reaps them on request. Coded suppressions are not required by default anywhere (mypy `ignore-without-code` opt-in; ty `blanket-ignore-comment` defaults to `ignore`). Specify the required config per checker to make suppression debt visible, and note the interlocks: pyright's `enableTypeIgnoreComments` toggles PEP 484 comments but not `# pyright: ignore`; ty's `unused-ignore-comment` can only be silenced by naming itself.

**"Typing PEP status ledger (verified, with versions)"** -> NEW: `python_typing_pep_ledger.md`.
A single table of number, title, status, shipping Python version, and one-line contract, generated from `https://peps.python.org/api/peps.json` rather than recalled. Must separate Final from Draft in a way an agent cannot misread, because the currently-Draft set (718, 746, 764, 767, 781, 821, 827, 835) is exactly the set most likely to be hallucinated as available. Include the newly Final 3.15 additions absent from the current manifest: PEP 728, PEP 747 (`TypeForm`), PEP 800 (`@disjoint_base`), PEP 661 (builtin `sentinel`).

**"Narrowing contracts: TypeIs vs TypeGuard"** -> `python_typing_contract_manifest.md` §2.
`TypeIs` (PEP 742, Final, 3.13) narrows in both branches, intersects with the prior type on True, and requires its narrowed type to be consistent with the parameter type. `TypeGuard` (PEP 647, Final, 3.10) narrows only on True and imposes no such relationship. Default to `TypeIs`; reserve `TypeGuard` for deliberate non-subtype narrowing (for example `list[object]` -> `list[str]`). Note that checkers differ in which *built-in* expressions narrow at all (pyright supports `x == L`, `x in y`, `bool(x)`; mypy does not), so a portable contract states the narrowing predicate as an explicit `TypeIs` function rather than relying on inference.

## Traps for coding agents

1. **"mypy --strict has 15 flags" is now wrong.** It has 13 in mypy 2.3. An agent reproducing the 1.19 list will add `--warn-unused-configs` and `--strict-bytes` as if strict implied them; strict does not, and `--strict-bytes` is now a global default instead.
2. **Upgrading mypy 1.x -> 2.x silently REDUCES some checking.** `--warn-unused-configs` leaves the strict set (stale `[mypy-*]` sections stop being reported) and the legacy bundled-stub special case is gone, so `--ignore-missing-imports` now suppresses reports it previously could not. Net strictness is not monotonic across the major bump.
3. **`--strict` is not a floor.** "The strict flag does not take precedence over other strict-related flags ... regardless of the order in which they are passed." `mypy --strict --no-warn-return-any` is quietly weaker than strict, and reordering the arguments will not fix it.
4. **Neither mypy strict nor pyright strict reports unreachable code.** mypy's docs say so outright ("the `--warn-unreachable` flag is not automatically enabled by the strict flag"), and pyright's `reportUnreachable` is `"none"` in all four modes. An agent that assumes strict covers dead code is wrong in both tools.
5. **pyright strict leaves ten rules off.** `reportUnnecessaryTypeIgnoreComment`, `reportImplicitOverride`, `reportUninitializedInstanceVariable`, `reportImportCycles`, `reportUnusedCallResult`, `reportMissingSuperCall`, `reportPropertyTypeMismatch`, `reportCallInDefaultInitializer`, `reportImplicitStringConcatenation`, and `reportUnreachable` are `"none"` even in strict. "strict" is not "all".
6. **pyright has no default `pythonVersion`.** It uses the ambient interpreter. An agent that omits `pythonVersion`/`pythonPlatform` from `pyrightconfig.json` writes a CI job whose verdict depends on the runner image.
7. **`reportAny` / `reportExplicitAny` are basedpyright, not pyright.** They do not appear in microsoft/pyright's `docs/configuration.md`. Emitting them into `pyrightconfig.json` targets a fork the project may not use.
8. **`@deprecated` comes from `warnings`, not `typing`.** `from warnings import deprecated`. And it is reported by default almost nowhere: mypy's `deprecated` code is opt-in, pyright's `reportDeprecated` is `"none"` outside strict, ty's `deprecated` rule is `warn`.
9. **`sentinel` is a builtin in 3.15, not `typing.Sentinel`.** `MISSING = sentinel("MISSING")`. In `typing_extensions` 4.16.0 the capitalized `Sentinel` is a soft-deprecated alias for lowercase `sentinel`, and the default repr changed from `<X>` to `X` — code asserting on repr breaks.
10. **PEP 764 (inline TypedDicts) and PEP 718 (subscriptable functions) are DRAFT.** So are PEP 746, 767, 781, 821, 827, and 835. None are available in any released Python. These are the likeliest typing hallucinations because they read like natural extensions.
11. **`TypeForm` is 3.15, not 3.14.** mypy's own 2.2 changelog says "TypeForm (introduced in Python 3.14)", but PEP 747 records Python-Version 3.15 and `docs.python.org/3.15/library/typing.html` says "Added in version 3.15." The primary docs win; the changelog parenthetical is wrong. On 3.14 and earlier, import it from `typing_extensions`.
12. **`TypeGuard` does not narrow the else-branch.** Choosing `TypeGuard` where `TypeIs` was meant silently forfeits negative narrowing, producing no error and no diagnostic — just weaker types downstream that nothing flags.
13. **`from __future__ import annotations` DISABLES PEP 649 rather than reinforcing it.** With the import present, annotations remain strings and the lazy model does not apply. An agent "modernizing" a 3.14 file by adding the import to be safe removes the feature it thinks it is enabling.
14. **`annotationlib.Format` is not 1/2/3.** `VALUE = 1`, `FORWARDREF = 3`, `STRING = 4`. Hard-coding `2` or assuming contiguity fails.
15. **Calling `__annotate__` directly only supports `VALUE`.** `annotationlib.call_annotate_function(annotate, format, owner=...)` exists precisely because compiler-generated annotate functions reject other formats when invoked directly.
16. **`mypy --num-workers N` can change results, not just speed.** It implicitly enables the native parser and "There are still some minor semantic differences between parallel and non-parallel modes." A parallel CI run and a serial local run are not guaranteed to agree.
17. **`mypy --allow-redefinition` changed meaning in 2.0.** It now means what `--allow-redefinition-new` meant in 1.20, requires `--local-partial-types`, and no longer permits two annotations for the same variable. Previously-clean code errors. The old behaviour is `--allow-redefinition-old`.
18. **`warn_redundant_casts` cannot be set per module in mypy.** Nor can `python_version`, `platform`, `plugins`, `exclude`, or the cache options. Writing them under `[[tool.mypy.overrides]]` is silently ineffective — the flag is simply never applied where the agent thinks it was.
19. **ty exits non-zero on warnings by default.** `terminal.error-on-warning` defaults to `true`. Enabling a `warn`-level ty rule is a CI-breaking change, not an advisory one.
20. **ty has no strict mode and will not accept strict-mode flags.** "ty does not have flags such as `--check-untyped-defs` or `strictListInference`, because these are ty's default behaviour and are not currently configurable." Passing mypy or pyright flags to ty is an error, not a no-op.
21. **ty's `missing-type-argument` is OFF by default.** Bare `list` / `dict` pass a default ty run but fail `mypy --disallow-any-generics` (in `--strict`) and pyright strict's `reportMissingTypeArgument`. Migrating to ty can look like a strictness win while losing generic-argument enforcement.
22. **A default pyrefly run on a config-less project uses the `basic` preset**, which "shows only high-confidence errors." Green means almost nothing until a preset is chosen explicitly.
23. **pyrefly silently inherits mypy/pyright config.** It "reads your existing configuration and does its best to match" it. Deleting `mypy.ini` therefore changes pyrefly's behaviour — a config file no one pointed pyrefly at is nonetheless load-bearing.
24. **ty prints types no other checker emits.** Intersections (`Serializable & Versioned`, `Unknown & Iterable`) and materializations (`Top[list[Unknown]]`) will not parse in tooling written against mypy or pyright output.
25. **Conformance percentage is not strictness and not quality.** mypy sits at 76.8% and is still the ecosystem default; the suite explicitly excludes the many behaviours "not standardized at all," and marks spec-optional lines `# E?`. Do not rank checkers for a project on this number alone.
26. **Conformance figures found in blog posts may not be in the official table.** The official python/typing results list exactly mypy, pycroscope, pyrefly, pyright, ty, and zuban. A "100% (141/141)" claim for a checker absent from that file is a vendor claim, and the official file's denominator is 142.
27. **Scores in the conformance table are keyed to the versions tested, not the current releases.** The 2026-08-07 file reports mypy 2.1.0 (not 2.3.0), pyright 1.1.410 (not 1.1.411), ty 0.0.67 (not 0.0.69), and pyrefly 1.3.0-dev.1 (a dev build ahead of the released 1.2.0). Quoting a score against the wrong version is a fabrication.
28. **`closed=True` on a TypedDict is 3.15 / mypy 2.2 and newer only.** It is not available on 3.13 or 3.14 runtimes without `typing_extensions`, and older checkers reject the unknown keyword rather than ignoring it. Do not emit it against an older pinned target.
29. **Assignability is not transitive under gradual typing.** "The consistency relation is not transitive." An agent chaining `A -> B` and `B -> C` assignability proofs to justify `A -> C` is reasoning unsoundly, and different checkers will disagree about the result.
30. **The spec tells checkers to be LENIENT about `Any`, not strict.** "A static type checker should not emit static type errors on an expression or statement if `Any` might represent a static type which would avoid the error." Strictness about `Any` is a checker policy layered on top of the spec, which is why the `Any` story differs so much between tools.
31. **`typing.cast` and friends do nothing at runtime.** `cast`, `assert_type`, `Final`, `@final`, `@override`, `TypeForm(x)`, `@disjoint_base`, and `NewType` are all checker-only or identity functions. None will ever raise. An agent adding `cast` to "fix" a validation bug has fixed nothing.
32. **`assert_type` checks equivalence, not assignability.** Asserting a supertype or Protocol against an inferred concrete subtype FAILS. It is a lock on the inferred type, not an assertion about compatibility.
33. **PEP 585 deprecation of `typing.List` is not reported by default in pyright.** `deprecateTypingAliases` is `false` in every mode including strict. An agent expecting strict mode to drive the `List` -> `list` migration will get silence.
34. **`useLibraryCodeForTypes` defaults to `true` in pyright**, so unstubbed dependencies produce inferred `Unknown` rather than hard import errors. This is the source of most `reportUnknown*` noise, and turning the rules on without addressing stubs produces an unfixable error wall.
35. **mypy has no baseline; do not invent a flag for one.** There is no `--baseline` / `--baseline-file`. Use `mypy-baseline` (0.7.4) or per-module `ignore_errors = True`. pyrefly is the only checker with a native bulk-suppression command (`pyrefly suppress`).
