## TL;DR

- **Put contract outcomes in the type system; raise only for the exceptional.** Python has **no checked exceptions**, so a raised exception is invisible in the signature and no checker can force a caller to handle it — a discriminated union closed with `assert_never` can be. Expected, recoverable domain outcomes return typed; bugs and genuinely exceptional conditions raise. ESTABLISHED (the asymmetry) / OPEN (where the seam sits) — §1, §3–§6.
- **Every failure path ends in one of three named dispositions:** raise, return typed, or **absorb-and-mark** (a frozen `Invalid`/`Missing` value rejected at the output boundary). Row-at-a-time work is dominated by the third, and absorbing without a **rejects sink** is the defect the taxonomy exists to prevent. OPEN (synthesis over the SWE corpus) — §3, §7b.
- **Bound every outbound call and retry inside a fixed budget — and import nothing beyond that ungated.** Timeout and bounded retry are near-universal at this scale, a decaying rate counter is what separates a self-clearing transient from a persistent fault, a circuit breaker is conditional, and retry budgets, supervision trees, dead-letter channels and N-version programming are **out of scope for one process**. OPEN — §7a–§7b.
- **No check that must run in production may be an `assert`.** `-O` removes `assert` statements *and* any `if __debug__:` code (and disables every `icontract`/`deal` contract by design); `-OO` also discards docstrings, deleting doctests-as-checks. `assert` is for internal can't-happen invariants only, and in `src` such a site carries a per-site `# noqa: S101` with its reason. ESTABLISHED (mechanism) / OPEN (ship policy) — §14.
- **Chain, catch narrowly, log once.** `raise X from Y` on every conversion (`__cause__` over an implicit `__context__`), never a bare `except`, explicit `contextlib.suppress` where suppression is intended, and one `logger.exception()` at the handling boundary — with handler/formatter policy deferred to `logging_observability_manifest.md`. ESTABLISHED — §8–§12, §20.
- **Aggregate concurrent failures with `ExceptionGroup`/`except*`, not with the first exception that wins.** The constructor you call is not necessarily the type you get, and callable `split`/`subgroup` conditions plus group-aware `contextlib.suppress` are the behaviours that argue for the hub's `>=3.13` default floor. VERSION-DEPENDENT (3.11+ for groups; 3.12+/3.13+ for the rest) — §18, §21; floor policy in `python_platform_baseline_manifest.md` §3e.

## 1. Purpose and scope

This manifest covers errors as a **public, version-stable contract** for a strictly-typed small app. Two facts frame everything below. **ESTABLISHED:** Python has **no checked exceptions** — a raised exception is invisible to the static type system, so it is *not* part of a function's statically-enforced signature (https://docs.python.org/3/library/typing.html). **ESTABLISHED:** an in-band result *can* be modeled in the type system as a discriminated union and statically enforced for exhaustive handling (https://typing.python.org/en/latest/spec/special-types.html). The whole design follows from this asymmetry: outcomes that belong to the contract should be **typed and in-band**; outcomes that are genuinely exceptional should be **raised**. Scope is single-process, small-scale apps; distributed tracing and metrics are out of scope and deferred to `logging_observability_manifest.md`. **Scale discipline:** much of the published error-handling vocabulary is distributed-systems machinery. §7a–§7b name those mechanisms and then **gate each one explicitly** for a small single-process app; the gate is content, not an omission, and importing the un-gated forms (retry budgets, supervision trees, dead-letter channels, N-version programming) would make this contract actively harmful.

## 2. Guiding principles (PEP 20)

**ESTABLISHED.** The Zen of Python anchors the error stance verbatim: **"Errors should never pass silently. Unless explicitly silenced."**, **"Explicit is better than implicit."**, and **"In the face of ambiguity, refuse the temptation to guess."** (https://peps.python.org/pep-0020/). Operationalized: never catch-and-ignore; if you suppress, suppress explicitly and narrowly (§10). Beyond PEP 20, the operating slogan for this manifest is **fail loud, fail typed** — a failure that is part of the contract is a typed value the checker forces you to handle; a failure that is a bug or a genuinely exceptional condition raises loudly with a traceable record.

**One clarification the slogan invites getting wrong (OPEN — synthesis over the SWE corpus edge `riding-over-transients -alternative-to-> fail-fast`, whose naming works are Hanmer, *Patterns for Fault Tolerant Software* (**UNVERIFIED**) and Nygard, *Release It!* (**UNVERIFIED**)):** *"Errors should never pass silently"* is a rule about **silence**, not about **immediate escalation**. Counting a self-clearing transient and retrying it within a bounded budget (§7a) is not passing silently; catching it and recording nothing is. An agent handed only "fail loud" will escalate on the first network blip, and an agent handed only "ride over transients" will hide a persistent fault — §7a supplies the decision mechanism (a decaying rate counter) that separates the two.

## 3. Two propagation channels, three dispositions

**ESTABLISHED.** Exactly two *propagation channels* exist, with different static guarantees (https://docs.python.org/3/library/typing.html; https://typing.python.org/en/latest/spec/special-types.html):

- **In-band typed value** — a discriminated union return such as `EmitOk | EmitError`. A static checker verifies the caller handles every arm: after narrowing all members away, the residual type is `Never`, and a final `assert_never(x)` typechecks only when no member remains. "Who handles which failure" becomes a **checked** part of the public contract, not tribal knowledge.
- **Out-of-band raised exception** — invisible to the type system (no checked exceptions). It does **not** appear in the signature; the checker cannot force a caller to handle it.

**Two channels, three dispositions.** A *channel* is how a failure travels; a *disposition* is what you decide to do with it. The channel count is **ESTABLISHED** (above); the three-disposition taxonomy is **OPEN** — it is a synthesis over the SWE design corpus, and each name below carries its own naming work. A manifest that names only two dispositions pushes authors into `try/except/continue` with no record, which is the most common real-world error-handling defect in data-shaped Python:

| disposition | mechanism | named vocabulary (naming work) | use when |
|---|---|---|---|
| **raise** | `raise SpecificError(...) from low` | **Samurai Principle** — Preschern, *Fluent C: Principles, Practices, and Patterns* (2022) | bug, unrecoverable at this layer, or truly exceptional (§7) |
| **return typed** | a discriminated union return, `EmitOk \| EmitError` | **Result Type** — Wlaschin, *Railway Oriented Programming* (2014); Douglas, *P1028 SG14 status_code and standard error object* (WG21, 2020) | an expected, recoverable, contract-level domain outcome the caller must branch on (§4) |
| **absorb and mark** | a frozen `Invalid(raw=..., reason=...)` or `Missing` value that flows through the domain and is rejected at the output boundary, with the rejection recorded | **Exceptional Value** and **Meaningless Behavior** — Cunningham, *The CHECKS Pattern Language of Information Integrity* (PLoP 1994); **Marked Data** — Hanmer, *Patterns for Fault Tolerant Software* (**UNVERIFIED**) | row-at-a-time work where one bad record must not stop the batch (§7b) |

**Why absorb-and-mark is a third category and not a flavour of raise (OPEN — the taxonomy; the quoted pair below is corpus-sourced):** the absorbing value *prevents the exception arising at all*. Cunningham's two patterns are defined in terms of each other — *"Meaningless Behavior operates over Exceptional Values, rejecting meaningless results at output"* (https://c2.com/ppr/checks.html) — so you may not adopt "no defensive checks in the domain" (§13) unless some value can carry the badness forward, and you may not absorb without a rejects sink (§7b `marked-data`). For ETL, batch and reporting work **absorb-and-mark is the dominant disposition**, and its sink at this scale is a rejects file, table or output variant — not a broker dead-letter queue (§7b, scale gate).

**Design rule (OPEN — convention, see §6):** expected/recoverable *domain* outcomes that belong to the contract → typed union; genuinely exceptional, unrecoverable-at-this-layer, or programmer-error conditions → raise; individually-bad records inside an otherwise-valid batch → absorb into an explicit invalid value and mark the rejection.

## 4. Typed result objects: `EmitOk | EmitError`

**ESTABLISHED.** Python ships **no built-in `Result`/`Either`**; the idiomatic encoding is a union of **frozen result variants** (a tagged/discriminated union), e.g. two frozen dataclasses `EmitOk` and `EmitError` distinguished by a literal tag or by type (https://docs.python.org/3/library/typing.html). **Named vocabulary (naming works, so the pattern is citable rather than a house preference):** the encoding is **Result Type** — Wlaschin, *Railway Oriented Programming* (2014); Douglas, *P1028 SG14 status_code and standard error object* (WG21, 2020) — specializing **Tagged Union**, and it is distinct from **Option Type** (`T | None`) on a rule worth stating: a Result carries *why* it failed, an Option only signals presence or absence with no reason. Use `T | None` when absence is the whole story; use `EmitOk | EmitError` the moment a caller could plausibly ask "why not?". Properties that make this the preferred channel for contract-level failures:

- **Statically checkable exhaustiveness.** Branch on each member (if/elif or `match`); after narrowing all members the residual type is `Never`; the final `assert_never(arg)` typechecks only when nothing is left.
- **Add-a-variant breaks the build.** Adding a new error variant to the union makes `arg` non-`Never` at every non-exhaustive consumer, so the checker flags **every** call site that fails to handle it — exactly the property wanted for "errors as part of the public contract."
- **`Never` / `assert_never` baseline:** added in **Python 3.11**; `NoReturn` (equivalent semantics) since 3.6.2 (§21). `Never` is the bottom type — the empty set of values (https://typing.python.org/en/latest/spec/special-types.html).

**Prefer in-band typed returns when** the failure is an expected, recoverable, domain outcome the caller must reason about (validation rejections, "not found" where absence is normal, business-rule denials). The dependency-vs-control choice — hand-rolled union vs a third-party `Result` library — is **OPEN**; §4b gives the 2026-08-08 landscape and the decisive engineering facts, and §21 carries the open question.

(Union mechanics, narrowing, `Literal` tags, and frozen-dataclass patterns: `python_typing_contract_manifest.md`.)

### 4a. Composing result-returning steps (railway-oriented programming)

**ESTABLISHED as vocabulary (a verified naming work), OPEN as a practice.** **Railway-Oriented Programming** — Wlaschin, *Railway Oriented Programming* (2014), https://fsharpforfunandprofit.com/rop/ . The SWE corpus records the dependency as a sourced edge: `railway-oriented-programming -composes-with-> result-type`, *"ROP is defined as composition over result types."* **You cannot import the Result encoding and skip the composition discipline** — without it, every call site re-implements the same "if it's an error, stop" branch, and the union's benefit is spent on boilerplate.

**The rule (OPEN — convention; adopt the discipline, not a monad stack).** A pipeline of N steps, each returning `Ok | Err`, needs exactly **one** short-circuit helper — a `bind`/`then` function that takes a result and a `Callable[[OkValue], Ok | Err]`, returns the error untouched, and applies the function only to the success arm — or, equivalently, one loop with an early return. Two honest constraints:

- **Python has no do-notation.** A deep monadic chain reads *worse* than an explicit early-return pipeline, which is why this manifest imports the discipline and not a combinator library by default. Write the shape that a reader can single-step in a debugger.
- **One error type per pipeline, or an explicit widening step.** If step 2's error arm is a different type from step 1's, the union grows at every stage and exhaustiveness (§5) becomes noise. Normalize at the seam (§6) into the project's error taxonomy (§11, §15a) before composing.

**Enforcement route:** type-catchable. Give the helper a precise signature and the checker will reject a step whose error arm is not in the pipeline's union, and `assert_never` (§5) will reject a consumer that forgets an arm. Nothing mechanical enforces that authors *use* the helper rather than hand-rolling the branch — that is review-only, and worth one line in the project's practice notes (`python_linting_practices_manifest.md`).

### 4b. The `Result`-library landscape (2026-08-08) and the dependency-vs-control choice

**VERSION-DEPENDENT / ESTABLISHED as of 2026-08-08.** There is **no stdlib `Result`/`Either`**, and the third-party landscape is thinner than its reputation suggests. These are library facts, pinned here because they change the shape of your error surface:

| option | state | Python floor | decisive engineering fact |
|---|---|---|---|
| hand-rolled frozen-dataclass union + `assert_never` | no dependency, no plugin, no abandonment risk | whatever your floor is (`Never`/`assert_never` are 3.11+, §21) | works in **every** checker with no configuration; the runtime failure of a reached `assert_never` is exactly `AssertionError("Expected code to be unreachable, but got: <repr>")` with the repr truncated at 100 characters (`_ASSERT_NEVER_REPR_MAX_LENGTH = 100`), so an enormous offending value is **not** fully logged |
| `returns` (dry-python) **0.29.0**, released 2026-08-02 | the only actively released option; self-classifies `Development Status :: 4 - Beta` | `>=3.11` (3.10 dropped in 0.27.0) | full inference **requires its own mypy plugin** `returns.contrib.mypy.returns_plugin` (0.29.0 declares mypy 1.19–2.4 support) — **choosing `returns` silently chooses mypy**, and disqualifies it for pyright-only or ty-only projects |
| `expression` **5.6.0**, released 2025-02-19 | classifies `Development Status :: 5 - Production/Stable` but has not shipped in roughly 17 months | `>=3.10, <4` | stable label, dormant release cadence; supplies `Option`, `Result`, `Try` and pipeline combinators |
| `result` (rustedpy) **0.17.0**, released 2024-06-02 | **dead — do not add.** README banner *"THIS PROJECT IS NO LONGER MAINTAINED"*; issue #201 *"Project Status: UNMAINTAINED"* (2024-12-23): *"no more releases will be made, no more fixes or features"*; repository archived read-only 2026-06-25 | classifiers stop at 3.12 | an agent reaching for `from result import Ok, Err` is adding an abandoned dependency whose last release predates Python 3.13 |

**The call for this collection's target (OPEN — the project must pin it, §21):** for a small, strictly-typed, single-process app the **hand-rolled frozen-dataclass union plus `assert_never` is the lowest-risk option** — zero dependency, zero checker coupling, zero maintenance risk — and the cost is that you write your own `bind` (§4a) and your own `map`. Reach for `returns` only if the project has already committed to mypy *and* the pipeline volume justifies the combinators. `expression` is defensible where its dormancy is acceptable. `result` is not a live option.

## 5. `assert_never` / `Never` exhaustiveness

**ESTABLISHED.** `assert_never(arg)` is the canonical exhaustiveness mechanism (https://docs.python.org/3/library/typing.html#typing.assert_never). A **missed case** leaves `arg` with a non-`Never` static type, so the checker emits an error; **at runtime** a reached `assert_never` raises `AssertionError`. Canonical pattern: branch on each union member, and in the final `case _:` / `else` call `assert_never(arg)`. This is a *special, intended* assertion (exhaustiveness) backed by static checking — distinct from the runtime-invariant assertions of §14, and it is the one assertion whose primary value is at type-check time, not run time.

**`assert False` is not a substitute (ESTABLISHED).** Writing `assert False` or a hand-rolled `raise AssertionError` in the fallback branch loses the static guarantee outright — *"we would not get the benefits of exhaustiveness checking"* because *"the type checker will not warn us"* (https://typing.python.org/en/latest/guides/unreachable.html). `assert_never` also survives `-O`: it is a **function call**, not an `assert` statement, so the `-O` removal rule (§14) does not reach it — a deduction from the two documented rules, not a quoted guarantee. **VERSION-DEPENDENT (3.11+):** `typing.assert_never` and `typing.Never` are stdlib from 3.11 and available from `typing_extensions` 4.1.0 below that; *"Never and NoReturn have the same meaning in the type system and static type checkers treat both equivalently"* (https://docs.python.org/3/library/typing.html).

**Enforcement route — type-catchable, but check what your checker does by default (VERSION-DEPENDENT):** `assert_never` works in mypy and pyright with **no configuration**, which is why it is the baseline mechanism here. Checker-native `match` exhaustiveness is *opt-in*: mypy needs `--enable-error-code exhaustive-match` (available from **mypy 1.17**; docs current for mypy 2.3.0) and pyright's `reportMatchNotExhaustive` is on only in strict mode. A project relying on native `match` checking without enabling the flag has no exhaustiveness check at all. Flag wiring belongs to `python_quality_gates_manifest.md`; the rule here is that **every discriminated-union consumer ends in `assert_never`**, independent of checker configuration.

## 6. The functional-core / imperative-shell boundary — where conversion happens

**Two tags, deliberately split — the earlier blanket OPEN was too pessimistic.** The **pattern is named and citable**: *Functional Core, Imperative Shell* — Bernhardt, *Destroy All Software* (2012), with its failure-side twin *Error Kernel* — Kuhn, Hanafee & Allen, *Reactive Design Patterns* (2017). What remains **OPEN** is only the **seam placement in this codebase**: no primary source prescribes which module or function is the boundary, so that decision must be tagged and written down. The grounded inference, layered on the language facts (https://docs.python.org/3/library/typing.html and PEP 20):

- The **pure functional core** returns **typed results** for expected/domain failures and stays exception-light; raised exceptions in the core are reserved for can't-happen invariant violations (§14).
- The **imperative shell** is where exceptions are **caught** and **converted**: translate low-level/library exceptions into typed results going *inward*, and translate typed errors into raised exceptions / log+exit going *outward* (§16 for the logging side).
- **Why the core is where irreplaceable state lives (Error Kernel, Kuhn et al. 2017).** The failure-side argument for the seam, in the corpus's own gloss on the element rather than a quotation from the book (the `error-kernel` element's `what` field in `elements.json`, which carries no quotation provenance): keep the irreplaceable state and critical logic in a small, maximally simple core, delegating risky or failure-prone work to expendable child components that can crash and be restarted. Crashing must be **cheap at the leaves** (§7b `let-it-crash`), and it is only cheap if nothing irreplaceable dies with the leaf. In Python that means: pure core holds the state and does no I/O; the risky work runs somewhere expendable — a `ProcessPoolExecutor` worker, a subprocess, or a task whose exception is confined and reported (§18b, §20a). The corpus records the dependency as a sourced edge, `error-kernel -composes-with-> let-it-crash`, citing Armstrong, *Programming Erlang*, and glossing it in the corpus's own note on that edge: let expendable children crash while the small, simple error kernel preserves irreplaceable state.
- **The shell concentrates error processing (Error Handler — Hanmer, *Patterns for Fault Tolerant Software*, **UNVERIFIED**).** Conversion, logging policy and disposition live in one place outside the mainline flow, not sprinkled through the core. This is the same claim as §20's "the shell owns logging policy", named.
- **Teams differ on exactly where the line sits.** This manifest mandates that the design **tag the exact seam** (which module/function is the shell boundary, what gets converted, in which direction) as an explicit OPEN/convention decision in the spec, per the epistemic-tagging discipline of `software_spec_discipline_manifest.md`. Do not leave it implicit.

(Functional-core/imperative-shell rationale and testability payoff: `architecture_manifest_default.md`, `software_spec_discipline_manifest.md` §F1.)

## 7. Raised exceptions: when they are the right channel

**ESTABLISHED (by the no-checked-exceptions fact, §3).** Raise — rather than return a typed result — when the condition is one of: **truly exceptional** (violates an assumption the contract is entitled to make), **unrecoverable at this layer** (this code cannot meaningfully decide what to do), or **programmer error** (a bug: a can't-happen state reached). Because raised exceptions are not in the static signature, reserving them for these cases keeps the *checkable* contract (the typed-union returns) honest and complete. A failure a caller is expected to branch on routinely should be a typed return (§4), not an exception the caller might forget to catch.

**OPEN — imported design rule, citable; the name is stronger than the prose (naming work: Preschern, *Fluent C*, 2022).** The **Samurai Principle** — *"return victorious or not at all"* — is the sourced form of this decision, recorded in the SWE corpus as the edge `return-status-code -alternative-to-> samurai-principle`: *"return an error the caller can handle vs assert/abort when it cannot be meaningfully handled."* It goes one step further than §7 as written: for a genuinely unhandleable error you should **not return an error value at all**, because *"propagating unhandleable errors buries the fault and corrupts state downstream."* A function that returns `Err("internal invariant broken")` has handed a bug to a caller who can only re-raise it badly.

**Fail Fast at startup (naming work: Nygard, *Release It!*, **UNVERIFIED**).** The cheapest place to raise is before any work happens. Put a preflight in the shell entry point: validate config, resolve paths, check writability, probe each external dependency with a **short** timeout (§7a), then start. The corpus element's summary: check preconditions and resource availability up front and report failure immediately, rather than doing work that is doomed to fail slowly. The counter-pole is §7a's *Riding Over Transients*, and the two are genuinely opposed — preflight is the right place for fail-fast precisely because a startup probe has no in-flight work to lose, and a steady-state request loop is where riding over transients is right instead.

## 7a. Transient faults: bound every call, retry within a budget, decide with a rate

**Scope and gate.** All of the following is **OPEN — imported vocabulary, gated per mechanism.** These patterns come from fault-tolerant and distributed-systems literature; at small-to-mid single-process scale exactly two of them are near-universal (**timeout**, **bounded retry**), two are cheap and worth having (**riding over transients**, **leaky-bucket counter**), one is conditional (**circuit breaker**), and one must not be built (**retry budget**). The gate is the content: adopting the whole set uncritically buys distributed-systems complexity for a program that has one process.

| mechanism | naming work | verdict at this scale | Python form |
|---|---|---|---|
| **Timeout** | Nygard, *Release It!* (**UNVERIFIED**); Bass, Clements & Kazman, *Software Architecture in Practice* 4th ed. (2021) — "BCK" below — for the tactic twin | **ADOPT — unconditionally.** The single highest-value import in this slice | every blocking call takes an explicit bound (below) |
| **Retry with exponential backoff and jitter** | Brooker, *Timeouts, Retries, and Backoff with Jitter*, Amazon Builders' Library (**UNVERIFIED** — and **no verified source exists in the corpus for backoff-with-jitter itself**, see Sources); BCK (2021) for the bare `retry` tactic | **ADOPT — bounded, and only for idempotent operations** | `tenacity` (`@retry(stop=stop_after_attempt(n), wait=wait_exponential_jitter())`), `urllib3.util.Retry(total=, backoff_factor=, backoff_jitter=)` behind an `HTTPAdapter`, or ~12 lines with `random.uniform` |
| **Riding Over Transients** | Hanmer (**UNVERIFIED**) | **ADOPT — as a logging/escalation policy, not a component** | do not act on the first failure; act when failures *persist*. The first N failures log at DEBUG/INFO; escalation is gated by the counter below |
| **Leaky Bucket Counter** | Hanmer (**UNVERIFIED**) | **ADOPT — ~10 lines, no dependency** | `score += 1` on error; on read, `score -= (now - last) * leak_rate` using `time.monotonic()`; trip at a threshold. It encodes an acceptable **rate**, not a count |
| **Circuit Breaker** | Nygard (**UNVERIFIED**); Kuhn, Hanafee & Allen, *Reactive Design Patterns* (2017) | **CONDITIONAL — import the name; adopt the mechanism only when the same dependency is called repeatedly in a loop and failing fast beats waiting.** A one-shot CLI invocation needs timeout + bounded retry, **not** a breaker | `pybreaker`, or a three-state class (closed/open/half-open) over the leaky-bucket counter |
| **Retry Budget** | Beyer et al., *Site Reliability Engineering* (2016), ch. 22 | **DO NOT BUILD — over-engineering at this scale.** It caps *aggregate* retry load as a fraction of primary traffic across many clients; one small process cannot generate retry amplification worth budgeting | name it in prose as the thing you are *not* doing; adopt only if many instances ever retry one backend |

**Two preconditions that are requirements, not tips (sourced corpus edges).** `retry-with-exponential-backoff-and-jitter -composes-with-> idempotent-receiver` (Hohpe & Woolf, *Enterprise Integration Patterns*, 2003): *"safe automatic retry requires the receiver to tolerate duplicate delivery idempotently."* Retrying a non-idempotent write is a data-corruption recommendation, not a resilience measure. And `retry-with-exponential-backoff-and-jitter -composes-with-> timeout` (Nygard, **UNVERIFIED**): *"each attempt is bounded by a timeout so a hung call fails and frees the retry to try again."* **Retry without a per-attempt timeout is a hang, not a retry.** Also sourced: `timeout -composes-with-> circuit-breaker` — *"timeouts detect the slow failure, the breaker stops repeating it"* — and `leaky-bucket-counter -composes-with-> riding-over-transients` — *"Riding Over Transients uses Leaky Bucket Counters to distinguish transient from persistent faults"*: mechanism and policy arrive as a pair.

**The bounded-call surface.** **ESTABLISHED where cited:** `asyncio.timeout()` / `asyncio.timeout_at()` convert the cancellation they cause into `TimeoutError`, and *"the `TimeoutError` can only be caught **outside** of the context manager"* (https://docs.python.org/3/library/asyncio-task.html) — a `try/except TimeoutError` *inside* the block never fires (§18b); `concurrent.futures.Future.result(timeout=...)` raises `TimeoutError` on expiry (https://docs.python.org/3/library/concurrent.futures.html). The wider surface, as recorded in this pass's seed pack — `socket.settimeout`, `subprocess.run(timeout=)`, `asyncio.wait_for`, `threading.Event.wait(timeout=)`, `queue.get(timeout=)`, `httpx.Timeout`, `requests.get(..., timeout=(connect, read))`, and driver-level `connect_timeout` / `statement_timeout` — is **OPEN** in one respect only: the *default* behaviour of individual third-party clients was not re-verified against their documentation this pass (the seed pack records that `requests` applies **no** default timeout). Treat every library's default as "no bound" until you have read its docs; that assumption is never dangerous, and its opposite is.

**Enforcement route — mostly contract-only, and say so.** Nothing in the type system or in a rule code verified by this pass forces a bound onto a blocking call. The mechanically enforceable substitutes, in order of strength: (1) wrap each external dependency in a project-owned client whose constructor **requires** the timeout as a non-default argument, so omission is a type error; (2) a lint rule for the specific "call without timeout" patterns your stack uses — the rule code is **OPEN** here and must be pinned in `python_linting_practices_manifest.md`, not guessed; (3) a test that injects a hanging fake and asserts the call raises within a bounded wall-clock window. Retry logic must be tested with an injected clock and an injected sleep, or the suite becomes slow and flaky — see `python_testing_tooling_manifest.md` and `python_concurrency_determinism_manifest.md`.

## 8. Exception chaining: `raise X from Y`, `__cause__` vs `__context__`

**ESTABLISHED** (https://docs.python.org/3/reference/simple_stmts.html; https://docs.python.org/3/library/exceptions.html):

- **`raise X from Y`** sets `X.__cause__ = Y` (the **explicit** cause; `__cause__` is writable). Setting `__cause__` also sets `__suppress_context__ = True`.
- **Implicit context:** when a new exception is raised *while another is being handled*, the prior one is auto-attached as `X.__context__`.
- **Display rules:** `__cause__` is **always** shown — *"The above exception was the direct cause of the following exception."* `__context__` is shown **only if** `__cause__` is `None` **and** `__suppress_context__` is false — *"During handling of the above exception, another exception occurred."*
- **Use** `raise Domain from low` when wrapping a low-level error in a domain exception at an abstraction boundary, so the original is preserved for tracing (§10, §11).

## 9. `from None` — use sparingly

**ESTABLISHED.** `raise NewError(...) from None` *"effectively replaces the old exception with the new one for display purposes (e.g. converting `KeyError` to `AttributeError`), while leaving the old exception available in `__context__` for introspection when debugging."* (https://docs.python.org/3/library/exceptions.html#BaseException.__suppress_context__). The original is **not lost** — it stays in `__context__` — but it is hidden from the rendered traceback. **Use sparingly:** suppressing context can hide the real source from a traceback, which works directly against source-tracing. Justify each use (typically: the wrapped exception is an irrelevant implementation detail of the lookup, and surfacing it would mislead).

## 10. Re-raise vs wrap vs explicit-suppress

**ESTABLISHED** (https://peps.python.org/pep-0020/; https://docs.python.org/3/library/exceptions.html; https://docs.python.org/3/library/contextlib.html):

- **Re-raise** with a bare `raise` (no expression) inside the handler to **preserve the original traceback** — the cheapest way to add nothing but let it propagate. (To add context without changing type, prefer `add_note`, **§19**.)
- **Wrap** with `raise Domain(...) from low` when crossing an **abstraction boundary**, keeping the cause chained (§8). This is the shell's primary tool for not leaking low-level exceptions across an API boundary (**§22** anti-pattern), and the same tool converts a boundary library's `ValidationError` into the project taxonomy (§15a).
- **Explicitly suppress** — and *only* explicitly, per PEP 20 *"Unless explicitly silenced"* — with `contextlib.suppress(SpecificError)`, narrowly scoped to the specific exception, with a comment or log explaining why. Never catch-and-ignore (**§22**). **VERSION-DEPENDENT (3.12+):** `suppress` only looks inside `BaseExceptionGroup`s from 3.12 (§18).

## 11. Custom exception hierarchy

**ESTABLISHED** (https://docs.python.org/3/library/exceptions.html; https://docs.python.org/3/tutorial/errors.html):

- **Root at `Exception`, never `BaseException`.** *"Programmers are encouraged to derive new exceptions from the `Exception` class or one of its subclasses, and not from `BaseException`."* `BaseException` also covers `SystemExit`/`KeyboardInterrupt`/`GeneratorExit`, which must not be swallowed (§12).
- **Single inheritance.** *"It's recommended to only subclass one exception type at a time"* — multiple inheritance of exception types causes args-handling and C-level memory-layout conflicts.
- **`Error` naming.** *"Most exceptions are defined with names that end in `Error`."*
- **One package base.** Define a single `PackageError(Exception)` base so callers can catch the whole library's failures with one handler, plus **narrow subclasses** for specific conditions. This makes the error surface a documented, reusable part of the public contract (§17).
- **Define vs reuse.** Define a custom exception when callers need to **distinguish it programmatically** or when it **crosses an API boundary**; otherwise **reuse a built-in** (`ValueError`, `TypeError`, `KeyError`, …). Do not invent a class where a builtin already carries the right meaning.

## 12. Catch narrowly; `else` / `finally`; never bare `except`

**ESTABLISHED** (https://docs.python.org/3/tutorial/errors.html):

- **Catch narrowly.** Name the specific exception type(s). **Bare `except:` and `except BaseException:` also catch `KeyboardInterrupt`/`SystemExit`/`GeneratorExit`**, which user code should not intercept — pair this with §11's `Exception`-not-`BaseException` rule. **VERSION-DEPENDENT (3.8+):** they also catch `asyncio.CancelledError`, which became a `BaseException` subclass in 3.8 — swallowing it silently breaks cancellation for the whole program (§18b).
- **The `as` name is destroyed at the end of the clause (ESTABLISHED).** *"When an exception has been assigned using `as target`, it is cleared at the end of the `except` clause"* — the same is true of `except*`. Reading the name after the block therefore fails; the docs state only that it is cleared, so do not depend on *which* error you get — if you need the exception later, bind it to another local inside the clause (https://docs.python.org/3/reference/compound_stmts.html).
- **VERSION-DEPENDENT (3.14+): parentheses became optional for a tuple of types** — `except TimeoutError, ConnectionRefusedError:` is legal for both `except` and `except*` (PEP 758). **`except A, B as e:` is still a SyntaxError**: *"when using the `as` clause to capture the exception instance parentheses must be used as before."* Two consequences for an agent: the unparenthesized form is a hard SyntaxError below 3.14, and in Python 2 the same text meant `except A as B`, so mechanically porting old code can produce a construct that looks legal, is version-gated, and means something different from its source. Keep the parentheses; the feature buys nothing and costs portability.
- **`else`** runs only if the `try` body raised nothing and *"is better than adding additional code to the `try` clause because it avoids accidentally catching an exception that wasn't raised by the code being protected."* Keep the protected region minimal — this directly aids tracing the true source.
- **`finally`** *"will execute as the last task … whether or not the `try` statement produces an exception"* — for releasing external resources. **The exception information is not available to the program during execution of the `finally` clause**, and if the `finally` clause itself raises, the original is attached as the new exception's `__context__` (§8).
- **NEVER transfer control out of a `finally` block (ESTABLISHED behaviour; VERSION-DEPENDENT (3.14) for the warning).** If a `finally` clause executes `return`, `break` or `continue` while an exception is in flight, *"the saved exception is discarded"* — the reference docs' own example is `try: 1/0` with `finally: return 42`, which returns **42** and loses the `ZeroDivisionError` entirely. A `return` in `finally` also overrides a `return` in the `try` body: *"a `return` statement executed in the `finally` clause will always be the last one executed."* No flag recovers the lost exception. Since **3.14** the compiler emits a `SyntaxWarning` for exactly this construct (PEP 765, Final, `Python-Version: 3.14`), and the PEP explicitly leaves *"whether, and when, this will become a `SyntaxError`"* open — on 3.13 and earlier there is **no signal at all**. (Historical detail: `continue` in a `finally` clause was illegal before 3.8.) Restrict `finally` bodies to cleanup calls, and prefer `with` / `contextlib.ExitStack` so there is no `finally` to get wrong. **Enforcement route — lint-catchable via the compiler itself:** `SyntaxWarning` is *not* in the default-ignored filter set, so it is visible without configuration, and the 3.14 notes give the CI shape as `-Werror -Wignore::SyntaxWarning` (or `PYTHONWARNINGS=error,ignore::SyntaxWarning`) — invert that to make this specific class fatal with `-W error::SyntaxWarning` on a **clean** build. It is a compile-time warning, so whether it is re-emitted from a cached `.pyc` is undocumented (**OPEN**): do not rely on seeing it on the second run. Wiring: `python_quality_gates_manifest.md`.

## 13. EAFP over LBYL (with the TOCTOU caveat)

**ESTABLISHED** (https://docs.python.org/3/glossary.html):

- **EAFP** ("Easier to ask for forgiveness than permission") is the idiomatic Python style: *"assumes the existence of valid keys or attributes and catches exceptions if the assumption proves false. This clean and fast style is characterized by the presence of many `try` and `except` statements."*
- **LBYL** ("Look before you leap") tests preconditions before acting and is the contrast. **TOCTOU caveat:** *"In a multi-threaded environment, the LBYL approach can risk introducing a race condition between the looking and the leaping … `if key in mapping: return mapping[key]` can fail if another thread removes `key` … This issue can be solved with locks or by using the EAFP approach."* Prefer EAFP; where LBYL is unavoidable across a shared resource, recognize the time-of-check/time-of-use window.

**OPEN — imported design rationale, citable. EAFP has a design-level name, not just an idiom label (naming work: Cunningham, *The CHECKS Pattern Language of Information Integrity*, PLoP 1994).** **Meaningless Behavior** is the placement decision behind the idiom: write domain functions with **no** defensive `is None` / `isinstance` guards, let the computation fail, and recover at the shell/presentation boundary — *"defensive checks duplicated through every domain method obscure the model; centering recovery at the presentation boundary keeps domain code minimal while tolerating bad data."* That is EAFP as an architectural placement (§6), not a stylistic preference. **The precondition is sourced and binding:** `exceptional-value -composes-with-> meaningless-behavior` — *"Meaningless Behavior operates over Exceptional Values, rejecting meaningless results at output"* — so you may not adopt "no defensive checks" unless some value can carry the badness forward (§3, absorb-and-mark). Omitting guards *without* an absorbing value is not EAFP; it is an unhandled `TypeError` at the wrong altitude.

## 14. Assertions — what they are FOR and NOT for

**ESTABLISHED** (https://docs.python.org/3/reference/simple_stmts.html):

- **Mechanism.** `assert expr, msg` compiles to `if __debug__: if not expr: raise AssertionError(msg)`. `__debug__` is *"True under normal circumstances, False when optimization is requested (`-O`)"*, and *"the current code generator emits no code for an `assert` statement when optimization is requested at compile time."*
- **FOR:** internal **can't-happen invariants** and **pre/post-conditions** — programmer-believed facts whose violation means a **bug**, not bad input (e.g. "this list is non-empty here", a postcondition on a pure function). `assert_never` (§5) is the special, intended, statically-backed assertion. **The lint consequence (OPEN — house convention; it is the only sanctioned escape):** `S101` flags every bare `assert` outside the test tree and `python_linting_practices_manifest.md` §4.2 enforces it in `src`, exempting `tests/**` through `per-file-ignores` only — so a legitimate internal-invariant assert in production code carries a **per-site** `# noqa: S101  # internal invariant, §14` naming its reason, never a global `ignore` and never a `per-file-ignores` entry outside `tests/**`.
- **NOT for:** validating **untrusted/boundary input**, auth, or resource state — **any check that must run in production must not be an `assert`**, because under `-O` it vanishes silently, which is both a correctness and a **security** hole.
- **A third kind of check exists, and it is not an assertion (naming work: Douglass, *Real-Time Design Patterns*).** **Sanity Check** is a plausibility test on a *computed output* that **must survive `-O`**: `if not (0.0 <= p <= 1.0): raise ImplausibleResult(...)`, counted and logged at WARNING. The corpus element's statement of the problem it addresses: full result verification is often infeasible, but gross faults are cheap to catch. Write it as an `if`/`raise`, never an `assert`. The corpus also files `executable-assertions` under BCK's category `bck-cat:control-and-observe-system-state` — i.e. as a **testability/observability** tactic whose point, in the corpus's wording, is that the program flags when and where it enters a faulty state — which is the bridge from this section into `python_runtime_diagnostics_manifest.md`, the owner of self-checking surfaces.
- **Production policy is OPEN (§21), and the audit is wider than bare `assert` statements.** `-O` removes *"assert statements **and any code conditional on the value of `__debug__`**"*, so `if __debug__:`-guarded checks vanish too; `-OO` additionally *"discard[s] docstrings"*, which deletes every doctest and every docstring-rendered contract. **Python Development Mode does not rescue any of it:** *"the Python Development Mode does not prevent the `-O` command line option from removing `assert` statements nor from setting `__debug__` to False."* All `icontract` and `deal` contracts are disabled under `-O` **by their own design**, so design-by-contract decorators inherit `assert`'s vanishing problem exactly and must never be the enforcement mechanism for a boundary, authorization or resource check. Worst of all, **pydantic converts an `AssertionError` raised inside a validator into its `ValidationError`**, and pydantic's own docs warn that `assert` *"statements are skipped when Python is run with the -O optimization flag"* — so an `assert` inside a `@field_validator` does not fail loudly under `-O`, it **silently passes validation**.
- **The audit, as a greppable checklist.** Search for and re-express: (1) bare `assert` used as a boundary, auth or resource check — an internal-invariant assert per the FOR bullet above is legitimate and stays, with its per-site `# noqa: S101`; (2) `if __debug__:` blocks; (3) doctests relied on as checks (gone under `-OO`); (4) `icontract` / `deal` decorators; (5) `assert` inside any pydantic validator. **Policy (OPEN — pin it):** production images are built **and** run **without** `-O`/`-OO`, and no check that must survive is expressed as `assert`, `if __debug__:`, or a DbC decorator. **Enforcement route:** fitness-function — a CI check that the production entry point is not invoked with `-O`/`-OO` and that `PYTHONOPTIMIZE` is unset, plus a lint rule for `assert` outside `tests/` whose exact code is pinned in `python_linting_practices_manifest.md`. `assert_never` (§5) is exempt: it is a function call, not an `assert` statement, so it survives.

## 15. Boundary validation & "parse, don't validate"

**OPEN — best-practice synthesis; library identity is now pinnable, the choice among libraries is not.** *"Parse, don't validate"* (Alexis King, 2019) and *"make illegal states unrepresentable"*: push checking to the boundary and **encode the proof in a type** so the core can assume the invariant holds (https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/). **Pydantic** positions itself as exactly this border control: *"Pydantic guarantees the types and constraints of the output, not the input data … after parsing and validation, Pydantic guarantees that the fields of the resultant model instance will conform to the field types."* (https://pydantic.dev/docs/validation/latest/concepts/models/ — pydantic's `docs.pydantic.dev/latest/...` paths return HTTP 301 to `pydantic.dev/docs/validation/latest/...` as of 8 August 2026; the quoted guarantee is unchanged at the new location). This is the **production-grade replacement** for the (wrong) use of `assert` on boundary input (§14): validation raises a real, catchable `ValidationError` with structured, actionable detail that **survives `-O`**.

**The relationship to chain together:** parse at the imperative-shell boundary → typed objects flow into the functional core → asserts guard internal invariants the parser already guarantees. **VERSION-DEPENDENT — library identity is pinnable as of 2026-08-08:** pydantic **2.13.4** (2026-05-06), msgspec **0.21.1** (2026-04-12), cattrs **26.1.0** (2026-02-18). What remains **OPEN** is the project's **choice** among them and the resulting error-surface shape, because the three raise structurally different errors — one `ValidationError` carrying a list of machine-readable dicts (pydantic), a PEP 654 `ExceptionGroup` (cattrs, **by default**), or one `ValidationError` that is also a `ValueError` with the path rendered into the message string (msgspec). The boundary adapter must therefore be written against the chosen library, not against a shared base (§15a). Pydantic **v1 is no longer a live option**: it survives only as the vendored `pydantic.v1` compatibility namespace shipped inside v2.

**The three validation-placement policies, named — and this collection's choice (OPEN — the choice is this collection's; the three names and the `alternative-to` edge between them are corpus-sourced).** The corpus records three *mutually exclusive* placement policies joined by an explicit `alternative-to` edge, so "push checking to the boundary" is a choice with a cost, not a self-evident truth:

| policy | naming work | what it says | cost its own source states |
|---|---|---|---|
| **Complete Parameter Checking** | Hanmer, *Patterns for Fault Tolerant Software* (**UNVERIFIED**) | validate all parameters at component boundaries, **every time** — `pydantic` / `TypeAdapter.validate_python` at every public entry point | *"detecting errors close to their source at the cost of some performance"* |
| **Deferred Validation** | Cunningham, CHECKS (PLoP 1994) | *"delay comprehensive validity checking … until an action requires it, scaling the rigor of the check to the consequences of that action"*, because *"eager validation at entry time rejects legitimately incomplete in-progress data and hard-codes one rigidity level"* | in-progress data can reach the core unvalidated; the commit path must be the only gate |
| **Meaningless Behavior** | Cunningham, CHECKS (PLoP 1994) | omit checks in the domain entirely; recover at the presentation boundary (§13) | requires an absorbing value (§3) or it degrades into unhandled errors |

**This collection picks Complete Parameter Checking (OPEN — a project decision, not a language mandate), and "parse, don't validate" *is* that policy** (`deferred-validation -alternative-to-> complete-parameter-checking`, *"opposite validation-placement policies"*). State the cost honestly: a per-object validation charge at every public entry point. **The one case where Deferred Validation is correct** is editable / in-progress data — a draft record a user is still filling in. Its Python form is an all-optional `Draft` model plus `Model.model_validate()` only at save/commit; `model_construct()` exists to skip validation **deliberately** and is a hole in the boundary (§15's forgery test), not a performance tip.

**The parse-function contract (ESTABLISHED from the source's own mechanic).** King's distinction is mechanical, not rhetorical: `validateNonEmpty` *"always returns `()`, the type that contains no information"* while `parseNonEmpty` returns *"a refinement of the input type that preserves the knowledge gained in the type system"* — hence the maxim *"be suspicious of functions that return unit"*, and the named anti-pattern **shotgun parsing**: *"a programming antipattern whereby parsing and input-validating code is mixed with and spread across processing code — throwing a cloud of checks at the input, and hoping, without any systematic justification, that one or another would catch all the 'bad' cases."* Therefore:

- **Signature.** `def parse_x(raw: Mapping[str, object]) -> ParsedX` — one input, one distinct output type, raising on rejection (or returning `ParsedX | Invalid` if the caller must branch, §3).
- **Return type.** A **distinct type** the rest of the program could not have built by accident: a frozen dataclass, an `attrs.frozen` class, a `msgspec.Struct`, or a pydantic model. **Never** `bool`, `None`, or the input `dict` — those carry no proof and force every downstream caller to re-check.
- **The forgery test.** *If arbitrary code elsewhere can construct the return type without going through the parser, the type carries no proof.* Named leaks that fail the test: `model_construct()` (*"creates models without running validation"*), `object.__setattr__` (which the generated frozen `__init__` uses itself), `typing.NewType` (a no-op callable — *"calling a `NewType` returns its argument unchanged"*), `typing.cast` (*"this returns the value unchanged"*), and plain attribute assignment on a pydantic model with `validate_assignment=False` (the default). **Enforcement route:** contract-only for the leaks — none of them is a type error — so the mechanically enforceable part is a lint/fitness check that the parsed type's constructor is called in exactly one module (`python_module_boundaries_manifest.md` owns the direction rule; `python_typing_contract_manifest.md` owns the immutability-depth facts).

## 15a. Converting library validation errors into the project taxonomy

**ESTABLISHED per library (VERSION-DEPENDENT on the library major).** The invariant first: **the project's error taxonomy is public API (§17) and must not leak the boundary library's exception types.** A caller who has to `except pydantic.ValidationError` is coupled to your dependency choice; swapping msgspec for pydantic then becomes a breaking change for every consumer. The shell (§6) converts, once, at the boundary — and each of the three live libraries needs a different adapter, because the error *shapes* differ:

| boundary library | error shape | adapter |
|---|---|---|
| **pydantic 2.13.4** | one `ValidationError` carrying a list of machine-readable dicts | catch `ValidationError`, call `.errors(include_url=False)`, map each entry's `type` string to a project error code, keep `loc` as a **structured sequence** — never `".".join(loc)`, because list indices in `loc` are `int`s — and re-raise the project error `from exc` (§8) |
| **cattrs 26.1.0** | a **PEP 654 `ExceptionGroup`** by default: *"a detailed validation mode since version 22.1.0, and this mode is enabled by default"*, in which errors are *"grouped and raised together as a `cattrs.BaseValidationError`"* (concretely `cattrs.ClassValidationError` or `cattrs.IterableValidationError`) | use `except*` (3.11+) or walk `.exceptions` explicitly, flattening to the same code/path/message triple; or build the converter with `detailed_validation=False` and accept first-error reporting. **A cattrs boundary makes ExceptionGroup handling mandatory, not optional** (§18, §21) |
| **msgspec 0.21.1** | one `msgspec.ValidationError` — which is **also a `ValueError`** (`ValidationError` → `DecodeError(MsgspecError, ValueError)`) — with the path rendered **into the message string** | catch `msgspec.ValidationError`; accept that the location arrives as text (`Expected str, got int - at $.groups[1]`) and either parse it or carry it as an opaque detail string. Note that `except ValueError` also catches it, which is easy to do by accident |

**Rules for the adapter.** (1) One adapter module, called only from the shell. (2) Always chain with `from exc` (§8) so the library's own detail survives in the traceback. (3) Map to a **stable project code** (§16) — the library's `type` strings are the library's contract, not yours, and they change across majors. (4) Never re-raise the library exception unchanged across your API boundary (§22). (5) The mapping table itself is the thing to test: one case per error code, asserting on structured attributes rather than on `str(exc)` (`python_testing_tooling_manifest.md`).

## 16. Descriptive messages — anatomy & structured attributes

**OPEN — best-practice synthesis; tag the 5-part anatomy as a team convention.** A high-quality error/exception, written to let a reader trace the failure to its source, carries five parts:

1. **Operation context** — what was being attempted.
2. **Expected vs actual** — what was required against what was found.
3. **Offending identifier/value** — the specific input/id at fault.
4. **Remediation hint** — what the caller can do about it.
5. **Stable error code** — a namespaced, machine-greppable code (ideally as an attribute, not embedded in prose).

The specific 5-part anatomy is a synthesis, **not** a single primary spec, but it is grounded in two facts (https://docs.python.org/3/reference/simple_stmts.html; https://docs.python.org/3/tutorial/errors.html): the assert-statement note says including the failing expression text is unnecessary because *"it will be displayed as part of the stack trace"* — i.e. **a message should add information the traceback lacks** (values, intent, remediation), not echo it; and custom exception classes *"often only offering a number of attributes that allow information about the error to be extracted by handlers"* — i.e. carry **structured fields** (offending id, code) **as attributes, not just a string**, so handlers and loggers can consume them. **Prefer structured attributes over bare strings.** Stable error codes as attributes make errors machine-greppable across versions (a convention, not mandated — §17, §21). **Carry this OPEN forward honestly:** a search across the whole SWE design/architecture element corpus (1083 elements) found **no element for a stable or namespaced error code, and none for an error-code registry**. There is therefore no named pattern and no citable authority for the stable-code scheme in part 5 above, nor for §17's version-stable error contract — they are this project's convention and must stay tagged **OPEN**. Do not dress them up with a borrowed citation.

## 17. Errors as a documented, version-stable public contract (reusability)

**ESTABLISHED / OPEN.** The exception hierarchy (§11) and the typed-result unions (§4) **are** public API surface. **ESTABLISHED:** a single `PackageError` base plus narrow subclasses lets a caller catch the whole library with one handler while distinguishing specific conditions — a documented, reusable contract (https://docs.python.org/3/library/exceptions.html; https://docs.python.org/3/tutorial/errors.html). **OPEN (convention):** the **stability of error codes and exception types across versions** — namespaced codes as exception attributes, deprecation guarantees on the error surface — is a versioned-contract decision the team must pin (§21). Treat adding a union variant or renaming an exception as a **breaking change** to consumers, subject to the reusability discipline in `software_spec_discipline_manifest.md` (§C, §G). **The wider change contract — what counts as a breaking change, how the version number moves, what the support window is — is owned by `python_module_boundaries_manifest.md` and is not restated here.** What follows in §17a is only the error-surface half: the mechanism that turns "we renamed this exception" from a changelog note into a machine-checked diagnostic.

## 17a. Deprecating a member of the error contract

An exception type, an error code and a union variant are all public API (§17). Retiring one needs a channel that a consumer can *see* and a checker can *flag*. **ESTABLISHED:** the stdlib channel for this is `warnings`, and it is far quieter than agents assume. (That it is the *only* such channel is a synthesis, not a documented claim — **OPEN**.)

**The mechanism (VERSION-DEPENDENT (3.13+); `typing_extensions` 4.5.0 below that).** `@warnings.deprecated` (PEP 702, Final, `Python-Version: 3.13`) is the machine-readable retirement marker. It emits a `DeprecationWarning` **at call time** (wrapping `__new__` for classes), accepts `category=` — including `category=None` to keep **only** the static diagnostic and emit nothing at runtime — and `stacklevel=`, and it applies to classes, functions, methods, `TypedDict`, `NamedTuple` and individual `@overload`s. The load-bearing half is the static one: type checkers *"must produce diagnostics when encountering usage of deprecated objects"*, **including attribute access and imports**. Decorating a retiring exception class therefore fails the consumer's type check, not just their logs.

**The visibility rules that make deprecations invisible (ESTABLISHED — this is the trap).** In a regular release build the default filters are exactly, in precedence order: `default::DeprecationWarning:__main__`, `ignore::DeprecationWarning`, `ignore::PendingDeprecationWarning`, `ignore::ImportWarning`, `ignore::ResourceWarning`. *"In a debug build, the list of default warning filters is empty."* **VERSION-DEPENDENT (3.7+):** *"`DeprecationWarning` is once again shown by default when triggered directly by code in `__main__`"* — and **only** there. **Consequence:** a library that deprecates an exception type shows a user nothing in a normal run. The library's own test can assert the warning fires and pass, while no consumer ever sees it. The switches that surface it are `-W`, `PYTHONWARNINGS`, `-X dev`, or a pytest `filterwarnings` setting — and `SyntaxWarning` and `RuntimeWarning` are *not* in the ignored set, which is why the PEP 765 `finally` warning (§12) and *"coroutine 'x' was never awaited"* (§18b) are visible without configuration while `DeprecationWarning` is not.

**How tests must assert on it (ESTABLISHED mechanics; the recipe is the testing manifest's to own).** Four facts decide the shape of a correct test:

- **`__warningregistry__` makes a naive test pass once and fail forever after.** Under the `default` or `once` actions a warning already emitted is not shown again unless the registry is cleared, *even after the filters change*. Use `simplefilter("always")` **inside** `catch_warnings(record=True)`; `catch_warnings` alone does not clear the registry.
- **`warnings.resetwarnings()` discards the defaults and any `-W` options too**, not merely your own `filterwarnings` calls — calling it in a fixture changes global visibility for everything that follows.
- **Filter precedence runs in opposite directions depending on the mechanism.** For `-W` and `PYTHONWARNINGS` the *last* matching entry wins; `filterwarnings` and `simplefilter` insert at the **front**, so the *first* wins, unless `append=True`.
- **`catch_warnings` is not thread-safe or asyncio-safe in a normal build.** **VERSION-DEPENDENT (3.14):** `sys.flags.context_aware_warnings` (`-X context_aware_warnings`, `PYTHON_CONTEXT_AWARE_WARNINGS`) makes it `ContextVar`-based and safe — but it defaults to true **only for free-threaded builds**.

Two more grammar facts an agent will otherwise get wrong: the `-W` / `PYTHONWARNINGS` field grammar is `action:message:category:module:lineno` with actions `default`, `error`, `ignore`, `always`, `all`, `module`, `once`; in `-W` the `message` field is a **literal, case-insensitive whole-message match**, whereas `filterwarnings(message=...)` is a **regex** matched at the start — **VERSION-DEPENDENT (3.15)** adds slash-delimited `/regex/` fields to `-W` and `PYTHONWARNINGS` so the two converge.

**Enforcement route.** Type-catchable (a checker flags every use of a `@deprecated` member, including the import) plus test-catchable (`filterwarnings = ["error::DeprecationWarning"]` in `pyproject.toml` turns a deprecated error type into a build failure) plus `-X dev` in the test command. **The CI wiring is `python_quality_gates_manifest.md`'s; the assertion recipe is `python_testing_tooling_manifest.md`'s; the removal calendar — which stdlib name disappears in which version — is a schedule fact and lives in `python_platform_baseline_manifest.md`.** What this file owns is the obligation: **no member of the error contract is removed without at least one release in which it is `@deprecated` and the project's own CI treats `DeprecationWarning` as an error.**

## 18. ExceptionGroup / `except*` (PEP 654, 3.11+)

**VERSION-DEPENDENT (3.11+)** (https://peps.python.org/pep-0654/; https://docs.python.org/3/library/exceptions.html):

- **`ExceptionGroup(msg, excs)`** wraps `Exception` subclasses — it *"raises a `TypeError` if any contained exception is not an `Exception` subclass"* — while **`BaseExceptionGroup`** wraps any `BaseException` and **downgrades**: it *"returns an `ExceptionGroup` rather than a `BaseExceptionGroup` if all contained exceptions are `Exception` instances."* **The constructor you call is not necessarily the type you get**, so `isinstance` checks and `type(...) is` comparisons written against the constructor name are wrong whenever every member happens to be an `Exception`. Members must be **instances, not types**: `ExceptionGroup("m", [ValueError])` is a mistake the type name invites. The documented shape is accumulate-then-raise — `excs.append(e)` in a loop, then `raise ExceptionGroup("Test Failures", excs)`. Groups *"are generic over the type of their contained exceptions"*, so `except* ValueError as e` gives a checker an `ExceptionGroup[ValueError]`-shaped binding.
- **`except*` semantics (ESTABLISHED).** Each clause runs **at most once**, on the matching **subgroup** produced by `split()`: *"each `except*` clause splits it into the subgroups of matching and non-matching exceptions. If the matching subgroup is not empty, it becomes the handled exception … and assigned to the target"*, and the non-matching remainder passes to the next clause. **Leftovers need no manual re-raise:** *"after all `except*` clauses execute, the group of unhandled exceptions is merged with any exceptions that were raised or re-raised from within `except*` clauses. This merged exception group propagates on."* A hand-written `raise` at the end duplicates them.
- **Five rules that are compile- or run-time ERRORS, not style advice (ESTABLISHED).** Treat these as hard constraints an agent must check before editing a `try` block: (1) a single `try` *"can have either `except` or `except*` clauses, but not both"* — mixing them is a **SyntaxError**, so refactoring one clause at a time produces a file that will not compile; (2) `except*:` with no type is a **SyntaxError** — *"the exception type for matching is mandatory in the case of `except*`"*; (3) naming a group type is a **runtime `TypeError`**, not a syntax error — *"a `TypeError` is raised if a matching type is a subclass of `BaseExceptionGroup`, because that would have ambiguous semantics"* — which includes **your own** `ExceptionGroup` subclasses, so it survives linting and fails in production; (4) `break`, `continue` and `return` *"cannot appear in an `except*` clause"* (**SyntaxError**), because *"the exceptions in an `ExceptionGroup` are assumed to be independent, and the presence or absence of one of them should not impact handling of the others"* — the natural "handle the first error and return early" shape is illegal; (5) the `as` target is **always a group**, never a leaf — a non-group exception that matches is *"caught and wrapped by an exception group with an empty message string"*, *"to ensure that the type of the target `e` is consistently `BaseExceptionGroup`"* — so `except* ValueError as e: log(e.args[0])` reads the **group's** args, not the `ValueError`'s. Read leaves from `e.exceptions`.
- **`split(condition)` / `subgroup(condition)`** partition by an exception type or tuple of types; **VERSION-DEPENDENT (3.13+)** for an arbitrary callable — *"condition can be any callable which is not a type object"* — so on 3.11 and 3.12 a lambda simply fails. They preserve nesting, omit empty nested groups, and copy `__traceback__`, `__cause__`, `__context__` and `__notes__` onto the derived group. **`derive(excs)` must be overridden by any group *subclass*** or the subclass's type is lost through a `split`/`subgroup`; and because `BaseExceptionGroup` defines `__new__`, a subclass needing a different constructor signature must override **`__new__`, not `__init__`**.
- **Backward compatible for `ExceptionGroup` only — not for `BaseExceptionGroup`.** *"This design is so that `except Exception` catches an `ExceptionGroup` but not `BaseExceptionGroup`."* A `TaskGroup` whose members include even one `BaseException` raises a `BaseExceptionGroup`, which walks straight through **every** `except Exception` in the stack and reaches the interpreter's last-resort hooks (§20a). This is the single most consequential correction in this section: "plain `except Exception` still catches a group" is true only half the time (§18b).
- **Use selectively, and for the case PEP 654 actually argues for.** PEP 654: *"exception groups and `except*` will be used selectively, only when they are needed"*, and adoption *"will normally be done by introducing a new API rather than modifying an existing one."* The case it argues for is **concurrent tasks** (§18b). Batch or field validation is the case where a group is usually the *wrong* channel: §3's own rule sends contract-level outcomes **in-band**, so a validator that discovers ten bad fields should return an aggregate value, not raise (§18a). In a small single-process app single-exception flow is usually sufficient — with one forced exception: a **cattrs** boundary raises groups by default and makes group handling mandatory (§15a, §21).
- **Backport (VERSION-DEPENDENT):** `exceptiongroup` **1.3.1** supplies the group *classes* for < 3.11, plus `catch()`, `TracebackException` patches, an exception hook, group-aware `traceback` functions and a backported `contextlib.suppress()`. **`except*` is syntax and therefore cannot be backported** — below 3.11 you must use the callback form: *"due to the lack of the `except*` syntax introduced by PEP 654 in earlier Python versions, you need to use `exceptiongroup.catch()`"*, whose argument *"must be a dict (or any Mapping) where each key is either an exception class or an iterable of exception classes"* mapping to a one-argument callable. The package is a deliberate no-op on modern interpreters: *"if this package is imported on Python 3.11 or later, the built-in implementations of the exception group classes are used instead."*
- **`contextlib.suppress` is group-blind before 3.12 (VERSION-DEPENDENT).** From **3.12**, *"if the code within the `with` block raises a `BaseExceptionGroup`, suppressed exceptions are removed from the group. Any exceptions of the group which are not suppressed are re-raised in a new group which is created using the original group's `derive()` method."* On 3.11 a `suppress(FileNotFoundError)` wrapped around code that raises an `ExceptionGroup` containing a `FileNotFoundError` suppresses **nothing** (§10, §21).

## 18a. Reporting many failures at once — three channels, one choice rule

**OPEN — the taxonomy is a synthesis; each mechanism below is ESTABLISHED.** "Several things went wrong" has three legitimate encodings, and picking by habit rather than by rule is how a validation API ends up raising groups that callers cannot compose:

| channel | shape | named vocabulary | choose when |
|---|---|---|---|
| **first-error Result** | `EmitOk \| EmitError` returning the **first** failure and stopping | Result Type (§4) | the caller can only act on one problem anyway, and the remaining work depends on the failed step |
| **in-band Notification** | a frozen `Notification(errors: tuple[Err, ...])` **returned**, not raised | **Notification** — Fowler, *Further Enterprise Application Architecture development* (eaaDev, living): *"an object that accumulates errors … instead of throwing on first failure"* | batch or per-field validation, where the user wants every problem at once. **Python already ships one:** `pydantic.ValidationError.errors()` *is* a notification once the shell converts it (§15a) |
| **raised `ExceptionGroup`** | `raise ExceptionGroup(msg, excs)`, handled with `except*` | PEP 654 (§18) | **independent concurrent tasks** that failed simultaneously (§18b), or a boundary library that gives you no choice (cattrs, §15a) |

**The choice rule.** Ask whether the failures are *independent work items* (group) or *findings about one input* (notification). The corpus states the trade-off as an edge — `notification -alternative-to-> result-type`: *"gather all errors before returning vs short-circuiting on the first error value"* — and the decisive constraint is composability: a Notification is a value the caller can merge, filter, count, serialise and return; a group is a control-flow event that must be caught and unpacked at every layer, and inside an `except*` clause you may not even `return` (§18).

**Test route (VERSION-DEPENDENT, pytest 8.4+).** `pytest.RaisesGroup` and `pytest.RaisesExc` assert on group *shape* including nesting, with flags emulating `except*`, and `pytest.raises(check=fn)` asserts a predicate over the raised exception — the natural way to test "callers can depend on `err.code` and `err.offending_id`" instead of grepping `str(exc)`. The recipes belong to `python_testing_tooling_manifest.md`; what belongs here is the obligation that **each error channel has a test that asserts on structured attributes, not on message text** (§16).

**One rendering fact that argues against wide groups (VERSION-DEPENDENT (3.11+)):** group tracebacks are **truncated by default** — `TracebackException(..., max_group_width=15, max_group_depth=10)` and *"the formatted output is truncated when either limit is exceeded"* — so a 200-member validation group does not print in full, which reads to an operator like lost errors (§19a).

## 18b. Asynchronous failure surfaces

**Scope.** Concurrency **design** — which execution model to choose, structured concurrency, determinism under test — belongs to `python_concurrency_determinism_manifest.md`. What belongs here is the set of places where an async program's failures behave differently from a synchronous program's, because each one is a hole in the error contract that no type checker will point out.

- **`CancelledError` is a `BaseException`, and that is on purpose (VERSION-DEPENDENT (3.8+)).** *"Changed in version 3.8: `CancelledError` is now a subclass of `BaseException` rather than `Exception`."* So `except Exception` correctly misses it — and bare `except:` / `except BaseException:` catastrophically swallow it, after which cancellation silently stops working. The docs are explicit: *"in almost all situations the exception must be re-raised."*
- **Suppressing cancellation is a two-part operation (VERSION-DEPENDENT (3.11+)).** *"Should the coroutine nevertheless decide to suppress the cancellation, it needs to call `Task.uncancel()` in addition to catching the exception."* `uncancel()` decrements the request count and returns the remainder, and *"once execution of a cancelled task completed, further calls to `uncancel()` are ineffective"*; `Task.cancelling()` returns requests minus `uncancel()` calls. Also: `Task.cancel()` *"arranges for a `CancelledError` exception to be thrown into the wrapped coroutine on the next cycle of the event loop"*, returns `False` if the task was already done, and *"does not guarantee that the Task will be cancelled"*.
- **`Task.exception()` is not a nullable getter (ESTABLISHED).** It *"raises a `CancelledError` exception"* if the task was cancelled and *"raises an `InvalidStateError` exception"* if the task is not done. Code that treats it as "returns the exception or `None`" crashes on the cancellation path. `Task.result()` behaves the same way and additionally re-raises the coroutine's exception.
- **`asyncio.timeout()` converts cancellation into `TimeoutError`, catchable only *outside* the block (ESTABLISHED).** A `try/except TimeoutError` **inside** the `async with` never fires (§7a).
- **`TaskGroup` aggregates; `gather` does not cancel (ESTABLISHED).** On the first non-`CancelledError` failure in a `TaskGroup`, *"the remaining tasks in the group are cancelled"* and the surviving non-`CancelledError` exceptions *"are combined in an `ExceptionGroup` or `BaseExceptionGroup` (as appropriate) which is then raised"* from `__aexit__`; the sibling-cancellation `CancelledError` is **not** a member of the group. **Two base exceptions are special:** *"if any task fails with `KeyboardInterrupt` or `SystemExit`, the task group still cancels the remaining tasks and waits for them, but then the initial `KeyboardInterrupt` or `SystemExit` is re-raised instead of `ExceptionGroup` or `BaseExceptionGroup`."* By contrast `asyncio.gather(..., return_exceptions=False)` (the default) propagates the first exception to the awaiting task but *"other awaitables in the `aws` sequence won't be cancelled and will continue to run"* — the opposite of a TaskGroup; with `return_exceptions=True`, *"exceptions are treated the same as successful results, and aggregated in the result list"*, which is a Notification (§18a) in all but name. **VERSION-DEPENDENT (3.15):** `asyncio.TaskGroup.cancel()` is added *"to allow early termination of a task group, eliminating the need for unintuitive boilerplate involving custom exceptions"*; it does **not** exist in 3.14.
- **A never-retrieved exception is reported at garbage-collection time, or never (ESTABLISHED).** *"If a `Future.set_exception()` is called but the Future object is never awaited on, the exception would never be propagated to the user code. In this case, asyncio would emit a log message when the Future object is garbage collected."* Worse, the loop holds only **weak** references to tasks: *"save a reference to the result of this function, to avoid a task disappearing mid-execution … for reliable 'fire-and-forget' background tasks, gather them in a collection"* — a `set` plus `task.add_done_callback(background_tasks.discard)` — and the docs add that this pattern *"never awaits the tasks, so if a task fails, its exception is never retrieved."* **House rule:** every background task is held in a strong-reference set **and** given a done-callback that retrieves and reports its exception. **And the report needs a sink:** *"asyncio uses the `logging` module and all logging is performed via the `asyncio` logger. The default log level is `logging.INFO`"*, so with no logging configured a never-retrieved exception can be invisible (the exact level chosen by `loop.default_exception_handler` for that record is **OPEN** — not confirmed from a primary page this pass). Logging configuration: `logging_observability_manifest.md`.
- **A coroutine that is called but never awaited raises nothing at all (ESTABLISHED).** It emits `RuntimeWarning: coroutine 'x' was never awaited`, visible only because `RuntimeWarning` is not in the default-ignored filter set (§17a).
- **`concurrent.futures` drops two whole classes of failure (ESTABLISHED).** For `Future.add_done_callback(fn)`: *"if the callable raises an `Exception` subclass, it will be logged and ignored. If the callable raises a `BaseException` subclass, the behavior is undefined."* And `Executor.map` defers: *"if a `fn` call raises an exception, then that exception will be raised when its value is retrieved from the iterator"* — a never-iterated map result reports nothing, ever.
- **`@contextlib.contextmanager` swallows silently if you forget one line (ESTABLISHED).** The generator sees the exception re-raised at the `yield`; if it catches it merely to log, *"the generator must reraise that exception. Otherwise the generator context manager will indicate to the `with` statement that the exception has been handled"* — execution continues past a failure that was never handled.
- **Debug mode is the cheap diagnostic (ESTABLISHED).** asyncio debug mode is enabled by `PYTHONASYNCIODEBUG=1`, Python Development Mode, `asyncio.run(..., debug=True)` or `loop.set_debug()`; it makes non-threadsafe API misuse raise, logs slow callbacks (`loop.slow_callback_duration`, default 100 ms), and adds the task-creation traceback to never-retrieved reports. Live task-graph inspection (`python -m asyncio ps|pstree`, `asyncio.print_call_graph()`) belongs to `python_runtime_diagnostics_manifest.md`.

## 19. Notes & tracebacks (PEP 678, 3.11+)

**VERSION-DEPENDENT (3.11+)** (https://peps.python.org/pep-0678/; https://docs.python.org/3/library/exceptions.html#BaseException.add_note):

- **`add_note(note: str)`** appends to the **`__notes__`** list, which *"is created when `add_note()` is called"* — so **`exc.__notes__` does not exist on a fresh exception** and `exc.__notes__.append(...)` raises `AttributeError`; always go through `add_note`. Notes render *"immediately after the exception message, in the order in which they were added, with each note starting on a new line"*, `TypeError` is raised if `note` is not a `str` (including an object you meant to format), and `del err.__notes__` clears them. **VERSION-DEPENDENT (3.11/3.13):** `traceback.format_exception_only()` has included `__notes__` since 3.11, and `TracebackException` exposes both `__notes__` and `exceptions` from 3.11; 3.13 adds `show_group=` to `format_exception_only()` to render nested group members recursively, indented by depth.
- **Preferred over re-wrapping when you only need to add context.** PEP 678 rationale: exception chaining *"reports several lines of additional detail, which are distracting … and can be very confusing for beginners"*; notes add context **without changing the exception type or cause**.
- **For tracing:** catch as it bubbles, `e.add_note(f"while processing user={uid}")`, `raise` — the call-site context lands in the traceback **without** losing the original type or chained cause.
- **Pairs with** ExceptionGroups (each member carries its own context) and retry loops (record attempt count/timestamp).
- **How a traceable record assembles:** the **message** (§16: values + intent + remediation + code) + **notes** (§19: propagation context) + **chained cause** (§8: the underlying error) combine into one source-traceable traceback. **Correction — there is NO backport for `add_note` (ESTABLISHED).** Earlier text in this manifest claimed `typing_extensions` or `exceptiongroup` shim it; neither does. The `exceptiongroup` package's contents are exactly the group classes, `catch()`, `TracebackException` patches, an exception hook, group-aware `traceback` functions and a backported `contextlib.suppress()` — it does not touch `BaseException`; `typing_extensions` is a typing backport and never patched `BaseException` either. On < 3.11 you have two honest options: raise the floor to 3.11+ (§21 recommends higher), or carry propagation context in a wrapper exception's **own attributes** (§16) and accept that it will not render as a note.

## 19a. Traceback fidelity — and the switches that silently erase it

A traceback is the primary diagnostic artefact of the whole contract. Several interpreter switches degrade it, and **their only symptom is a worse traceback** — no error, no warning, no failing test. An agent optimising a base image can therefore destroy its own diagnosability and never find out.

- **Fine-grained error locations (VERSION-DEPENDENT (3.11+); PEP 657, Final).** The caret/tilde markers that underline the *offending sub-expression* rather than the whole line are the single largest source-tracing win in the version matrix. They come from per-instruction position tables, reachable as `code.co_positions()` — four-tuples `(start_line, end_line, start_column, end_column)` per instruction, or `None` — and at C level via `PyCode_Addr2Location()`. The tables cost roughly **22%** additional `.pyc` size (CPython's stdlib measured 28.4 MB → 34.7 MB).
- **`-X no_debug_ranges` / `PYTHONNODEBUGRANGES` erase them process-wide (VERSION-DEPENDENT (3.11+)).** Both suppress the location tables, and suppressing them **removes the column markers from every traceback the process will ever print**. **House rule:** never set either in a production or CI image, and **audit base images for both** — the 22% `.pyc` saving is not worth a permanently degraded traceback. **OPEN — an unresolved spelling conflict worth auditing around:** this pass's error-handling fact pack records the environment variable three times as `PYTHONNODEBUGRANGES` (matching PEP 657), while the platform fact pack records it twice as `PYTHON_NODEBUGRANGES`. Neither was re-read at the character level against `using/cmdline.html` in this pass, so **grep an image for both spellings** — the audit costs nothing and the failure mode is silent. **Enforcement route:** fitness-function — assert at startup or in CI that neither switch is active, under either spelling (`python_quality_gates_manifest.md` owns the wiring).
- **`sys.tracebacklimit` is the other silent destroyer (ESTABLISHED).** It *"determines the maximum number of levels of traceback information printed … The default is 1000. When set to 0 or less, all traceback information is suppressed and only the exception type and value are printed."* Anything setting it in a config file destroys source-traceability with no other symptom.
- **Group output is truncated by default (VERSION-DEPENDENT (3.11+)).** `max_group_width=15`, `max_group_depth=10`; *"the formatted output is truncated when either limit is exceeded"* (§18a).
- **Colourised tracebacks and the exact colour-control chain (VERSION-DEPENDENT (3.13+)).** The `traceback` module docs carry *"Added in version 3.13: Output is colorized by default"*. The precedence chain is exact and worth writing down: **`PYTHON_COLORS` > `NO_COLOR` > `FORCE_COLOR` > `TERM`**. `PYTHON_COLORS=1` forces colour on and `0` off (added 3.13); `TERM=dumb` disables colour; `NO_COLOR` disables all colour and *"takes precedence over FORCE_COLOR"*. **3.14** extends colour beyond tracebacks — the default interactive shell highlights syntax (disabled by `PYTHON_BASIC_REPL` or any colour-disabling variable), and `argparse` help, `calendar` and `json` CLI output are coloured by default. **3.15** colourises **unraisable exceptions** by default (§20a), plus `ast`, `pickletools`, `tokenize`, `sqlite3`, `timeit` and `http.server` output and `python --help`. **Rule:** log sinks and captured CI output run with colour **off** (`PYTHON_COLORS=0` or `NO_COLOR=1`); CI systems that render ANSI can set `FORCE_COLOR`. **Never let ANSI escape sequences reach a structured log** — cross-reference `logging_observability_manifest.md`, which owns formatter and transport policy.
- **Reading the current exception programmatically (VERSION-DEPENDENT (3.11/3.12)).** `sys.exception()` (3.11) returns the instance handled by the innermost active handler, or `None`, and `sys.exc_info()` is now derived from it — so mutating a handled exception (adding a note, §19) is reflected in later `exc_info()` calls. `sys.last_exc` (3.12) supersedes the deprecated `sys.last_type` / `sys.last_value` / `sys.last_traceback`; it is the handle post-mortem tooling uses, and post-mortem itself belongs to `python_runtime_diagnostics_manifest.md`. **VERSION-DEPENDENT (3.13):** `TracebackException.exc_type` is deprecated in favour of the string `exc_type_str` (the constructor gained `save_exc_type`, default `True`) — tooling that reads `exc_type` should move.
- **Three 3.15 changes that alter where an error appears to come from (VERSION-DEPENDENT (3.15)).** `ImportError.__repr__` and `ModuleNotFoundError.__repr__` now render `name=<name>` and `path=<path>`; `AttributeError` suggestions get better (reachable nested attributes, cross-language method-name hints, and suggestions for `delattr` / `del obj.x`); and **PEP 810 lazy imports move an import failure in time**: the exception type is unchanged (`ImportError`, `ModuleNotFoundError`, `SyntaxError`) but it surfaces at **first use of the name**, not at the `import` statement, and *"the exception is enhanced with chaining to show both where the lazy import was defined and where it was accessed"*. **Consequence for the error contract:** the common idiom of wrapping a top-of-module `import` in `try/except ImportError` to detect an optional dependency **will not catch it** under `-X lazy_imports` / `PYTHON_LAZY_IMPORTS`. Also relevant to `sys.monitoring`-based tooling: 3.15 allows per-code-object enable/disable of `PY_THROW`, `PY_UNWIND`, `RAISE`, `EXCEPTION_HANDLED` and `RERAISE`, and returning `DISABLE` from a callback now disables the event for that code object instead of raising `ValueError`.

## 20. Observability & logging — error-side obligations only

**ESTABLISHED** (https://docs.python.org/3/howto/logging.html) — stated here as the *error contract's* logging obligations; **all handler/formatter/transport policy lives in `logging_observability_manifest.md` and is not duplicated here**:

- **Module logger:** `logger = logging.getLogger(__name__)`.
- **`logger.exception()`** *"dumps a stack trace along with it. Call this method only from an exception handler"* (logs at ERROR + traceback); equivalently `logger.error(msg, exc_info=True)`.
- **Libraries add only `NullHandler`:** *"do not add any handlers other than `NullHandler` to your library's loggers … configuration of handlers is the prerogative of the application developer."*
- **The error/observability tie-in:** structured exception attributes (offending id, stable code — §16) + `add_note` context (§19) + chained cause (§8) give the log a **complete, source-traceable record**. The **shell** (not the core) owns logging policy (§6).

## 20a. The four unhandled-exception hooks — and the coverage gaps between them

**ESTABLISHED.** A process that installs `sys.excepthook` and believes every failure is now logged is wrong on **four** counts. There are four separate last-resort channels plus one library that has none, and each covers a disjoint set of failures:

| channel | covers | does NOT cover / trap |
|---|---|---|
| **`sys.excepthook(type, value, traceback)`** | an exception *"other than `SystemExit`"* raised and uncaught on the main thread | never called for `SystemExit`; never for thread failures; never for destructor/GC failures; never for asyncio failures |
| **`threading.excepthook(args)`** (**3.8+**; `threading.__excepthook__` only from **3.10**) | *"uncaught exception raised by `Thread.run()`"*; `args` carries `exc_type`, `exc_value`, `exc_traceback`, `thread` | *"if `exc_type` is `SystemExit`, the exception is silently ignored"* — a worker thread calling `sys.exit()` produces **no output at all**. If the hook itself raises, `sys.excepthook` handles that |
| **`sys.unraisablehook(unraisable)`** (**3.8+**) | exceptions Python cannot raise: *"when a destructor raises an exception or during garbage collection (`gc.collect()`)"*; fields `exc_type`, `exc_value`, `exc_traceback`, `err_msg`, `object`; the default hook formats `f'{err_msg}: {object!r}'` and uses the *"Exception ignored in"* message when `err_msg` is `None` | in a **custom** hook, storing `exc_value` can create a reference cycle and storing `object` can **resurrect a finalizing object** — the `sys` docs warn about both. **VERSION-DEPENDENT (3.15):** these are colourised by default (§19a) |
| **`loop.set_exception_handler(handler)`** with `handler(loop, context)` | asyncio callback failures and never-retrieved exceptions (§18b); `context` keys are `'message'` plus optionally `'exception'`, `'future'`, `'task'`, `'handle'`, `'protocol'`, `'transport'`, `'socket'`, `'source_traceback'`, `'handle_traceback'`, `'asyncgen'` | `loop.call_exception_handler` *"should not be overloaded in subclassed event loops"*; **VERSION-DEPENDENT (3.12):** the handler *"may be called in the Context of the task or handle where the exception originated"*, so context-local state (correlation ids) may differ from the main task's |
| **`concurrent.futures` — no hook exists** | — | done-callback exceptions are *"logged and ignored"* for `Exception` and **undefined** for `BaseException`; `Executor.map` failures surface only when the iterator is consumed (§18b). The only fix is to write the retrieval yourself |

**The rule.** Ship **one** `install_error_hooks()` function, called from the shell entry point (§6), that installs all four channels and routes each to the same structured record (§16, §20). Three constraints on the implementation: the hooks **report, they never recover** — no hook should attempt to continue the program; a hook must not raise (a `threading.excepthook` that raises merely relocates the problem to `sys.excepthook`); and the custom `unraisablehook` must not retain `exc_value` or `object` beyond formatting. **Enforcement route:** test-catchable — one test per channel that provokes the failure (an uncaught exception in a thread, a raising `__del__` plus `gc.collect()`, an un-awaited failing task) and asserts a record was emitted. This is the only mechanism that catches a partially-installed hook set; nothing static will.

**Open questions to resolve before building** (carry into the spec per `software_spec_discipline_manifest.md` §G5):
- **Seam placement (OPEN, §6):** where exactly is the result/exception boundary, and do all domain "expected failures" become typed unions while only truly-exceptional conditions raise?
- **Stable error-code scheme (OPEN, §16–17):** project-wide namespaced codes as exception attributes, part of the versioned public contract with deprecation guarantees?
- **Minimum Python (VERSION-DEPENDENT, §21):** adopt the hub's default floor (`>=3.13`, and 3.14 where nothing forces compatibility — `python_platform_baseline_manifest.md` §3e), or accept a lower floor and its missing behaviours (no `add_note`, no group-aware `suppress`, no compiler warning on `finally`)?
- **Boundary tool (VERSION-DEPENDENT, §15, §15a):** pydantic v2 vs msgspec vs cattrs vs plain dataclasses + manual parsing. Pydantic v1 is not a live option (it survives only as the vendored `pydantic.v1` namespace inside v2). The three live libraries raise **structurally different** errors — a `ValidationError` with a list of machine-readable dicts, a PEP 654 `ExceptionGroup`, or a `ValidationError` that is also a `ValueError` with the path in the message string — so the adapter is written against the chosen one, not a shared base.
- **Result type (OPEN, §4, §4b):** hand-rolled discriminated union vs a third-party library, where the 2026-08-08 landscape is thin: `returns` 0.29.0 is the only actively released option but is self-classified Beta, needs Python ≥ 3.11, and **requires its own mypy plugin** for full inference — choosing it silently chooses mypy; `expression` 5.6.0 is stable-labelled but has not shipped in ~17 months; `result` (rustedpy) is archived read-only and must not be added. Default answer for this scale: the frozen-dataclass union plus `assert_never`.
- **Logging policy (OPEN, §20):** structured logging (JSON, error codes, correlation IDs) vs plain `logger.exception` — defer detail to `logging_observability_manifest.md`.
- **ExceptionGroup aggressiveness (§18, §18a):** **yes, if cattrs is the boundary tool** — its detailed validation mode has been on by default since 22.1.0 and raises a PEP 654 group, so a cattrs boundary *requires* `except*` or explicit `.exceptions` traversal, or the converter must be built with `detailed_validation=False`. Otherwise: are there concrete **concurrent** call sites that justify groups, given that field validation should be an in-band Notification instead (§18a)?
- **Transient-fault policy (OPEN, §7a):** what is the bound on every outbound call, which operations are idempotent enough to retry, how many attempts, and what leak rate distinguishes an acceptable background error rate from a persistent fault? Is any dependency called often enough to justify a circuit breaker, or is that over-engineering here?
- **Failure disposition (OPEN, §7b):** for each failure class, which of let-it-crash / rollback / roll-forward applies, what is the named safe state, and **which exit code** does the program leave with? Who restarts it?
- **Rejects sink (OPEN, §3, §7b):** where does marked data go — an output-union variant, an `errors` column, or a `rejects.jsonl` — and who reads it?
- **Hook coverage (OPEN, §20a):** does the shell install all four unhandled-exception channels, and is there a test per channel?
- **Traceback fidelity (OPEN, §19a):** does CI assert that `-X no_debug_ranges` / `PYTHONNODEBUGRANGES` are unset and `sys.tracebacklimit` untouched in the production image?
- **Deprecation obligation (OPEN, §17a):** does the project promise at least one release in which a retiring exception type or error code is `@deprecated`, with `DeprecationWarning` fatal in CI?
- **Assertions in production (OPEN, §14):** ship with or without `-O`/`-OO`? If either is ever used, run the **full** audit — bare `assert`, `if __debug__:` blocks, doctests-as-checks, `icontract`/`deal` decorators, and `assert` inside any validator — not just a search for `assert`.

## 22. Anti-patterns checklist

Each is a violation of a section above; reject on sight.

- **Bare `except:` / `except BaseException:`** — swallows `KeyboardInterrupt`/`SystemExit`/`GeneratorExit` (§11, §12).
- **`assert` on untrusted/boundary input** — stripped under `-O`; a correctness and security hole (§14, §15).
- **Swallow-and-continue** (catch and ignore) — violates PEP 20 *"never pass silently"* (§2, §10).
- **String-only errors** — no structured attributes; not machine-consumable, not greppable across versions (§16).
- **Raising the base package exception directly** — defeats narrow handling; raise a specific subclass (§11).
- **Leaking low-level/library exceptions across an API boundary** — wrap with `raise Domain from low` instead (§8, §10).
- **`from None` by default** — hides the real source from the traceback; use sparingly with justification (§9).
- **Exceptions for routine, expected, contract-level outcomes** — those belong in a typed union the checker forces callers to handle (§3, §7).
- **Non-exhaustive union handling** — missing `assert_never` lets an unhandled variant slip past the checker (§5).
- **Retrofitting `ExceptionGroup`/`except*` onto an existing single-exception API** — introduce a new API instead (§18).

Added this pass — the failure modes the sections above introduce:

- **Mixing `except` and `except*` in one `try`** — SyntaxError; the file will not compile (§18).
- **`except* ExceptionGroup` or `except* MyGroupSubclass`** — runtime `TypeError`; survives linting, fails in production (§18).
- **Reading the leaf from an `except*` `as` target** — `e` is always a group; read `e.exceptions` (§18).
- **Re-raising the leftovers of `except*` by hand** — they are merged and propagated automatically; you have duplicated them (§18).
- **`return` / `break` / `continue` in a `finally` block** — silently discards an in-flight exception and overrides the `try` body's return (§12).
- **`-X no_debug_ranges` / `PYTHONNODEBUGRANGES` in an image, or `sys.tracebacklimit` in a config** — permanently degrades every traceback with no other symptom (§19a).
- **ANSI colour reaching a structured log or captured CI output** — set `PYTHON_COLORS=0` / `NO_COLOR=1` for log sinks (§19a).
- **Swallowing `CancelledError`** — it is a `BaseException` for a reason; cancellation stops working. If you truly must, `Task.uncancel()` is also required (§18b).
- **`try/except TimeoutError` *inside* an `async with asyncio.timeout(...)` block** — it can only be caught outside (§7a, §18b).
- **Treating `Task.exception()` as a nullable getter** — it *raises* on a cancelled or unfinished task (§18b).
- **Fire-and-forget `create_task` with no strong reference and no exception retrieval** — the task can vanish mid-flight, and its failure is reported at GC or never (§18b).
- **A `@contextmanager` that catches an exception only to log it** — without a re-raise, the `with` statement treats the failure as handled (§18b).
- **Installing only `sys.excepthook`** — it covers none of: thread failures, destructor/GC failures, asyncio failures, executor done-callback failures, or `SystemExit` (§20a).
- **`assert` inside a pydantic validator** — under `-O` it does not fail loudly, it silently **passes** validation (§14).
- **`if __debug__:` guarding a must-survive check, or an `icontract`/`deal` contract as the enforcement mechanism for a boundary check** — all removed by `-O` (§14).
- **Retrying a non-idempotent operation, or retrying without a per-attempt timeout** — the first is data corruption, the second is a hang (§7a).
- **A circuit breaker in a one-shot CLI invocation** — over-engineering; a timeout plus bounded retry is the whole answer (§7a).
- **A hand-rolled supervision tree, retry budget, or dead-letter queue in a single-process app** — the restarter is systemd or the orchestrator; the rejects sink is a file or table (§7b).
- **Raising an `ExceptionGroup` for per-field validation** — contract-level outcomes go in-band; return a Notification (§18a).
- **Letting a boundary library's exception type cross your API** — `except pydantic.ValidationError` in a consumer couples them to your dependency choice (§15a).
- **`".".join(loc)` on a pydantic error location** — `loc` contains `int` indices; keep it structured (§15a).
- **`model_construct()` / `object.__setattr__` / `cast` / `NewType` used to get past the parse boundary** — the type then carries no proof (§15).
- **`exc.__notes__.append(...)` on a fresh exception** — `__notes__` does not exist until `add_note()` has been called (§19).
- **Claiming an `add_note` backport for < 3.11** — there is none (§19).
- **Removing an exception type, error code or union variant without a release in which it is `@deprecated`** — and without `DeprecationWarning` fatal in CI, since it is invisible by default outside `__main__` (§17a).
- **`warnings.resetwarnings()` in a test fixture** — it discards the default filters and `-W` options, not just your own calls (§17a).
- **`assert False` in the exhaustiveness fallback** — loses the static check that is the whole point (§5).
- **Adding `result` (rustedpy)** — archived read-only; its last release predates Python 3.13 (§4b).
- **Absorbing a bad record with no rejects sink** — that is `try/except/continue` with extra steps (§3, §7b).
- **`contextlib.suppress(X)` wrapped around code that can raise an `ExceptionGroup`, on 3.11** — it looks inside groups only from 3.12, so it suppresses nothing (§10, §18).
- **Relying on unparenthesized `except A, B:`** — 3.14+ only, and `except A, B as e:` is a SyntaxError at every version (§12).
- **A failure path that ends in an unhandled traceback rather than a named state and a distinct exit code** (§7b, §23).

## 23. Decision flowchart

```
Is the failure a momentary, self-clearing TRANSIENT (network blip,
lock contention, rate limit)?
   YES → bound the call (timeout), retry within a budget with
         exponential backoff + jitter — ONLY if idempotent — and
         count it in a decaying (leaky-bucket) counter.               [§7a]
         Escalate only when the counter crosses its threshold.        [§7b]
   NO  ↓
Is it ONE bad record inside an otherwise-valid batch?
   YES → absorb: produce an explicit Invalid/Rejected value, write it
         to the rejects sink (marked data), advance the cursor
         (roll-forward), keep going.                                  [§3,§7b]
   NO  ↓
Is the failure an expected, recoverable, contract-level DOMAIN outcome
the caller must branch on?
   YES → return a typed discriminated union (EmitOk | EmitError);
         enforce exhaustiveness with assert_never / Never.            [§3,§4,§5]
   NO  ↓
Is it truly exceptional / unrecoverable-at-this-layer / programmer error?
   YES → raise a specific subclass of your PackageError(Exception).   [§7,§11]
   ↓
Are you crossing an abstraction / API boundary while raising?
   YES → raise DomainError(...) from low_level   (keep the cause)     [§8,§10]
         (add e.add_note(context) instead of re-wrapping if only
          context is needed)                                          [§19]
   ↓
Did MANY failures occur at once?  Pick the channel by their kind:     [§18a]
   findings about ONE input (per-field validation)
        → return an in-band Notification (aggregate value)            [§18a]
   INDEPENDENT concurrent tasks that failed simultaneously
        → raise ExceptionGroup(msg, excs); handle with except*        [§18,§18b]
          (3.11+; except* cannot be backported — exceptiongroup.catch())
          Rules that are ERRORS: no except/except* mixing; no bare
          except*:; no group type in except*; no return/break/continue
          inside except*; the `as` target is always a group.          [§18]
   caller can act on only one
        → first-error Result                                          [§4]
   ↓
Untrusted input at the shell boundary?
   → parse, don't validate: produce typed objects (pydantic-style),
     raising a real catchable ValidationError — never assert.         [§14,§15]
     The parse function returns a DISTINCT type, never bool/None/dict;
     apply the forgery test.                                          [§15]
     Convert the library's error into the project taxonomy at the
     seam; never let its exception type cross your API.               [§15a]
   ↓
Always: write a descriptive message (context + expected/actual +
offending value + remediation + stable code), log with
logger.exception() inside the handler, never pass silently.           [§2,§16,§20]
   ↓
Then answer the question this chart used to skip:
WHAT STATE IS THE PROGRAM IN NOW?                                     [§7b]
   → a NAMED safe state: refuse-to-start with a distinct exit code,
     read-only mode, feature disabled, workers parked (cooperative
     shutdown) — or deliberate let-it-crash: exit non-zero and let
     the external restarter (systemd / orchestrator / worker manager)
     recreate the process.  "Unhandled traceback" is not a state.
   → and make sure the crash left evidence: all four unhandled-exception
     hooks installed, tracebacks not degraded by -X no_debug_ranges
     or sys.tracebacklimit.                                    [§19a,§20a]
```
