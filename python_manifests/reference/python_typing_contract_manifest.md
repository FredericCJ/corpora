# Python Typing & Contract-Enforcement — Ground-Truth Manifest

**Purpose.** A citable ground-truth reference for expressing and MECHANICALLY ENFORCING contracts in small-to-mid-scale, strictly-typed, single-process Python organized as a functional core inside an imperative shell. It answers four questions: what the type system can carry, what it cannot, which mechanism actually enforces each contract at runtime, and which of those mechanisms silently does nothing. This file is **GROUNDING, not a rulebook**: cite a rule when it materially shapes a decision; reason past it when the situation does not match. Every factual claim is tagged **ESTABLISHED** (normative and stable in the cited primary source), **VERSION-DEPENDENT** (bound to an exact Python/checker/library version), **OPEN** (no authoritative source — a convention the project must pin), or **CC-FACT** (Claude-Code mechanics; none arise here). **FLAGGED-SECONDARY** marks a claim whose only evidence was secondary or vendor-published. **UNVERIFIED** marks an imported-vocabulary citation whose bibliographic record the SWE corpus itself records as unverified; it must not be presented as verified ground truth, and the status is not upgraded without a fresh primary check (the naming sources are listed under "Named-vocabulary sources"). **MEASURED** — established by running the tool in this environment rather than by reading its documentation, and therefore pinned to the tool version named beside it — is the collection's marker for tool-behaviour facts; none arise here, since the checker claims below are sourced from documentation, PEPs and the typing spec rather than from local runs. An untagged factual claim in this file is a defect. Blocks marked **(decision)** or **(principle)** are this file's synthesis rather than factual claims and carry no tag; where such a block rests on a fact, the fact is tagged at its point of establishment above.

**Version anchor:** `python_platform_baseline_manifest.md` (verified 2026-08-08) owns CPython release dates, support phases, and PEP-status-by-version. This file states BEHAVIOUR and names the behaviour-relevant gate inline — e.g. **VERSION-DEPENDENT (3.14+)**, **VERSION-DEPENDENT (3.15)** — and never re-derives a release date. Tool versions the behavioural claims below were verified against on 8 August 2026 (VERSION-DEPENDENT): **mypy 2.3.0** (13 Jul 2026), **pyright 1.1.411** (25 Jun 2026), **pyrefly 1.2.0** (1 Aug 2026), **ty 0.0.69** (6 Aug 2026), **pydantic 2.13.4** (6 May 2026), **attrs 26.1.0**, **cattrs 26.1.0**, **msgspec 0.21.1**, **beartype 0.22.9** (13 Dec 2025), **typeguard 4.6.0** (26 Jul 2026), **icontract 2.7.3**, **deal 4.24.6**, **annotated-types 0.8.0**, **typing-extensions 4.16.0**. A checker's behaviour is only as pinned as its version: re-verify at every bump, and treat a major bump as a re-baselining event, not a patch.

## TL;DR

- **"Strict static typing" is not a single, portable meaning, and cross-checker agreement is not an adoptable goal.** Four checkers are in practical use — mypy, pyright, pyrefly, ty — and they ratchet strictness through four *incompatible* mechanisms (flags, a 91-row rule table, 122 rule levels, six presets), so a spec that says "strict mode" specifies nothing (VERSION-DEPENDENT, §1). Divergence is permitted by design: PEP 729 (Active) states the Typing Council "has no direct authority over type checkers; it cannot force them to implement particular features or make behavior changes" (ESTABLISHED). The correct mandate names ONE checker as the release gate, pins its exact version, commits the enabled-rule set to version control, and treats every other checker's findings as advisory triage.
- **The type system cannot express value ranges, cross-field invariants, ordering/temporal constraints, units, or stateful protocols.** These MUST become boundary parsing and/or runtime contracts and be documented in the contract docstring — never assumed to be carried by annotations (§4). `typing.cast`, `assert_type`, `Final`/`@final`, `@override`, `TypeForm(x)`, `@disjoint_base` and `NewType` are checker-only or identity functions that will never raise; `Annotated` metadata is inert unless a runtime consumer reads it; and `assert` is stripped from the bytecode under `python -O` (ESTABLISHED, §4).
- **Parse once at the boundary, then trust types internally.** Validate untrusted data at the system edge (pydantic 2.13.4, Rust-cored `pydantic-core`), produce trusted typed objects the caller could not have forged, and reserve `assert` for internal "can't happen" guards — raising explicit exceptions for anything that must run in production. Pydantic's own "Performance - Pydantic V2 is 5-50x faster than Pydantic V1" figure dates from the v2 pre-release announcement of 3 April 2023 and compares v2 against v1 only: it is vendor-sourced, three years old, and says nothing about pydantic's speed relative to msgspec, cattrs, or hand-written parsing (FLAGGED-SECONDARY). Cite it as a historical migration figure, never as a current benchmark. The two named halves of this discipline are **Smart Constructor** (*Smart constructors*, haskell.org wiki, living) and **Functional Core, Imperative Shell** (Gary Bernhardt, *Functional Core, Imperative Shell*, Destroy All Software screencast, 2012) — §5.
- **Annotations are no longer evaluated where they are written.** VERSION-DEPENDENT (3.14+): PEP 649 and PEP 749 make deferred evaluation the default, `from __future__ import annotations` is deprecated *and mutually exclusive with it* (adding the import forfeits the feature), and three annotation execution models now coexist. Every library that reads `__annotations__` is therefore version-sensitive (§2a).
- **Runtime type-checkers are samplers, not validators.** beartype is O(1) by design and checks one randomly selected item per container per call; typeguard's default `collection_check_strategy` is `CollectionCheckStrategy.FIRST_ITEM`. A `list[int]` holding one int and nine strings passes both defaults (ESTABLISHED, §5). They are development-time defect detectors; they never replace a parse step.

## Key Findings

1. **mypy `--strict` enables a documented, mutable set of 13 flags as of mypy 2.3**, and explicitly does NOT forbid all `Any`. The set is NOT unchanged through 2.x: `mypy/main.py` marks 15 options `strict_flag=True` at tag `v1.19.0` but only 13 at tag `v2.3.0`. `--strict-bytes` left the set because it became a global default in 2.0; `--warn-unused-configs` left the set outright and must now be passed explicitly, or stale `[mypy-*]` config sections rot unreported. mypy also *skips unannotated function bodies entirely* by default — its single biggest divergence from every other checker. VERSION-DEPENDENT (mypy 2.3); the unannotated-body default is ESTABLISHED.
2. **pyright has four modes** (`off`/`basic`/`standard`/`strict`; CLI and config default `standard`, Pylance VS Code default `off`) over a **91-row** per-mode severity table. Exactly **36** rules escalate to `error` in `strict` from a non-error level in `standard`, and **TEN remain `"none"` even in `strict`** and must be opted into by name. "strict" is not "all". VERSION-DEPENDENT (pyright main-branch docs, read 8 Aug 2026).
3. **A codebase clean under `mypy --strict` is frequently NOT clean under `pyright --strict`, and agreement is not merely unachieved but not required.** PEP 729 (Active) states that "The Typing Council has no direct authority over type checkers; it cannot force them to implement particular features or make behavior changes," and that checkers "are free to deviate from the spec if they do not have the resources to fully implement it or if they believe a different behavior better serves their users," obliging them only to document deviations. The typing spec likewise declines to bind the gradual guarantee: "we don't take the gradual guarantee as a strict requirement, but it's a useful guideline." The official conformance suite encodes this optionality in its markup — `# E` means an error must be raised, `# E?` means one may be raised "because the spec allows multiple behaviors" — and its README concedes that "many important aspects of type checking are not standardized at all, and therefore not covered by conformance tests." ESTABLISHED.
4. **`typing.cast` returns its second argument unchanged with no check or coercion** — an unchecked promise the checker trusts blindly. ESTABLISHED.
5. **pydantic v2 is a ground-up rewrite** with a Rust core (`pydantic-core`) and renamed APIs (`@validator`→`@field_validator`, `Config`→`model_config`, `.dict()`→`.model_dump()`) — and it is **lax by default**: `ConfigDict.strict` defaults to `False`, `extra` to `'ignore'`, `validate_assignment` to `False`, `validate_default` to `False`, and `revalidate_instances` to `'never'`. The parse boundary guarantees the object at construction only. VERSION-DEPENDENT (pydantic 2.13.4).
6. **`assert` is removed from bytecode under `-O`/`PYTHONOPTIMIZE`** and must never be used for validation, auth, or input checks. ESTABLISHED.
7. **`frozen=True` dataclasses give shallow, bypassable immutability**; the type system cannot express deep immutability or purity at all. `object.__setattr__` is not an exotic bypass — it is the mechanism the generated frozen `__init__` itself uses. ESTABLISHED.
8. **The four checkers differ in maturity, not just in defaults.** mypy 2.3.0 and pyright 1.1.411 are mature; **pyrefly 1.2.0** (Meta) is `Development Status :: 5 - Production/Stable` and stable since 1.0.0 on 12 May 2026; **ty 0.0.69** (Astral) is `Development Status :: 4 - Beta` and states "breaking changes, including changes to diagnostics, may occur between any two versions" — usable as a fast local pre-check, not as a release gate. mypy is the only one with a plugin API, so any correctness a project derives from a mypy plugin evaporates under every other checker. VERSION-DEPENDENT (mypy 2.3.0, pyright 1.1.411, pyrefly 1.2.0, ty 0.0.69).
9. **Deferred annotation evaluation (PEP 649/749) is the default from 3.14** and `from __future__ import annotations` *disables* it rather than reinforcing it. Read annotations through `annotationlib.get_annotations()`, never `__annotations__` directly; `annotationlib.Format` has four members with non-contiguous usable values (`VALUE=1`, `VALUE_WITH_FAKE_GLOBALS=2` internal-only, `FORWARDREF=3`, `STRING=4`). VERSION-DEPENDENT (3.14+).
10. **The four boundary libraries disagree on all four enforcement axes.** pydantic is the only one that validates at construction; `attrs` under `@define`/`@frozen` is the only one that validates on *attribute assignment*; `msgspec` is the only one strict by default (and validates only on decode/convert, never in `__init__`); stdlib `dataclasses` validates nothing at all — "nothing in `@dataclass` examines the type specified in the variable annotation" (§5). VERSION-DEPENDENT (pydantic 2.13.4, attrs 26.1.0, msgspec 0.21.1); the `dataclasses` quotation is ESTABLISHED.
11. **`TypeIs` (PEP 742) narrows in BOTH branches; `TypeGuard` (PEP 647) narrows only the True branch** and imposes no relationship between the narrowed type and the parameter type. Choosing `TypeGuard` where `TypeIs` was meant forfeits negative narrowing with no error and no diagnostic (§2). ESTABLISHED.
12. **Design-by-contract libraries are disabled in production by default.** icontract and deal are both gated on `__debug__` and vanish under `-O`/`-OO`. They are executable documentation and test-time oracles — never the enforcement mechanism for a boundary, authorization, or resource check (§5). ESTABLISHED.

**Two further checkers appear in the official results and are not folklore (VERSION-DEPENDENT).** `pycroscope` 0.4.0 scored 131/142 (92.3%) and `zuban` 0.9.1 (tested at 0.8.2) scored 141/142 (99.3%). zuban's PyPI classifier is `Development Status :: 1 - Planning` despite a 0.9.x version number — the classifier and the version disagree, so treat its maturity as **OPEN**. Separately, `basedpyright` 1.39.9 is a *fork* of pyright with extra rules: its rule names (`reportAny`, `reportExplicitAny`, `reportIgnoreCommentWithoutRule`) do **not** exist in `microsoft/pyright`'s `docs/configuration.md`, so emitting them into a `pyrightconfig.json` targets a tool the project may not use (ESTABLISHED).

**mypy `--strict` — the exact set (VERSION-DEPENDENT; mypy 2.3).** As of mypy 2.3 (docs `command_line.html`, corroborated by `strict_flag=True` in `mypy/main.py` at tag `v2.3.0`), `--strict` turns on exactly: `--disallow-any-generics`, `--disallow-subclassing-any`, `--disallow-untyped-calls`, `--disallow-untyped-defs`, `--disallow-incomplete-defs`, `--check-untyped-defs`, `--disallow-untyped-decorators`, `--warn-redundant-casts`, `--warn-unused-ignores`, `--warn-return-any`, `--no-implicit-reexport`, `--strict-equality`, and `--extra-checks`. mypy's docs carry two escape clauses a spec must honour: "the exact list of flags enabled by running `--strict` may change over time," and "The strict flag does not take precedence over other strict-related flags. Directly specifying a flag of alternate behavior will override the behavior of strict, regardless of the order in which they are passed" — so `mypy --strict --no-warn-return-any` is quietly weaker than strict, and reordering the arguments will not fix it. `--strict` does NOT enable `--disallow-any-explicit` (error code `explicit-any`), `--warn-unreachable` ("the `--warn-unreachable` flag is not automatically enabled by the strict flag"), or the opt-in codes `deprecated`, `redundant-expr`, `possibly-undefined`, `truthy-bool`, `truthy-iterable`, `ignore-without-code`, `unused-awaitable`, `explicit-override`, `mutable-override`, `unimported-reveal`, `redundant-self`, and `exhaustive-match`. Teams that believe "strict" forbids all `Any` are mistaken (ESTABLISHED caveat). With `--strict`, mypy's docs still claim "you will basically never get a type related error at runtime without a corresponding mypy error, unless you explicitly circumvent mypy somehow."

**The mypy 1.x → 2.x bump is not monotonically stricter (VERSION-DEPENDENT; mypy 2.0+).** Five changes an upgrade must plan for. (1) `--strict-bytes` became a global default: "Per PEP 688, mypy no longer treats `bytearray` and `memoryview` values as assignable to the `bytes` type" — code that passed a `bytearray` where `bytes` was annotated compiled clean under 1.x and errors under 2.x; `--no-strict-bytes` restores the old behaviour. (2) `--local-partial-types` is now default on, and the changelog warns that "explicitly disabling this continues to be supported, but this support will be removed in the future as the legacy behaviour is hard to support with other current and future features in mypy." (3) `--allow-redefinition` was redefined: it "now behaves like `--allow-redefinition-new` in mypy 1.20 and earlier," requires `--local-partial-types`, and no longer permits two annotations for the same variable — previously-clean code can error; the old semantics survive as `--allow-redefinition-old`. (4) mypy "now consistently respects `--ignore-missing-imports` for all packages," which *loses* strictness: packages that previously reported missing types despite the flag now go quiet. (5) `--warn-unused-configs` left the `--strict` set, so stale or misspelled `[mypy-*]` sections stop being reported. Net strictness is **not** monotonic across the major bump.

**mypy parallelism can change verdicts, not just speed (VERSION-DEPENDENT; mypy 2.0+).** `--num-workers N` (short `-nN`) claims "performance gains of up to 5x when using 8 worker processes," but "Parallel type checking implicitly enables the new native parser. There are still some minor semantic differences between parallel and non-parallel modes" — so a parallel CI run and a serial local run are not guaranteed to agree. mypy 2.3 announces "We are planning to enable the new native parser (`--native-parser`) by default soon"; any project already passing `--num-workers` is on the native parser today whether or not it asked. mypy 2.2 also made the fixed-format cache the default (`--no-fixed-format-cache` reverts) and enabled the SQLite cache by default, which invalidates incremental state across the upgrade.

**mypy default behaviour (ESTABLISHED).** Without `--strict` or `--check-untyped-defs`, mypy SKIPS the bodies of unannotated functions entirely — a function with no annotations gets no type checking. pyright, ty and pyrefly all check unannotated bodies by default. This is the single most common surprise for teams and the largest source of "we are typed" illusions.

**pyright modes (VERSION-DEPENDENT; pyright main-branch docs read 8 Aug 2026).** `typeCheckingMode` has four values: `"off"`, `"basic"`, `"standard"`, `"strict"`. The CLI and config default is `"standard"`; the Pylance VS Code extension default is `"off"`. `off` still reports "Python syntax and semantic errors." The authoritative source for which rules each mode enables is the per-mode default-severity table in `microsoft/pyright/blob/main/docs/configuration.md`, which must be read from the version-matched build; it currently documents **91 rows**. Five rules escalate `basic` → `standard` (`reportFunctionMemberAccess`, `reportIncompatibleMethodOverride`, `reportIncompatibleVariableOverride`, `reportOverlappingOverload`, `reportPossiblyUnboundVariable`), so **override-compatibility checking is absent in `basic`**.

**What pyright `strict` adds, and what it still leaves off (VERSION-DEPENDENT).** Exactly **36** rules escalate to `error` in `strict` from a non-error level in `standard`. Eight come from `"warning"`: `reportMissingTypeStubs`, `reportAssertAlwaysTrue`, `reportInvalidStringEscapeSequence`, `reportInvalidTypeVarUse`, `reportSelfClsParameterName`, `reportUnsupportedDunderAll`, `reportUnusedExpression`, `reportWildcardImportFromLibrary`. Twenty-eight come from `"none"`: `reportConstantRedefinition`, `reportDeprecated`, `reportDuplicateImport`, `reportIncompleteStub`, `reportInconsistentConstructor`, `reportInvalidStubStatement`, `reportMatchNotExhaustive`, `reportMissingParameterType`, `reportMissingTypeArgument`, `reportPrivateUsage`, `reportTypeCommentUsage`, `reportUnknownArgumentType`, `reportUnknownLambdaType`, `reportUnknownMemberType`, `reportUnknownParameterType`, `reportUnknownVariableType`, `reportUnnecessaryCast`, `reportUnnecessaryComparison`, `reportUnnecessaryContains`, `reportUnnecessaryIsInstance`, `reportUnusedClass`, `reportUnusedImport`, `reportUnusedFunction`, `reportUnusedVariable`, `reportUntypedBaseClass`, `reportUntypedClassDecorator`, `reportUntypedFunctionDecorator`, `reportUntypedNamedTuple`. The `reportUnknown*` family — implicit `Any` propagating out of untyped third-party code — is the defining feature of pyright strict and has no direct mypy equivalent. Three inference-widening booleans (`strictListInference`, `strictDictionaryInference`, `strictSetInference`) are `true` only in strict, so strict changes what pyright *believes*, not merely what it *says*. **TEN rules remain `"none"` even in strict** and must be opted into by name: `reportCallInDefaultInitializer`, `reportImplicitOverride`, `reportImplicitStringConcatenation`, `reportImportCycles`, `reportMissingSuperCall`, `reportPropertyTypeMismatch`, `reportUninitializedInstanceVariable`, `reportUnnecessaryTypeIgnoreComment`, `reportUnreachable`, `reportUnusedCallResult`. Two booleans are `false` even in strict: `deprecateTypingAliases` (so the PEP 585 deprecation of `typing.List`/`typing.Dict` is **not** reported by default in any mode — strict will not drive that migration) and `enableExperimentalFeatures`. `reportMissingModuleSource` is `"warning"` in all four modes — the only rule that never reaches `error`, so a stub-only dependency with no source never fails a strict run on severity alone. Note the symmetry with mypy: **neither checker reports unreachable code in strict** (`--warn-unreachable` is off in mypy strict; `reportUnreachable` is `"none"` in all four pyright modes).

**pyright reproducibility is not the default (ESTABLISHED).** `pythonVersion` has NO fixed default: "If no version is specified, pyright will use the version of the current python interpreter, if one is present." `pythonPlatform` behaves the same way. The same source tree checked on two machines with different interpreters gets two different verdicts, so both MUST be pinned in `pyrightconfig.json` for reproducible CI. `useLibraryCodeForTypes` defaults to `true`, meaning pyright infers types from unstubbed library source — this is the origin of most `Unknown` leakage that strict's `reportUnknown*` family then reports, so turning those rules on without addressing stubs produces an unfixable error wall. `enableTypeIgnoreComments` (default `true`) governs PEP 484 `# type: ignore` and "does not affect `# pyright: ignore` comments" — disabling it leaves pyright-specific suppressions live while silently reactivating every PEP 484 suppression in the tree. `disableBytesTypePromotions` defaults to `true` in all four modes, matching PEP 688 and mypy 2.0's `--strict-bytes` default: on this one point the two checkers have converged.

**ty has no strict mode, and its defaults are unusual (VERSION-DEPENDENT; ty 0.0.69).** Its docs state plainly: "ty does not have flags such as `--check-untyped-defs` or `strictListInference`, because these are ty's default behaviour and are not currently configurable," and "ty's default mode is currently stricter by default than either mypy or pyright in many ways." Passing mypy or pyright flags to ty is an error, not a no-op. Of 122 documented rules, 91 default to `error`, 23 to `warn`, and 8 to `ignore`; the eight off-by-default are `blanket-ignore-comment`, `division-by-zero`, `missing-override-decorator`, `missing-type-argument`, `possibly-missing-attribute`, `possibly-missing-import`, `possibly-unresolved-reference`, `unsupported-dynamic-base`. Note that `missing-type-argument` is OFF — **ty does not flag bare `list`/`dict` by default**, unlike `mypy --disallow-any-generics` (in `--strict`) and pyright strict's `reportMissingTypeArgument` — so migrating to ty can look like a strictness win while losing generic-argument enforcement. `terminal.error-on-warning` defaults to `true`, the opposite of the usual convention: ty exits non-zero on warnings, so enabling any `warn`-level rule is a CI-breaking change rather than an advisory one. `python-version` defaults to 3.14 (selectable 3.7–3.15) — a fixed default, unlike pyright's ambient-interpreter default — and ty officially supports targets 3.10 and later, with 3.7–3.9 selectable but liable to "false negatives or false positives due to a lack of bundled standard library stubs." ty exposes two named soundness knobs instead of a strict mode: `strict-equality-semantics` (refuses to narrow `x: str` to `Literal["a"]` after `if x == "a"`, because a `str` subclass could compare equal) and `strict-generic-narrowing` (narrows `isinstance(value, list)` to the top materialization `Top[list[Unknown]]`). ty has first-class **intersection** types (`A & B`) that neither mypy nor pyright expresses, and prints diagnostics no other checker emits (`Serializable & Versioned`, `Unknown & Iterable`, `Top[list[Unknown]]`) — any log-scraping or error-matching tooling written against mypy/pyright output will not parse them. It distinguishes `Unknown` (implicit, inferred from untyped code) from `Any` (explicit), the same axis pyright draws. It ships library-specific rules (e.g. `pydantic-discarded-extra-argument`, default `warn`), so checker rule sets are no longer library-agnostic and a rule name may have no analogue in any other tool. Its escape hatches for untyped dependencies are `analysis.allowed-unresolved-imports` (glob suppression) and `analysis.replace-imports-with-any` — the latter a deliberate, auditable `Any` injection point declared in config rather than hidden in a comment. Finally, ty permits **redeclaration**: rebinding one name with a different declared type in the same scope (`paths: str` then `paths: list[str]`) is allowed by design, "designed for adoption," where mypy rejects it even under `--allow-redefinition`.

**pyrefly configures by preset, and inherits config it was never pointed at (VERSION-DEPENDENT; pyrefly 1.2).** Six presets, not a strict boolean: `off` ("Silences every error kind"), `basic`, `legacy` (looser, for mypy migration), `default`, `strict`, and `all` ("Enables every error kind at error severity"), selected by the `preset` key. For a project with **no** existing type-checker config the default is the `basic` preset, which "shows only high-confidence errors that are very likely to indicate real bugs or crashes, like syntax errors and missing imports" — **a green pyrefly run on a fresh project therefore means almost nothing** until a preset is chosen explicitly. If a mypy or pyright config *is* present, "Pyrefly reads your existing configuration and does its best to match your configuration," synthesizing an in-memory config: deleting `mypy.ini` silently changes pyrefly's behaviour, so a config file no one pointed pyrefly at is nonetheless load-bearing. `strict` is not a single switch either — `strict-callable-subtyping` is `true` only under the `strict` preset. Key defaults: `check-unannotated-defs` `true` (like ty, unlike mypy), `infer-return-types` `"checked"`, `min-severity` `"error"`, `permissive-ignores` `false`, `enabled-ignores` `["type", "pyrefly"]`. Per-path overrides use `[[sub-config]]` with a `matches` glob, and only `errors`, `replace-imports-with-any`, `check-unannotated-defs`, `infer-return-types` and `ignore-errors-in-generated-code` may be overridden there. pyrefly versions its own breaking changes loosely — its PyPI page recommends running `pyrefly suppress` when upgrading, because breaking diagnostic changes may land across minor versions — so **a pyrefly minor bump is a re-baselining event, not a patch**.

**Why cross-checker agreement is not a goal you can adopt (ESTABLISHED).** The typing spec at `typing.python.org/en/latest/spec/` is normative for the *type system* only, and PEP 729 (Status: Active) explicitly denies it force over implementations: "The Typing Council has no direct authority over type checkers; it cannot force them to implement particular features or make behavior changes," and checkers "are free to deviate from the spec if they do not have the resources to fully implement it or if they believe a different behavior better serves their users," requiring only that deviations be documented. The spec declines to make the gradual guarantee binding ("In Python's type system, we don't take the gradual guarantee as a strict requirement, but it's a useful guideline"), warns that "The consistency relation is not transitive" — so chaining `A`-assignable-to-`B` and `B`-assignable-to-`C` to justify `A`-to-`C` is unsound reasoning that different checkers will resolve differently — and its normative rule for `Any` is *permissive*, not strict: "A static type checker should not emit static type errors on an expression or statement if `Any` might represent a static type which would avoid the error." A checker that errors on an `Any`-mediated expression is being **more** strict than the spec requires, which is precisely why the `Any` story differs so much between tools. Agreement is therefore not merely unachieved in practice — it is not required in principle, and no authority exists to make it so.

**The divergences that actually bite (ESTABLISHED; from `microsoft/pyright`'s own `docs/mypy-comparison.md` unless noted).**

| axis | pyright | mypy | consequence for a "both must pass" mandate |
|---|---|---|---|
| unannotated function bodies | analyzed and inferred | "skips all functions or methods that do not have type annotations" unless `--check-untyped-defs` | a whole file can be invisible to one tool and fully checked by the other |
| return-type inference | "infers the return type from `return` and `yield` statements within the function's body" | "never infers return types and assumes that functions without a return type annotation have a return type of `Any`" | changes the type of **every** unannotated call site |
| merging types | "always uses a union operation" | "typically (but not always) uses a 'join' operation, which merges types by finding a common supertype"; for heterogeneous containers the join "often produces a type that is not what was intended" | container element types differ, so downstream errors differ |
| literals in tuples | "retains these literal types" | "widens the types to their non-literal type" | code depending on literal-typed tuple elements checks differently |
| narrowing `Any` | "never narrows `Any` when performing type narrowing for assignments" | "inconsistent about when it applies type narrowing to `Any` type arguments" | rely on neither behaviour |
| annotated-variable narrowing | narrows on assignment "regardless of whether the assignment statement includes a variable type annotation" | "skips assignment-based type narrowing when the target variable includes a type annotation" | adding a *redundant* annotation can LOSE narrowing in mypy |
| built-in narrowing forms | supports `x == L`, `x in y`, `bool(x)`, and aliasing a conditional expression used as a type guard | supports none of these | a portable contract must state the predicate as an explicit `TypeIs` function (§2) |
| `...` function bodies | "does not enforce the return type annotation" | "treats `...` function bodies as though they are executable and enforces the return type annotation" | Protocol/stub-style declarations need different handling per checker |
| consuming a `-> None` result | "does not special-case `None` in this manner" | "flags as an error" | a mypy-only error class |
| constructor evaluation | "attempts to follow the runtime behavior as closely as possible," evaluating `__new__` and conditionally `__init__` | "first evaluates the `__init__` method if present, and it ignores the annotated return type of the `__new__` method" — mypy 2.2 partially closed this and now respects explicitly annotated `__new__()` return types, with two back-compat exceptions (an `Any` return, and a supertype return inherited from a superclass, both still yield the current class) — VERSION-DEPENDENT (mypy 2.2) | factory / `__new__` patterns type differently |
| value-constrained TypeVars | uses "conditional types" | "analyzes the class or function multiple times, once for each constraint," emitting one error per constraint | error **counts** are not comparable even when both tools are correct |
| overload resolution under `Any` | return type evaluated "as the supertype" | return type evaluated "as `Any`" | the mypy result silently disables downstream checking |
| class decorators | "honors class decorators" | "largely ignores them" | decorator-based class transforms need PEP 681 `@dataclass_transform` to behave alike |
| import side effects | "intentionally does not model implicit side effects of the Python import loading mechanism" | "models side effects of the import loader" | `pkg.submodule` after only `import pkg` is legal to mypy, an error to pyright |
| circular references | cannot resolve some cycles | the "multi-pass analyzer" resolves metaclass dependencies, TypeVar bounds and class decorators | one of the few axes where mypy is strictly more capable |
| type comments | "supports type comments only in locations where there is a way to provide an annotation using modern syntax" | "full support" | legacy `# type:` comments are not portable |
| `Any` accounting | "differentiates between explicit and implicit forms of `Any`," surfacing the implicit form as `Unknown` under `reportUnknown*` (ty draws the same axis) | tracks `Any` uniformly, gated behind `--warn-return-any` / `--disallow-any-*` | there is **no** rule-name mapping between the two families |
| plugins | none | a plug-in mechanism | any correctness derived from a mypy plugin evaporates under every other checker |

**Conformance scores: what they do and do not mean (VERSION-DEPENDENT; `results.html` last committed 2026-08-07).** The official suite lives at `python/typing` `conformance/`, is organized by spec chapter (concepts, annotations, typeforms, specialtypes, generics, qualifiers, classes, aliases, literals, protocols, callables, constructors, overloads, dataclasses, typeddicts, tuples, namedtuples, narrowing, directives, distribution, historical), and scores fractionally — partial conformance counts as a half, which is why figures like `136.5 / 142` appear against a total of 142 tests. Three rules for using the numbers. (1) **Percentage is not strictness and not quality.** The suite "focuses on static type checking not general Python semantics," and its README concedes that "many important aspects of type checking are not standardized at all, and therefore not covered by conformance tests" — a 99.3% checker and a 76.8% checker can still disagree on any unspecified behaviour, of which there are many. mypy is the lowest-scoring checker in the table and remains the ecosystem default; its dominance is historical, not spec-driven, so "mypy accepts it" does not mean "the spec permits it," and "mypy rejects it" does not mean "the spec forbids it." (2) **Scores are keyed to the versions tested, not to current releases** — the 2026-08-07 file reports mypy 2.1.0, pyright 1.1.410, ty 0.0.67 and pyrefly 1.3.0-dev.1, none of which is the current release. Quoting a score against the wrong version is a fabrication. (3) **A conformance figure absent from that file is a vendor claim.** The official table lists exactly mypy, pycroscope, pyrefly, pyright, ty and zuban; a circulating "100% (141/141)" claim for a checker not present in it is unverified, and the official denominator is 142 (FLAGGED-SECONDARY / OPEN).

**Speed claims are all first-party (FLAGGED-SECONDARY).** ty's README claims "10x - 100x faster than mypy and Pyright"; mypy 2.0's changelog claims "performance gains of up to 5x when using 8 worker processes" for `--num-workers`; pyrefly's v1.0 post reports "a full type check on PyTorch is 34% faster" than its beta with incremental editor updates "up to 125x faster." All three are vendor self-reports. Treat them as directional, benchmark on the target repository, and never let speed override the maturity distinction between production-stable (mypy, pyright, pyrefly) and beta-with-no-stable-API (ty).

**Strictness ratcheting: four incompatible mechanisms (VERSION-DEPENDENT; mypy 2.3, pyright 1.1.411, ty 0.0.69, pyrefly 1.2).** There is no portable strictness axis. mypy ratchets by FLAG plus per-module config section; pyright by a 91-row RULE table plus ordered `executionEnvironments` ("Each source file within a project is associated with at most one execution environment — the first one whose root directory contains that file," so a broad `root` placed first shadows every later entry); ty by 122 RULE LEVELS plus `[[overrides]]` (later wins); pyrefly by six PRESETS plus `[[sub-config]]`. mypy's per-module precedence is: inline source config > concrete module names > unstructured wildcards (later wins) > structured wildcards (more specific wins) > command line > global `[mypy]`. Critically, some mypy options are **global-only and cannot be ratcheted per module** — `warn_redundant_casts`, `python_version`, `platform`, `mypy_path`, `files`, `exclude`, `namespace_packages`, `explicit_package_bases`, `cache_dir`, `incremental`, `sqlite_cache`, `num_workers`, `plugins` — so writing them under `[[tool.mypy.overrides]]` is silently ineffective, and the flag is simply never applied where the author thinks it was. `warn_unused_ignores`, `enable_error_code` and `disable_error_code` ARE per-module settable, and are therefore the real mechanism for per-module ratcheting. mypy's own documented adoption order is bottom-up rather than a global flag flipped at the end: suppress whole packages with per-module `ignore_errors = True`; fix imports with per-module `ignore_missing_imports = True` (preferred over the global `--disable-error-code=import-untyped`, which "can hide errors later on"); require annotations on new and modified code; enable `disallow_untyped_defs` per completed module; then aim at `--strict`. Baseline strategies differ in kind and determine migration cost: mypy has **no** native baseline (there is no `--baseline` flag — use `mypy-baseline` 0.7.4 or per-module `ignore_errors`), pyrefly has native bulk annotation via `pyrefly suppress`, and ty and pyright have suppression comments but no documented bulk-insert command. **Where the ratchet is wired into CI, how it fails a build, and how a standard is adopted incrementally without a big-bang rewrite is owned by `python_quality_gates_manifest.md`; this file states only what each checker can and cannot ratchet.**

**Implication for a team mandating "strict static typing" as a global rule (decision).** "Strict" is not a portable, single-meaning setting, and a mandate naming two checkers has *two* moving rule sets plus a permanent stream of disagreements that no authority will resolve (see PEP 729 above). The operational rule: **pick ONE checker as the release gate**; pin its exact version; commit the full enabled-rule set to version control (`pyproject.toml` / `mypy.ini` / `pyrightconfig.json` / ty and pyrefly config); pin `python_version` and, for pyright, `pythonPlatform`; and treat every other checker as **advisory** — its findings are triaged, not merged, and never block a release. Justify the choice on the axes that genuinely differ: plugin dependence (mypy only), bulk-suppression cost (pyrefly only), maturity (ty is beta with no stable API), unannotated-body coverage (mypy alone skips it), and whether the team can absorb a diagnostic change between two adjacent versions. Record the decision, the pinned versions, and the reason a second checker is *not* a gate; treat any deviation as a spec violation.

### 2. The typing vocabulary for contracts

Each construct below is verified against `docs.python.org`, `typing.python.org`, and the cited PEP; PEP statuses were re-verified against `peps.python.org` on 8 August 2026. **The version in which a construct became available is a hub fact — see `python_platform_baseline_manifest.md` for the shipping ledger; the inline gate here is the behaviour-relevant one.** Where a construct has a citable pattern name from the design literature, the name and its naming source are given, because uncited vocabulary is a preference rather than grounding.

- **`typing.Protocol` — structural typing (PEP 544; Python 3.8). ESTABLISHED.** Defines an interface by shape (methods/attributes), not inheritance: any class with the right shape conforms, with no explicit subclassing. Contract use: express "anything that can `read()`/`close()`" capability contracts, especially for third-party types you do not control. Checked statically only. `@runtime_checkable` enables `isinstance()` but verifies only member *existence* — "will check only the presence of the required methods or attributes, not their type signatures or types" — and "can be surprisingly slow compared to an `isinstance()` check against a non-protocol class"; the docs suggest `hasattr()` for structural checks in performance-sensitive code. `isinstance()` works against both data and non-data protocols, but `issubclass()` works **only** against non-data protocols, "because some data attributes can be set on an instance in constructor and this information is not always available on the class object"; applying `@runtime_checkable` to a non-protocol class raises `TypeError`. Two 3.12 changes alter results silently: `isinstance()` now uses `inspect.getattr_static()` rather than `hasattr()`, so "some objects which used to be considered instances of a runtime-checkable protocol may no longer be considered instances of that protocol on Python 3.12+, and vice versa"; and protocol members are frozen at class creation, so "Monkey-patching attributes onto a runtime-checkable protocol will still work, but will have no impact on `isinstance()` checks" (VERSION-DEPENDENT (3.12)). **Never use a runtime-checkable Protocol as a validation gate** — it accepts any object with the right attribute names. A `Protocol` also captures shape at one instant, not a legal call sequence (§4).
- **`abc.ABC` — nominal typing (`abc` module). ESTABLISHED.** Conformance requires explicit inheritance/registration. Use when implementations share code or when you control the hierarchy and want enforced subclassing. Contrast: Protocol = structural/duck, ABC = nominal/declared.
- **`@dataclass` (`dataclasses` module; PEP 557; Python 3.7). ESTABLISHED.** Generates `__init__`/`__repr__`/`__eq__` from annotated fields. Stdlib dataclasses do NOT validate types at runtime — "With two exceptions described below, nothing in `@dataclass` examines the type specified in the variable annotation," and the two exceptions are detecting `typing.ClassVar` and `dataclasses.InitVar`, both structural, neither a value check. Full decorator defaults, verbatim: `init=True, repr=True, eq=True, order=False, unsafe_hash=False, frozen=False, match_args=True, kw_only=False, slots=False, weakref_slot=False` — note `slots` is **False**, the opposite of `attrs.define`. Distinction: `attrs` (`@define`) offers per-attribute converters and validators, `slots=True` by default, and — uniquely — runs validators on **attribute assignment** as well as in `__init__` under `@define`/`@frozen` (legacy `@attr.s` runs them only at init); attrs nonetheless disclaims the role ("attrs emphatically does **not** try to be a validation library"), never coerces from annotations, and its validators can be switched off process-wide via `attrs.validators.set_disabled(True)`. `msgspec.Struct` sits at the opposite corner: annotations "are not checked at runtime during normal use. Types are only checked when decoding a serialized message when using a typed decoder" — construction is unchecked, decode is strict-by-default. `pydantic` (`BaseModel`, `TypeAdapter`, or `pydantic.dataclasses.dataclass`) is the only one of the four that validates and coerces at construction, and it is lax by default. Use a stdlib dataclass for plain typed records inside the trusted core; see the §5 decision table before choosing anything else.
- **`TypedDict` (`typing`; PEP 589; Python 3.8). ESTABLISHED.** Types a dict with a fixed set of string keys and per-key value types. At runtime it is a plain `dict` — no key or value enforcement whatsoever, so it means nothing at a boundary without a validator (pydantic `TypeAdapter`, msgspec typed decode). Extensions: `Required`/`NotRequired` (PEP 655, 3.11), `ReadOnly` (PEP 705, 3.13), and closed / typed-extra-items (PEP 728, **Final**, shipped in 3.15 — VERSION-DEPENDENT (3.15)): `closed=True` forbids extra keys and `extra_items=T` types them, `extra_items=Never` is equivalent to `closed=True` (the latter preferred), the two are mutually exclusive at runtime, extra items are always non-required regardless of `total=`, and combining `extra_items` with `Required[]`/`NotRequired[]` is an error. Runtime introspection uses `__extra_items__` (holding `typing.NoExtraItems` when unset) and `__closed__` (holding `None` when unset); both reflect only what was passed, ignoring inheritance. A closed or all-`NotRequired` TypedDict becomes assignable to `dict[str, VT]`, unlocking `.clear()` and `__setitem__`. mypy implements `closed` from 2.2 — VERSION-DEPENDENT (mypy 2.2). **Closedness is what makes `in`-check narrowing across a TypedDict union sound at all**, so it is a contract feature, not a convenience. Do not emit `closed=True` against a pinned target below 3.15 without `typing_extensions`: older checkers reject the unknown keyword rather than ignoring it.
- **`NamedTuple` (`typing`; based on `collections.namedtuple`). ESTABLISHED.** Immutable typed tuple with named fields. Generic NamedTuples supported from 3.11.
- **`Enum` (`enum` module; Python 3.4) and `Literal` (`typing`; PEP 586; Python 3.8). ESTABLISHED.** `Enum` gives a closed set of named constants checkable at runtime and statically. `Literal["a","b"]` constrains a value to specific literal constants at the type level only. Per the mypy enum spec, enum members must be left unannotated. Contract use: model closed value domains (states, modes, discriminators).
- **`NewType` (`typing`; PEP 484; Python 3.5.2; became a class in 3.10). ESTABLISHED.** `UserId = NewType('UserId', int)` creates a distinct subtype of `int` for the checker with minimal runtime cost. It is a **no-op at runtime**: "At runtime, however, calling a `NewType` returns its argument unchanged," and "the expression `some_value is Derived(some_value)` is always true at runtime." Contract use: prevent mixing semantically different values that share a representation (`UserId` vs `OrderId`). Corpus aka for the same idea: "tiny types", "strong typedef", "micro type". **The load-bearing rule the name alone hides: a `NewType` without a smart constructor is a naming convention, not a contract** — `UserId(-1)` type-checks fine. The sourced composition rule is `smart-constructor` composes-with `newtype` (haskell.org wiki, *Smart constructors*): "A smart constructor wraps a newtype and is exported instead of the raw constructor, so the type's invariant cannot be bypassed." Pair them or claim nothing (§5). Version note: `NewType` "became a class in 3.10 with some additional runtime cost," and "The performance of calling `NewType` has been restored to its level in Python 3.9" in 3.11 — VERSION-DEPENDENT (3.10, 3.11).
- **Sealed trait — the variant set as a single visible edit (`OPEN` for enforcement; named in the Rust API Guidelines, C-SEALED, living).** **Python has no sealing mechanism.** The transposable half is `@final` on every variant class plus a module-level `type X = A | B` alias that is the only public spelling, so adding a variant is a one-line, reviewable edit rather than a silent extension elsewhere. Enforcement route: **checker-and-convention only** — `@final` is checker-enforced (nothing at runtime), and nothing prevents a third party from writing a new class and passing it where the alias is expected as long as it structurally fits. Say this plainly in the contract rather than implying sealing.
- **Exhaustiveness, and the error codes that actually report it (VERSION-DEPENDENT).** `assert_never(x)` in the fall-through `case` is the portable idiom: a checker that still considers the branch reachable reports the call as an error, which is how the exhaustiveness claim is mechanically enforced. Beyond it, the *dedicated* non-exhaustive-match diagnostics are **off by default in both major checkers**: mypy's `exhaustive-match` is an opt-in error code (not in `--strict`) and pyright's `reportMatchNotExhaustive` is `"none"` in `standard` and escalates to `error` only in `strict`. Enforcement route: enable the code explicitly, or rely on `assert_never`; do not assume a default configuration catches a missing variant. **OPEN:** the packs for this pass do not record the Python release that added `assert_never`, so treat its exact availability gate as unverified here and confirm it against `python_platform_baseline_manifest.md` before targeting an older runtime.
- **`NewType` (`typing`; PEP 484; Python 3.5.2; became a class in 3.10). ESTABLISHED.** `UserId = NewType('UserId', int)` creates a distinct subtype of `int` for the checker with minimal runtime cost (a thin callable that returns its argument). Contract use: prevent mixing semantically different values that share a representation (e.g., `UserId` vs `OrderId`).
- **`Generic`/`TypeVar` (PEP 484; 3.5), `ParamSpec` (PEP 612; 3.10), `TypeVarTuple` and `Unpack` (PEP 646; 3.11). ESTABLISHED.** `TypeVar` parameterizes by a single type; `ParamSpec` (with `Concatenate`) captures a callable's full parameter signature, which is what makes a decorator type-preserving; `TypeVarTuple` enables variadic generics (`tuple[int, *Ts]`). PEP 695 (Final, 3.12) added the `class Foo[T]:` / `def f[T]()` native syntax and the `type` statement for lazily-evaluated aliases, with variance **inferred** rather than declared. PEP 692 (Final, 3.12) types `**kwargs` per keyword via `**kwargs: Unpack[SomeTypedDict]`. PEP 696 (Final, 3.13) adds type-parameter defaults (`TypeVar("T", default=int)`, or `class Box[T = int]` in PEP 695 syntax) — but mypy declared support "complete" only in 2.2, and earlier mypy silently mishandled recursive defaults and inter-parameter dependencies (VERSION-DEPENDENT (3.13; mypy 2.2)).
- **Phantom type — a type parameter with no runtime representation. ESTABLISHED for the PEP 695 mechanism; the naming source is corpus-UNVERIFIED (naming source: Leijen & Meijer, *Domain Specific Embedded Compilers*, DSL '99, 1999 — recorded as **UNVERIFIED** in the SWE corpus; do not upgrade that status without a fresh primary check).** The catalog definition is "a type parameter that appears in a type's signature but not in its runtime representation." Python spelling with PEP 695: `class Tainted[S]: __slots__ = ("raw",)` where `S` is never stored, plus marker classes `class Raw: ...` / `class Clean: ...`, so the checker separates `Tainted[Raw]` from `Tainted[Clean]` at **zero runtime cost**. Enforcement route: type-catchable only — a phantom parameter is invisible at runtime by construction, so there is nothing to check and nothing to bypass. This is the mechanism behind the partial typestate story in §4 (`phantom-type` implements `typestate`, sourced in the corpus to *The Embedded Rust Book*, "Typestate Programming" — also **UNVERIFIED** in the corpus).
- **`Self` (`typing`; PEP 673; Python 3.11). ESTABLISHED.** Annotates methods returning an instance of their own (possibly subclass) type — fluent/builder APIs, `__enter__`, copy/clone. Equivalent to but more concise than a bound `TypeVar`. Rejected in staticmethods and metaclasses per the PEP.
- **`Final` and `@final` (`typing`; PEP 591; Python 3.8). ESTABLISHED.** `Final` marks a name that must not be reassigned/redefined/overridden; `@final` marks a class/method as non-subclassable/non-overridable. "There is no runtime checking of these properties" (typing docs) — enforced by checkers only.
- **`Annotated` (`typing`; PEP 593; Python 3.9). ESTABLISHED.** `Annotated[T, x]` attaches arbitrary metadata `x` to type `T`. Tools without special logic for `x` "should ignore it and simply treat the type as T." Basis for pydantic field constraints and the `annotated-types` library.
- **`Never` and `NoReturn` (`typing`). VERSION-DEPENDENT.** `NoReturn` (PEP 484; added 3.6.2) annotates functions that never return normally. `Never` (added in Python 3.11 with NO dedicated PEP) is the explicit spelling of the bottom type (uninhabited). Checkers treat the two equivalently. NOTE: the frequently seen "PEP 661" attribution for `Never` is incorrect — PEP 661 is "Sentinel Values" (**Final**, shipped in 3.15) and is unrelated; `Never` has no PEP.
- **`TypeIs` (PEP 742; Final, 3.13) vs `TypeGuard` (PEP 647; Final, 3.10) — narrowing contracts. ESTABLISHED.** `TypeGuard[T]` narrows on the **True branch only** and imposes no relationship between `T` and the parameter type: "When a `TypeGuard` function returns `False`, type checkers cannot narrow the type of the variable at all." `TypeIs[T]` narrows in **both** branches — "When a `TypeIs` function returns `False`, type checkers can narrow the type of the variable to exclude the `TypeIs` type" — intersects with the prior type on True, and requires the returned type to be "consistent with" the parameter type. **Default to `TypeIs`.** Reserve `TypeGuard` for deliberate non-subtype narrowing (e.g. `list[object]` → `list[str]`, where the narrowed type is not a subtype of the argument type). Choosing `TypeGuard` where `TypeIs` was meant produces **no error and no diagnostic** — just weaker types downstream that nothing flags. Because the checkers disagree about which *built-in* expressions narrow at all (pyright narrows on `x == L`, `x in y` and `bool(x)`; mypy narrows on none of them — §1), a portable contract states the predicate as an explicit `TypeIs` function rather than relying on inference.
- **`@override` (PEP 698; Final, 3.12). ESTABLISHED.** Asserts that a method does override a base-class member; inert at runtime. The **inverse** — requiring the decorator on every override — is off by default everywhere: pyright's `reportImplicitOverride` is `"none"` even in strict, and mypy's `explicit-override` is an opt-in error code. Enforcement route: type-catchable **only if explicitly enabled**.
- **`@deprecated` (PEP 702; Final, 3.13) — imported from `warnings`, NOT `typing`. ESTABLISHED.** `from warnings import deprecated`. "Decorator to indicate that a class, function or overload is deprecated ... static type checkers will also generate a diagnostic on usage of the deprecated object." Reporting is advisory in the PEP's own words ("Type checkers should produce a diagnostic"), and it is off by default almost everywhere: mypy's `deprecated` code is opt-in, pyright's `reportDeprecated` is `"none"` outside strict, and ty's `deprecated` rule defaults to `warn` — though ty exits non-zero on warnings by default, so on ty it does fail CI. Enforcement route: runtime `DeprecationWarning` plus an explicitly enabled checker code. The deprecation *policy* for a project's own public API lives in `python_module_boundaries_manifest.md`.
- **`LiteralString` (PEP 675; Final, 3.11). ESTABLISHED.** A string built only from literals — the type-level defence against SQL/shell injection at the boundary where a query or command is assembled. Checker-only.
- **`TypeForm[T]` (PEP 747; Final, 3.15). VERSION-DEPENDENT (3.15).** Annotates values that *are* type expressions — "the set of all type form objects that represent the type `T` or types assignable to `T`". At runtime `TypeForm(obj)` returns `obj` unchanged. This is the correct annotation for a function that takes a type and returns a parser or adapter for it (`TypeAdapter`-shaped APIs). On 3.14 and earlier, import it from `typing_extensions`. mypy promoted `TypeForm` out of experimental in 2.2 — VERSION-DEPENDENT (mypy 2.2). **Trap:** mypy's own 2.2 changelog says "TypeForm (introduced in Python 3.14)", but PEP 747 records Python-Version 3.15 and `docs.python.org/3.15/library/typing.html` says "Added in version 3.15" — the primary docs win; the changelog parenthetical is wrong.
- **`@typing.disjoint_base` (PEP 800; Final, 3.15). VERSION-DEPENDENT (3.15).** "Type checkers do not allow child classes of a disjoint base `C` to inherit from other disjoint bases that are not parent or child classes of `C`," which lets a checker detect unreachable `isinstance` branches and impossible intersections. Aimed primarily at stubs for builtins and extension modules, **not** at ordinary user code — importing it into application classes is over-engineering at this scale. Returns the decorated object unchanged; `typing_extensions.disjoint_base` backports it (added in 4.15.0).
- **`sentinel` (PEP 661; Final, 3.15) — a *builtin*, not `typing.Sentinel`. VERSION-DEPENDENT (3.15).** `class sentinel(name, /, *, repr=None)`. Sentinels "are truthy and compare equal only to themselves," are intended for `is` comparison, do not support subclassing, and return themselves from shallow and deep copies; those importable by module and name survive pickling while locals do not. They may appear directly in type expressions: `def next_value(default: int | MISSING = MISSING)`. **Two calls with the same name return DISTINCT objects**, so a sentinel must be created once at module scope and shared by reference — the same discipline as `MISSING = object()`. In `typing_extensions` 4.16.0 the capitalized `Sentinel` is a soft-deprecated alias for lowercase `sentinel`, "following the name that has been adopted for `builtins.sentinel` on Python 3.15," and the default repr of `X = sentinel("X")` changed from `<X>` to `X` — code asserting on that repr breaks (VERSION-DEPENDENT (typing_extensions 4.16.0)).
- **`@dataclass_transform` (PEP 681; Final, 3.11). ESTABLISHED.** Tells checkers that a decorator, base class, or metaclass synthesizes `__init__` from annotated fields — the mechanism by which pydantic and attrs get dataclass-like static checking. Relevant here because pyright honours class decorators and mypy "largely ignores them" (§1): expressing a class transform through `@dataclass_transform` is what makes it behave the same under both.
- **Typing PEPs that are still DRAFT and therefore NOT AVAILABLE in any released Python (OPEN).** Do not emit these; they are the likeliest typing hallucinations because they read like natural extensions of what exists. **PEP 718** subscriptable functions (`f[int](...)` at a call site), **PEP 764** inline typed dictionaries, **PEP 746** type checking `Annotated` metadata, **PEP 767** annotating read-only attributes, **PEP 781** making `TYPE_CHECKING` a built-in constant, **PEP 821** unpacking TypedDicts in `Callable` hints (all Draft, targeted 3.15), plus **PEP 827** type manipulation and **PEP 835** shorthand syntax for `Annotated` metadata (Draft, targeted 3.16). Also not features: **PEP 677** callable type syntax `(int) -> str` is **Rejected**; **PEP 724** and **PEP 727** are **Withdrawn**; **PEP 729** is **Active** (Process), describing governance rather than a construct. Use a named `TypedDict` instead of an inline one, and an explicit generic parameter instead of call-site subscription.
- **Distribution of type information is a packaging contract, not a typing one. ESTABLISHED.** PEP 561 (Final, 3.7) defines the `py.typed` marker, inline vs stub-only packages, and the `-stubs` suffix convention. Those rules — and who owns the public API surface they expose — live in `python_module_boundaries_manifest.md`; this file only notes that a dependency without `py.typed` is the origin of most implicit `Any` (§3).

### 2a. Deferred annotation evaluation (PEP 649 / PEP 749) and `annotationlib`

**Three annotation execution models now coexist, and they are mutually exclusive rather than layered (VERSION-DEPENDENT (3.14+)).** (1) **Eager** — the stock behaviour up to and including 3.13: an annotation is an expression evaluated at function/class definition time. (2) **Stringified** — `from __future__ import annotations` (3.7+): annotations are stored as strings and never evaluated. (3) **Deferred / lazy** — the 3.14 default: "The annotations on functions, classes, and modules are no longer evaluated eagerly. Instead, annotations are stored in special-purpose annotate functions and evaluated only when necessary (except if `from __future__ import annotations` is used)." PEP 649 ("Deferred Evaluation Of Annotations Using Descriptors") and PEP 749 ("Implementing PEP 649") are both **Final** for 3.14. Any spec that touches annotation introspection must name which of the three models it assumes.

**`from __future__ import annotations` DISABLES PEP 649 rather than reinforcing it (VERSION-DEPENDENT (3.14+)).** With the import present, annotations remain strings and PEP 649's lazy-object model does not apply, so `get_annotations()` retrieves the stringified form. Leaving the import in place on 3.14 forfeits the entire feature; "modernizing" a 3.14 file by *adding* the import removes the behaviour the author believes it enables. The import is now **deprecated** but its behaviour is **unchanged**: "this statement is now deprecated and it is expected to be removed in a future version of Python. This removal will not happen until after Python 3.13 reaches its end of life in 2029 ... In Python 3.14, the behavior of code using `from __future__ import annotations` is unchanged." Per PEP 749 the path is three-stage: works in 3.14 → `DeprecationWarning` after 3.13 reaches EOL → `SyntaxError` two releases after that. PEP 563 ("Postponed Evaluation of Annotations") is formally **Superseded**, not merely deprecated in prose. It also carries a live footgun: with the future import, `def foo(a: "str")` yields `{'a': "'str'"}` — the annotation "is quoted *twice*". **Decision:** do not add it to new 3.14+ code; remove it once 3.13 support is dropped, but only after auditing every library that reads `__annotations__`. On 3.14+ "It is no longer necessary to enclose annotations in strings if they contain forward references," so quoted forward references become removable at the same time.

**Read annotations through `annotationlib`, never `__annotations__` (VERSION-DEPENDENT (3.14+)).** The stdlib annotations HOWTO is explicit: "You should avoid accessing `__annotations__` directly on any object. Instead, use `annotationlib.get_annotations()` (Python 3.14+) or `inspect.get_annotations()` (Python 3.10+)." `annotationlib` was added in 3.14 and "supersedes `inspect.get_annotations()`". Signature: `annotationlib.get_annotations(obj, *, globals=None, locals=None, eval_str=False, format=Format.VALUE)`, returning a NEW dict on each call.

**`annotationlib.Format` has FOUR members and is not contiguous (VERSION-DEPENDENT (3.14+)).** `VALUE = 1` (evaluate; may raise `NameError`), `VALUE_WITH_FAKE_GLOBALS = 2` ("only used internally and should not be passed to the functions in this module"), `FORWARDREF = 3` (real values where defined, `ForwardRef` proxies elsewhere; "never throws an exception"), `STRING = 4` (source-like strings; cannot recover comments, whitespace, or certain expression forms). PEP 649's originally proposed third format `SOURCE` was **renamed `STRING`** by PEP 749 — an agent citing `Format.SOURCE`, or assuming a contiguous 1/2/3 enum, is wrong. `annotationlib.call_annotate_function(annotate, format, *, owner=None)` exists specifically because "compiler-generated annotate functions only support `VALUE` format when called directly," so calling `__annotate__` yourself with `FORWARDREF`/`STRING` does not work. `annotationlib.ForwardRef` carries `__forward_arg__` (the code string, which "may not be exactly equivalent to the original source") and `evaluate(*, owner=None, globals=None, locals=None, type_params=None, format=Format.VALUE)`. `inspect.signature()` gained an `annotation_format` argument and `inspect.Signature.format()` gained `unquote_annotations`, both in 3.14, for choosing the format.

**What this changed in code that reads annotations — the part that produces confusing bugs (VERSION-DEPENDENT (3.14+)).**

| consumer | what changed | what an implementer must do |
|---|---|---|
| CPython's own `dataclasses` | reads annotations via `annotationlib.get_annotations(cls, format=annotationlib.Format.FORWARDREF)` | a dataclass field annotated with an **undefined** name is now accepted at class-creation time and its annotation is a `ForwardRef`, not a type object; the failure moves to whoever later resolves it (a validator, a schema generator) — often far from the definition |
| `dataclasses` `ClassVar`/`InitVar` detection | remains partly **textual**, with a documented blind spot: an alias bound inside the class body (`CV = ClassVar` in class scope) is not recognised | such a field silently becomes a real per-instance dataclass field. CPython judged the fix "not worth it" because it "would involve a eval() penalty for every single field of every dataclass"; the module's own words call it a "fairly obscure corner case" |
| pydantic | does **not** yet lean on `annotationlib`; its internals page says only "There's a hope that PEP 649 (introduced in Python 3.14) will greatly simplify the process," and current behaviour is "If the annotation failed to evaluate, it is kept as is, so that the model can be rebuilt at a later stage" | resolve deferred models explicitly with `Foo.model_rebuild()` (optionally `_types_namespace=...`) rather than assuming import order fixes it |
| `if TYPE_CHECKING:` imports | unchanged and still `False` at runtime | any name imported only under `TYPE_CHECKING` and then resolved in **VALUE** format — a pydantic annotation, a `TypeAdapter` target, `get_type_hints()` — raises `NameError`. pydantic's escape hatch is `model_rebuild(_types_namespace=...)` |
| `attrs` | added 3.14/PEP 749 support in 25.4.0 ("Added support for Python 3.14 and PEP 749"); 26.1.0's note frames the line as still moving — the release "ships the first pieces of work for Python 3.14 and PEP 749. There will be more work required and there's going to be a lot more churn once everyone starts testing 3.14 earnestly" | treat attrs-on-3.14 as supported but young; pin and test |
| `beartype` | 0.22.9 (13 Dec 2025) is still the newest release and does **not** contain the fix for issue #610, "CPython 3.14.2 + PEP 649 `annotationlib.ForwardRef` + PEP 484 self-reference = `TypeError: unhashable type: 'cell'`" (closed in trunk, unreleased) | a self-referential annotation under `@beartype` fails at **decoration** time, i.e. at import, on 3.14. Pinning beartype on a 3.14 target is a live risk. The maintainer's release timeline is **OPEN** |
| `typeguard` | 4.6.0 (26 Jul 2026) "Dropped support for Python 3.9", "Fixed compatibility with Python 3.15", and added checking against the PEP 661 `sentinel` type; 4.5.0 "Fixed `NameError` when evaluating forward references on Python 3.14" | use 4.5.0 or newer on 3.14+ |
| `icontract` / `deal` | neither project's metadata asserts 3.14/PEP 649 readiness. icontract 2.7.3 declares **no** Python floor (`requires_python` is `null`) and its classifiers stop at 3.13; deal 4.24.6 declares `>=3.8` and carries no per-version classifiers at all | **OPEN:** whether either actually works on 3.14 was not determined this pass. Dependency resolvers will install both on 3.14 with no compatibility signal — verify against your interpreter before relying on either |

**Enforcement route (OPEN — nothing mechanical).** Nothing catches an annotation-model mismatch: there is no checker rule for "this library reads `__annotations__` eagerly." The available mechanisms are a test that imports every module under the target interpreter (`python_testing_tooling_manifest.md`) and a lint rule banning `from __future__ import annotations` in new files (`python_linting_practices_manifest.md` owns the rule selection). Treat the model as a **contract-only** decision recorded in the spec.

### 3. Explicit conversion and cast discipline

- **`typing.cast(typ, val)` (PEP 484; `typing`). ESTABLISHED.** Has NO runtime effect: per the typing spec, "At runtime a cast always returns the expression unchanged – it does not check the type, and it does not convert or coerce the value," and the CPython implementation is literally `def cast(typ, val): return val`. It is a promise the checker trusts blindly — an unchecked assertion, not a conversion. A wrong cast silently propagates a lie until something downstream crashes.
- **`assert_type(val, typ)` (`typing`; Python 3.11; NO dedicated PEP). VERSION-DEPENDENT.** Asks the checker to confirm the inferred type of `val` equals `typ`; "At runtime this does nothing: it returns the first argument unchanged." It checks *type equivalence* (not assignability), so asserting a parent type or a Protocol against an inferred concrete subtype **fails**. Use it in test files to lock down inferred types — it is the only mechanism that makes an inference claim a regression test. (The commonly seen "PEP 675" attribution is wrong: PEP 675 is `LiteralString`; `assert_type` has no dedicated PEP, confirmed via PEP 729's typing-PEP ledger.)
- **`reveal_type(obj)` (`typing`; runtime function added Python 3.11). VERSION-DEPENDENT.** Causes the checker to emit the inferred static type as a diagnostic (e.g., `Revealed type is "builtins.int"`). Historically a checker-only magic name; now also importable at runtime.
- **Sources of implicit `Any` and how each checker surfaces them (ESTABLISHED).** Implicit `Any` enters via: untyped third-party imports and missing stubs, unannotated function parameters/returns, untyped containers, and `# type: ignore`. `mypy --strict` catches missing annotations via `--disallow-untyped-defs`/`--disallow-incomplete-defs` and unwarranted returns via `--warn-return-any`, and can audit residual `Any` via `--any-exprs-report`; but mypy tracks a **single** `Any`, so it cannot distinguish "I wrote `Any`" from "this leaked out of an unstubbed dependency". pyright and ty both draw that distinction: the implicit form is surfaced as `Unknown`, reported by pyright strict's `reportUnknown*` family — the most direct surface for implicit `Any` — and there is **no rule-name mapping** between the two families, so an `Any` budget expressed in one checker's vocabulary does not transfer. Note the amplifier: pyright's `useLibraryCodeForTypes` defaults to `true`, so unstubbed dependencies yield inferred `Unknown` rather than a hard import error, which is why enabling `reportUnknown*` before fixing stubs produces an unfixable wall. ty's declared, auditable equivalent is `analysis.replace-imports-with-any` — an `Any` injection point visible in config rather than buried in a comment.
- **"No implicit coercion / explicit conversion" concretely (ESTABLISHED).** It means: do not rely on truthiness as a stand-in for an explicit boolean test or count; do not depend on implicit numeric promotion at type boundaries; call `int(x)`, `str(x)`, `float(x)` explicitly when changing representation. `mypy --strict-equality` (in `--strict`) prohibits comparisons between non-overlapping types (e.g., `42 == 'no'`, `b'x' != s`), catching a major class of silent-coercion bugs.
- **When a cast is genuinely unavoidable, and how to confine it (decision).** A cast is legitimate only when the human knows something the checker provably cannot — e.g., narrowing an `object`/`Any` from a deserializer where a runtime `isinstance` check just preceded it, or working around a missing/incorrect third-party stub. Confine it: (1) put the `cast` on the smallest possible expression immediately after a runtime check that actually validates the assumption; (2) add a comment stating WHY it is safe; (3) never use `cast` to silence a real type error you could fix structurally. With `--warn-redundant-casts` (in `--strict`), mypy flags casts that are unnecessary, keeping the cast surface minimal.

### 3a. Suppression hygiene — the `# type: ignore` contract

**Suppressions are the only escape hatch that grows silently, and no checker stops it by default (VERSION-DEPENDENT).** A suppression is a claim about a *specific* diagnostic at a *specific* line. The contract has four clauses, and each has a named enforcement route or an honest admission that it has none.

| clause | mechanism that enforces it | status |
|---|---|---|
| Every suppression names the code it suppresses (`# type: ignore[arg-type]`, `# pyright: ignore[reportUnknownMemberType]`, `# ty: ignore[unresolved-import]`, `# pyrefly: ignore[bad-return]`) | mypy error code `ignore-without-code` (**opt-in**, not in `--strict`); ty rule `blanket-ignore-comment` (**defaults to `ignore`**, i.e. off) | must be explicitly enabled in both; nothing enforces it in pyright |
| Every suppression carries a justifying comment | nothing mechanical | **contract-only** — review-enforced or not enforced |
| A suppression that is no longer needed is removed | mypy `--warn-unused-ignores` (**in `--strict`**, error code `unused-ignore`); pyright `reportUnnecessaryTypeIgnoreComment` (**`"none"` even in strict**); ty `unused-ignore-comment` / `unused-type-ignore-comment` (**`warn`**, though ty exits non-zero on warnings by default); pyrefly `pyrefly suppress --remove-unused` (also `--remove-unused=type` / `--remove-unused=all`) | asymmetric: mypy strict reports them, pyright strict does **not** |
| Suppression count trends down over time | a CI ratchet, which is **not built here** | owned by `python_quality_gates_manifest.md` |

**The unused-ignore asymmetry is the ratchet's ratchet (VERSION-DEPENDENT; mypy 2.3, pyright 1.1.411, ty 0.0.69, pyrefly 1.2).** Because pyright strict does not report useless suppressions, a codebase gated on `pyright --strict` accumulates permanent `# type: ignore` comments that no tool will ever flag; a codebase gated on `mypy --strict` gets them reported for free. If the release gate is pyright, `reportUnnecessaryTypeIgnoreComment` must be turned on by name — it is one of the ten rules that stay `"none"` in strict (§1). Note also the per-checker interlocks: pyright's `enableTypeIgnoreComments` toggles PEP 484 comments but **not** `# pyright: ignore`; ty's `unused-ignore-comment` diagnostic "can only be suppressed using `# ty: ignore[unused-ignore-comment]`" — a bare ignore will not silence it; and ty honours `# type: ignore` (all rules) plus `# type: ignore[ty:<rule>]`, governed by `analysis.respect-type-ignore-comments` (default `true`). pyrefly's file-level `# pyrefly: ignore-errors` MUST appear before any code, otherwise it yields a `misplaced-ignore` warning rather than failing silently — which is the correct design and the exception in this table.

**Scope boundary.** This section covers **type-checker** suppressions only. Lint-rule suppression (`# noqa`, per-rule disables) and the formatter/linter/checker division of labour are owned by `python_linting_practices_manifest.md`. The ratchet — where the check runs, how it fails a build, and how a suppression budget is driven to zero incrementally — is owned by `python_quality_gates_manifest.md`. Do not build a ratchet in this file.

### 4. What the type system CANNOT express

The Python type system is (broadly) about the *shape* and *identity* of values, not their runtime *values* or *history*. The following are out of scope for static checkers and MUST become runtime contracts or boundary parsing — never silently dropped (principle).

**Read this section positively, because the design literature files it that way.** In the SWE corpus, seven design elements — `option-type`, `newtype`, `tagged-union`, `phantom-type`, `units-of-measure-types`, `smart-constructor` and `trampoline` — are all recorded as realizing the SAME architecture tactic, **Exception Prevention** (*Software Architecture in Practice*, 4th ed. — Bass, Clements & Kazman, 2021, Addison-Wesley/SEI, ISBN 978-0-13-688609-9), whose intent is "keep faults from arising" rather than handle them. (Those seven `realizes` edges are marked **editorial** in the corpus — house judgment about which mechanism serves which tactic, not a claim any cited author made. Throughout this file, an edge described as *sourced* means a citable source states the relation; an edge described as *editorial* is the corpus's own judgment and is presented as such.) So the list below is not an inventory of impossibilities: it is a list of invariants that must move to a *different* named mechanism, and Python supports most of those mechanisms. Each bullet therefore ends with where the invariant goes.

- **Value-range constraints (ESTABLISHED).** "a positive int", "0 ≤ x ≤ 100", "non-empty string". The type system has no dependent types; `int` cannot be narrowed to "positive int" statically.
- **Cross-field invariants (ESTABLISHED).** "`start_date` ≤ `end_date`", "if `kind=='A'` then `payload` is required". No checker enforces relationships between fields.
- **Ordering/temporal constraints (ESTABLISHED).** "`open()` must precede `read()`", "monotonically increasing timestamps". Sequencing is a stateful runtime property.
- **Units of measure (ESTABLISHED) — and `NewType` is the weakest of three named options, not the answer.** "meters vs feet", "seconds vs milliseconds" cannot be stated as types: `NewType` per unit prevents accidental substitution at call boundaries, but arithmetic between them is not dimensionally checked — `Meters(3) + Feet(2)` type-checks as plain `int` addition. The design literature holds three distinct mechanisms, one **sourced** edge and two **editorial** ones between them: **`units-of-measure-types`** (type-level unit parameters, which the corpus records as *using* `phantom-type`, sourced to Kennedy 2009 / F# 2.0 / `boost::units` / Haskell `dimensional`), **`quantity`** (*Analysis Patterns: Reusable Object Models* — Martin Fowler, 1996), and **`newtype`** — the `units-of-measure-types` → `quantity` and `units-of-measure-types` → `newtype` alternative-to edges are both editorial. Python **cannot** take the type-level branch: there is no dimension inference through arithmetic operators. Therefore the correct primary recommendation is the **`quantity`** branch — a runtime value object: `pint.Quantity`, `astropy.units`, or a frozen dataclass `Measure(value: float, unit: Unit)` whose `__add__` rejects mismatched units at runtime — with `NewType` as the zero-dependency **fallback**, not the best answer. Enforcement route: runtime (the value object's own arithmetic), plus type-catchable substitution errors at boundaries if the quantity type is distinct per dimension.
- **Stateful protocols / typestate (ESTABLISHED, with a partial yes).** "a socket is connected before send", "a transaction is open". `Protocol` captures shape at one instant, not a legal call sequence, and an object's type does not change when its internal state mutates. But the flat "no typestate in Python" is too coarse to act on. The mechanism named in the literature is `phantom-type` implementing `typestate` (corpus-sourced to *The Embedded Rust Book*, "Typestate Programming" — **UNVERIFIED** in the corpus; and the concept's naming source, Strom & Yemini, IEEE TSE SE-12(1), 1986, is likewise **UNVERIFIED** there). **What Python CAN do:** encode protocol state in the type at each transition boundary — `def connect(self: Closed) -> Open: ...` returning a *different* class, or a PEP 695 phantom parameter `Conn[Open]` — and that is checker-enforced. **What Python CANNOT do:** invalidate the stale handle, because it has no move semantics and no linear types; the pre-transition value remains usable and well-typed. The corrected claim to put in a contract: *"Python can encode protocol state in the type at each transition boundary; it cannot prevent reuse of the pre-transition value."* Enforcement route: type-catchable for the transition, **runtime-guard-only** for the stale handle (raise from the object's own methods once it has transitioned). The architecture-level reason to bother is the corpus's editorial edge `typestate` realizes **Interlock** (BCK 2021) — ordering protection moved to check time.

**Partial mitigations and their limits (ESTABLISHED).** (1) `Literal` and `Enum` close a value domain but express no ordering or interval; a **tagged union** (§2) is the checkable approximation of the discriminated cross-field case, and PEP 728 `closed=True` is what makes `in`-check narrowing across such a union sound — VERSION-DEPENDENT (3.15). (2) `Annotated[int, ...]` carries constraint metadata — via the `annotated-types` library (current v0.8.0, released 23 July 2026, PyPI classifier `Development Status :: 4 - Beta`): `Gt`, `Ge`, `Lt`, `Le`, `Interval`, `MultipleOf`, `MinLen`, `MaxLen`, `Len`, plus `Timezone` and `Predicate`. These are PURE METADATA that static type checkers IGNORE per PEP 593 ("Annotated[T, x] should be treated as T by any tool or library without special logic for x"), and the library performs no checking of its own: "While `annotated-types` avoids runtime checks for performance, users should not construct invalid combinations such as `MultipleOf("non-numeric")` or `Annotated[int, Len(3)]`," and "It is up to the implementer to determine how this metadata is used." `Annotated[int, Gt(0)]` on a stdlib dataclass field or an attrs field therefore enforces **nothing**; the constraint exists only where a runtime consumer (pydantic, msgspec via its own `Meta`) reads it. (3) `NewType` distinguishes representations but adds no validation — pair it with a smart constructor (§2, §5) or it is a naming convention. (4) Refinement-style/verification tools (e.g. CrossHair, which integrates with icontract) explore constraints but are analyzers/test-generators, not part of the type checker, and do not scale to arbitrary code. **Conclusion:** encode these invariants at the boundary (parsing/validation, §5) and as runtime contracts in the core; document them in the contract docstring (§7). Container-level immutability improves slightly on 3.15 — a builtin `frozendict` (PEP 814, listed in the 3.15 release highlights: immutable, hashable, order-independent equality and hash) gives a genuinely immutable mapping, but still not *deep* immutability, and it "is not a `dict` for `isinstance` purposes" (the docs steer you to `isinstance(arg, (dict, frozendict))` or `collections.abc.Mapping`, so validation code gated on `isinstance(x, dict)` starts rejecting valid 3.15 mappings) — VERSION-DEPENDENT (3.15); PEP 814's own status line was not verified this pass (**OPEN** on status, pack-sourced from the 3.15 highlights).

### 5. Runtime contract-enforcement landscape

- **pydantic (boundary validation/parsing). VERSION-DEPENDENT (pydantic 2.13.4).** pydantic validates and coerces external data into typed models at runtime. **v2 is a ground-up rewrite**: the validation core (`pydantic-core`) was rewritten in **Rust**. API/behaviour changes from v1→v2: `class Config` → `model_config` (a `ConfigDict`); `@validator` → `@field_validator`; `@root_validator` → `@model_validator`; `.dict()` → `.model_dump()`, `.json()` → `.model_dump_json()`; `parse_obj` → `model_validate`; `allow_mutation` config → `frozen`. v1 is no longer a live option — it survives only as the vendored `pydantic.v1` compatibility namespace inside v2 (matching 1.10.26 as of pydantic 2.13.0). v2 added `TypeAdapter` for validating non-`BaseModel` types (dataclasses, primitives, `list[SomeModel]`, `TypedDict`), exposing `validate_python()`, `validate_json()`, `dump_python()`, `dump_json()`, `json_schema()` and `rebuild()`; note `TypeAdapter.dump_json()` returns **bytes** while `BaseModel.model_dump_json()` returns **str**. Four validator modes exist (`before`/`after`/`plain`/`wrap`, via `@field_validator(mode=...)` or the `Annotated` pattern `BeforeValidator`/`AfterValidator`): *before* receives raw input of any type ahead of pydantic's own parsing; *after* validators "run after Pydantic's internal validation. They are generally more type safe and thus easier to implement"; *plain* validators "**terminate validation immediately** after returning, so no further validators are called and Pydantic does not do any of its internal validation against the field type"; *wrap* can run code on both sides and can terminate. `@model_validator` supports only `before`/`after`/`wrap` — there is **no** `mode='plain'` for model validators. **Validator order in an `Annotated` stack is asymmetric**: "*before* and *wrap* validators are run from right to left, and *after* validators are then run from left to right" — writing `Annotated[int, BeforeValidator(a), BeforeValidator(b)]` and expecting `a` then `b` is wrong. **When it runs:** at model instantiation/validation (boundary) — and *only* there unless configured otherwise. **Cost:** per-object validation plus a one-time schema build per model/`TypeAdapter`. The schema build is the dominant avoidable cost — pydantic's own guidance is that constructing a `TypeAdapter` "comes with some non-trivial overhead, so it is recommended to create a `TypeAdapter` for a given type just once and reuse it in loops or other performance-critical code," so building one inside a request handler pays full schema analysis per request. Per-object cost is small but not free: msgspec's benchmark (vendor-sourced, self-flagged as biased, CPython 3.11) claims ~12× faster serialise-plus-validate than pydantic 2.5.2 and ~17× faster struct creation (FLAGGED-SECONDARY). Measure your own workload; treat both vendors' numbers as directional. pydantic's own performance guidance: prefer `model_validate_json()` over `model_validate(json.loads(...))` so parsing and validation happen in one pass; prefer concrete `list`/`tuple`/`dict` annotations over `Sequence`/`Mapping`; "Use tagged union, not union"; avoid wrap validators, which "are generally slower than other validators"; apply `FailFast` to sequences to stop at the first bad item. **Where it belongs:** the system boundary (request/response parsing, config, deserialization), NOT hot inner loops.
- **pydantic's own guarantee is one-directional, and its defaults are lax (ESTABLISHED).** "Pydantic guarantees the types and constraints of the output, not the input data" — nothing about the input object survives validation as a claim; only the constructed instance is guaranteed. Six `ConfigDict` defaults silently weaken enforcement, each verbatim from the config reference: `strict` `False` (lax mode "will attempt to coerce values to the desired type when possible", e.g. `'123'` → `int`); `extra` "Defaults to `'ignore'`" (unknown input keys are **dropped, not rejected** — the single most common cause of "my setting had no effect"); `frozen` `False`; `validate_assignment` "Defaults to `False`" (a validated model can be walked into an invalid state one attribute at a time, immediately after a successful parse); `validate_default` "Defaults to `False`" (a field default that violates its own `Field(gt=0)` constraint is never checked, so the bug appears only for callers who omit the field); `revalidate_instances` "The default is `'never'`" (an already-constructed model instance, including a subclass carrying extra state, passed as a nested field skips validation entirely). Also `arbitrary_types_allowed` `False`, `coerce_numbers_to_str` `False`, `defer_build` `False`. And `model_construct()` "Creates models without running validation" — pydantic's own guidance is to use it "only ... with data which has already been validated, or that you definitely trust". It is a deliberate, reachable hole in the parse boundary. **Two more traps that are specific to enforcement.** (a) `assert` inside a validator fails **OPEN**: pydantic builds its `ValidationError` from a `ValueError` or `AssertionError` raised in a validator, and its own docs warn that assert "statements are skipped when Python is run with the -O optimization flag" — so under `-O` no `AssertionError` is raised and **validation PASSES**. Always `raise ValueError(...)` or `PydanticCustomError(error_type, message_template, context)`. Any other exception type raised inside a validator escapes uncaught and never becomes a `ValidationError`. (b) In a `pydantic.dataclasses.dataclass`, `__post_init__()` "will be called between the calls to *before* and *after* model validators" — **not last**, as in stdlib dataclasses — so cross-field invariants placed there can still be invalidated by an after-validator. pydantic dataclasses are also explicitly "**not** a replacement for Pydantic models" (no `validate_python`/`dump_python`/JSON-schema methods; wrap with a `TypeAdapter` instead), and **generic pydantic dataclasses do not validate their parameters**: "Pydantic currently treats `Foo[int]` the same as `Foo[Any]`, without performing validation" — generic `BaseModel`s do not share this limitation. `TypeAdapter(SomeStdlibDataclass).validate_python({...})` is the documented, cheapest retrofit for a codebase already built on stdlib `dataclasses`.
- **dataclasses with `__post_init__` (`dataclasses`; stdlib). ESTABLISHED.** Stdlib `@dataclass` validates nothing: "With two exceptions described below, nothing in `@dataclass` examines the type specified in the variable annotation" — the two exceptions are detecting `typing.ClassVar` and `dataclasses.InitVar`, both structural, neither a value check. `__post_init__` runs after the generated `__init__` and is the canonical place for creation-time validation and derived fields. **When it runs:** at construction — *unless* the dataclass is declared `init=False`, because "If no `__init__()` method is generated, then `__post_init__()` will not automatically be called", so a dataclass built entirely by a classmethod factory silently skips every check placed there. **Cost:** whatever you write. **Where it belongs:** lightweight invariant checks on plain dataclasses when you do not want a pydantic dependency. Caveats: on a `frozen=True` dataclass, assigning derived attributes in `__post_init__` raises `FrozenInstanceError` and you must use `object.__setattr__(self, name, value)` (§6); and mutable-default detection is **hashability-based** since 3.11 — "Instead of looking for and disallowing objects of type `list`, `dict`, or `set`, unhashable objects are now not allowed as default values. Unhashability is used to approximate mutability" — so a custom mutable-but-hashable class sails through and is shared across all instances, while the caught case raises `ValueError` with the exact message `mutable default {type} for field {name} is not allowed: use default_factory` (VERSION-DEPENDENT (3.11)).
- **attrs, cattrs and msgspec — three other shapes of the same job. ESTABLISHED.** `attrs` (`@define`, `@frozen`) offers per-attribute converters and validators, `slots=True` by default (the opposite of stdlib `@dataclass`, so code that monkey-patches an attribute onto an attrs instance fails where it worked on a dataclass), and — uniquely — runs validators on **attribute assignment** as well as in `__init__` under `@define`/`@frozen`: "When using `attrs.define()` or `attrs.frozen`, however, attrs will run the validators even when setting the attribute." Legacy `@attr.s` classes run them only at initialisation, so porting between the decorator families silently changes when checks fire. Per-attribute order is default/factory → **converter** → validators → `__attrs_post_init__`: "Converters are run before validators, so you can use validators to check the final form of the value" — a validator written to reject the raw input form will find the converter has already transformed it. attrs nonetheless disclaims the role: "attrs emphatically does **not** try to be a validation library, but a toolkit to write well-behaved classes like you would write yourself," it never coerces from annotations, and **its validators can be switched off process-wide** by `attrs.validators.set_disabled(True)` or the `with attrs.validators.disabled():` context manager, from anywhere in the process. Never treat an attrs validator as a security or boundary guarantee. `msgspec.Struct` sits at the opposite corner: annotations "are not checked at runtime during normal use. Types are only checked when decoding a serialized message when using a typed decoder" — `Point(x="not a number")` succeeds — but the decode path is **strict by default**: "Unlike some other libraries (e.g. pydantic), `msgspec` won't perform any unsafe implicit conversion by default ("strict" mode)", with `strict=False` available per decode call. Its `__post_init__` runs on decode and convert as well as `__init__`, which is exactly why Struct invariants belong there; constraints are `Annotated[T, msgspec.Meta(...)]` (`gt, ge, lt, le, multiple_of, pattern, min_length, max_length, tz, title, description, examples, extra_json_schema, extra`); `forbid_unknown_fields` defaults to `False`, so unknown input keys are silently discarded on decode; and `msgspec.convert(obj, type, *, strict=True, from_attributes=False, ...)` / `msgspec.json.decode(buf, *, type=..., strict=True, ...)` are the in-memory and one-pass parse entry points. `cattrs` is converter-based structuring for attrs classes and dataclasses that deliberately avoids "polluting your data model with serialization details" and states the principle "validation belongs to the edges"; its detailed-validation mode "is enabled by default", so structuring errors arrive as a **PEP 654 `ExceptionGroup`** (`cattrs.ClassValidationError` / `cattrs.IterableValidationError`) requiring `except*` or `.exceptions` traversal, unless the converter is built with `detailed_validation=False`.
- **Design-by-contract libraries. VERSION-DEPENDENT (icontract 2.7.3, deal 4.24.6).** **icontract** (`@icontract.require` / `@icontract.ensure` / `@icontract.invariant`, each taking `condition`, `description`, `enabled` and `error`; postconditions receive a reserved `result` parameter) provides preconditions, postconditions and class invariants with the most diagnosable violation message of any Python DbC library — `icontract.ViolationError` includes "the human-readable representation of the condition", the description, and a "representation of all the values". It implements the Liskov rules: adding preconditions in a child class **weakens** them ("The caller needs to provide either arguments that satisfy the preconditions associated with the function of the parent class *or* arguments that satisfy the preconditions of the function of the child class"), while postconditions and invariants are strengthened — with the exception that "preconditions and postconditions of base classes are *not* inherited for the `__init__` method". It has a second, orthogonal off-switch: `icontract.SLOW` "reflects the environment variable `ICONTRACT_SLOW`", so `@require(lambda x: expensive(x), enabled=icontract.SLOW)` does not run in any environment where `ICONTRACT_SLOW` is unset. It integrates with CrossHair and Hypothesis (icontract-hypothesis). Maturity, stated from primary metadata rather than a rating badge: icontract 2.7.3 (29 January 2026) declares **no Python floor at all** (`requires_python` is `null`) and its classifiers stop at Python 3.13 — the project does not advertise Python 3.14/PEP 649 support, so verify it against your interpreter before relying on it (**OPEN**; §2a). **deal** (`@deal.pre`, `@deal.post`, `@deal.ensure`, `@deal.inv`, `@deal.example`, `@deal.raises`, `@deal.reason`, `@deal.has`, `@deal.safe`, `@deal.chain`, `@deal.dispatch`, `@deal.pure`) offers DbC plus static analysis, a linter, property-based test generation, and runtime switches. `deal.safe` is "Alias for `@deal.raises()`" and `deal.pure` is "Alias for `@deal.chain(deal.has(), deal.safe)`" — i.e. purity in deal means "no side effects declared and no exceptions raised", enforced at runtime only while contracts are enabled. Its switches are `deal.disable()`, `deal.enable()`, `deal.reset()` (restores the default derived from `__debug__`) and `deal.activate()`; the permanent form is documented with a misspelled keyword, `deal.disable(permament=True)` — guessing `permanent=True` raises `TypeError`. deal emits a `RuntimeWarning` "if you accidentally enable contracts in production or disable them in tests" (suppress with `warn=False`), and even when disabled non-permanently "functions are still get wrapped in case you want to enable contracts again," so a residual per-call cost remains. `deal.ContractError` **inherits from `AssertionError`** (subclasses: `PreContractError`, `PostContractError`, `InvContractError`, `ExampleContractError`, `RaisesContractError`, `ReasonContractError`, `MarkerError` with `SilentContractError`/`OfflineContractError`, and `NoMatchError`), so a blanket `except AssertionError` swallows every deal violation and a `pytest.raises(AssertionError)` test can pass for the wrong reason. deal 4.24.6 declares `>=3.8` and carries no per-version classifiers at all. **When they run:** on each decorated call (runtime) — while enabled. **Cost:** per-call overhead proportional to the predicate. **Where they belong:** core-logic functions whose invariants are non-trivial and worth documenting executably. **The decisive caveat:** the ability to disable contracts in production is the **DEFAULT for both libraries, not an opt-in**. icontract's contracts respect `__debug__` and are disabled entirely under `-O`/`-OO`; deal states "If you run Python with `-O` option, all contracts will be disabled. Under the hood, it's controlled by the `__debug__`". Design-by-contract decorators therefore inherit `assert`'s vanishing problem exactly and **MUST NOT be the enforcement mechanism for any boundary, authorization, or resource check**. They are executable documentation and test-time oracles.
- **Plain `assert` statements. ESTABLISHED — with a critical caveat.** `assert cond, msg` is the cheapest runtime check and compiles to `if __debug__: if not cond: raise AssertionError(msg)`, but `-O` (and `-OO`), or `PYTHONOPTIMIZE`, sets `__debug__=False` and STRIPS all `assert` statements from the compiled bytecode: "The current code generator emits no code for an `assert` statement when optimization is requested at compile time." `-O` is broader than asserts — it removes "assert statements **and any code conditional on the value of `__debug__`**", so an `if __debug__: check_invariants(x)` block vanishes too — and `-OO` additionally discards docstrings, deleting every doctest and every docstring-carried contract (§7). `__debug__` cannot be toggled at runtime: "Assignments to `__debug__` are illegal. The value for the built-in variable is determined when the interpreter starts." Therefore `assert` MUST NEVER be used for data validation, input sanitization, authorization, or any check that must run in production — nor inside a pydantic validator, where its removal turns a failure into a silent pass (see above). Use `assert` only for internal invariants that are acceptable to disable; raise explicit exceptions (`ValueError`, `TypeError`, custom) for anything that must always run. On message design, the assert docs state the rule: "it is unnecessary to include the source code for the expression that failed in the error message; it will be displayed as part of the stack trace" — a message should add what the traceback lacks (values, intent, remediation). **Where it belongs:** developer-facing "this should never happen" guards, never boundary validation. **The full `-O`/`-OO` production audit — what to grep for and what policy to adopt — is owned by `error_tracing_contract_manifest.md`; this file states only which enforcement mechanisms disappear.**

**Decision — boundary vs core placement, and the two names for it.** Parse/validate untrusted data ONCE at the boundary, producing trusted typed objects; then rely on types plus targeted contracts and asserts internally. Never re-validate trusted core data in hot paths, and never lose a boundary invariant by assuming the type system carries it. This is usually called "parse, don't validate" (Alexis King, 2019-11-05), and the essay's actual mechanic is sharper than the slogan: `validateNonEmpty` "always returns `()`, the type that contains no information," whereas `parseNonEmpty` "returns `NonEmpty a`, a refinement of the input type that preserves the knowledge gained in the type system." **A Python parse function must therefore return a NEW type that only the parser can construct** — a frozen dataclass, an `attrs.frozen` class, a msgspec Struct, a pydantic model — never `None`, `bool`, or the same `dict` it received. The antipattern the essay names is **shotgun parsing**: "a programming antipattern whereby parsing and input-validating code is mixed with and spread across processing code — throwing a cloud of checks at the input, and hoping, without any systematic justification, that one or another would catch all the 'bad' cases." Its maxims: make illegal states unrepresentable; push the burden of proof upward; let your datatypes inform your code; be suspicious of functions that return unit.

The slogan has **no name in the design corpus** (a full-text scan of the element set finds zero hits), but its two halves do, and naming them makes the decision citable and composable. Both entries below are ESTABLISHED as *named, cited vocabulary*; the Python spellings are the conventional instantiation and are **OPEN** to project preference:

- **Smart Constructor** (*Smart constructors*, haskell.org wiki, living). "Hiding the raw data constructor makes invalid values unrepresentable to the rest of the program." Python spelling: `@dataclass(frozen=True, slots=True)` whose `__init__` is not public API, fronted by exactly one `@classmethod parse(cls, raw: object) -> Self` that validates and normalises. Library forms: `pydantic.TypeAdapter(T).validate_python`, an attrs field `validator=`/`converter=`. It `specializes` the static-factory-method idea (an editorial edge), and it `composes-with` `newtype` (**sourced**, Haskell wiki) (§2) — which is where the rule "a `NewType` without a smart constructor is a naming convention" comes from.
- **Functional Core, Imperative Shell** (Gary Bernhardt, *Functional Core, Imperative Shell*, Destroy All Software screencast, 2012; corpus aka "impureim sandwich"). A pure module of decision functions that import no clock, no HTTP client and no session, wrapped by a thin edge layer that performs all IO. The corpus records a **sourced** alternative-to edge against `monad` (Mark Seemann, *Impureim sandwich*, ploeh blog, 2020): "Both separate pure logic from effects: an impure/pure/impure boundary vs type-level (IO) monadic sequencing." That is the citable reason Python takes the FCIS branch and drops the monad branch — Python has no do-notation and no higher-kinded types, so monadic effect sequencing here is over-engineering that produces a library nobody reads.

**Apply the forgery test to every parse boundary (decision).** If arbitrary code elsewhere can construct the parsed type *without going through the parser*, the type carries no proof and the boundary is decorative. The named leaks, all confirmed above: `model_construct()` (skips all validation by design), `object.__setattr__` (bypasses a frozen dataclass, §6), plain attribute assignment on a pydantic model with `validate_assignment=False`, `NewType` (a no-op callable), `cast` (returns its argument unchanged, §3), a `msgspec.Struct` constructor (unchecked; only decode/convert validate), and `attrs.validators.set_disabled(True)` anywhere in the process.

#### The four-way boundary-library decision table

VERSION-DEPENDENT (pydantic 2.13.4, attrs 26.1.0, cattrs 26.1.0, msgspec 0.21.1). The load-bearing cells are the counter-intuitive ones.

| | stdlib `dataclasses` | `attrs` (`@define`/`@frozen`) | `pydantic` (`BaseModel`/`TypeAdapter`/`pydantic.dataclasses`) | `msgspec.Struct` | `cattrs` |
|---|---|---|---|---|---|
| validates at construction? | **no** — "nothing in `@dataclass` examines the type specified in the variable annotation" | only what you write in a `validator=`/`converter=` | **yes** — the only one that validates and coerces at construction | **no** — `Point(x="not a number")` succeeds | n/a (structures *into* attrs/dataclasses) |
| validates on attribute assignment? | no | **yes, uniquely** — under `@define`/`@frozen`, not under legacy `@attr.s` | only if `validate_assignment=True` (default `False`) | no (and `frozen=True` blocks assignment outright) | n/a |

**Rules that follow from the table (decision).** (1) **Pick ONE boundary library per project and wrap it behind a project-owned parse function** — a smart constructor — so the choice is reversible and the library's exception types never leak into the caller's API. (2) The three error shapes are structurally different, so a boundary adapter must be written against the chosen one; there is no useful common base to catch. **The mapping from library errors into the project's own taxonomy is owned by `error_tracing_contract_manifest.md`** — including the rule that `loc` is a heterogeneous list (`str` keys, `int` indices) that must not be joined with `"."`. (3) If unknown-key rejection matters — and for configuration it always does — set it explicitly: `ConfigDict(extra='forbid')` or `forbid_unknown_fields=True`. Neither library does it for you. (4) Porting between msgspec and pydantic without setting `strict=`/`ConfigDict(strict=True)` silently changes the acceptance set of the API.

#### Runtime type-checkers are samplers, not validators

VERSION-DEPENDENT (beartype 0.22.9, typeguard 4.6.0). `beartype` and `typeguard` look like they enforce annotations, and both check only a **sample**.

- **beartype is O(1) by design.** Its FAQ: wrapper functions are "guaranteed to unconditionally run in **O(1)** non-amortized worst-case time with negligible constant factors" because beartype performs "a one-way random walk over the expected data structure", doing a shallow isinstance check at each nesting level plus "a **deep type-check** that an item randomly selected from that container itself satisfies the first check". It claims to cover all reachable children "in **O(n log n)** calls" over many calls (vendor-sourced). Its own FAQ quantifies the contrast on a triply-nested list of 1000³ integers: typeguard "~6,420 seconds (107 minutes)" checking every integer versus beartype "~13.8 microseconds" checking one random integer per call — a vendor claim *about a competitor*, so directional only (FLAGGED-SECONDARY).
- **typeguard's default is `FIRST_ITEM`.** `CollectionCheckStrategy` has members `FIRST_ITEM` ("check only the first item") and `ALL_ITEMS`; `TypeCheckConfiguration.collection_check_strategy` defaults to `FIRST_ITEM`, and `check_type(value, expected_type, *, forward_ref_policy=ForwardRefPolicy.WARN, typecheck_fail_callback=None, collection_check_strategy=CollectionCheckStrategy.FIRST_ITEM)`. **A `list[int]` containing one int and nine strings passes both tools' defaults.**
- **Operational hazards.** typeguard raises `TypeCheckError`, not `TypeError`. Its `ForwardRefPolicy` default is `WARN` ("emit a TypeHintWarning if the forward reference lookup fails"), so an unresolvable annotation degrades to a warning and **no check**. `@typechecked` instruments by rewriting source — it "instruments functions by fetching the source code, parsing it to an abstract syntax tree using `ast.parse()`, modifying it to add type checking, and finally compiling the modified AST into byte code" — with two documented limitations: it "is not reliable when used in nested functions", and "You should always place this decorator closest to the original function, as it will not work when there is another decorator wrapping the function". `install_import_hook()` does the same at import time. beartype 0.22.9 additionally fails at **decoration** time on 3.14 self-referential annotations (§2a).
- **Where they belong (decision).** Development-time defect detectors and API-contract smoke tests — enable them in tests and in development runs, and treat a failure as a real bug. They are **not** boundary validators and never replace a parse step. Do not enable them as the production enforcement mechanism for a boundary invariant, and do not report their passing as evidence a container is well-typed.

#### Which channel does failure or variance leave a function through?

The default assumption in a manifest like this one is "raise, plus a `Raises:` docstring section". The design corpus supplies a named five-way decision space instead. Each entry below is ESTABLISHED as named, cited vocabulary; the tactic edges that relate them are editorial. The useful point is that these are **positions on one spectrum**, not rival religions — `result-type` carries an editorial `realizes` edge to the same **Exception Handling** tactic (BCK 2021), placing it at "the typed evolution of the tactic's return-code end of the handling-mechanism range."

- **Result type** (naming source: N. Douglas, WG21 *P1028: SG14 status_code and standard error object*, 2020, R3; corpus aka `expected`, `outcome`, "error union"). Python spelling: `@dataclass(frozen=True, slots=True) class Ok[T]` / `class Err[E]` with `type Result[T, E] = Ok[T] | Err[E]` (PEP 695), consumed by `match` with a final `case _ as x: assert_never(x)` so the checker proves exhaustiveness. Library: `returns.result`.
- **Option type** — `T | None` / `Optional[T]`, which the corpus records (editorially) as a *specialization* of `tagged-union` (the two-case sum). The corpus's editorial distinction against Result: "Result carries an error value where Option only signals presence/absence with no reason." (Provenance caveat carried forward: the corpus's `named_in` for `option-type` is the Haskell 98 Report, which has **no** corpus work record; the backing works are Hutton's Haskell text and *The Rust Programming Language*.)
- **Notification** (*Notification* — Martin Fowler, eaaDev, living). Accumulate **all** failures and return them together rather than short-circuiting on the first. **This is exactly what `pydantic.ValidationError.errors()` returns**, and naming it lets the manifest state the rule it otherwise cannot express: **boundary validation uses Notification semantics (accumulate); core logic uses Result or exceptions (short-circuit).** The stdlib form is a `list[Problem]` returned from a validator instead of raising.
- **Railway-Oriented Programming** (Scott Wlaschin, *Railway Oriented Programming*, 2014, fsharpforfunandprofit.com / NDC) — defined as composition over Results, so do not present it as a separate idea. Python spelling: a `bind(f, r)` helper folded over a list of Result-returning steps, `returns.pipeline.flow(...).bind(...)`, or in plain stdlib an early-return `for step in steps:` loop that short-circuits on the first `Err`.
- **Raise** — the default, and the right default for genuinely exceptional outcomes.

**Threshold, not preference (decision).** Use a typed in-band channel (`Result`/`Option`) when the failure is an expected, enumerable outcome of the contract that most callers must handle; raise when the outcome is exceptional and most callers cannot do anything locally. Use Notification when a caller needs *all* the problems at once (form and config validation). **The propagation contract, the exception taxonomy, and the `Raises:` obligation are owned by `error_tracing_contract_manifest.md`; this file states only what the type system can carry about the channel** — namely that a discriminated union is statically exhaustively checkable and a raised exception is not.

### 6. Immutability and purity signalling

The pattern this section teaches is named **Immutable Value** — ESTABLISHED as named, cited vocabulary (*POSA Vol. 4: A Pattern Language for Distributed Computing* — Buschmann, Henney & Schmidt, 2007) — and the catalog's problem statement is the sentence that makes the whole section actionable: *"Shared mutable values require defensive copies or synchronization; immutability makes sharing safe by construction."* That is also why this section is a **prerequisite** for `python_concurrency_determinism_manifest.md` rather than a separate topic — the corpus records `immutable-value` as *enabling* the Introduce-Concurrency tactic (BCK 2021) — an editorial edge, alongside three others (`value-semantics`, `copied-value`, `safe-publication`) reaching the same tactic.

**The decision rule, in order (decision).** Do not stop at `frozen=True`; it is only step one of three.

1. **Make the value immutable by construction.** `@dataclass(frozen=True, slots=True)` (or `attrs.frozen`, or a `frozen=True` msgspec Struct) with field types that are themselves immutable: `tuple`, `frozenset`, `str`, `bytes`, numbers, and on 3.15 the builtin `frozendict` (§4). Annotating a field `Mapping[str, int]` is a *static* promise the callee will not mutate, not a runtime guarantee — the object may still be a `dict`.
2. **If a field must hold a collection supplied by a caller, copy it at the boundary.** The named mechanism is **Defensive Copy** (*Effective Java*, 3rd ed. — Joshua Bloch, 2018, Item 50), and the corpus records a **sourced** tradeoff edge against Immutable Value: *"Both stop external aliases mutating internal state; immutability removes the need, else copy defensively."* Python spelling: `tuple(items)` / `dict(mapping)` / `frozenset(...)` in `__post_init__` (via `object.__setattr__` when frozen), `copy.deepcopy` at genuine trust boundaries, and returning `types.MappingProxyType(self._d)` from an accessor so callers cannot mutate the internal mapping.
3. **If the state is large and shared, use a persistent structure instead of copying.** The named mechanism is **Persistent Data Structure** (which the corpus records as *using* `immutable-value`, **sourced** to Okasaki); its carrying work is Chris Okasaki, *Purely Functional Data Structures*, 1998, Cambridge UP, doi:10.1017/CBO9780511530104 (the usual naming citation, Driscoll/Sarnak/Sleator/Tarjan 1989, has **no** corpus work record — carry that gap forward rather than inventing the citation). Python spelling: `pyrsistent.PMap`/`PVector`, or `immutables.Map` — the HAMT (Bagwell, *Ideal Hash Trees*, 2001) that **CPython's own `contextvars` is implemented on**. This is the branch to take when copying per update is the cost you are trying to avoid.

**The four frozen mechanisms are all SHALLOW, and each fails differently (ESTABLISHED).** None of stdlib `frozen=True`, `attrs.frozen`, pydantic `frozen=True`, or msgspec `frozen=True` is deep: all four block rebinding the attribute; none freezes the referenced object. The CPython docs are explicit at the top of the frozen-instances section: **"It is not possible to create truly immutable Python objects."**

| mechanism | what it raises on assignment | notes |
|---|---|---|
| stdlib `@dataclass(frozen=True)` | `FrozenInstanceError`, which is "a subclass of `AttributeError`" | generated `__setattr__`/`__delattr__` |
| `attrs.frozen` | `FrozenInstanceError` | `attrs.frozen` "Behaves the same as `attrs.define` but sets *frozen=True* and *on_setattr=None*" |
| pydantic `frozen=True` | the `ValidationError` family on assignment | pydantic calls it "faux-immutable": it controls "whether `__setattr__` is allowed, and also generates a `__hash__()` method for the model" |
| `msgspec.Struct(frozen=True)` | plain `AttributeError` — message form `AttributeError: immutable type: 'Point'` — **not** `FrozenInstanceError` | "disables modifying attributes after initialization, and adds a `__hash__` method to the class definition" |

**The bypasses, named explicitly (ESTABLISHED).** State these in any contract that claims immutability; the corpus name for the deliberate, bounded version of the first one is **Interior Mutability** (*The Rust Programming Language* — Klabnik & Nichols, living, "RefCell<T> and the Interior Mutability Pattern"), recorded with an editorial `alternative-to` edge against `immutable-value`: *"Given a shared reference, keep the value truly immutable or allow controlled runtime-checked mutation."* Treat it exactly as this file treats `cast` and `# type: ignore` — a bounded, commented, deliberate escape hatch, never an accident.

1. **`object.__setattr__(inst, name, value)` bypasses the freeze completely** — and it is not exotic: it is the documented mechanism the generated frozen `__init__` itself uses, because "`__init__()` cannot use simple assignment to initialize fields, and must use `object.__setattr__()`". It is also the *required* technique for setting derived attributes in `__post_init__` on a frozen dataclass. The same call is therefore both the sanctioned tool and the hole; say which use is which.
2. **Mutable field contents.** A frozen dataclass holding a `list` still permits mutation of that list's contents. Fix with step 1 or step 2 of the decision rule above.
3. **`init=False` skips `__post_init__` entirely.** "If no `__init__()` method is generated, then `__post_init__()` will not automatically be called" — so every defensive copy and every invariant check placed there is silently skipped for objects built by a classmethod factory.
4. **`eq=False` silently restores id-based hashing.** The truth table, verbatim: "If *eq* and *frozen* are both true, by default `@dataclass` will generate a `__hash__()` method for you. If *eq* is true and *frozen* is false, `__hash__()` will be set to `None`, marking it unhashable... If *eq* is false, `__hash__()` will be left untouched meaning the `__hash__()` method of the superclass will be used" — the last branch gives a value object identity semantics, which is exactly the bug the value object was meant to prevent. Only `eq=True, frozen=True` yields a value-based `__hash__`.
5. **Frozen-ness cannot be mixed in a dataclass hierarchy.** CPython 3.14's `dataclasses.py` raises `TypeError` with exactly these messages: "cannot inherit non-frozen dataclass from a frozen one" and "cannot inherit frozen dataclass from a non-frozen one" (confirmed in the 3.14 source; the prose docs do not state this rule). A common failure when wrapping a third-party frozen dataclass. Relatedly, defining `__setattr__` or `__delattr__` on a class you also decorate `@dataclass(frozen=True)` raises `TypeError`.

**How do you update a nested frozen record? `dataclasses.replace` (decision).** This is the question a frozen-by-default codebase hits on day two, and the answer is a named pattern: **Lens** (Foster, Greenwald, Moore, Pierce & Schmitt, *Combinators for Bi-Directional Tree Transformations: A Linguistic Approach to the View Update Problem*, ACM TOPLAS 29(3), 2007 — the corpus record omits the DOI). Python has no idiomatic optics library, so **import the name and the problem, not the machinery**: the problem is that "each level otherwise requires manual copy-and-replace code", and the transposable core is `dataclasses.replace(outer, inner=replace(outer.inner, field=value))`, wrapped in small named `with_*` helpers (`def with_retries(cfg: Config, n: int) -> Config: return replace(cfg, http=replace(cfg.http, retries=n))`). The pydantic equivalent is `BaseModel.model_copy(update=...)`, which is **shallow** — it does not recurse into nested models. The corpus also records (editorially) `lens` as composing with `persistent-data-structure` and as an alternative to `zipper`; at this scale, named `with_*` helpers over `replace` are the right depth and a lens library is over-engineering.

- **`Final` (PEP 591; ESTABLISHED).** Signals "do not reassign/override" to the checker only — "There is no runtime checking of these properties." It prevents rebinding the name, never mutation of the referenced object. Assigning over a `Final` name succeeds at runtime; subclassing a `@final` class succeeds at runtime. (`Final` became nestable inside `ClassVar` and vice versa in 3.13 — VERSION-DEPENDENT (3.13).)
- **Read-only containers (ESTABLISHED).** `Mapping`/`Sequence` (abstract, read-only interfaces) vs `MutableMapping`/`MutableSequence`; `tuple` and `frozenset` are genuinely immutable at the container level (but their elements may be mutable). Annotating a parameter as `Mapping[str, int]` tells the checker the callee will not mutate it — a *static* promise, not a runtime guarantee. Note the performance caution from the other direction: pydantic's guidance prefers concrete `list`/`dict` annotations over `Sequence`/`Mapping` at validated boundaries, because abstract types force extra isinstance checks and multiple validation attempts. Read-only *interface* inside the core; concrete type at the parse boundary.
- **`@property` without a setter (ESTABLISHED).** Exposes a read-only computed attribute; assignment raises `AttributeError` at runtime. Communicates "derived, not settable."
- **What the type system can and cannot guarantee (principle).** Checkers can enforce that *your code* does not reassign a `Final` name or mutate a `Mapping`-typed parameter, and `frozen`/`tuple`/`frozenset`/`frozendict` give runtime shallow immutability. The type system CANNOT guarantee deep immutability, nor side-effect freedom / purity — there is no `pure`/`const` qualifier in Python's type system. A purity claim (e.g. `@deal.pure`, itself an alias for `@deal.chain(deal.has(), deal.safe)`) is runtime-checked by a DbC library **only while contracts are enabled**, and contracts are disabled under `-O` by default (§5) — so in a production image built with `-O` a purity claim is convention-only. State the gap explicitly in contracts: distinguish "checker-enforced immutability" (limited, shallow), "runtime shallow immutability" (frozen, bypassable), and "convention-only purity" (documented, unverified).

### 7. Contract documentation conventions

**What belongs in the type signature vs. the docstring (decision).** The type signature carries everything the checker can verify: parameter/return types, `Optional`/union shape, generics, `Literal`/`Enum` domains, `Final`/`Self`, and `Protocol` conformance. The docstring carries everything the type system CANNOT express (see §4): **preconditions** (value ranges, non-emptiness, cross-argument relations), **postconditions** (guarantees about the return value, invariants preserved), **invariants** (object-state properties), and **error modes** (which exceptions are raised and under what conditions). Rule: if a checker can enforce it, put it in the signature; if only a human or a runtime check can enforce it, put it in the docstring (and back it with a runtime contract where it matters).

**Common docstring conventions (ESTABLISHED).** Three dominant machine-parseable styles, all supported by Sphinx (the latter two via the `sphinx.ext.napoleon` preprocessor):
- **Google style** — indented `Args:`, `Returns:`, `Raises:`, `Yields:` sections; highly readable.
- **NumPy style** — underlined `Parameters`/`Returns`/`Raises` headers with name-type-description blocks; verbose, favored in scientific code.
- **reStructuredText / Sphinx ("classic")** — `:param x:`, `:type x:`, `:returns:`, `:rtype:`, `:raises:` field lists; the reST style is the one referenced by PEP 287. PEP 257 defines the baseline docstring conventions (one-line summary, etc.).

Pick ONE style per project and enforce consistency; `Raises:`/`:raises:` is the canonical place to document error modes.

**`Raises:` versus a typed failure channel (decision).** `Raises:` is the right documentation slot only for outcomes that leave the function as exceptions. If the failure is an in-band typed channel — a `Result`/`Ok`/`Err` union, an `Option`, or a Notification list (§5) — then the *return type* already carries the failure and the docstring must document the **variants and what each means**, not invent a `Raises:` entry for something that never raises. Getting this wrong produces the worst of both: a `Raises:` section a caller writes a `try` around, and a returned `Err` nobody handles. Two obligations follow: state the channel explicitly in the docstring's first line for any function that can fail, and if the union is discriminated, the exhaustiveness guard (`assert_never`, §2) is what makes "all variants documented" mechanically checkable rather than a claim. The propagation contract itself — which outcomes are exceptional, and the project's exception taxonomy — is owned by `error_tracing_contract_manifest.md`.

**Machine-checkable forms (ESTABLISHED).** (1) **doctest** — executable examples in docstrings (`>>> ...`) run by `python -m doctest`/pytest, keeping examples provably correct. (2) **icontract decorators** — `@require`/`@ensure`/`@invariant` make pre/postconditions executable and renderable into docs, so the contract and its documentation cannot drift. (3) **deal decorators** similarly. (4) **Type comments** (`# type:` / function `# type: (...) -> ...`) are the legacy pre-3.0-annotation form, still parsed by mypy but only partially by pyright ("only in locations where there is a way to provide an annotation using modern syntax") and flagged by pyright strict's `reportTypeCommentUsage`; avoid in new code. The strongest contract documentation pairs a typed signature, a styled docstring (Google/NumPy/reST) with explicit `Raises`, and an executable contract (doctest or icontract/deal) for the invariants the type system cannot carry. **Two limits to state honestly.** (a) `-OO` "discard[s] docstrings", which deletes every doctest and every docstring-carried contract from the running image, and `-O` disables all icontract and deal contracts — so the documentation layer and the runtime-contract layer vanish together under optimisation (the production audit lives in `error_tracing_contract_manifest.md`). (b) Nothing mechanically enforces that a docstring's stated precondition matches the code: docstring *style* consistency is lint-catchable (rule selection is owned by `python_linting_practices_manifest.md`), and *content* correctness is enforced only by doctest, a DbC decorator, or a test. Where the precondition is load-bearing, back it with one of those three or admit in the docstring that it is unverified.

### 8. Open questions and version caveats

**VERSION-DEPENDENT items (pin the version in any contract spec; release dates live in `python_platform_baseline_manifest.md`):**
- `mypy --strict`'s exact flag set changes between releases: **13 flags as of mypy 2.3**, down from 15 at 1.19 (`--warn-unused-configs` and `--strict-bytes` left the set). `--strict-bytes` and `--local-partial-types` became global defaults in mypy 2.0, `--allow-redefinition` changed meaning, and `--ignore-missing-imports` became universally respected — so migrating 1.x → 2.x both adds and removes errors.
- pyright's per-mode diagnostic-rule table changes between releases; the authoritative source is the version-matched `docs/configuration.md` (currently 91 rows). The CLI/config default mode is `standard`; Pylance's default is `off`. pyright has **no** default `pythonVersion` or `pythonPlatform` — it uses the ambient interpreter, so both must be pinned for reproducible CI.
- ty 0.0.69 states that "breaking changes, including changes to diagnostics, may occur between any two versions" — an unpinned `uvx ty check` can change its verdict between two runs on unchanged code. pyrefly permits breaking diagnostic changes across minor versions and recommends `pyrefly suppress` on upgrade. Pin both to an exact patch version or do not gate on them.
- pydantic is at 2.13.4; v1 exists only as the vendored `pydantic.v1` namespace inside v2 (matching 1.10.26 as of 2.13.0). Its `docs.pydantic.dev/latest/...` URLs now **301-redirect** to `pydantic.dev/docs/validation/latest/...`; version-pinned paths still resolve. A tool that treats a non-200 as a dead link will report pydantic's documentation as missing.
- `assert_type`, `reveal_type` (as a runtime function), and `Never` all entered `typing` in Python 3.11.
- TypedDict feature set is release-bound: `Required`/`NotRequired` (3.11), `ReadOnly` (3.13), closed / typed-extra-items (PEP 728, **landed in 3.15**; `closed` implemented in mypy from 2.2). The keyword-argument creation form was deprecated in 3.11 and removed in 3.13, and 3.15 removes the fieldless / `None` functional syntax along with `typing.no_type_check_decorator` and the undocumented `typing.NamedTuple` keyword syntax.
- PEP 695 native generic syntax requires Python 3.12+. PEP 649 and PEP 749 (both **Final**, 3.14) make deferred annotation evaluation the default in 3.14, so quoted forward references become unnecessary; `from __future__ import annotations` is **deprecated** with behaviour **unchanged**, and its removal "will not happen until after Python 3.13 reaches its end of life in 2029"; PEP 563 is formally **Superseded**. The two models are mutually exclusive — with the `__future__` import present, annotations are still stored as strings and PEP 649's lazy model does not apply, so leaving the import in place on 3.14 forfeits the feature. Introspection goes through `annotationlib` (added 3.14) with `Format.VALUE = 1`, `VALUE_WITH_FAKE_GLOBALS = 2` (internal only), `FORWARDREF = 3`, `STRING = 4` (§2a).
- 3.15 typing surface, all **Final** for 3.15: PEP 728 (`closed=`/`extra_items=`), PEP 747 (`typing.TypeForm`), PEP 800 (`@typing.disjoint_base`), PEP 661 (builtin `sentinel`). `typing_extensions` 4.16.0 backports them and renamed `Sentinel` → `sentinel` (old name soft-deprecated; default repr changed from `<X>` to `X`).
- `annotated-types` is at 0.8.0 (`Development Status :: 4 - Beta`) and performs no runtime checking of its own; `beartype` 0.22.9 predates the fix for its 3.14 forward-reference failure; `typeguard` 4.6.0 dropped 3.9 and fixed 3.15 compatibility; `icontract` 2.7.3 advertises no 3.14 support and declares no Python floor; `deal` 4.24.6 carries no per-version classifiers.

**OPEN items (no single authoritative source resolves these — each is a decision the project must record; cross-reference `software_spec_discipline_manifest.md` §G5):**
- **Which single checker is the release gate, and which are advisory?** There is no authoritative cross-conformance matrix, and PEP 729 establishes that none can exist: agreement is not required of implementations. Decide, pin, and write down why the others are not gates (§1). A mandate of "must pass both mypy --strict and pyright --strict" is a standing, unresolvable disagreement generator.
- **What is the project's `Any` budget, and in whose vocabulary?** mypy tracks one `Any` (`--any-exprs-report`, `--disallow-any-explicit`); pyright and ty split implicit `Unknown` from explicit `Any` (`reportUnknown*`). There is no rule-name mapping between the families, so a budget expressed in one does not transfer (§3).
- **What is the suppression policy — coded ignores required, and who reports the stale ones?** Coded suppressions are not required by default anywhere (mypy `ignore-without-code` is opt-in; ty `blanket-ignore-comment` defaults to off), and pyright strict does not report unused ignores while mypy strict does (§3a). Pick the config; the ratchet itself belongs to `python_quality_gates_manifest.md`.
- **Which ONE boundary library, and is it wrapped behind a project-owned parse function?** The three live options raise structurally different errors, and swapping them is a breaking API change unless the boundary is wrapped (§5).
- **Is `-O`/`-OO` ever used in a production image?** If yes, every `assert`, every `if __debug__:` block, every doctest, every icontract/deal contract, and every `assert` inside a validator changes behaviour — and the pydantic case fails *open*. The audit belongs to `error_tracing_contract_manifest.md`; the decision belongs to the project.
- **When is `from __future__ import annotations` removed from this codebase?** The trigger is dropping 3.13 support, but only after auditing every dependency that reads `__annotations__` (§2a). Until then, record which of the three annotation models each module assumes.
- **Maturity judgements that remain unresolved.** `zuban` 0.9.1 ships `Development Status :: 1 - Planning` against a 0.9.x version number — classifier and version disagree, so its maturity is unresolved. Whether `icontract` and `deal` work on 3.14/PEP 649 was not determined. The maintainer's release timeline for the beartype 3.14 fix is unknown. PEP 814's own status line was not verified this pass (only its appearance in the 3.15 highlights). Any conformance figure not present in `python/typing`'s `results.html` is a vendor claim.
- **"design-by-contract"** (the minimalist `Annotated`-based package on PyPI, distinct from icontract/deal) is explicitly marked by its author as not production-ready; treat as experimental (OPEN maturity).

## Recommendations

**Stage 1 — Pin the toolchain and name ONE gate (do first).** Commit a `pyproject.toml` that pins exact versions of the checkers in use — e.g. mypy 2.3.x and pyright 1.1.411 — the target `python_version` **and** `pythonPlatform` (pyright defaults both to the ambient interpreter, making unpinned CI non-reproducible), and the full enabled-rule set for each. Designate exactly one checker as the release gate and record why the others are advisory (§1). If pyrefly (1.2.x) or ty (0.0.69) is adopted, pin to an exact patch version: pyrefly permits breaking diagnostic changes across minor versions and recommends `pyrefly suppress` on upgrade, and ty's own policy states "breaking changes, including changes to diagnostics, may occur between any two versions." Do NOT write "use strict mode" in any spec; write the literal flag/rule lists. *Benchmark that changes this:* a checker major-version bump (mypy 1.x→2.x changed defaults in both directions) requires re-baselining and a fresh review of the enabled set.

**Stage 2 — Define the boundary, and give it a smart constructor.** Choose ONE boundary library (§5 decision table) and mandate it for ALL untrusted inputs — HTTP bodies, config, env, deserialized data — converting them to typed objects at the edge. Front it with a project-owned `parse` classmethod that returns a distinct type the caller could not have forged, so the library is replaceable and its exception types never leak (Smart Constructor; Functional Core, Imperative Shell). Set the enforcement-relevant defaults explicitly rather than inheriting them: `extra='forbid'` / `forbid_unknown_fields=True`, `strict=True` where the API contract is strict, and `validate_assignment=True` if models are mutated after construction. Forbid `assert` for any validation — and specifically inside any validator, where `-O` turns it into a silent pass — and require explicit exceptions or `PydanticCustomError`. *Threshold:* if a value can originate outside the process, it is boundary data and must be parsed, not assumed.

**Stage 3 — Encode the inexpressible, using the named mechanism rather than the nearest one.** For every value-range, cross-field, ordering, unit, or stateful invariant (§4), require either a boundary validator, an icontract/deal contract, or a `__post_init__` check, AND a docstring precondition/postcondition/`Raises:` entry. Prefer the mechanism the literature ranks first: a **tagged union** for discriminated cross-field cases (not a bag of optional fields); a **quantity value object** (`pint`/`astropy.units`/a `Measure` dataclass) for units, with `NewType` only as the zero-dependency fallback; a **phantom type** or transition-returning method for protocol state, plus a runtime guard for the stale handle Python cannot invalidate. *Threshold:* any invariant the checker cannot verify must appear in BOTH a runtime check and the docstring — and if the runtime check is a DbC decorator, it must not be the only thing standing between the system and a boundary violation, because it is disabled under `-O`.

**Stage 4 — Confine escape hatches, and make the stale ones visible.** Treat every `cast`, `# type: ignore`, and `Any` as tracked debt: smallest scope, mandatory justifying comment, coded suppression (`# type: ignore[arg-type]`), and the per-checker config that actually reports staleness (§3a) — `--warn-redundant-casts` and `--warn-unused-ignores` come free in `mypy --strict`, but `reportUnnecessaryTypeIgnoreComment` and `ignore-without-code` must be turned on by name. *Threshold:* a rising count of casts/ignores/`Any` in the report is a signal to refactor structurally rather than suppress. The CI ratchet that drives the count down belongs to `python_quality_gates_manifest.md` — wire it there, not here.

**Stage 5 — Standardize documentation.** Choose one docstring style (Google/NumPy/reST) project-wide, require `Raises` on every public function, and back critical examples with doctest. *Threshold:* mixed styles in one project are a spec violation; fix before merge.

**Stage 6 — Decide the annotation model, then audit for it.** Record which of the three annotation execution models each package assumes (§2a), ban `from __future__ import annotations` in new 3.14+ code, and add an import-every-module smoke test on the target interpreter — because nothing mechanical catches a library that reads `__annotations__` eagerly. *Threshold:* before dropping 3.13 support and removing the `__future__` import, every dependency that introspects annotations must be verified on the target interpreter; today that list includes pydantic (still resolves eagerly, falls back to `model_rebuild()`), beartype (0.22.9 fails at decoration on 3.14 self-references), icontract and deal (no 3.14 claim in their metadata).

## Anti-patterns (rejection list)

One line each; each names the section it violates. This is the part an agent should obey literally.

- Writing "the project uses strict typing" in a spec without naming the checker, its exact version, and the enabled-rule set — violates §1.
- Mandating that code pass both `mypy --strict` and `pyright --strict` and treating disagreements as bugs to be fixed — violates §1: PEP 729 removes any authority that could resolve them.
- Reproducing the 15-flag `mypy --strict` list, or assuming `--strict` implies `--warn-unused-configs`, `--strict-bytes`, `--warn-unreachable`, or "no `Any`" — violates §1.
- Assuming `--strict` is a floor and adding `--no-warn-return-any` after it — violates §1: strict does not take precedence, in any argument order.
- Omitting `pythonVersion`/`pythonPlatform` from `pyrightconfig.json` — violates §1: the verdict then depends on the CI runner image.
- Emitting `reportAny` / `reportExplicitAny` / `reportIgnoreCommentWithoutRule` into a pyright config — violates §1: those are basedpyright rules, absent from upstream pyright.
- Passing mypy or pyright flags (`--check-untyped-defs`, `strictListInference`) to ty — violates §1: ty has no strict mode and rejects them.
- Treating a green default `pyrefly` run, or a green default `mypy` run over unannotated code, as evidence of type safety — violates §1: pyrefly defaults to the `basic` preset on a config-less project, and mypy skips unannotated bodies.
- Ranking checkers for a project on conformance percentage, or quoting a score against a version the suite did not test — violates §1.
- Using a bare `# type: ignore` with no code and no comment, or relying on a default configuration to report stale suppressions — violates §3a.
- Building a suppression ratchet, CI wiring, or metrics in this file's terms — violates §3a: that is `python_quality_gates_manifest.md`.
- Using `typing.cast` to make a type error go away, or `assert_type` as a runtime assertion — violates §3: both are inert at runtime, and `assert_type` checks equivalence, not assignability.
- Claiming `Final`, `@final`, `@override`, `NewType`, `TypeForm(x)`, `@disjoint_base`, `TypedDict`, `Literal` or `Annotated` add runtime safety — violates §4: they are checker-only or metadata-only and will never raise.
- Putting `Annotated[int, Gt(0)]` on a stdlib dataclass or attrs field and calling the constraint enforced — violates §4: `annotated-types` performs no checks; only a consumer like pydantic acts on the metadata.
- Recommending `NewType` as the answer to units of measure — violates §4: the ranked answer in Python is a quantity value object; `NewType` is the fallback.
- Declaring typestate impossible, or claiming Python can prevent reuse of a pre-transition handle — violates §4: the transition is encodable, the stale handle is not.
- Using `assert` for validation, authorization, or sanitization — violates §5; using it inside a pydantic validator is worse, because under `-O` validation silently PASSES.
- Using `@deal.pre` / `@icontract.require` as the enforcement mechanism for a boundary or authorization check — violates §5: both are disabled under `-O` by default.
- Emitting `deal.disable(permanent=True)` — violates §5: the documented keyword is misspelled `permament`.
- Calling `model_construct()` as a performance fix on untrusted data — violates §5: it skips all validation by design and deletes the boundary.
- Constructing a `TypeAdapter` inside a request handler or loop — violates §5: schema analysis is a non-trivial per-construction cost, so hoist it to module scope.
- Shipping a pydantic model with default `extra='ignore'` for configuration — violates §5: a typo'd key is silently dropped rather than reported.
- Treating a `msgspec.Struct` constructor as validating, or porting between msgspec and pydantic without setting `strict=` — violates §5: msgspec validates only on decode/convert and is strict by default where pydantic is lax.
- Relying on an `attrs` validator as a boundary or security guarantee — violates §5: `attrs.validators.set_disabled(True)` disables them process-wide from anywhere.
- Reporting a passing `@beartype` or `@typechecked` run as evidence a container is well-typed — violates §5: both check a sample (one random item / the first item).
- Placing a cross-field invariant in `__post_init__` of a **pydantic** dataclass and assuming it runs last — violates §5: it runs between the before- and after-model validators.
- Describing `frozen=True` as immutability, or as deep — violates §6: all four frozen mechanisms are shallow, and `object.__setattr__` is the documented bypass the generated `__init__` itself uses.
- Putting a defensive copy or invariant check in `__post_init__` of a dataclass declared `init=False` — violates §6: `__post_init__` is never called.
- Setting `eq=False` on a value object and expecting value-based hashing — violates §6: `__hash__` falls back to the superclass's id-based hash.
- Hand-rolling nested-record updates with manual copy-and-replace, or reaching for an optics library — violates §6: use `dataclasses.replace` behind named `with_*` helpers.
- Adding `from __future__ import annotations` to a 3.14+ file "to be safe" — violates §2a: it disables PEP 649 and double-quotes explicit string annotations.
- Reading `obj.__annotations__` directly, citing `Format.SOURCE`, or assuming `Format` is a contiguous 1/2/3 enum — violates §2a.
- Emitting inline `TypedDict` literals, call-site generic subscription (`f[int](...)`), or any other Draft-PEP syntax — violates §2: PEPs 718, 746, 764, 767, 781, 821, 827 and 835 are Draft and available in no released Python.
- Importing `deprecated` from `typing` — violates §2: it comes from `warnings`.
- Writing `typing.Sentinel(...)`, or creating a sentinel twice with the same name and comparing by identity — violates §2: `sentinel` is a builtin in 3.15 and two calls return distinct objects.
- Choosing `TypeGuard` when both branches must narrow — violates §2: use `TypeIs`; the wrong choice produces no diagnostic at all.
- Relying on a default checker configuration to report a non-exhaustive `match` — violates §2: mypy's `exhaustive-match` is opt-in and pyright's `reportMatchNotExhaustive` is strict-only; use `assert_never` as the portable guard.

## Caveats

- **"Current" is release-bound.** Every flag list, default, rule count and version statement here reflects the toolchain versions named in the header, verified 8 August 2026; re-verify against the version-matched docs at each toolchain bump. The mypy `--strict` flag set, the pyright per-mode rule table, the ty rule list, and the pyrefly preset definitions are all explicitly documented by their maintainers as subject to change between releases — and ty and pyrefly say so between *adjacent* releases.
- **Release dates, support phases and PEP-status-by-version are not owned here.** They live in `python_platform_baseline_manifest.md`. If a version fact in this file appears to disagree with the hub, the hub wins and this file is stale.
- **Two commonly repeated PEP attributions are wrong, and are corrected here:** `assert_type` is NOT introduced by PEP 675 (PEP 675 is `LiteralString`; `assert_type` has no dedicated PEP and landed in Python 3.11); and `Never` is NOT tied to PEP 661 (PEP 661 is "Sentinel Values", Final for 3.15; `Never` has no PEP). A third: mypy's own 2.2 changelog calls `TypeForm` "introduced in Python 3.14", but PEP 747 and the 3.15 typing docs say 3.15 — the primary docs win.
- **Runtime tools enforce; the type system documents.** Static checkers verify shape, not values, history, or purity. Any claim that "strict typing guarantees correctness" is false: the type system cannot carry §4 invariants, `cast`/`Final`/`Annotated`/`@override` are checker-or-metadata-only, `assert` vanishes under `-O`, DbC decorators vanish with it, and runtime type-checkers sample rather than validate.
- **Cross-checker conformance is not merely empirical — it is not required.** There is no authoritative matrix mapping `mypy --strict` clean ⇒ `pyright --strict` clean, and PEP 729 establishes that no body has the authority to create one. Pick one gate.
- **Some claims rest on vendor or secondary evidence and are tagged FLAGGED-SECONDARY where they appear:** every speed multiplier in this file (pydantic's 5–50×, msgspec's 12×/17×, ty's 10–100×, mypy's 5×, pyrefly's 34%/125×) is a first-party publication, several measured against stale competitor versions on unstated hardware; msgspec itself states "it's hard to write a nonbiased benchmark. I wrote msgspec, naturally whatever benchmark I publish it's going to perform well in." Benchmark on the target repository before any of these figures shapes a decision. Maturity is reported from PyPI classifiers and each project's own words rather than from third-party health ratings.
- **One documented source inconsistency, carried forward:** the `typing_extensions` CHANGELOG heads its 4.16.0 entry "July 2, 2025", which is a year typo; the PyPI upload record (2 July 2026) and the adjacent rc2 entry (25 June 2026) establish the correct year. Resolved in favour of the PyPI record.
