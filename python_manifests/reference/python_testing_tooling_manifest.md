**Scope.** Ground truth for a specification team defining TEST OBLIGATIONS and an integration-test strategy for small-to-mid-scale, strictly-typed, single-process Python applications. This file is **GROUNDING, not a rulebook**: cite a rule where it materially shapes a decision, and reason past it where the situation does not match. An untagged factual claim is a defect. **Version anchor:** CPython release dates, support phases and PEP-status-by-version are owned by `python_platform_baseline_manifest.md` (verified 2026-08-08); this file states test *behaviour* and names only the version gate that changes it. The tool versions below (pytest, Hypothesis, coverage.py and the plugin set) are this file's own subject matter and were verified 2026-08-08. **The enforcement rule that governs every practice here:** a testing practice that nothing runs is not a practice. ## TL;DR
- Adopt pytest 9.1.1 (released 2026-06-19) on Python 3.14.7 as the default runner for small Python projects; it gives plain-assert testing, dependency-injected fixtures with five scopes, and parametrization with no boilerplate — VERSION-DEPENDENT. Pin **>= 9.1.0**, not merely "pytest 9": versions 9.0.0 through 9.0.3 silently ignored `--strict-markers` and `--strict-config` when those arrived through `addopts` (issue #14442), so a suite that looked strict was not — VERSION-DEPENDENT (broken 9.0.0–9.0.3, fixed 9.1.0). unittest remains the zero-dependency stdlib fallback — ESTABLISHED.
- Specify obligations as observable contracts at a **named substitution mechanism** — dependency injection, a `Protocol`, a Gateway, a Plugin, a Humble Object — rather than at "a seam": Feathers' seam is a *property* of code, not an artefact a reviewer can point at (§2). Partition inputs (equivalence classes + boundary values), cover error paths, and prefer fakes implementing the real contract over mocks — where a double earns the word *fake* only if one parametrized contract suite runs against both it and the real implementation (§6). Use coverage.py 7.15.x as a diagnostic for untested code, never as a target — ESTABLISHED.
- Use Hypothesis 6.165.x property-based testing for pure-core logic (round-trip, invariant, oracle, metamorphic, stateful) and example-based tests for side-effectful shells — noting that since 6.156.0 (2026-07-01) Hypothesis carries Rust internals and requires a Rust toolchain to build from source where no native wheel exists, and that it rewrites its own settings when it detects a CI environment variable (§4a). Design for testability via dependency injection and Protocol-typed substitution points (PEP 544) and functional-core/imperative-shell — and choose each testing construct by the **testability tactic** it realizes (§7a), which is what turns a tool list into a reviewable architecture rule — ESTABLISHED/VERSION-DEPENDENT.
- Three documented mechanisms — not environment mystery — make a CI run behave differently from a local one, and an agent debugging "it only fails in CI" must rule out all three first: Hypothesis loads a `"ci"` profile (`derandomize=True, deadline=None, database=None, print_blob=True`) when it sees any of twelve CI environment variables (§4a); coverage.py's default measurement core on Python 3.14+ is `sysmon`, which supports neither plugins nor dynamic contexts (§5a); and `pytest-xdist --dist load` guarantees no ordering, so order-coupled tests fail only under `-n`, and then intermittently (§6e) — VERSION-DEPENDENT.
- Coverage answers *was this line executed*. Nothing in coverage answers *would a wrong version of this line have been caught* — execution is not verification, and a suite of assertion-free tests raises the number without adding one obligation. Mutation testing (mutmut 3.7.0) is the only mechanism in this stack that tests the assertions themselves; its cost is multiplicative in mutant count, so scope it to protected modules on a nightly cadence and gate on "no new surviving mutants", never on a score — VERSION-DEPENDENT / OPEN (no primary source quantifies the runtime cost).
- Determinism is an obligation with four named closures (order, clock, network, RNG) and one escape clause: eliminate nondeterminism where possible, **record at a declared interface and replay** where it is not, and only then retry (§6c). A suite that cannot reproduce a failure from its own printed seed has no determinism story — ESTABLISHED/VERSION-DEPENDENT.

- **Test-double taxonomy (Meszaros/Fowler):** dummy, fake, stub, spy, mock — only mocks insist on behavior verification. ESTABLISHED.
- **Over-mocking hazard is documented:** mocks couple tests to implementation; a fake with a working implementation of the real contract is often preferable. ESTABLISHED (Fowler).
- **Coverage % is a diagnostic, not a target** (Fowler; Goodhart's law framing). ESTABLISHED.

Inside `pyproject.toml`, `[tool.pytest]` (native TOML types, since pytest 9.0) and `[tool.pytest.ini_options]` (since pytest 6.0) cannot coexist. VERSION-DEPENDENT (pytest 9.x). Detail in §1a.
- **Hypothesis silently changes its own defaults in CI**, keyed off any of twelve environment variables. The consequence that matters most: `database=None` in CI means yesterday's counterexample is not replayed today. VERSION-DEPENDENT (Hypothesis 6.165.x). Detail in §4a.
- **A pytest function-scoped fixture requested by an `@given` test runs once for the whole test function, not once per generated case.** `HealthCheck.function_scoped_fixture` exists to say so; suppressing it to get a green run converts a real state leak into a silent one. VERSION-DEPENDENT (Hypothesis 6.165.x).
- **The arithmetic of a coverage threshold makes it lie:** `fail_under` compares one global number, exits with status `2` (not `1`) on failure, and is interpreted at `[report] precision`, whose default of `0` makes a true 89.6% report and compare as 90% and therefore *pass* `fail_under = 90`. There is no per-file or per-module form. ESTABLISHED (coverage.py 7.15.x docs). Detail in §5a.
- **The two async pytest plugins differ in task semantics, not syntax.** AnyIO's bundled plugin runs all async fixtures and tests in the same task; pytest-asyncio uses a new task per fixture setup/teardown operation, which prevents context-variable propagation and stops task groups and cancel scopes from working across the fixture boundary. Code that is correct under one is broken under the other. ESTABLISHED (AnyIO docs — this is AnyIO's own characterisation of pytest-asyncio). Detail in §6d.
- **Every testing construct realizes exactly one testability tactic**, and naming the tactic is what makes a substitution reviewable and gives it an exit criterion (§7a). ESTABLISHED (Bass, Clements & Kazman, *Software Architecture in Practice*, 4th ed., 2021, ISBN 978-0-13-688609-9, for the tactics themselves; the construct→tactic edges are SWE-corpus editorial judgments and are marked as such).

## Details

### 1. Test framework landscape

**pytest (default recommendation for small projects).** pytest 9.1.1 (2026-06-19) is the current stable release and requires Python >= 3.10; the 9.0.0 major release (2025-11-05) dropped Python 3.9, turned `PytestRemovedIn9Warning` into errors by default, added native TOML config under `[tool.pytest]`, added the umbrella `strict` config option, merged `pytest-subtests` into core as the experimental `subtests` fixture, and **removed** nose-style bare `setup`/`teardown` methods (use `setup_method`/`teardown_method`), the `pytest.Instance` collector (the collection tree is now Class → Function, not Class → Instance → Function), `py.path.local`-flavoured path arguments to collection hooks such as `pytest_ignore_collect` / `pytest_collect_file` / `pytest_pycollect_makemodule`, and the tolerance for marks applied to fixtures; a synchronous test that depends on an asynchronous fixture is now an error rather than a warning. pytest 9.1.0 added official Python 3.15 support (#14524). VERSION-DEPENDENT (pytest 9.x). Removals of this shape are quiet by nature — a renamed-away `setup` method is simply not called — so port an old suite by asserting that setup ran, not by reading the changelog. pytest lets you use plain `assert` statements with detailed introspection, auto-discovers test modules/functions, and has a large plugin ecosystem: the official plugin list at docs.pytest.org/en/stable/reference/plugin_list.html states "This list contains 2016 plugins" as of 2026-08-08, which supersedes both the homepage's rounder figure and every older mirror — VERSION-DEPENDENT (a moving figure; the list page is the precise source). ESTABLISHED (docs.pytest.org; pytest PyPI).

- **Fixtures** are functions decorated with `@pytest.fixture` that provide a fixed baseline and are injected into tests by parameter name (dependency injection). A test (or another fixture) requests a fixture by naming it as a parameter. ESTABLISHED.
- **Fixture scopes (VERIFIED complete set = five).** Per the official "How to use fixtures" page: "Fixtures are created when first requested by a test, and are destroyed based on their `scope`: `function`: the default scope, the fixture is destroyed at the end of the test. `class`: … last test in the class. `module`: … last test in the module. `package`: … last test in the package where the fixture is defined, including sub-packages and sub-directories within it. `session`: … at the end of the test session." A second doc passage confirms: "Possible values for `scope` are: `function`, `class`, `module`, `package` or `session`." Higher-scoped fixtures execute before lower-scoped ones; a callable scope (added in pytest 5.2) must still return one of the five. ESTABLISHED.
- **`@pytest.mark.parametrize`** calls a test function multiple times with different argument sets; e.g. `@parametrize('arg1', [1,2])` yields two calls. Stacking decorators produces the Cartesian product. pytest builds a test ID per parameter set, usable with `-k` and shown by `--collect-only`. ESTABLISHED.
- **Markers** (`@pytest.mark.<name>`) attach metadata to tests, used for selection (`-m`) and plugin behavior. Custom marks should be registered in config (`[pytest] markers = …` / `[tool.pytest.ini_options]`) or via a `pytest_configure` hook; unregistered marks always warn "in order to avoid silently doing something surprising due to mistyped names", and `--strict-markers` turns unknown marks into errors. The file-config equivalents are `strict_markers = true` and, since pytest 9.0, the umbrella `strict = true` (§1a). Caveat with teeth: pytest 9.0.0 through 9.0.3 silently ignored `--strict-markers` and `--strict-config` supplied through `addopts` — root cause the `OverrideIniAction` compatibility code added in pytest 9 (commit efa9eff), fixed in 9.1.0 (issue #14442) — so unknown markers and unknown config keys degraded from errors to warnings and the suite still went green. **Verify strictness by asserting that a deliberately misspelled marker errors**, not by reading `pyproject.toml`; that assertion is the enforcement. VERSION-DEPENDENT (broken 9.0.0–9.0.3, fixed 9.1.0). Marks apply to tests, not fixtures — and since pytest 9.0 this is enforced: decorating a fixture function with a mark such as `@pytest.mark.usefixtures` raises an error rather than being silently ignored. ESTABLISHED/VERSION-DEPENDENT (pytest 9.0+).
- **conftest.py** provides fixtures, hooks, and plugin config for an entire directory tree without imports; pytest auto-discovers them. ESTABLISHED.
- **Assertion rewriting.** pytest rewrites `assert` statements in test modules at import time (an AST/import-hook transform) to produce detailed failure introspection; it writes cached `.pyc` files. It "only rewrites test modules directly discovered by its test collection process," plus plugin modules; other imported helper modules are not rewritten unless you call `register_assert_rewrite` before importing them. Mode is controlled by `--assert=rewrite` (default) or `--assert=plain`. ESTABLISHED.
- **Fixture finalisation is LIFO, and the order is the parameter list read right to left.** Yield fixtures "use `addfinalizer` behind the scenes"; with multiple fixtures "the first teardown code to run is from the right-most fixture, i.e. the last test parameter", and among finalizers "the first fixture to run is last call to `request.addfinalizer`". If a yield fixture raises **before** its `yield`, pytest "won't try to run the teardown code after that yield fixture's yield statement", but every fixture that already completed for that test is still torn down; `request.addfinalizer` differs — "pytest will run that finalizer once it's been added, even if that fixture raises an exception after adding the finalizer". A fixture whose teardown touches a sibling fixture is therefore correct or broken depending on which side of the parameter list it sits on. ESTABLISHED.
- **conftest.py has two different orderings, and conflating them is a standing bug source.** Discovery walks **downward from the filesystem root**: "Before a `conftest.py` file is loaded, load `conftest.py` files in all of its parent directories." *Hook* implementations from conftests "closer to the root of the filesystem" are invoked **first**; *fixture* overrides resolve the other way — directory conftest < module-level fixture < direct test parametrization, with a subdirectory conftest overriding its parent and the overridden "base or super fixture" still reachable from the overriding one. As of pytest 9.1.0 (#14513), "Fixture definition override resolution [is] now determined first by visibility in the collection tree rather than registration order", so a suite that relied on registration order to pick between two same-named fixtures can resolve differently after upgrading, with no error. ESTABLISHED/VERSION-DEPENDENT (pytest 9.1.0).
- **`@pytest.mark.parametrize(..., indirect=True)` changes what the test receives.** Each parameter value is routed into a fixture of the same name, which reads it as `request.param` and returns the transformed value; the test then sees the fixture's return value, not the parameter. `indirect` also accepts a list of argnames for partial indirection (`indirect=["x"]`), leaving the others direct. The documented motivation is "more expensive setup at test run time in the fixture, rather than having to run those setup steps at collection time". Two failure modes: no fixture of that name is a fixture-lookup error, and a fixture that ignores `request.param` yields silently constant test data. ESTABLISHED.
- **Native `subtests` since pytest 9.0, and explicitly experimental.** The `subtests` fixture's `subtests.test(msg=..., **kwargs)` context manager reports each block independently and continues after failure; the docs say "Added in version 9.0" and "This feature is experimental. Its behavior, particularly how failures are reported, may evolve in future releases." It was merged in from the `pytest-subtests` plugin. Decision rule: subtests run at execution time and **cannot be selected individually from the command line**, whereas parametrized cases are created at collection time and can be — so when the case set is known statically, `parametrize` and pay nothing; reach for `subtests` only when the cases are discovered while running. VERSION-DEPENDENT (pytest 9.0+).
- **What pytest 9.1.0 added, deprecated and broke.** Added: `--max-warnings` plus a `max_warnings` config option to fail a run above a warning count; `assertion_text_diff_style` to render string-equality failures as separate Left/Right blocks; `pytest.register_fixture()` for imperative fixture registration; and `datetime`/`timedelta` support in `pytest.approx()`, where an explicit `abs` or `rel` timedelta tolerance is required because relative tolerance is not supported for `datetime`. Deprecated for removal in pytest 10: class-scoped fixtures written as plain instance methods without `@classmethod` (#10819 — they set attributes on a different instance than the test methods see, so a class-scoped fixture assigning `self.client` is invisible to the tests); `request.getfixturevalue()` during teardown for a fixture not already requested (#12882); non-Collection iterables such as generators as `argvalues` for `parametrize` (#13409 — generators are exhausted after first iteration, which silently collected fewer cases on re-collection); `config.inicfg` (#13946); `pytest.console_main()` (#1764); `--pastebin` (#14434, moved to the `pytest-pastebin` plugin); and marker-based hook configuration (#14335). `pytest.yield_fixture` is deprecated for removal in pytest 10, and 9.1.0 marks it deprecated *to type checkers* via the `deprecated` decorator (#14342) — which is the rare case where the enforcement is mypy/pyright rather than a runtime warning. One breaking change to know before enabling doctests: under `--doctest-modules`, autouse fixtures with module, package or session scope defined inline in a Python test module "now possibly execute twice" (#14533), so expensive or non-idempotent session setup silently doubles; the documented workaround is to move those definitions into `conftest.py`. VERSION-DEPENDENT (pytest 9.1.0).
- **Do not pin against the unreleased line.** A `pytest 9.2 [UNRELEASED DRAFT] (2026-08-06)` section exists in the development changelog and already carries breaking changes: `indirect`, `ids` and `scope` become keyword-only parameters of `@pytest.mark.parametrize` (#8593), so `@pytest.mark.parametrize("x", vals, True)` written today will raise `TypeError` there; and `-c` will error on non-existent paths, directories and unsupported formats (#14716). Nothing in it is released. OPEN (unreleased — informational, never a pin target).

**stdlib unittest (zero-dependency fallback).** A test case subclasses `unittest.TestCase`; test methods are named with a `test` prefix. Checks use assertion methods — `assertEqual()`, `assertTrue()`/`assertFalse()`, `assertRaises()` (these "are used instead of the assert statement so the test runner can accumulate all test results and produce a report"). `setUp()`/`tearDown()` run before/after each test method; `setUpClass()`/`tearDownClass()` (classmethods) run once per class; `addCleanup()` registers LIFO cleanups that run even if `setUp` fails. `unittest.main()` provides a CLI. ESTABLISHED (docs.python.org/3/library/unittest.html).

**Sensible default for small projects: pytest.** Rationale (decision): plain-assert syntax with introspection removes `self.assert*` boilerplate; fixtures give composable, scoped dependency injection superior to repeated `setUp`; parametrization and markers are first-class; and pytest can run existing unittest suites unchanged, so adoption is incremental and reversible. Keep unittest where a zero-dependency stdlib-only suite is a hard requirement. Decision-ready.

### 1a. The pytest 9 configuration surface (settled)

The previous edition of this manifest hedged between two `pyproject.toml` tables. The question is settled below, and it matters because an agent that gets it wrong sees **no error at all** — only ignored configuration.

**Which file wins (precedence, pytest 9.x).** `pytest.toml` / `.pytest.toml` → `pytest.ini` / `.pytest.ini` → `pyproject.toml` → `tox.ini` (needs a `[pytest]` section) → `setup.cfg` (needs a `[tool:pytest]` section). "Options from multiple `configfiles` candidates are never merged — the first match wins", and `pytest.toml` "will always match and take highest precedence, even if empty." VERSION-DEPENDENT (pytest 9.x).

| where | table name | data model | notes |
|---|---|---|---|
| `pytest.toml` / `.pytest.toml` | `[pytest]` — **not** `[tool.pytest]` | native TOML | Highest precedence, even when the file is empty. The `tool.` prefix belongs to `pyproject.toml` only. |
| `pytest.ini` / `.pytest.ini` | `[pytest]` | INI strings | Beats `pyproject.toml` outright. |
| `pyproject.toml` | `[tool.pytest]` (since pytest 9.0) | native TOML types (booleans, integers, arrays) | **Cannot coexist** with `[tool.pytest.ini_options]` in the same file. |
| `pyproject.toml` | `[tool.pytest.ini_options]` (since pytest 6.0) | INI-flavoured values | Still supported; not a synonym for the row above. |
| `tox.ini` | `[pytest]` | INI strings | Only if the section is present. |
| `setup.cfg` | `[tool:pytest]` | INI strings | Lowest precedence. |

ESTABLISHED (docs.pytest.org customize page) / VERSION-DEPENDENT (pytest 9.0+ for `[tool.pytest]`). Three consequences worth writing into a repo convention: (1) adding `[tool.pytest]` to `pyproject.toml` in a repo that already has an empty `pytest.ini` anywhere up the tree changes nothing, silently; (2) `[tool.pytest]` and `[tool.pytest.ini_options]` are different data models, so copying values across without retyping produces wrong config or a parse error; (3) the project must pin exactly one config location and treat the appearance of a second as a build break — OPEN, because nothing in pytest enforces single-location config; a `pre-commit` guard or a structural CI check (see `python_quality_gates_manifest.md`) is the only mechanical route.

**The strictness set, and what it covers.** pytest 9.0 added a "strict mode" umbrella: "Added a 'strict mode' enabled by the `strict` configuration option. When set to `true`, the `strict` option currently enables `strict_config`, `strict_markers`, `strict_parametrization_ids`, `strict_xfail`." `strict_xfail` is an alias for the older `xfail_strict`, `strict_config` for `--strict-config`, and `strict_markers` for `--strict-markers`; the unifying PR is pytest-dev/pytest#13839, merged 2025-10-26. VERSION-DEPENDENT (pytest 9.0+). **Because `strict` picks up future strictness options automatically, use it only under a locked pytest pin.** A project that floats its pytest version should enable the four options individually, so a new strictness rule arrives as a deliberate upgrade rather than as a mystery failure.

**Minimum enforcing configuration for a new project.** Register every custom marker under `markers`; set the strictness options (individually, or `strict = true` behind an exact pin); and set `filterwarnings = ["error::DeprecationWarning"]` so a deprecation in a dependency or in your own error contract fails the build instead of scrolling past — warnings-as-errors is the mechanism that makes the removal calendar in `error_tracing_contract_manifest.md` actionable rather than aspirational, and it pairs with running the suite under `-X dev`. ESTABLISHED (pytest docs for each option) / OPEN (the specific set is this project's convention, not a pytest default).

**Test-tree layout — the three coupled decisions, and a default (OPEN — pin it).** Nothing else in this collection states how the *test* tree is laid out: `python_module_boundaries_manifest.md` owns project layout but covers the importable tree only. Three decisions are coupled, and getting them wrong is the best-known breakage under the src layout this collection mandates: (a) whether `tests/` carries `__init__.py`, (b) which `--import-mode` pytest uses, (c) whether ruff's `INP001` (`implicit-namespace-package`, "Checks for packages that are missing an `__init__.py` file") fires on the test tree. **The default for a src layout: `tests/` with no `__init__.py`, `--import-mode=importlib`, `testpaths = ["tests"]`, and `INP001` ignored for `tests/**`.** The measured behaviour, because each cell changes what a green run means:

| `tests/__init__.py` | import mode | duplicate test-module basenames | `ruff check --select INP` |
|---|---|---|---|
| absent | `prepend` (pytest's default) | **collection error** — "import file mismatch … use a unique basename" | `INP001` on every test file |
| absent | `importlib` | collected, both pass | `INP001` on every test file |
| present in every test dir | `prepend` | collected, both pass | clean |

MEASURED (pytest 9.1.1 and ruff 0.16.2, 2026-08-08). Commands: `pytest -q` and `pytest -q --import-mode=importlib` over `tests/a/test_dup.py` + `tests/b/test_dup.py`; `ruff check --isolated --select INP tests/`; the mode set and its default from `pytest --help` — `--import-mode={prepend,append,importlib}`, "Default: prepend."

Two consequences worth writing into the repo convention. (1) The `INP001` hit is not optional to resolve: an agent that wires the mandated src layout and the recommended `select` (which includes `INP`) gets a lint failure on its own test tree on the first run, and the two mechanical answers point in opposite directions — add `"INP001"` to the `tests/**` entry of `lint.per-file-ignores` (keeps the test tree non-importable, which is what the default above wants), or add the `__init__.py` files (silences the rule and permits duplicate basenames under the default import mode). Choose once; the linting rule set itself is owned by `python_linting_practices_manifest.md`. (2) The alternative — `__init__.py` in every test directory with the default prepend mode — buys duplicate basenames at the cost of making the test tree an importable package, and therefore a candidate for accidental packaging and shipping; the packaging consequence is owned by `python_module_boundaries_manifest.md`. Unique test-module basenames are worth keeping either way, because they are the one convention that survives a later change of import mode. OPEN (the choice is this project's to pin; nothing in pytest or ruff prefers one) / MEASURED (the consequences of each cell, above).

### 2. The unit–integration boundary (definitional)

- **Unit test (working definition).** A test that exercises a single component in isolation, fast and deterministic, failing only when that component's behavior fails. Michael Feathers' widely cited operational definition states what is NOT a unit test: a test is not a unit test if it talks to a database, communicates across the network, touches the file system, or cannot run without environmental setup. Secondary source: this negative formulation is most often quoted from Feathers and circulated via blog summaries; the canonical source is *Working Effectively with Legacy Code* (2004). FLAGGED secondary.
- **Unit-testable in isolation.** A component is unit-testable when its dependencies can be substituted at a seam so it runs without real infrastructure, and its observable behavior (return values or observable state/effects) can be asserted deterministically.
- **Integration test (working definition).** A test that exercises two or more components together across a real boundary (e.g., real filesystem, real DB, real subprocess), validating that their contract holds when wired together.
- **The seam (Michael Feathers, *Working Effectively with Legacy Code*, 2004 — PRIMARY).** Feathers' definition: "a seam is a place where you can alter behavior in your program without editing in that place," with an associated "enabling point" where the choice between behaviors is made. Feathers catalogs seam types — preprocessor seams, link seams, and object (polymorphic) seams — the last being "pretty much the most useful seams available in object-oriented programming languages." The seam determines the boundary: where you can substitute a double or a real collaborator is exactly where the unit/integration line can be drawn. ESTABLISHED (primary; quotes corroborated via InformIT excerpt of the book chapter — FLAGGED that the book text was read via the publisher's posted chapter excerpt, not the print book).

### 2a. Test shape: the four-phase test, and fixture strategy as a decision

**Four-Phase Test (Gerard Meszaros, *xUnit Test Patterns: Refactoring Test Code*, 2007, ISBN 978-0-13-149505-0; also catalogued at xunitpatterns.com as "Four Phase Test").** The phases are setup, exercise, verify, teardown. In pytest they map onto: fixture argument injection (a `@pytest.fixture` requested by parameter name) → the single call under test → `assert` / `pytest.raises` / `pytest.RaisesGroup` → teardown after `yield` in the fixture, or `request.addfinalizer`. ESTABLISHED (Meszaros, primary catalogue; the pytest mapping is this manifest's). Two rules follow, and they are what the shape is *for*: **one behaviour per test**, and **teardown never in the test body**. What enforces them: `tmp_path` and `monkeypatch` make phase 4 automatic and therefore unskippable ("All modifications will be undone after the requesting test function or fixture has finished"), so teardown discipline is mechanical the moment you use the builtin fixtures instead of hand-rolled cleanup. Nothing mechanically enforces one-behaviour-per-test — OPEN, review convention. The sourced relation to record: `four-phase-test` **uses** `test-fixture` — "Phase 1 (setup) constructs the test fixture the exercise phase runs against" (Meszaros).

**Fixture strategy is a named design decision; `scope=` is only its encoding.** The corpus states the tradeoff the tooling section (§1) cannot: a test's start state must be "cheap to build, isolated enough to prevent inter-test coupling, and expressive enough to read; fixture strategy is the named design decision governing that trade-off", with **Fresh Fixture** and **Shared Fixture** as the two positions (Meszaros, 2007). Consequence in Python: `scope="function"` *is* a Fresh Fixture decision, and `scope="session"` on anything mutable *is* a Shared Fixture decision — usually one made by accident, and the direct cause of tests that pass alone and fail in a suite. Decide it per fixture and record the reason. ESTABLISHED (the element and its aka); OPEN for enforcement — nothing detects an accidentally-shared mutable fixture, and the closest mechanical probes are `pytest-randomly` reordering (§6c) and `pytest-xdist` distribution (§6e), which surface the coupling as an intermittent failure rather than as a diagnosis.

(Provenance carried forward honestly: `four-phase-test` and `test-fixture` are *admitted-but-contested* elements in the SWE corpus — its exclusion register argues that xUnit test-organization patterns are practice rather than code-level constructs, while the shipped catalog includes them with a borderline note. Cite them as named vocabulary with a real naming source; do not cite the exclusion register against them. OPEN, corpus-internal tension.)

### 3. Test doubles, precisely

**The taxonomy is one dial, not five species (corpus refinement).** The SWE catalog folds dummy, fake, stub, spy and mock into a *single* element whose defining axis it states outright: the family "spans dummy, fake, stub, spy, and mock by increasing behavioral sophistication". That reframes the familiar advice. "Prefer fakes over mocks" is not a choice among five kinds — it is a position on one dial, and the rule is **take the least behaviour that still lets you assert the contract**. The sharper corollary is visible in the fact that the only family member the catalog keeps as its own element is `service-stub`, individuated not by verification style but by the boundary it occupies ("implements the same gateway interface"): **substitutes are individuated first by the boundary they sit at, and only then by how much behaviour they carry**. Ask "which boundary, and how little behaviour will do" before reaching for a class name. ESTABLISHED (catalog wording); the naming sources for the taxonomy itself are immediately below.

**Taxonomy (Gerard Meszaros, *xUnit Test Patterns*, popularized by Martin Fowler, "Mocks Aren't Stubs" / "Test Double" — PRIMARY).** "Test Double" is the generic term (after "stunt double"). Fowler, summarizing Meszaros:
- **Dummy** — objects passed around but never actually used; usually just fill parameter lists.
- **Fake** — has a working implementation, but takes a shortcut unsuitable for production (an in-memory database is the canonical example).
- **Stub** — provides canned answers to calls made during the test, not responding outside what's programmed.
- **Spy** — a stub that also records information about how it was called (e.g., how many messages were "sent").
- **Mock** — pre-programmed with expectations forming a specification of the calls it expects; verifies those calls.
Key distinction: "only mocks insist upon behavior verification"; stubs use state verification (or either). ESTABLISHED.

**unittest.mock (VERIFIED against docs.python.org/3/library/unittest.mock.html).**
- **`Mock`** — flexible mock object; callable; auto-creates attributes/methods as they are accessed; records usage so you can assert on calls (`assert_called_with`, `assert_called_once_with`, etc.). ESTABLISHED.
- **`MagicMock`** — a `Mock` subclass with magic (dunder) methods pre-created and ready to use. ESTABLISHED.
- **`patch()`** — decorator/context manager that temporarily replaces a target (module/class attribute) with a mock for the scope of a test, restoring it afterward; `new_callable` controls the replacement class (AsyncMock for async functions, MagicMock otherwise by default). ESTABLISHED.
- **`spec` / `spec_set`** — constrain a mock's interface to a real object's attributes; `spec_set` additionally forbids setting attributes that don't exist on the spec. ESTABLISHED.
- **`autospec` / `create_autospec()`** — "Auto-speccing creates mock objects that have the same attributes and methods as the objects they are replacing, and any functions and methods (including constructors) have the same call signature as the real object." Calling with the wrong signature raises `TypeError`. Use via `patch(..., autospec=True)` or `create_autospec(obj, spec_set=True, instance=True)`. ESTABLISHED.

**Over-mocking hazard (documented).** Fowler notes mocks (behavior verification) make tests "tightly coupled to implementation, which makes them very fragile"; he and others recommend stubs/fakes where possible and reserving mocks for genuine command-style interactions. A fake that implements the real contract (e.g., an in-memory repository) tests behavior against the actual interface and survives refactors, whereas a forest of `autospec=False` mocks can pass while the real integration is broken. Decision: prefer fakes-implementing-the-contract; use `autospec`/`spec_set` whenever you must mock, to prevent silent drift when the real API changes. ESTABLISHED (Fowler — PRIMARY).
- **`Service Stub` and `Gateway` — the two names §6's advice presupposes (Martin Fowler, *Patterns of Enterprise Application Architecture*, 2002).** A **Gateway** is one application-owned class per external system, with the method set shaped for the caller rather than for the vendor API (`class PaymentGateway: def charge(self, amount: Money) -> ChargeId`); the catalog's justification is that external APIs are "awkward, unstable, and hard to fake". A **Service Stub** is the in-process stand-in implementing that same gateway interface. The sourced edge is the operative sentence: `gateway` **composes-with** `service-stub` — "Code behind a Gateway is tested by substituting a Service Stub for the external resource." So the rule is not "mock the HTTP client"; it is *own a gateway, type it with a `Protocol`, and substitute at that one class* — which also collapses the four-way clock/network/filesystem/subprocess bullet list of §6 into a single derivation. ESTABLISHED (Fowler, PoEAA — primary work; the Python spelling is this manifest's).
- **A bare `Mock()` asserts nothing, and that failure is silent.** An unspecced `Mock` accepts every call including misspelled ones and returns a truthy `Mock`, so `assert result.is_valid()` passes against a method that does not exist. Enforcement: `autospec=True` or `spec_set=True` on every mock, which raises `TypeError` on a wrong call signature and refuses attributes absent from the spec — that is the only mechanical check in this subsection. Note what it does *not* buy: auto-speccing pins the collaborator's *shape*, never its behaviour; only a shared contract suite (§6) pins behaviour. ESTABLISHED (docs.python.org unittest.mock; the failure framing is this manifest's).
- **Vocabulary provenance, so nobody hunts for an element id that does not exist.** The canonical Fake example — an in-memory test database — is not an element in the SWE corpus: it is recorded in the exclusion register as a "test-environment substitution technique — practice, plus covered conceptually by test-double/service-stub territory". Likewise **Test Harness** is an excluded entry ("testing infrastructure/practice, not a runtime design mechanism"), so that phrase names something the corpus rejected rather than citable vocabulary. This manifest keeps both words because they are useful English; it does not present them as grounded names. OPEN (naming convention, no element id).

### 4. Property-based testing (Hypothesis)

**Library identity (VERIFIED).** Hypothesis is "the property-based testing library for Python," maintained by the HypothesisWorks organization; PyPI lists authors David R. MacIver and Zac Hatfield-Dodds, with maintainers including DRMacIver, tybug, and Zac-HD; license MPL-2.0; docs at hypothesis.readthedocs.io. Latest version 6.165.2 (2026-08-05), requires Python >= 3.10. Native wheels are published for CPython 3.10–3.14 plus 3.14t and (except musllinux) PyPy 3.11, on Linux x86_64/aarch64 manylinux+musllinux, macOS x86_64/arm64 and Windows x64, plus Pyodide wasm32 for 3.13. **Hypothesis is no longer pure Python:** 6.156.0 (2026-07-01) began migrating internals to Rust and states that Hypothesis "now requires a rust toolchain to build from source (if not installing from a native wheel)"; the docs describe no retained pure-Python fallback. Any platform, architecture or interpreter variant outside that wheel matrix now fails at *install* time in a container with no `cargo`, which makes the wheel matrix a deployment fact rather than a footnote. Two smaller version notes: 6.159.0 (2026-07-22) renamed user-facing "example" to "test case" in messages and docs while leaving the `max_examples` setting name unchanged, so log-scraping or quoted output from an earlier edition will mismatch; and 6.160.0 (2026-07-22) gave `Bundle` efficient `.filter()`/`.map()` while 6.164.0 (2026-07-30) taught `functions()` to generate async and generator functions. VERSION-DEPENDENT (Hypothesis 6.156.0+ / 6.159.0 / 6.160.0 / 6.164.0 / 6.165.2).

- **What it generates / strategies.** You write a test that should pass for all inputs in a described range and let Hypothesis choose inputs, including edge cases. The described range is a **strategy** (e.g., `st.integers()`, `st.lists(st.integers())`, `st.text()`); strategies are composable and can be built with `@st.composite` and adapted with `.filter()` / `assume()`. ESTABLISHED.
- **`@given`** is "the standard entrypoint"; it takes strategies and supplies generated arguments to the test. Default is 100 examples per test, controllable via the `max_examples` setting. ESTABLISHED.
- **Shrinking.** "When Hypothesis does find a bug, it doesn't just report any failing example — it reports the simplest possible one," reducing complex failing inputs to a minimal counterexample. ESTABLISHED.
- **Stateful / rule-based testing.** `hypothesis.stateful.RuleBasedStateMachine` plus `@rule`, `@initialize`, `@precondition`, `@invariant`, and `Bundle` let Hypothesis generate sequences of operations and shrink failing sequences. `@rule` defines actions (args drawn from strategies); `Bundle` passes values between rules; `@invariant()` runs after every rule; `@precondition` gates rules. Default `stateful_step_count` is 50. ESTABLISHED.
- **Property classes it fits:**
  - **Round-trip:** `decode(encode(x)) == x` (serializers/parsers). 
  - **Invariant:** a property that must always hold (e.g., `sorted(xs)` is ordered and same length/multiset as `xs`). 
  - **Oracle (differential):** compare against a trusted reference implementation (`my_sort(xs) == sorted(xs)`). 
  - **Metamorphic:** relate outputs of related inputs without a full oracle (e.g., filtering a search result set must yield a subset). Metamorphic testing addresses the "test oracle problem" and was invented by Tsong Yueh Chen, S.C. Cheung, and S.M. Yiu in "Metamorphic Testing: A New Approach for Generating Next Test Cases," Technical Report HKUST-CS98-01, Department of Computer Science, The Hong Kong University of Science and Technology, 1998 (primary report). ESTABLISHED.
- **When example-based tests are better.** Property-based testing fits pure functions, data transforms, parsers, serializers, and algorithms; it is weaker for code that is mostly side effects (sending email, writing to a DB), for GUI flows, and where the "right" output is hard to define without rebuilding the function. Use targeted example-based tests there. FLAGGED secondary (botmonster blog) for the "when to prefer examples" framing; consistent with Hypothesis docs guidance to start with simple properties.
- **Where the name comes from, and why citation hygiene matters here.** Property-based testing as a mechanism is named in Koen Claessen & John Hughes, "QuickCheck: A Lightweight Tool for Random Testing of Haskell Programs" (ICFP 2000; official QuickCheck page, Chalmers); Hypothesis is that lineage's Python descendant. ESTABLISHED (naming source per the SWE corpus work record — the corpus omits a DOI because ACM DL returned 403, carried forward as recorded).
- **Property-based testing *uses* a seeded PRNG, and that is what makes a failure reportable (sourced edge; Donald E. Knuth, *The Art of Computer Programming* Vol. 2, 3rd ed., 1997, ISBN 0-201-89684-2, ch. 3 "Random Numbers").** The edge's wording: "Generators draw inputs from a seeded PRNG; the seed makes failing cases reproducible/shrinkable." The same discipline applies to the code under test — inject a `random.Random(seed)` instance rather than calling module-level `random.*`, and `numpy.random.default_rng(seed)` rather than the legacy global state (§6c). ESTABLISHED (edge sourced in the SWE corpus; the Python spelling is this manifest's).
- **Numeric properties need approximate equality, not `==` (sourced edge to `epsilon-ulp-float-comparison`).** Round-trip and oracle properties over floats are asserted with `pytest.approx(expected, rel=..., abs=...)`, `math.isclose` (PEP 485) or `numpy.testing.assert_allclose`, never bare equality. The trap is the one stated in §5: **a fixed absolute epsilon is wrong across magnitudes**, so `abs=1e-9` against a strategy that draws `floats()` across the full range is a latent flake rather than a tolerance. ESTABLISHED (Bruce Dawson, "Comparing Floating Point Numbers, 2012 Edition", 2012, randomascii.wordpress.com; ULP framing also Knuth TAOCP v2 and Goldberg, 1991).
- **Two named alternatives, so "use Hypothesis" stays a choice rather than a reflex.** Both `parameterized-test` and `golden-master-testing` carry an `alternative-to` edge against property-based testing: they are three ways to stop hand-writing expected values — a table of rows (§6a), a universally-quantified property (here), or an approved recording (§6b). Choose by where you want the oracle to live: in the table, in the property, or in the approved artefact. ESTABLISHED (edges as recorded; marked editorial in the corpus).

### 4a. Hypothesis settings, the CI profile, and the health checks

This subsection exists because these mechanics are a leading source of "it fails locally but not in CI" in a property-based suite — and every one of them is documented rather than mysterious. (The ranking is this manifest's editorial judgment; each mechanism below is separately tagged.)

**Documented defaults (Hypothesis 6.165.x API reference).** `max_examples = 100`; `deadline = 200` milliseconds (accepts int, float or `timedelta`); `derandomize = False`; `print_blob = False`; `database` = a `DirectoryBasedExampleDatabase` at `.hypothesis/examples`, and if that location is unusable "Hypothesis will emit a warning and fall back to an `InMemoryExampleDatabase`", while `database=None` means "no storage will be used". `Phase` members are exactly `Phase.explicit`, `Phase.reuse`, `Phase.generate`, `Phase.target`, `Phase.shrink`, `Phase.explain`, and all are enabled by default — `Phase.reuse` is what replays the database and `Phase.explicit` is what runs `@example` cases, so disabling phases silently changes what a green run proves. `stateful_step_count` defaults to 50. VERSION-DEPENDENT (Hypothesis 6.165.x).

**Hypothesis rewrites its own settings when it detects CI.** `is_in_ci()` checks twelve environment variables — `CI`, `__TOX_ENVIRONMENT_VARIABLE_ORIGINAL_CI`, `TF_BUILD` (Azure Pipelines), `bamboo.buildKey`, `BUILDKITE`, `CIRCLECI`, `CIRRUS_CI`, `CODEBUILD_BUILD_ID`, `GITHUB_ACTIONS`, `GITLAB_CI`, `HEROKU_TEST_RUN_ID`, `TEAMCITY_VERSION` — and when any is set it loads the `"ci"` profile: `derandomize=True, deadline=None, database=None, print_blob=True, suppress_health_check=[HealthCheck.too_slow]`. VERSION-DEPENDENT (Hypothesis 6.165.x). The consequences, in the order they bite:

| CI override | consequence to plan for |
|---|---|
| `database=None` | **No example database in CI.** A counterexample found in yesterday's CI run is not replayed today; there is no ratchet, so nothing accumulates. |
| `derandomize=True` | The input set becomes a deterministic function of the test function plus the Hypothesis and Python versions — so "flaky" property failures instead appear and disappear *in blocks* when any of those changes. |
| `print_blob=True` | The intended recovery path: a `@reproduce_failure(...)` blob is printed for pasting into a local run. Truncated or discarded CI logs destroy the only handle on the failure. |
| `deadline=None` | A slow-test regression is invisible in CI and fails locally at 200 ms — the opposite of the direction people expect, and a real source of wasted debugging. |
| `suppress_health_check=[HealthCheck.too_slow]` | Generation-speed problems are not reported in CI at all. |

**Overriding it deliberately** is a `conftest.py` profile: `settings.register_profile("...", ...)` followed by `settings.load_profile(...)`, selected by an environment variable your CI sets explicitly rather than inherited from Hypothesis's guess. The mechanism is documented; which profile a project loads, and whether CI keeps a shared example database, is the project's decision — OPEN (pin it in the repo, because the default is a silent behaviour change between environments).

**The seven health checks, named exactly** (`HealthCheck` members, Hypothesis 6.165.x): `data_too_large`, `filter_too_much`, `too_slow`, `large_base_example`, `function_scoped_fixture`, `differing_executors`, `nested_given`. A tripped check raises `FailedHealthCheck`. VERSION-DEPENDENT. The documented suppression route is a profile — `settings.register_profile("my_profile", suppress_health_check=[HealthCheck.filter_too_much])` then `settings.load_profile("my_profile")` — and the docs warn against blanket suppression because several checks "catch subtle interactions that may save you hours of debugging". ESTABLISHED.

**The function-scoped-fixture trap, stated plainly.** `HealthCheck.function_scoped_fixture` exists because a pytest function-scoped fixture requested by an `@given` test "runs once for the whole function, not once per test case". The fixture is **not** reset between generated inputs, so anything mutable it holds — a list, a dict, an in-memory database, a `Mock` — accumulates across all 100 cases, and a property that passes may be an artefact of that accumulation. Suppress it only when the fixture is genuinely idempotent; suppressing it to turn a red test green converts a real leak into a silent one. The health check *is* the enforcement — there is no other detector — which is exactly why every entry in a `suppress_health_check` list belongs in code review. VERSION-DEPENDENT (Hypothesis 6.165.x).

**`deadline` is a soft limit, not a performance assertion.** "We treat the deadline as a soft limit in some cases, where that would avoid flakiness due to timing variability": the deadline is raised during generation and shrinking, and the failing case is then replayed against the real deadline, so "tests right on the cusp of being too slow may pass artificially". Exceeding it raises `DeadlineExceeded`. Do not use `deadline` as a benchmark gate — performance measurement and profiling belong to `python_runtime_diagnostics_manifest.md`. VERSION-DEPENDENT (Hypothesis 6.165.x).

**Two further mechanics that decide whether a property test does anything at all.** First, rejection is not free: `.filter(pred)` narrows inside the strategy and `assume()` rejects at test level — `assume()` is the least efficient of the four adaptors (`.map`, `.filter`, `.flatmap`, `assume`) — and heavy rejection silently reduces the effective case count long before it trips `HealthCheck.filter_too_much`. Construct the constrained strategy (`integers(min_value=1)`) instead of filtering a wide one. Second, **pytest does not collect a `RuleBasedStateMachine`**: without an explicit `TestMyMachine = MyMachine.TestCase` line the whole state machine is dead code reporting zero tests and zero failures. When it does fail, it prints a replayable transcript (`state = DatabaseComparison(); var1 = state.add_key(k=b'')`, and so on) that "most of the time you should just be able to copy and paste ... into a test to reproduce it". ESTABLISHED / VERSION-DEPENDENT (Hypothesis 6.165.x).

### 5. Specifying obligations vs. writing tests

A **test obligation** names what must be verified, not how. Express each obligation as:
1. **Observable contract under test** — the externally visible behavior at a named seam: return value, raised exception, or observable state/effect. (Do not specify internal calls unless the contract is the interaction itself.)
2. **Input partitioning** — divide the input domain into **equivalence classes** (sets expected to be handled identically) and pick representatives; apply **boundary-value analysis** at the edges of each class (min, min±1, max, max±1, empty, zero, overflow). 
3. **Expected observable** — the asserted result for each partition/boundary, stated as a checkable predicate.
4. **Error-path coverage** — obligations for invalid inputs and failure modes: which exception type, which message/contract, which cleanup/rollback must occur. 
5. **Blame assignment** — for every obligation, say which side a failure indicts. This is the half `design-by-contract` supplies that an assertion alone does not (Bertrand Meyer, *Object-Oriented Software Construction*; the element cites the 1988 first edition while the corpus work record is the 1997 second edition — carried forward as recorded, OPEN on which edition to cite): a failed **precondition** indicts the caller, a failed **postcondition** indicts the callee, and that is precisely what decides whether the missing test is a caller test or a callee test. Python spellings: `__post_init__` invariant checks on frozen dataclasses; explicit `if not cond: raise ValueError` for contracts that must survive `-O`; `icontract` / `deal` decorators; `typing.assert_never` for exhaustiveness. ESTABLISHED (Meyer, primary work) / OPEN (nothing mechanically assigns blame — the obligation must state it).
6. **Obligations removed by construction** — a `smart-constructor` ("Smart constructors", Haskell wiki, living) makes one `@classmethod parse()` / `NewType` plus validating factory / pydantic model the only exported way to build a value, with the raw `__init__` private by convention. The testability payoff is arithmetic: error-path obligations that would otherwise repeat on *every* consumer collapse into one construction test. The chain worth stating, from the corpus edges: validate once at construction → later contracts may assume the invariant → whole families of error-path tests disappear. ESTABLISHED (Haskell wiki naming source; the chain is a corpus editorial edge, marked as such) / OPEN (the "private `__init__`" half is convention — Python cannot enforce it; a lint rule on direct construction is the only mechanical route, see `python_linting_practices_manifest.md`).
7. **How the expected observable is compared** — an obligation over floats is incomplete until it names its tolerance. `epsilon-ulp-float-comparison` (Bruce Dawson, "Comparing Floating Point Numbers, 2012 Edition", 2012; ULP framing also Knuth *TAOCP* v2 and Goldberg, 1991) states the trap: **a fixed absolute epsilon is wrong across magnitudes**, so a bare `abs=1e-9` gate is a latent flake, not a tolerance. Use `pytest.approx(expected, rel=..., abs=...)`, `math.isclose` (PEP 485) or `numpy.testing.assert_allclose`; state the relative term for general magnitudes and state the absolute term explicitly for the near-zero case, because relative tolerance degenerates there. For `datetime`/`timedelta`, `pytest.approx()` requires an explicit `abs` or `rel` timedelta and does not support relative tolerance for `datetime` — VERSION-DEPENDENT (pytest 9.1.0). ESTABLISHED (Dawson, primary).

**`assert` has three different lifetimes in Python, and "enforced by assertion" therefore names three different guarantees.** The `executable-assertions` tactic (Bass, Clements & Kazman, *Software Architecture in Practice*, 4th ed., 2021, ISBN 978-0-13-688609-9) says to place assertions "wherever the data is referenced or modified", and its useful framing is that assertions "embed the test oracle in the code". Python then splits that into three: (1) a pytest-**rewritten** `assert` exists only inside modules that pytest's collection discovered, and gives introspection; (2) a plain `assert` in production code **vanishes under `-O`**; (3) only an explicit `raise` survives optimisation. So an invariant that must hold in production is a `raise`, an invariant that documents a "cannot happen" is an `assert`, and an assertion in a shared test helper needs `pytest.register_assert_rewrite()` (§1) or it degrades to a bare `AssertionError`. ESTABLISHED (SAIP 4e for the tactic; CPython `-O` semantics and pytest rewriting scope for the three lifetimes — the type-system side of this split is owned by `python_typing_contract_manifest.md`).

**Which parts of this section are element-backed, and which are practice-backed.** Stated so an agent does not read both as equally grounded: `equivalence-partitioning`, `boundary-value-analysis`, `test-oracle`, `metamorphic-testing`, `test-pyramid`, `contract-test`, `mutation-testing`, `seam`, injected/virtual clock, in-memory database, `fault-injection`, `consumer-driven-contract` and `test-container` are all **absent from the SWE element layer by charter** — they are practice-layer vocabulary, verified absent from the `name` and `aka` fields of all 1083 nodes. **"Characterization test" is the one exception, and it is citable:** it is *present*, as an aka of `golden-master-testing` ("characterization testing (legacy-code framing)"), named in Feathers 2004 — so cite that element rather than treating characterization tests as unnamed practice (§6b). MEASURED (census re-run over `SWE/explorer/data/elements.json`, 1083 nodes, 2026-08-08; substring match over `id`/`name`/`aka`). What the element layer does contribute to this section is narrow and load-bearing: `executable-assertions` (the tactic that embeds the oracle in the code), `design-by-contract` (blame assignment), `smart-constructor` (obligations removed by construction) and `epsilon-ulp-float-comparison` (how an expected observable is compared at all). **Coverage % is a diagnostic, not a target (Martin Fowler, "TestCoverage" — PRIMARY).** Fowler: "Test coverage is a useful tool for finding untested parts of a codebase. Test coverage is of little use as a numeric statement of how good your tests are." He warns: "If you make a certain level of coverage a target, people will try to attain it. The trouble is that high coverage numbers are too easy to reach with low quality testing" (citing assertion-free testing), and expects "a coverage percentage in the upper 80s or 90s" from thoughtful testing while being "suspicious of anything like 100%." This is a textbook instance of **Goodhart's law** — when a measure becomes a target it ceases to be a good measure. Use coverage to find untested code; set obligations on behaviors, not on a percentage. ESTABLISHED.

### 5a. Coverage measurement mechanics, and the arithmetic that makes thresholds lie

§5 says coverage is a diagnostic. This subsection says *what it is actually measuring*, because three defaults make the number mean less than it appears to, and because a threshold's arithmetic is not the arithmetic people assume. Gate **wiring** — which check runs where, with what exit code, and how a standard is adopted incrementally — belongs to `python_quality_gates_manifest.md`; what follows is the measurement semantics that wiring depends on.

**Measurement surface.**

| mechanism | default | what an agent gets wrong |
|---|---|---|
| `[run] branch` | `False` | A quoted "94% coverage" without it is **statement** coverage, and is compatible with every `else:` in the codebase being untested. Branch coverage records "pairs of line numbers: a source and destination for each transition", compares measured transitions against statically-derived possible ones, and paints partial lines yellow in HTML with the un-taken destination annotated. |
| `[run] core` | `sysmon` on 3.14+ | `sysmon` "does not yet support plugins, dynamic contexts, or some concurrency libraries", and cannot do branch coverage at all on 3.12/3.13. If you need per-test attribution, set `[run] core = ctrace` explicitly. |
| `[run] dynamic_context` | unset | The only built-in value is `test_function` ("start a new dynamic context for every test function"). Static contexts come from `--context=` / `[run] context`; when both exist "they are joined with a pipe symbol to be recorded as a single string". Report with `--contexts` (comma-separated regexes) and `coverage html --show-contexts`. |
| `sysmon` + dynamic contexts | mutually exclusive | Config-file combinations were already rejected, but until coverage.py **7.15.3 (2026-08-02)** the context API that pytest-cov uses "would be silently dropped"; 7.15.3 makes it a warning. Symptom on older versions: an empty per-test attribution report that reads like a reporting bug. |
| subprocess measurement | off | **pytest-cov 7.0.0 (2025-09-09) dropped subprocess support** and requires coverage >= 7.10.6. Child-process coverage now needs `[run] patch = subprocess` in coverage config. `patch` (added in coverage.py 7.10) accepts `execv`, `_exit`, `fork`, `subprocess`; `subprocess` "configures Python to start coverage automatically" and covers `subprocess`, `os.system()` and the `execv`/`spawnv` families; `_exit` saves data before `os._exit()`; `execv` is "Not available on Windows". Symptom without it: a CLI's own module reports 0% while its tests pass. |
| `[run] parallel` / `relative_files` / `[paths]` | `False` / `False` / — | `parallel` appends "the machine name, process id and random number to the data file name"; `relative_files` stores relative paths, which is what makes data files from containers combinable; `[paths]` maps equivalent prefixes for `coverage combine`. Omitting the pair is why container and host data files refuse to merge. |
| `[run] concurrency` / `sigterm` | `"thread"` / `False` | Both are documented defaults. This file does **not** restate what other `concurrency` values do, and the coverage.py docs note only that `sysmon` "does not yet support … some concurrency libraries" — OPEN: check the configuration page against the concurrency model you actually use before trusting a number from a non-thread runtime. |

VERSION-DEPENDENT (coverage.py 7.15.x, pytest-cov 7.x) unless marked otherwise; the quoted strings are from the coverage.py configuration, branch and contexts pages. `# pragma: no branch` marks an intentionally partial branch such as `while True:` — and note the second-order effect: if one arm of a conditional is excluded, coverage.py stops treating the conditional as a branch at all, and a generator expression can report a partial branch "because the generator did not iterate until `StopIteration` is raised". ESTABLISHED.

**The arithmetic that makes a threshold lie.** Every item here is documented behaviour, not folklore:

- `[report] fail_under` is "a target coverage percentage. If the total coverage measurement is under this value, then exit with a status code of 2" — **status 2, not 1**, so a CI script testing `$? -eq 1` treats a threshold failure as success. ESTABLISHED.
- `[report] precision` defaults to `0` and "also affects the interpretation of the `fail_under` setting", so a true **89.6% is reported and compared as 90% and passes `fail_under = 90`**. Only `fail_under = 100` is documented to be immune: "A setting of 100 will fail any value under 100, regardless of the number of decimal places of precision." ESTABLISHED.
- `fail_under` compares the **total only**. The configuration reference documents no per-file or per-module threshold, so a project-wide 90% can hide a brand-new 0%-covered module; a per-file or changed-lines gate requires a separate tool. ESTABLISHED (absence across the full config reference).
- `[report] exclude_lines` **replaces** the built-in exclusion patterns — including `pragma: no cover` — so adding one custom pattern silently drops the defaults. `exclude_also` is the additive form; identically, `partial_branches` replaces while `partial_also` adds (the defaults include `pragma: no branch`). ESTABLISHED.
- Branch coverage is off by default (above), so the number being gated is usually the weaker of the two available numbers. ESTABLISHED.

**The honest conclusion, mechanically derived rather than asserted:** `fail_under` compares one global number computed from *executed* lines, and execution is not verification. A suite of assertion-free tests raises the number without adding a single obligation. **Coverage detects unexecuted code; it cannot detect unverified code.** The mechanism that does test the assertions is mutation testing — §5b. ESTABLISHED (derived from the documented semantics above; the judgement is Fowler's, quoted in §5).

### 5b. Verification depth beyond coverage: mutation testing

**What it answers.** Coverage answers *was this line executed*. Mutation testing answers *would a wrong version of this line have been caught* — it perturbs the source, reruns the suite, and reports the mutants that survived. A surviving mutant is a precise, addressable statement that no assertion discriminates that behaviour. ESTABLISHED (the mechanism, per mutmut's documentation quoted below); note that no element id exists for mutation testing in the SWE corpus — see §8.

**mutmut 3.7.0 (2026-07-31) is the default choice.** Workflow: `mutmut run`, `mutmut browse` (interactive TUI), `mutmut apply <mutant>`. It requires a suite that already passes and runs fast; it stores state and mutants in a `mutants/` directory, "Remembers work that has been done, so you can work incrementally", and only retests functions whose source changed. Configuration is `[tool.mutmut]` in `pyproject.toml` with keys including `source_paths`, `pytest_add_cli_args_test_selection`, `max_stack_depth`, `cache_invalidation_files`; deleting `mutants/` forces a full restart. VERSION-DEPENDENT (mutmut 3.x). The operators are deliberately small — "Integer literals are changed by adding 1. So 0 becomes 1, 5 becomes 6, etc." and comparison operators are perturbed (`<` becomes `<=`) — which is exactly why surviving mutants of this kind are the off-by-one and boundary defects that line coverage cannot see, and why mutation results pair naturally with the boundary-value obligations of §5. ESTABLISHED (mutmut docs).

**Two scope limits to state before anyone trusts a score.** First, **mutmut 3 does not mutate code outside functions**: "If you want to mutate code outside of functions, you can try using mutmut 2, which has a different execution model than mutmut 3+." Module-level constants, dataclass field defaults and top-level configuration are untouched, so a clean score says nothing about them. VERSION-DEPENDENT (mutmut 3.x). Second, **cost is multiplicative**: the suite runs once per surviving-candidate mutant, so wall-clock scales as mutant count × suite runtime. **No primary source quantifies it** — the percentage claims circulating in 2026 blog posts trace to marketing content, not to a loadable survey — OPEN, carried forward as unquantified rather than estimated.

**How to adopt it without building a timeout.** Mutation testing on a suite that is not already green, or not already fast, produces garbage or never finishes; adding `mutmut run` to a per-PR gate on a multi-minute suite is a timeout with extra steps. The defensible shape: scope it to a named set of protected modules, run it on a nightly or weekly cadence, and gate on **"no new surviving mutants in protected modules"** rather than on an absolute score. A 100% mutation-score gate is worse than no gate, for exactly the Goodhart reason Fowler gives for coverage in §5. cosmic-ray 8.4.6 (2026-04-02) is the alternative — alive but bursty (8.4.1 2024-11-10, 8.4.3 2025-09-21, 8.4.4 2026-02-21, 8.4.6 2026-04-02, versus mutmut's roughly monthly cadence) — and is the choice when you need distributed execution or pluggable operators. VERSION-DEPENDENT. OPEN (the cadence and the protected-module list are project decisions; nothing selects them for you).

**Why this matters for the "ban assertion-free tests" rule.** That ban is the natural companion to a coverage gate, and it is the clearest case in this manifest of a practice with no first-party enforcement: **no pytest option and no maintained, widely-used plugin that fails a test containing no assertion was confirmed in this pass** (`pytest-finer-verdicts` solves a different problem — treating non-assertion failures as errors — and `pytest-check` adds multiple soft checks per test). The two defensible mechanisms are therefore (a) a project-local `pytest_collection_modifyitems` hook in `conftest.py` that AST-inspects each collected item for an `assert`, a `pytest.raises` block or a `unittest` assertion method, and (b) mutation testing as the actual oracle for assertion strength. OPEN — say which one this project chose, because "we don't write assertion-free tests" enforces nothing.

### 5c. Testing the error contract

The error contract itself — exception hierarchy, structured attributes, chaining, the typed-result channel and the deprecation path for an error type — is owned by `error_tracing_contract_manifest.md`. This subsection is only the *assertion mechanics* that make those obligations checkable, because a contract nobody asserts on is a docstring.

**Asserting on structured exception attributes, not on message text.** `pytest.raises(check=fn)` takes a predicate over the raised exception (added in pytest 8.4.0, 2025-06-02), which is the mechanism that lets an obligation say "callers can depend on `err.code` and `err.offending_id`" instead of grepping `str(exc)`. Message-text assertions couple the test to prose; attribute assertions couple it to the contract. VERSION-DEPENDENT (pytest 8.4+).

**Asserting on an exception group.** `pytest.RaisesGroup` and `pytest.RaisesExc` were added in pytest 8.4.0 "as an equivalent to `pytest.raises()` for expecting `ExceptionGroup`", with flags that emulate `except*` and support for nesting; the same release added typed support for passing `ExceptionGroup[Exception]` / `BaseExceptionGroup[BaseException]` to `pytest.raises`. pytest 9.1.1 fixed bugs in `RaisesGroup` logic, which is one more reason the floor is 9.1.1 rather than 9.x. VERSION-DEPENDENT (pytest 8.4+ for the API, 9.1.1 for the fixes). Practical rule: any code path that uses `asyncio.TaskGroup` or `except*` raises *groups*, so a test written with plain `pytest.raises(ValueError)` against it asserts the wrong shape and may pass for the wrong reason — assert the group structure explicitly.

**Asserting on the typed-result channel.** When a function returns a result union rather than raising (a frozen-dataclass `Ok`/`Err` pair, or a library type), there is no exception to catch and `pytest.raises` is simply the wrong tool. The test-side obligation is different in kind: assert on the *variant* (`isinstance` / `match` narrowing) and then on its payload, and add one test per variant so the union's arms are all exercised. Static exhaustiveness is a checker's job, not a test's — mypy's `--enable-error-code exhaustive-match` (VERSION-DEPENDENT, mypy 1.17+) and pyright's `reportMatchNotExhaustive`, with `typing.assert_never` as the runtime backstop — and the division of labour is owned by `python_typing_contract_manifest.md` and `error_tracing_contract_manifest.md`. The point to hold onto is that a typed-error channel moves the obligation from "which exception" to "which variant, and is the match exhaustive".

**Making the deprecation of an error type fail the build.** Pair the above with `filterwarnings = ["error::DeprecationWarning"]` in the pytest config (§1a) and `-X dev` in the test command, so a deprecated exception type or a deprecated stdlib call surfaces as a red test rather than as a line of scrollback. That is the enforcement mechanism for the removal calendar; the calendar itself lives in `error_tracing_contract_manifest.md`, and the interpreter switches themselves are catalogued in `python_platform_baseline_manifest.md` and `python_runtime_diagnostics_manifest.md`. ESTABLISHED (pytest and CPython documented behaviour).

### 6. Integration-test strategy primitives

- **Contract testing at component boundaries — and the mechanical form that keeps a fake honest.** At each substitution point, define the contract (inputs, outputs, side effects, error behavior) and test that both sides honor it. The rule everyone states aspirationally is that the fake used in unit tests and the real implementation used in integration tests must satisfy the **same** contract test suite; the mechanical form in pytest is a fixture parametrized over both constructors — `@pytest.fixture(params=[make_fake, make_real])` — with the real case carrying an `integration` marker, so `-m "not integration"` yields the fast suite while the identical assertions still run against the real implementation elsewhere. Register that marker and run under `--strict-markers` (§1a) or the deselection silently stops working. Pair it with a `Protocol` at the boundary so mypy pins the static shape while the shared suite pins the behaviour: drift is then caught by the type checker or by the shared tests rather than by production. **Corollary worth stating bluntly: a fake with no contract suite behind it is a stub with better branding** — it encodes the author's belief about the contract, and the drift is undetectable. ESTABLISHED (the pytest mechanics are documented; the pairing convention is this manifest's). Naming provenance: this practice is **Contract Test** (Fowler, bliki "Contract Test", 2011), which the SWE corpus keeps deliberately outside its element layer as a "cross-component testing practice rather than an in-program construct" — so it is cited practice, not a citable element id, and this manifest carries no URL for it because none was recorded in the source pack. FLAGGED-SECONDARY for the naming attribution.
- **Own a Gateway per external system, then substitute a Service Stub behind it** (the four bullets below are one derivation, not four patterns — see §3 for the `gateway` / `service-stub` citations, ESTABLISHED, Fowler PoEAA):
  - **Filesystem** — use `tmp_path` (see below) instead of touching real paths.
  - **Clock** — inject a clock dependency or use `monkeypatch.setattr` to substitute `datetime`/time sources; do not call real wall-clock in core logic.
  - **Network** — substitute a fake client or block network (e.g., `monkeypatch.setattr` raising on `urllib.request.urlopen`); reserve real network for explicitly-marked integration tests.
  - **Subprocess** — wrap process invocation behind a seam and substitute a fake in unit tests.
- **Host-side testing.** Run logic in-process against fakes/harnesses on the developer/CI host; reserve real external systems for a smaller, marked integration layer. This mirrors Gary Bernhardt's formulation, stated verbatim as "Functional core — Many fast unit tests. Imperative shell — Few integration tests" (from his SCNA 2012 talk "Boundaries").
- **pytest-provided isolation (VERIFIED against official pytest docs):**
  - **`tmp_path`** — "Provide a `pathlib.Path` object to a temporary directory which is unique to each test function." Function-scoped. ESTABLISHED.
  - **`tmp_path_factory`** — "Make session-scoped temporary directories and return `pathlib.Path` objects"; its `mktemp()` creates multiple dirs; use it for session-scoped temp resources. ESTABLISHED.
  - **`tmp_path` vs older `tmpdir`** — `tmpdir` returns a legacy `py.path.local` object and is superseded: the docs state "These days, it is preferred to use `tmp_path`." `tmpdir`/`tmpdir_factory` remain for backward compatibility. ESTABLISHED.
  - **`monkeypatch`** — "Temporarily modify classes, functions, dictionaries, `os.environ`, and other objects"; methods include `setattr`, `delattr`, `setitem`, `delitem`, `setenv`, `delenv`, `syspath_prepend`, `chdir`, `context`. "All modifications will be undone after the requesting test function or fixture has finished." ESTABLISHED.
  - **`capsys`** — captures text written to `sys.stdout`/`sys.stderr`; `capsys.readouterr()` returns an `(out, err)` namedtuple. (Variants: `capsysbinary`, `capfd`, `capfdbinary`.) ESTABLISHED.
- **Treat fixtures and test data as version-controlled code.** Fixtures, conftest.py, and test data files live in the repo, are reviewed, and evolve with the contract; do not generate them ad hoc outside version control. ESTABLISHED (principle).

**Three different reasons to substitute — which is what tells you when a substitution is *done*.** The four bullets above look like one activity; the testability tactics of §7a split them into three, each with a different exit criterion. This is the distinction that lets a specification close a substitution obligation instead of leaving it open forever.

| you are substituting because… | tactic realized | exit criterion |
|---|---|---|
| the resource is **uncontrollable** (clock, network, filesystem, battery) | `sandbox` — "virtualizing uncontrollable resources" | the resource is consequence-free in the test environment: no real time passes, no real socket opens, no path outside `tmp_path` is written |
| the collaborator **could answer differently** on two runs | `limit-nondeterminism` | reruns agree — and agree under reordering (§6c) |
| you need **controlled input data** | `abstract-data-sources` | the input partition of §5 is covered by the supplied data |

ESTABLISHED for the tactics (Bass, Clements & Kazman, SAIP 4e, 2021, ISBN 978-0-13-688609-9); the construct→tactic assignment is SWE-corpus editorial, marked as such in §7a. A substitution whose reason you cannot name in this table is a substitution with no completion test.

- **The `sandbox` toolkit, Python-specific.** The resource-virtualization half of the tactic is what a test suite wants: `tmp_path` and `tmp_path_factory` for the filesystem, `monkeypatch.setenv` for environment, `sqlite3` `:memory:` for a database, `time-machine` or `freezegun` for the clock (always behind an injected clock — §6c), subprocess isolation via `sys.executable -I`, plus `pyfakefs` for a full fake filesystem and `pytest-socket` to block outbound network — OPEN for those last two: they are named in the source pack as the Python instantiations but no version or maintenance status was verified in this pass, so pin them deliberately if adopted. The OS-confinement half of `sandbox` (seccomp, jails) is **out of scope at this scale** — a single-process test suite that reaches for kernel confinement has bought a distributed-systems mechanism for a problem `tmp_path` already solves. ESTABLISHED (tactic wording: the motivating case is named exactly as "waiting for a real time boundary").
- **`Page Object` (Martin Fowler, bliki "PageObject", 2013 — records that it was first described as Window Driver at eaaDev and popularized by Selenium), and where it does *not* apply.** A test-side class wrapping an application surface behind intention-revealing methods: `api.place_order(...)` rather than `client.post("/orders", json=...)`. It applies when the project drives a UI or an HTTP surface — Playwright/Selenium wrappers, or an `httpx.ASGITransport` / test-client wrapper. It does **not** apply to a library, a CLI's own functions, or anything without a volatile external surface; importing it there adds an indirection layer with nothing behind it. The relation that explains why it works: `page-object` **specializes** `humble-object` — "a Page Object is a Humble Object for the UI: assertion-free wrapper delegating to test logic" (Fowler) — so the page object holds **no assertions**. ESTABLISHED (Fowler, primary).
- **Container-backed tests are integration tests by definition.** testcontainers (testcontainers-python) 4.15.0 (2026-07-24, after four release candidates) provides "throwaway instances of anything that can run in a Docker container". It requires a working container runtime on the test host, which by construction disqualifies its tests from the Feathers definition in §2. Mark them and exclude them from the default run; leaving them unmarked makes the whole suite fail on any machine without Docker, which is how a fast suite dies. VERSION-DEPENDENT (testcontainers 4.15.0).
- **Schema-driven API testing turns documentation into an executable contract.** schemathesis 4.24.3 (2026-07-25) does "Adaptive API testing for OpenAPI and GraphQL" and is "built on top of Hypothesis, a powerful property-based testing library for Python" — so every Hypothesis fact in §4a applies **transitively**: the CI profile, `deadline`, the health checks and the example database all govern a schemathesis run too. The payoff is that schema drift becomes a test failure instead of a support ticket. VERSION-DEPENDENT (schemathesis 4.24.3).

### 6a. Constructing test data: builder as the default, object mother as the named alternative

§6's "treat test data as version-controlled code" says where test data lives and nothing about how it is built. Two named mechanisms exist, and the tradeoff between them is a *sourced* one rather than a taste.

**Default: Test Data Builder (Nat Pryce, "Test Data Builders: an alternative to the Object Mother pattern", 2007; book form in Steve Freeman & Nat Pryce, *Growing Object-Oriented Software, Guided by Tests*, 2009, ISBN 978-0-321-50362-6).** The rule transposes verbatim: **a builder makes the significant values explicit while defaulting the rest.** Python spellings, in increasing ceremony: a frozen `@dataclass` plus `dataclasses.replace(default_order, total=Money(0))`; a `with_*` fluent builder; or `hypothesis.strategies.builds(Order, total=...)`, which also gets you the property-based path for free. `polyfactory` / `factory_boy` are the library forms — OPEN, no version or maintenance status verified in this pass. ESTABLISHED (naming source as recorded; note that the corpus carries the 2009 GOOS book as the work record and the 2007 article as the naming source only).

**The named alternative you are rejecting: Object Mother (Peter Schuh & Stephanie Punke, "ObjectMother: Easing Test Object Creation in XP", XP Universe 2001 — cite as a `named-in` string; the SWE corpus has **no work record** for it and its covering work is Meszaros, 2007).** In Python it is a `conftest.py` module of fixtures or plain functions returning canonical exemplars: `overdue_invoice()`, `standard_customer()`. The tradeoff is in the title of Pryce's article, and it is carried as a *sourced* `alternative-to` edge: an Object Mother "centralizes canonical test fixtures, at the cost of coupling tests to shared exemplars", while builders exist because "Object Mothers proliferate variants and obscure which attributes matter to a test". ESTABLISHED (the edge is sourced to Pryce 2007) / OPEN (the naming source has no corpus work record — do not present it as verified).

**Why this belongs in a testability manifest and not in a style guide:** both mechanisms realize `abstract-data-sources` (§7a), as does `parameterized-test` — "running one test body per row of an input/expected table abstracts test inputs into a substitutable data source". So the builder-vs-mother choice, the parametrize table, and reading cases from files under `tests/data/` are the same tactic at three ceremonies, and the exit criterion for all three is the one in §6's substitution table: the input partition of §5 is covered. ESTABLISHED (tactic, SAIP 4e) / editorial for the construct→tactic edges.

### 6b. Recorded-output tests: golden master, snapshots, and record/replay

**One mechanism, five names.** `golden-master-testing` folds approval testing, snapshot testing, characterization testing (the legacy-code framing), reference-output testing and golden-file testing into a single construct, named in Michael Feathers, *Working Effectively with Legacy Code*, 2004, ISBN 978-0-13-117705-5 (as "characterization test"), with ApprovalTests and Jest "snapshot testing" as aka-level names carrying no corpus work record. The mechanism is precise and has three required parts: **a stored reference artefact + a comparator + an explicit approve-the-diff step.** In Python: write observed output to a versioned file under `tests/golden/`, compare on rerun, and gate regeneration behind an explicit `--approve` / `--snapshot-update` option registered with `pytest_addoption`. Library forms: `syrupy`, `pytest-regressions`, `approvaltests` — of which only syrupy was version-verified in this pass (5.5.3, 2026-07-11, a "zero-dependency pytest snapshot plugin" using `assert x == snapshot`, whose stated soundness principle is failing when a snapshot is **missing**, not only when it differs); the other two are OPEN on version and maintenance. ESTABLISHED (Feathers, primary naming work) / VERSION-DEPENDENT (syrupy 5.5.3).

**The precondition nobody's quickstart mentions: canonical serialization.** `golden-master-testing` **uses** `canonical-serialization` — "the recorded output must be canonicalized (stable ordering, normalized noise) so reruns match the stored master" — and that single edge is the diagnosis for most flaky snapshot suites. Canonical form is a real standard rather than a habit: ITU-T Recommendation X.690 (02/2021) DER and RFC 8785 *JSON Canonicalization Scheme* (2020). The Python minimum: `json.dumps(obj, sort_keys=True, ensure_ascii=False, separators=(",", ":"))`, and normalize timestamps, uuids, absolute paths and float formatting **before** writing the master. If the artefact is not canonical, the suite is not testing behaviour — it is testing dict ordering. ESTABLISHED (X.690, RFC 8785 as the canonicalization sources; the edge is marked editorial in the corpus, and it is the most useful editorial edge in the pack).

**The discipline that makes the whole family safe:** a snapshot diff must be **read**, not accepted. An `--snapshot-update` in a pre-commit hook or a CI auto-approve turns a golden-master suite into a change-recorder that can never fail. That is a review rule, and nothing mechanical enforces it — OPEN. The one mechanical property to insist on is syrupy's: fail on a *missing* snapshot, so an untested surface cannot masquerade as a passing one.

**Record/playback is a different mechanism, and its scope is narrow.** `record-playback` (Bass, Clements & Kazman, SAIP 4e, 2021) records "information as it crosses interfaces" so a fault-inducing state can be re-entered — that is *not* what golden master does, which records only the final output. Distinguish them by what is stored: golden master stores the **output**; record/playback stores **what crossed the boundary**. Python forms: cassette recording at a Protocol or gateway boundary (`vcrpy` / `betamax` for HTTP; `responses` / `respx` for replay-only; or a hand-rolled decorator writing JSONL of `(call, args, result)` that a fake replays) — OPEN for `vcrpy` / `betamax`, named in the source pack but not version-verified in this pass. **The caveat is load-bearing:** record only at a *declared* boundary. Recording inside a Python process usually means monkeypatching, which records the patch rather than the interface, and the cassette then encodes your test harness instead of the contract. ESTABLISHED (tactic, SAIP 4e; the monkeypatch caveat is a corpus adjudication carried forward verbatim in substance).

### 6c. Determinism obligations for tests

A flaky test is not a fact about the universe; it is an unclosed obligation. Four sources of nondeterminism, the primitive that closes each, and — importantly — the escape clause for the case that cannot be closed. Concurrency *design* (structured concurrency, cancellation, the four execution models) belongs to `python_concurrency_determinism_manifest.md`; what follows is only the test-suite obligation.

| source | closing primitive | what enforces it |
|---|---|---|
| **order** — tests that depend on each other or on module-level global mutation | `pytest-randomly` 4.1.0: shuffles module order, then class order, then function order | Reordering *is* the detector. It reseeds at the start of the run and again before each test's setup, call and teardown, deriving each seed from the base seed plus the test ID, and prints the seed in the header. Replay with `--randomly-seed=last` (locally) or the printed integer (anywhere), and disable the plugin entirely with `-p no:randomly` while isolating a failure. |
| **clock** — wall-clock reads inside decision logic | an injected clock at a `Protocol` boundary; `time-machine` 3.3.1 or `freezegun` 1.5.5 only where injection is impossible | Nothing detects a hidden `datetime.now()` in the core — review is the only finder. Injection is the design fix; the libraries are the retrofit, and they make the effect controllable without revealing the call site. |
| **network** — real sockets in a "unit" test | `respx` 0.23.1 for HTTPX, `responses` 0.26.2 for `requests` | **Not interchangeable.** Installing the wrong one produces a suite that issues real outbound traffic while the fixture reports as active. Pair with network blocking (`pytest-socket`, OPEN on version — §6) so the failure mode is an error rather than a slow pass. |
| **RNG** — module-level `random.*`, legacy NumPy global state | inject `random.Random(seed)`; `numpy.random.default_rng(seed)`; `PYTHONHASHSEED` for iteration-order stability | `pytest-randomly` reseeds `random`, NumPy's legacy global random state, Faker, factory_boy, Model Bakery, and anything registered via the `pytest_randomly.random_seeder` entry point — so a suite that leans on the global RNG *appears* deterministic under the plugin and is not, outside it. |

VERSION-DEPENDENT (pytest-randomly 4.1.0, time-machine 3.3.1, freezegun 1.5.5, respx 0.23.1, responses 0.26.2). Two switch-level traps: `--randomly-dont-reorganize` still reseeds, and `--randomly-dont-reset-seed` still shuffles — they are independent switches, so an agent reaching for one "to turn off randomness" gets half of it. And on library choice: time-machine's release cadence is materially higher than freezegun's (3.3.1 on 2026-08-04 versus 1.5.5 on 2025-08-09), but the widely-repeated claim that time-machine is faster *because* it patches at the C level **could not be confirmed from a primary page in this pass** — OPEN, carried forward rather than restated as fact.

**The rule that makes the whole table worth anything:** a suite that cannot reproduce a failure from its own printed seed has no determinism story. Randomised order plus a random seed is reproducible only if the seed is recorded — CI logs that are truncated or discarded destroy the only handle on the failure, and `--randomly-seed=last` works locally, not across machines. OPEN (log retention is a project decision; nothing in pytest preserves the header for you).

**The escape clause, which the tactic states and most advice omits.** `limit-nondeterminism` says to eliminate nondeterminism "where possible", and — as a *sourced* `uses` edge to `record-playback` (Bass, Clements & Kazman, SAIP 4e, Testability chapter) — that "where nondeterminism is unavoidable, the tactic says to manage it with tactics like record/playback". So the graded rule is: **eliminate → if not eliminable, record at a declared interface and replay (§6b) → only then retry.** Retry-with-quarantine is the last rung, not the first, and a quarantine list with no expiry date is a permanent lie about the suite's status. ESTABLISHED (SAIP 4e, sourced edge).

**One design-level primitive belongs here because it removes a whole flake class.** `structured-concurrency` (Nathaniel J. Smith, "Notes on structured concurrency, or: Go statement considered harmful", vorpus.org, 2018; Trio nurseries; JEP 453) is a cited realizer of `limit-nondeterminism`: with `asyncio.TaskGroup` (VERSION-DEPENDENT, 3.11+) and `asyncio.timeout` there are no detached tasks, and therefore no test that passes because a stray task had not run yet. The reviewable rule is narrow: **ban bare `asyncio.create_task` outside a scope in test-covered code.** Enforcement is a lint rule rather than a test — see `python_linting_practices_manifest.md` — and the design rationale is owned by `python_concurrency_determinism_manifest.md`. The related state-ownership move, `thread-confinement` (Goetz, Peierls, Bloch, Bowbeer, Holmes & Lea, *Java Concurrency in Practice*, 2006, ISBN 978-0-321-34960-6; in Python: a single-threaded event loop, `threading.local`, `contextvars`), is the other cited realizer. ESTABLISHED (naming sources as recorded).

### 6d. Async test execution: two plugins, two task semantics

Honesty first: there is no single answer here, and the two options differ in **program semantics, not syntax**. Choosing by which decorator looks familiar is how a suite ends up with fixtures whose cancel scopes silently do not work.

| | pytest-asyncio 1.4.0 | AnyIO's bundled pytest plugin |
|---|---|---|
| install | separate plugin | ships **inside the AnyIO distribution** — nothing extra to install |
| opt-in | `@pytest.mark.asyncio`; `asyncio_mode` accepts `auto` and `strict`, and "If no asyncio mode is specified, the mode defaults to strict" | `@pytest.mark.anyio`, which "has the same effect as applying the `pytest.mark.usefixtures('anyio_backend')`" |
| backend | asyncio | the `anyio_backend` fixture is function-scoped and by default "runs everything on all supported backends" |
| **task semantics** | "runs the setup and teardown phases of each async fixture in a new async task per operation, making context variable propagation impossible and preventing task groups and cancel scopes from functioning properly" | "runs all async fixtures and tests in the same task, so context variables set in async fixtures or tests … will affect other async fixtures and tests within the same runner" |
| loop scope | `asyncio_default_fixture_loop_scope` unset "defaults to the fixture scope", and the plugin warns that "In future versions of pytest-asyncio, the value will default to `function` when unset"; `asyncio_default_test_loop_scope` unset defaults to function scope; both accept `function`, `class`, `module`, `package`, `session` | governed by the `anyio_backend` fixture's scope |

ESTABLISHED (each quoted string from the respective project's documentation; the task-semantics comparison is **AnyIO's own characterisation of pytest-asyncio**, which is how it is recorded here) / VERSION-DEPENDENT (pytest-asyncio 1.4.0). Four consequences, all inheriting those tags:

- **Decide by whether the code under test needs cancel-scope-correct fixtures.** If a fixture must open a task group or a cancel scope that spans setup and teardown, or must set a `contextvar` the test then observes, pytest-asyncio's new-task-per-operation model breaks it and AnyIO's same-task model does not. Code correct under one plugin can be broken under the other; this is not a marker rename.
- **An unmarked `async def test_...` is not run by pytest-asyncio in the default `strict` mode.** Combined with pytest 9's async handling, that is a test which reports as collected and contributes nothing. Set `asyncio_mode` explicitly.
- **Do not enable both auto modes.** AnyIO's docs state that its `anyio_mode = "auto"` "does not work if `pytest-asyncio` is installed and configured to use its own `auto` mode"; the fix is to remove `asyncio_mode` so pytest-asyncio falls back to strict.
- **Set `asyncio_default_fixture_loop_scope` explicitly today.** Unset means "the fixture's own scope" now and "`function`" in a future release, and the plugin warns about exactly this — an explicit value is the only way to keep behaviour stable across an upgrade.

Related pytest 9 fact from §1, repeated here because it lands in async suites: a **synchronous** test that depends on an **asynchronous** fixture is now an error rather than a warning (VERSION-DEPENDENT, pytest 9.0+). Previously it yielded a coroutine object that the test then compared or truth-tested, usually passing by accident. Concurrency design, cancellation semantics and the choice of execution model are owned by `python_concurrency_determinism_manifest.md`.

### 6e. Parallel execution: pytest-xdist distribution modes

| `--dist` mode | what it guarantees | use when |
|---|---|---|
| `load` (default) | "Sends pending tests to any worker that is available, without any guaranteed order" — **no ordering guarantee at all** | tests are genuinely independent |
| `loadscope` | groups by module for functions, by class for methods | an expensive module- or class-scoped fixture must not be built per worker |
| `loadfile` | groups by file | file-level fixtures or file-level resources |
| `loadgroup` | groups by the `xdist_group` mark | you need explicit co-location control |
| `worksteal` | even initial split, idle workers steal | wide runtime variance between tests |
| `no` | no distribution | debugging a parallel-only failure |

VERSION-DEPENDENT (pytest-xdist 3.8.0). `-n auto` "uses as many processes as your computer has physical CPU cores"; `-n logical` uses logical cores and requires `psutil` — so an agent that assumes `auto` counts hyperthreads will mis-size CI runners. Three rules follow. First, **`--dist load` guarantees no ordering**, so any test that depends on another test having run, on a shared module-level global, or on a session fixture's mutation order breaks only under `-n`, and then intermittently: xdist is therefore a *detector* of the coupling that §2a's fixture-strategy decision creates. Second, `loadscope` / `loadfile` / `loadgroup` co-locate but do not make dependent tests correct — **they hide the defect**, so reaching for them to fix an intermittent failure is a decision to keep the bug. Third, **pytest-xdist 3.8.0 (2025-07-01) predates pytest 9.0 entirely** and is the one load-bearing plugin in this stack with no release in over a year; distributors have carried out-of-tree pytest 9 compatibility patches — FLAGGED-SECONDARY (the existence of a downstream `pytest-xdist-3.8.0-pytest-9.patch` dated 2026-05-09 comes from a distribution changelog, not from upstream). Treat xdist-plus-pytest-9 as a combination to smoke-test, not to assume.

Environment-matrix orchestration is a different layer and a different owner: tox 4.58.0 (2026-07-21) is the declarative matrix (native TOML since 4.21.0, 2024-09-30, covering both `tox.toml` and `[tool.tox]` in `pyproject.toml`) and nox 2026.7.11 (2026-07-12) is the programmable one (sessions as decorated Python functions in a `noxfile.py`) — pick tox when the matrix is declarative and nox when it needs real control flow. VERSION-DEPENDENT. ### 7. Testability design patterns (verification-relevant facts)

- **Dependency injection in Python.** Pass collaborators in via the constructor or as function/method parameters rather than constructing them internally; this creates an object (polymorphic) seam where a fake/stub can be substituted. pytest fixtures are themselves a DI mechanism (a test declares a needed fixture as a parameter; the framework supplies it). ESTABLISHED.
- **The alternative DI is chosen *against*, named: `service-locator` (Alur, Crupi & Malks, *Core J2EE Patterns*, 2001 — cite as a `named-in` string; the SWE corpus has **no work record** for it, and its covering works are Fowler, 2004, and Nystrom, 2014).** The Python forms are so ordinary they are rarely recognised as a pattern choice: a module-level singleton, `get_settings()`, `current_app`, `django.conf.settings`, a `REGISTRY` dict. The testability consequence is exact — **the locator keeps the dependency out of the signature, so tests must `monkeypatch` a global instead of passing an argument** — which means the substitution point is invisible in the callee's type signature and cannot be checked by mypy. `registry` carries the same `alternative-to` edge. Both edges are *sourced* to Fowler, "Inversion of Control Containers and the Dependency Injection pattern" (2004), the same article the DI bullet above leans on: "Looking services up in a Registry/Service Locator vs having them injected are competing ways to obtain collaborators." ESTABLISHED (Fowler, primary) / OPEN (the naming source has no corpus work record).
- **Protocol-typed dependencies (typing.Protocol / PEP 544 — PRIMARY).** PEP 544 (accepted; available since Python 3.8) specifies **structural subtyping** ("static duck typing"): "Protocols are defined by including … `typing.Protocol` in the base classes list." Any class with matching members is a structural subtype without explicit inheritance, so a production implementation and a test fake both satisfy the same `Protocol` and are type-checked at the seam. "At runtime, protocol classes will be simple ABCs"; `@runtime_checkable` adds `isinstance()` support but "only checks that all protocol members exist, not that they have the correct type," and signatures are not checked at runtime. ESTABLISHED/VERSION-DEPENDENT (3.8+).
- **Where the `Protocol` lives is a separate decision: `Separated Interface` (Martin Fowler, *PoEAA*, 2002).** Put the `Protocol` in the **consumer's** module (`billing/ports.py`) and the implementation in `billing/adapters/stripe.py`. The consequence in Python is concrete: there is no import from consumer → adapter, so a test fake needs no third package, and mypy checks both sides against one declaration. This answers the question that "use Protocol-typed seams" leaves open — *where does the Protocol live* — and the sourced edge states the pairing: `separated-interface` **composes-with** `dependency-injection`, "DI wires the concrete implementation to a client that depends only on the separated interface." Enforcement of the resulting dependency direction is mechanical but lives elsewhere: `import-linter` / `Tach` contracts, owned by `python_module_boundaries_manifest.md`. ESTABLISHED (Fowler, PoEAA — primary work; the Python packaging consequence is this manifest's).
- **Functional core, imperative shell (Gary Bernhardt — PRIMARY for the phrasing).** The phrasing originates in Gary Bernhardt's talk "Boundaries" (SCNA 2012); per the talk page, "The 'Functional Core, Imperative Shell' screencast mentioned at the end is available as part of season 4 of the DAS catalog." Pattern: push decision logic into a pure, side-effect-free **functional core** (testable with many fast, isolated unit tests, no doubles needed), and confine I/O and mutation to a thin **imperative shell** (few conditionals, exercised by a small number of integration tests). ESTABLISHED (primary attribution; talk hosted at destroyallsoftware.com — FLAGGED that the screencast itself is paywalled, so content is corroborated via Bernhardt's published talk page and secondary summaries).
- **`Humble Object` is the local, retrofittable form of the same move (Gerard Meszaros, *xUnit Test Patterns*, 2007, ISBN 978-0-13-149505-0).** The framework touchpoint keeps **zero** logic: a Click/argparse `main()` that only parses and calls one function; a FastAPI route body that is one call; a thread or `asyncio` task wrapper that only awaits. The extracted collaborator is what tests import. This matters because "adopt functional-core/imperative-shell" is an architecture-of-the-whole move, unavailable in code you cannot re-architect, whereas a Humble Object can be extracted one touchpoint at a time. The corpus ties the two together and gives a ladder: `functional-core-imperative-shell` **composes-with** `humble-object` ("the thin imperative shell mirrors Humble Object"), `humble-object` **realizes** `limit-structural-complexity`, and `functional-core-imperative-shell` **realizes** `hexagonal-architecture` (Alistair Cockburn, "Hexagonal Architecture (Ports and Adapters)", 2005, HaT Technical Report 2005.02) — where the test suite is simply *one of the adapters*, which is the whole point of the citation. **The ladder, in adoption order:** strip the untestable touchpoint to glue (Humble Object) → push all effects into one shell (FCIS) → make the shell an adapter set (`app/ports.py` + `app/adapters/*` + a pure core). ESTABLISHED (Meszaros and Cockburn, primary naming works; the ladder is this manifest's reading of the corpus edges). Two provenance notes for §7's FCIS bullet: the same element carries the aka **"impureim sandwich"** and a sourced `alternative-to monad` edge (Mark Seemann, "Impureim sandwich", ploeh blog, 2020 — cited on the edge only, no corpus work record, and no URL recorded here), so FCIS has a stated alternative it is usually presented without; and the corpus supplies a precise locator for Bernhardt's screencast (Destroy All Software, **Classic Season 4**), which confirms that the episode exists without confirming its content — the OPEN flag on the paywalled content does not move.
- **Test hooks: `Specialized Interfaces` (Bass, Clements & Kazman, SAIP 4e, 2021), and the Python contradiction that must be recorded with it.** The tactic covers test-only control and observation: `debug_state() -> Mapping[str, object]`, `reset_for_test()`, a `verbose=` instrumentation switch, `__getstate__`. It requires that test interfaces be "clearly separated from functional interfaces **so they can be removed**", and it names its own cost: "shipping code different from tested code is problematic in performance- and safety-critical systems". **In Python nothing is removable** — no conditional compilation, no dead-code stripping, and an underscore prefix does not prevent import. So the consequence the source cannot draw, and this manifest must: **test hooks ship, therefore they are part of the public contract.** Name them honestly (`debug_state()`, not `_debug_state()`), keep them read-only wherever possible, and give the mutating ones (`reset_for_test()`) the same review, typing and deprecation discipline as any production API — see `python_module_boundaries_manifest.md` for the public-API and deprecation contract. Honest gap worth recording: **no design element among 709 realizes `specialized-interfaces`** — the corpus names no code-level construct for test-only control and observation, so this rule is a derivation from the tactic plus Python semantics, not an imported pattern. ESTABLISHED (tactic and its stated cost) / OPEN (the Python consequence and the naming convention are this manifest's, enforced by nothing but review).

(Tooling supports these patterns — DI via plain Python and fixtures, contracts via Protocol, isolation via pure functions. Which architecture to adopt is the team's strategy decision.)

### 7a. Testability tactics, and the construct→tactic mapping

This is the section that turns the rest of the file from a tool list into a reviewable architecture rule. The seven **testability tactics** plus the `sandbox` pattern are named in **Bass, Clements & Kazman, *Software Architecture in Practice*, 4th ed., 2021, ISBN 978-0-13-688609-9** (Testability chapter). The language-agnostic statement of these tactics is `architecture_manifest_default.md`'s to own; what follows is their Python instantiation and the mapping.

| tactic | what it does | Python instantiation |
|---|---|---|
| `abstract-data-sources` | repoint "from a production customer database to test databases or data files without changing functional code" | a `DataSource` `Protocol` with real-DB and fixture-file implementations; `parametrize` / `pytest_generate_tests` over data files under `tests/data/`; `tmp_path` plus a fixture-written file |
| `executable-assertions` | assertions placed "wherever the data is referenced or modified"; they "embed the test oracle in the code" | three distinct lifetimes — pytest-rewritten `assert` (test modules only), plain `assert` (**vanishes under `-O`**), explicit `raise` (survives). See §5. |
| `limit-nondeterminism` | eliminate behavioural variance where possible; **manage the rest with record/playback** | §6c in full: injected clock, injected seed, order shuffling, HTTP fakes, `asyncio.TaskGroup` instead of detached tasks |
| `localize-state-storage` | keep all mutable state in one place so a state can be *constructed* rather than driven to | one frozen dataclass (or one `State` enum plus an explicit transition function) threaded explicitly; tests build it at any value with `dataclasses.replace` instead of replaying steps. Its sole cataloged realizer is `finite-state-machine`, sourced to the tactic text naming "a state machine object". |
| `record-playback` | record "information as it crosses interfaces" so a fault state can be re-entered | cassettes at a declared Protocol/gateway boundary; JSONL of `(call, args, result)`. §6b, with the monkeypatch caveat. |
| `specialized-interfaces` | test-only control and observation | `debug_state()`, `reset_for_test()`, instrumentation switches — and the Python contradiction in §7: they ship, so they are public API. **Zero realizers among 709 design elements.** |
| `sandbox` | virtualize "uncontrollable resources (system clock, memory, battery, network)"; the motivating case is named as "waiting for a real time boundary" | `tmp_path`, `monkeypatch.setenv`, `sqlite3` `:memory:`, `time-machine` / `freezegun`, socket blocking, `sys.executable -I`. The OS-confinement half is out of scope at this scale (§6). |
| `limit-structural-complexity` | cut coupling so an exact state — and therefore a failure — can be recreated | the testability rationale for the coupling rules in `python_module_boundaries_manifest.md`: large operational state spaces make reproducing a failure hard. Sourced edges: it **composes-with** `limit-nondeterminism` and **uses** `encapsulate`, so cutting coupling and removing nondeterminism are the *same* move. |

ESTABLISHED (SAIP 4e for every tactic name, its purpose and the quoted wording; `sandbox` is catalogued there as a pattern serving both `qa:testability` and `qa:security`, and it **specializes** `limit-access`).

## Recommendations
1. **Baseline now (stage 1).** Pin **pytest 9.1.1** (not "9.x": 9.0.0–9.0.3 silently ignored `--strict-markers`/`--strict-config` from `addopts`), coverage.py 7.15.x and Hypothesis 6.165.x on Python 3.14.7. Pin coverage.py to an **exact patch** rather than a `7.15.*` range whenever `fail_under` is a required gate, because `[report] precision` participates in the threshold comparison (§5a). Put config in `pyproject.toml` under exactly **one** of `[tool.pytest.ini_options]` (since pytest 6.0) or `[tool.pytest]` (native TOML types, since pytest 9.0) — the two tables cannot coexist in one file, and a stray `pytest.ini` or `pytest.toml` anywhere up the tree wins over `pyproject.toml` outright because "Options from multiple `configfiles` candidates are never merged — the first match wins" (§1a). Register all custom markers and enable `--strict-markers` (or the four strictness options, or `strict = true` behind a locked pin). Benchmark to revisit: the re-validation trigger for Python 3.15 **has already fired** — 3.15.0rc1 (2026-08-04) declares no further ABI changes in the 3.15 series and states that wheels built against the release candidates will work with final 3.15, so add a 3.15 leg to the matrix now rather than waiting for the October final; consult `python_platform_baseline_manifest.md` for the schedule itself. Two 3.15 changes move test *results* rather than version strings: UTF-8 becomes the default encoding (PEP 686), and `cProfile` becomes an alias for `profiling.tracing` while `profile` starts emitting `DeprecationWarning` on import (PEP 799) — which a suite running `filterwarnings = ["error::DeprecationWarning"]` will surface as a failure. VERSION-DEPENDENT (all pins verified 2026-08-08; the 3.15 schedule facts belong to `python_platform_baseline_manifest.md`).
2. **Specify obligations, not tests (stage 2).** For each component, document: the seam, the observable contract, equivalence classes + boundary values, expected observables, and explicit error-path obligations. Require that every obligation maps to at least one assertion; forbid assertion-free tests.
3. **Choose doubles deliberately (stage 3).** Default to fakes implementing the contract; when mocking, require `autospec=True` or `spec_set=True`. Write one contract test suite run against both the fake and the real implementation. Threshold to change: if mock-heavy tests break on refactors without behavior changes, migrate those collaborators to fakes or Protocol-typed seams.
4. **Add property-based tests for the core (stage 4).** Apply Hypothesis to pure functions/parsers/serializers (round-trip, invariant, oracle, metamorphic) and `RuleBasedStateMachine` to stateful components; keep example-based tests for side-effectful shells.
5. **Use coverage as a flashlight, and know the arithmetic (ongoing).** Run coverage with `[run] branch = true` to locate untested branches and error paths; do NOT set a numeric gate as the goal. If a percentage gate is mandated externally, learn its arithmetic first (§5a): failure exits status **2**, `precision = 0` rounds 89.6% into a passing 90%, there is no per-file form, and `exclude_lines` silently deletes the built-in `pragma: no cover` patterns unless you use `exclude_also`. Pair the gate with a ban on assertion-free tests **and name the mechanism that enforces the ban** — a `pytest_collection_modifyitems` AST check or mutation testing, because no first-party option does it (§5b, OPEN). Review the *missing* lines, treating upper-80s/90s as a smell-check range rather than a target. Gate wiring, exit-code handling and the incremental-adoption ratchet belong to `python_quality_gates_manifest.md`.
6. **Architect for isolation (ongoing).** Adopt functional-core/imperative-shell and constructor/Protocol-typed DI so most logic is unit-testable without doubles and the integration layer stays small.
7. **Close determinism explicitly (stage 5).** Adopt `pytest-randomly` so ordering coupling surfaces as a failure rather than as luck, keep the printed seed in retained CI logs, inject the clock and the RNG rather than patching them in the core, and choose the HTTP fake that matches your client (`respx` for HTTPX, `responses` for `requests` — not interchangeable). Write the graded rule into the test policy: eliminate nondeterminism → where it is irreducible, record at a declared interface and replay → only then retry, with every quarantined test carrying an expiry date (§6c). VERSION-DEPENDENT for the tool pins (§6c) / OPEN for the policy.
8. **Assert the error contract, not the error message (stage 5).** Use `pytest.raises(check=fn)` for structured attributes and `pytest.RaisesGroup` / `pytest.RaisesExc` for exception-group shape (pytest 8.4+), assert the *variant* for typed-result channels, and set `filterwarnings = ["error::DeprecationWarning"]` plus `-X dev` so a deprecated error type fails the build (§5c). The contract itself is specified in `error_tracing_contract_manifest.md`. VERSION-DEPENDENT (pytest 8.4+ for the APIs; §5c).
9. **Name the tactic for every substitution (ongoing).** Require each double, fake, fixture and cassette in review to name the tactic it realizes — `sandbox`, `limit-nondeterminism`, `abstract-data-sources`, `record-playback` — because the tactic is what supplies the exit criterion (§6, §7a). This is a review rule with no mechanical enforcement (OPEN); its value is that it converts "we mocked it" into a claim that can be finished, checked and closed.
10. **Add mutation testing before adding a coverage number (stage 6).** When the suite is green and fast, run `mutmut` over a named set of protected modules on a nightly cadence and gate on "no new surviving mutants" (§5b). It is the only mechanism here that tests the assertions themselves, and the boundary and off-by-one mutants it produces map directly onto the boundary-value obligations of §5. Do not put it on a per-PR gate, and do not gate on an absolute score. VERSION-DEPENDENT (mutmut 3.x) / OPEN (cost unquantified, §5b).

## Anti-patterns checklist

A rejection list, not a summary: each line is a thing to refuse in review, with the section that says why. Every entry inverts material already stated above — nothing new is claimed here.

- **Writing "pytest 9" instead of `>= 9.1.0`** — 9.0.0–9.0.3 silently ignored `--strict-markers` and `--strict-config` when they arrived through `addopts`, so the suite looked strict and was not (§1a, §1).
- **Both `[tool.pytest]` and `[tool.pytest.ini_options]` in one `pyproject.toml`** — they cannot coexist, and they are different data models, so copied values are wrong values (§1a).
- **Adding pytest config to `pyproject.toml` while any `pytest.ini` or `pytest.toml` exists up the tree** — candidates are never merged, the first match wins, and an *empty* `pytest.toml` still takes highest precedence. The symptom is no error at all (§1a).
- **More than one pytest config location in a repo, unguarded** — nothing in pytest enforces single-location config; the second location must be a build break via pre-commit or a structural CI check (§1a).
- **`strict = true` under a floating pytest pin** — the umbrella picks up future strictness options automatically, so a new rule arrives as a mystery failure; float the pin and enable the options individually instead (§1a).
- **An unpinned test-tree layout** — `tests/` without `__init__.py` under the default `prepend` import mode makes duplicate test-module basenames a collection error, and `INP001` fires on the whole tree either way. Choose the import mode, the `__init__.py` question and the `per-file-ignores` entry together, once (§1a).
- **Porting an old suite by reading the changelog instead of asserting that setup ran** — pytest 9's removals are quiet by construction: a renamed-away bare `setup` method is simply never called (§1).
- **Pinning or reasoning against the `pytest 9.2 [UNRELEASED DRAFT]` changelog section** — it is informational and already contains breaking changes (§8).
- **Taking a current-version claim from a blog post** — 2026 posts variously assert pytest 8.x or 9.0.3; both are wrong for this pass (§8).
- **Inferring a `requires-python` floor from this file** — the minimum-target policy is owned by `python_platform_baseline_manifest.md` §3d–§3e; this file states only the interpreter gates that change test behaviour (§8).
- **Specifying an obligation "at a seam"** — a seam is a property of code, not an artefact a reviewer can point at. Name the mechanism: `dependency-injection`, `explicit-interface` / `Protocol`, `gateway`, `plugin`, `humble-object` (§2).
- **Teardown in the test body** — the four-phase shape puts it after `yield` in the fixture or in `request.addfinalizer`; `tmp_path` and `monkeypatch` make it unskippable (§2a).
- **`scope="session"` on anything mutable, chosen by convenience rather than decided** — that is a Shared Fixture decision made by accident, and the direct cause of tests that pass alone and fail in a suite (§2a).
- **A mock where a fake implementing the real contract was meant** — behaviour verification couples the test to implementation and makes it fragile; take the least behaviour that still lets you assert the contract (§3).
- **A mock without `autospec=True` or `spec_set=True`** — an unconstrained mock keeps passing after the real API changes signature (§3).
- **Mocking the HTTP client instead of owning a gateway** — one application-owned class per external system, typed with a `Protocol`, substituted in one place (§3, §6).
- **Calling a double a "fake" with no contract suite run against both it and the real implementation** — without that parametrized suite the word claims a guarantee nobody checks (§6).
- **A substitution with no named testability tactic** — the tactic is what supplies the exit criterion, so an unnamed substitution is an obligation that can never be closed (§7a, §6).
- **Suppressing `HealthCheck.function_scoped_fixture` to turn a red property test green** — the fixture runs once for the whole function, not once per generated case; the health check is the only detector, so suppressing it converts a real state leak into a silent one (§4a).
- **Blanket `suppress_health_check`** — several checks catch subtle interactions; every entry in the list belongs in code review (§4a).
- **Expecting Hypothesis to replay yesterday's counterexample in CI** — the auto-loaded `"ci"` profile sets `database=None`, so nothing accumulates; and `print_blob=True` is the recovery path only if CI logs are retained (§4a).
- **Using Hypothesis `deadline` as a performance gate** — it is a soft limit that is raised during generation and shrinking, so tests on the cusp pass artificially; and CI sets `deadline=None` anyway (§4a).
- **A `RuleBasedStateMachine` with no `TestMyMachine = MyMachine.TestCase` line** — pytest does not collect it, and it reports zero tests and zero failures (§4a).
- **Filtering a wide strategy instead of constructing a narrow one** — heavy rejection quietly reduces the effective case count long before `HealthCheck.filter_too_much` trips (§4a).
- **A float obligation with a bare absolute tolerance** — a fixed absolute epsilon is wrong across magnitudes, so `abs=1e-9` alone is a latent flake, not a tolerance: state the relative term for general magnitudes and the absolute term for the near-zero case (§5).
- **A plain `assert` guarding an invariant that must hold in production** — it vanishes under `-O`; only an explicit `raise` survives. An assertion in a shared test helper needs `pytest.register_assert_rewrite()` or it degrades to a bare `AssertionError` (§5, §1).
- **An obligation with no blame assignment** — which side a failure indicts is what decides whether the missing test is a caller test or a callee test, and nothing mechanical assigns it (§5).
- **A coverage percentage set as a target rather than read as a diagnostic** — high numbers are cheap to reach with low-quality testing; this is Goodhart's law with a CI badge (§5, §5a).
- **`fail_under` trusted without reading its arithmetic** — failure exits status **2**, not 1; `[report] precision = 0` makes a true 89.6% compare as 90% and therefore *pass* `fail_under = 90`; and there is no per-file or per-module form, so a project-wide 90% hides a new 0% module (§5a).
- **Quoting a coverage number with `[run] branch` off** — that is statement coverage, and it is compatible with every `else:` in the codebase being untested (§5a).
- **Adding a custom `exclude_lines` pattern** — it *replaces* the built-ins, including `pragma: no cover`; `exclude_also` is the additive form, and `partial_also` is the additive form of `partial_branches` (§5a).
- **Expecting `--cov-context=test` to work on the default `sysmon` core** — `sysmon` supports neither plugins nor dynamic contexts; set `[run] core = ctrace` explicitly (§5a).
- **Expecting child-process coverage without `[run] patch = subprocess`** — pytest-cov 7.0.0 dropped subprocess support; the symptom is a CLI's own module reporting 0% while its tests pass (§5a).
- **Assertion-free tests** — execution is not verification: they raise the number without adding one obligation. And banning them without naming the mechanism that enforces the ban enforces nothing, because no first-party pytest option does it (§5a, §5b).
- **Gating on a mutation score, or putting `mutmut run` on a per-PR gate** — gate on "no new surviving mutants in protected modules" on a nightly cadence; a 100% mutation-score gate is worse than no gate, and per-PR mutation testing on a multi-minute suite is a timeout with extra steps (§5b).
- **Reading a clean mutation score as covering module-level code** — mutmut 3 does not mutate code outside functions, so constants, dataclass field defaults and top-level config are untouched (§5b).
- **Asserting on an exception's message text instead of its structured attributes** — `pytest.raises(check=fn)` exists so the obligation can name `err.code` rather than grep `str(exc)` (§5c).
- **A snapshot artefact that was never canonicalized** — without stable ordering and normalized timestamps, uuids, paths and float formatting, the suite is testing dict ordering, not behaviour (§6b).
- **`--snapshot-update` in a pre-commit hook or a CI auto-approve** — that turns a golden-master suite into a change-recorder that can never fail; the diff must be read (§6b).
- **Recording a cassette by monkeypatching inside the process** — that records the patch, not the interface, so the cassette encodes your harness instead of the contract. Record only at a declared boundary (§6b).
- **A suite that cannot reproduce a failure from its own printed seed** — randomised order plus a random seed is reproducible only if the seed is retained, and `--randomly-seed=last` works locally, not across machines (§6c).
- **Reaching for one `pytest-randomly` switch "to turn off randomness"** — `--randomly-dont-reorganize` still reseeds and `--randomly-dont-reset-seed` still shuffles; they are independent (§6c).
- **Installing the HTTP fake that does not match the client** — `respx` is for HTTPX and `responses` for `requests`; the wrong one issues real outbound traffic while the fixture reports as active (§6c).
- **Retry or quarantine as the first move on a flake, or a quarantine entry with no expiry date** — the graded rule is eliminate → record at a declared interface and replay → only then retry (§6c).
- **Bare `asyncio.create_task` outside a scope in test-covered code** — a detached task is a test that passes because the task had not run yet (§6c).
- **Choosing between pytest-asyncio and AnyIO by which decorator looks familiar** — they differ in task semantics, not syntax: code whose fixtures need cancel scopes, task groups or `contextvar` propagation across the fixture boundary is correct under one and broken under the other (§6d).
- **Leaving `asyncio_mode` unset, or enabling both plugins' auto modes** — an unmarked `async def test_...` is collected and contributes nothing under the default `strict` mode, and AnyIO's auto mode does not work alongside pytest-asyncio's (§6d).
- **Leaving `asyncio_default_fixture_loop_scope` unset** — it means "the fixture's own scope" today and `function` in a future release; only an explicit value survives the upgrade (§6d).
- **Order-coupled tests under `-n`** — `--dist load` guarantees no ordering at all, so the coupling fails intermittently rather than reproducibly (§6e).
- **Citing the SWE exclusion register as authority against mutation testing, fuzzing or fake-clock work** — those exclusion entries carry an empty rationale field, so the corpus neither supplies nor justifies them; they stand here on tool documentation (§8).
- **Naming `pyfakefs`, `pytest-socket`, `vcrpy`, `betamax`, `pytest-regressions`, `approvaltests`, `polyfactory` or `factory_boy` in a spec as if pinned** — no version, date or maintenance status was verified for any of them in this pass (§8).
